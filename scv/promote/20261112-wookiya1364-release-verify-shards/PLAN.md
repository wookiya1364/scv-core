# 릴리스 검증 나눠 돌리기

## Summary

코어 릴리스의 검증 단계는 러너 한 대에서 시험을 하나씩 돌린다. 2026-11-12 의 0.92.0 릴리스에서 이 단계가 32분 33초 걸렸고, 릴리스 자산은 이 단계가 끝나야 올라오므로 래퍼 둘도 그만큼 늦게 움직였다.
같은 시험을 PR 검사는 여섯 조각으로 나눠 돌린다. 릴리스 검증도 같은 실행기로 여섯 조각으로 나누고, 그러려면 먼저 필요한 것 둘(재는 시험의 "혼자 돈다" 표시, 조각 시간표의 빠진 시험)을 채운다.

## Goals / Non-Goals

- **Goals**
  - 릴리스 검증을 여섯 조각으로 나눠 돌리고, 여섯이 모두 통과해야 릴리스 작업이 시작되게 한다
  - 가장 긴 조각이 4분 안에 끝난다 (지금 한 줄로 32분 33초)
  - 재는 명령을 돌리는 시험과 벽시계 한도를 보는 시험 셋에 "혼자 돈다" 표시를 붙인다 — 시험을 4개씩 함께 돌리는 래퍼 로봇에서 통과하게 한다
  - 조각 시간표 둘(리눅스 · 맥)을 2026-11-12 PR 검사의 실제 시간으로 새로 적는다 — 빠진 시험 13개가 들어간다
  - 이 모양을 지키는 시험을 더한다 (표시가 빠진 재는 시험, 릴리스 설정의 조각 수 어긋남)
- **Non-Goals**
  - 새 기능
  - 릴리스 검증에 맥 조각 더하기 (지금도 리눅스 한 대뿐이다)
  - 가장 긴 시험(재는 명령 시험 203초) 줄이기 — 여섯 조각에서는 더 빨라지지 않는다
  - 래퍼 저장소의 긴 단계 손보기 (코덱스 쪽 승급 약 20분)
  - 한 러너 안에서 시험을 겹쳐 돌리기

## Approach Overview

사용자가 2026-11-12 선택 창에서 정한 것: 줄거리 "이대로 씀", 조각 "여섯", 끝난 뒤 "릴리스와 래퍼 둘까지", 그림 "없이". 그 전에: 다음 기능보다 이 일을 먼저, 코덱스 래퍼는 이 코어 릴리스 때 함께.

읽은 사실 (2026-11-12, PR 검사 실행 43121732281 · 릴리스 실행 43124714022):

- 리눅스에서 시험 시간의 합은 1,269초, 가장 긴 시험은 재는 명령 시험 203초다. 여섯으로 고르게 나누면 조각 하나가 212초 안팎이다.
- 지난 PR 검사의 리눅스 조각은 169 ~ 322초로 쏠렸다. 시간표에 시험 13개가 없어 203초짜리가 5초로 계산됐기 때문이다.
- 릴리스 검증은 `core/tests/test-*.sh` 를 모두 돈다. 묶음 시험 둘(`test-choice-questions.sh` · `test-show-real.sh`)이 조각 다섯(155초 + 70초)을 한 번 더 부른다. 조각 실행기는 묶음을 건너뛰므로 이 225초가 없어진다.
- 코덱스 래퍼의 동기화 로봇은 가져온 코어 시험을 4개씩 함께 돌린다. 재는 명령 시험이 두 번 실패했다(1차 S5 · S13 · S15, 2차 S13). 이 시험에 "혼자 돈다" 표시가 없다.

하는 일:

1. **표시** — `# scv-test: serial` 을 `test-pure-bench.sh` · `test-pipe-arrange.sh`(재는 명령을 실제로 돌린다) · `test-slow-pure-functions.sh`(벽시계 5초 한도를 본다)에 붙인다. 실행기는 표시가 있는 시험을 다른 시험이 다 끝난 뒤 하나씩 돌린다.
2. **시간표** — `timings.tsv` · `timings-macos.tsv` 를 위 PR 검사의 조각 기록에서 옮겨 적는다(시험 110개).
3. **릴리스 검증** — `release.yml` 에 조각 작업(여섯)을 두고 PR 검사와 같은 한 줄로 돌린다. 릴리스 작업은 조각 작업이 모두 통과해야 시작한다. 한 줄로 돌던 단계는 지운다. DeckUI 확인 · 자산 만들기 · 올리기 · 래퍼 알림은 그대로다.
4. **지키는 시험** — 재는 명령을 돌리는 시험에 표시가 있는지(코어 시험), 릴리스 설정의 조각 수와 명령이 맞는지 · 릴리스가 조각을 기다리는지 · 한 줄로 도는 반복이 다시 생기지 않았는지(저장소 시험).

## 순수함수 · 파이프라인 (Pure functions & pipeline)

이미 있는 조각 실행기의 파이프라인을 그대로 쓴다. 이 계획은 그 파이프라인이 읽는 자료(표시 · 시간표)와 그것을 부르는 곳(릴리스 설정)을 고친다.

```
flow(
  rf_list_tests,   // 시험 폴더들 → '경로<탭>표시' 줄            (입구: 파일 읽기)
  rf_classify,     // '경로<탭>표시' → 'parallel|serial<탭>경로'  (순수)
  rf_partition,    // 줄 + 시간표 + I + N → 조각 I 의 줄          (순수)
  rf_run_batch,    // 조각의 줄 → 시험마다 결과 줄                (부수효과: 실행)
  rf_summarize,    // 결과 줄 → 표 줄 + 합계                      (순수)
  rf_report,       // 표 줄 → 출력 + 끝 코드                      (출구)
)
```

| # | 단계 | 하는 일 | 받는 값 → 돌려주는 값 | 순수/부수효과 |
|---|---|---|---|---|
| 1 | rf_list_tests | 시험 파일을 모으고 앞 30줄의 표시를 읽는다 | 폴더들 → 경로와 표시 | 부수효과 (입구) |
| 2 | rf_classify | 표시로 "함께 돎 · 혼자 돎"을 가린다 | 경로와 표시 → 분류된 줄 | 순수 |
| 3 | rf_partition | 시간표로 시험을 조각에 고르게 나눈다 | 줄 · 시간표 · 조각 번호 → 그 조각의 줄 | 순수 |
| 4 | rf_run_batch | 조각의 시험을 돌린다 — 표시가 있는 것은 끝에 하나씩 | 조각의 줄 → 결과 줄 | 부수효과 (실행) |
| 5 | rf_summarize | 결과를 오래 걸린 순으로 묶고 합계를 낸다 | 결과 줄 → 표 줄 | 순수 |
| 6 | rf_report | 표와 실패 기록을 찍고 끝 코드를 낸다 | 표 줄 → 출력 · 끝 코드 | 부수효과 (출구) |
| 7 | verify | 릴리스 설정의 조각 작업 — 조각마다 러너 한 대 | 꼬리표 → 조각 여섯의 통과 여부 | 부수효과 (러너) |
| 8 | release | 조각 여섯이 모두 통과하면 자산을 만들고 올린다 | 통과 여섯 → 릴리스 | 부수효과 (출구) |

- 부수효과 위치: 1 · 4 · 6 · 7 · 8. 분류 · 나누기 · 묶기(2 · 3 · 5)는 순수하다.
- 재사용: 1 ~ 6 은 `core/tests/run-focused.sh` 의 함수를 그대로 쓴다. 새 셸 함수는 만들지 않는다.

### 합성 설계 체크리스트 (Composition checklist)

| # | 물음 | 답 | 근거 |
|---|---|---|---|
| 1 | 각 단계가 요소 단위 단항 순수 함수인가 | 판정 쪽은 예 | `run-focused.sh` 의 `rf_classify` · `rf_partition` · `rf_summarize` 는 글만 받고 글만 낸다(파일 머리말의 파이프라인 줄) |
| 3 | 요소 단위로 먼저 합성한 뒤 순회는 한 번만 하는가 | 지금은 아니오 → 고친다 | `release.yml` 의 검증 단계는 묶음 시험이 조각을 한 번 더 불러 조각 다섯이 두 번 돈다(225초). 조각 실행기는 묶음을 건너뛴다(`rf_list_tests`) |
| 7 | 부수효과가 파이프라인 양 끝에만 있는가 | 예 | 읽기는 `rf_list_tests`, 실행은 `rf_run_batch`, 쓰기는 `rf_report` 와 릴리스 작업 |
| 8 | 독립인 일을 함께 돌리는가 | 지금은 아니오 → 고친다 | 시험은 서로 독립인데 릴리스 검증은 한 줄로 돈다. 러너를 나눠 함께 돌린다 — 한 러너 안에서 겹치면 시험이 느려진다(`run-focused.sh` 머리말: 맥 실측 719 → 1397초) |
| 10 | 핫패스는 측정한 뒤에 최적화했는가 | 예 | 2026-11-12 실측: 한 줄로 32분 33초, 시험 시간의 합 1,269초, 가장 긴 시험 203초. 릴리스 뒤 같은 숫자를 다시 읽는다 |
| 그 밖 | 2 · 4 · 5 · 6 · 9 | 해당 없음 | 큰 값을 나르거나 일찍 멈출 수 있는 순회, 구조 공유가 필요한 값이 없다 |

## Guardrails

- 릴리스 작업은 조각 여섯이 모두 통과한 뒤에만 시작한다. 조각이 실패하거나 취소되면 자산을 올리지 않고 래퍼에 알리지 않는다.
- 조각 안에서는 시험을 하나씩 돌린다. 한 러너 안에서 겹쳐 돌리지 않는다.
- 릴리스 검증이 도는 시험을 줄이지 않는다. 없어지는 것은 묶음 시험의 중복뿐이다.
- PR 검사의 조각 수와 필수 검사 이름을 바꾸지 않는다.
- 한도 숫자와 시험의 판정을 느슨하게 하지 않는다 — 표시는 "언제 도는가"만 바꾼다.
- 맥(BSD) · 리눅스(GNU), bash 3.2 에서 돈다. 코어 파일에 호스트 이름을 넣지 않는다.

## Exit criteria

- TESTS.md 의 시나리오 5개 통과
- 관련 시험과 순수 검사 · 사전 검사가 옛 셸과 새 셸에서 통과한다
- 올리기 전에 전체 시험을 한 번 돌려 통과한다
- 실제 릴리스 한 번에서: 조각 여섯이 모두 통과하고, 가장 긴 조각이 4분 안에 끝난다 — 걸린 시간을 실행 기록에서 읽어 적는다
- 코덱스 래퍼의 동기화 로봇이 가져온 코어 시험을 통과해 PR 을 연다

## Suggested path

1. 재는 시험 셋에 혼자 돈다 표시를 붙이고, 표시가 빠지면 잡는 시험을 더한다 — `rf_list_tests`, `rf_classify`
2. 조각 시간표 둘을 2026-11-12 PR 검사의 실제 시간으로 새로 적는다 — `rf_partition`
3. 릴리스 검증을 여섯 조각으로 바꾸고 릴리스 작업이 기다리게 묶는다. 이 모양을 지키는 저장소 시험을 더한다 — `verify`, `release`
4. 변경 기록 · 버전을 맞추고 관련 시험을 두 셸에서 돌린다 — 관련 시험과 순수 검사 · 사전 검사의 결과를 그대로 보인다
5. 전체 시험 한 번 뒤 PR · 코어 릴리스 · 래퍼 둘을 잇고, 릴리스 실행에서 조각마다 걸린 시간을 읽어 적는다 — 앞뒤 시간을 그대로 보인다

## Risks / Open Questions

- 표시를 붙인 뒤 코덱스 로봇에서 통과하는지는 릴리스 뒤에야 본다. 근거는 시험을 하나씩 도는 릴리스 검증(같은 리눅스)에서 이 시험이 통과했다는 것이다.
- 조각 하나가 러너를 못 받으면 릴리스가 그 조각을 기다린다. 리눅스 러너에서는 본 적이 없다(맥에서만 봤다).
- 가장 긴 조각 4분은 추정이다 — 212초에 준비 시간을 더한 값이다. 릴리스 러너가 PR 러너보다 느리면 넘을 수 있다(0.92.0 릴리스 검증은 같은 시험에 PR 검사의 합보다 약 7분 반 더 걸렸고, 그 가운데 225초만 중복으로 설명된다).
- 이 릴리스(0.92.1) 자체는 옛 릴리스 설정이 아니라 새 설정으로 돈다 — 꼬리표가 가리키는 커밋의 설정을 쓰기 때문이다. 조각이 실패하면 고쳐서 다시 올려야 한다.
