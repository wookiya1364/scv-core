# 마무리 보고 —

## 1. 문제

- 상황: SCV 답 규칙을 Fable 5.2 · Opus 5.5 공식 프롬프팅 가이드와 대조하니, 숫자 길이 상한과 매 턴 쌓이는 규칙 글이 가이드 권고와 부딪혔다.
- 기대: 규칙은 한 번 알아듣게 싣고, 길이는 숫자 대신 '짧게'로 둔다.
- 실제: 사람 턴마다 같은 규칙 글 약 4.8 KB 가 다시 붙고(세션 전체로 수 MB), 문장 수 상한(1–2문장) 경고가 답 모양 경고의 대부분이었다(다른 프로젝트 세션 21건 중 15건, 이 세션 26건 중 24건).
- 재현 조건: 아무 세션에서나 사람 턴 두 번 — 둘째 턴에도 같은 규칙 글 전문이 붙음.

## 2. 관찰

- 관찰한 사실과 측정값: 두 실제 세션 기록 재계산 — 턴당 4.3–6.0 KB 중 고정 규칙 글이 약 4.8 KB. 원칙 글만 이미 '지문마다 한 번'이었다.
- 정상일 때와 차이: 원칙 글은 둘째 턴부터 한 줄("이 세션에 이미 실음")인데 나머지 다섯 덩어리는 매 턴 전문.

## 3. 가설

- H1: 규칙 글을 지문마다 한 번만 실어도 규칙 어김이 늘지 않는다.

## 4. 실험

- 방법과 같게 둔 것: 헤드리스 claude(Opus 5.5) · 같은 질문 8개 · 같은 규칙 전문을 사용자 메시지 앞에 붙임 · A 매 턴 전문 / B 첫 턴만 전문 + 한 줄(경고 턴엔 답 모양 규칙 다시).
- 결과와 가설별 판정: A 16답 어김 2(영어 섞임) · B 8답 어김 1(문장 수 — 이번에 없애는 항목). H1 기각되지 않음(표본 작음, 8턴만). B 둘째 묶음은 헤드리스 첫 호출이 두 번 5분 멈춰 무효.

## 5. 원인

- 직접 원인과 일어난 길: 매 턴 훅이 언어 · 확인 범위 · 답 모양 · 선택 · 실물 보여 주기 덩어리를 조건 없이 매번 출력.
- 근본 원인: 긴 세션에서 규칙이 흐려지는 것을 막으려고 '매 턴 다시 싣기'를 택했지만, 이미 있던 지문(규약 다시 읽기 · 요약 뒤 재설정)과 경고 장치로 같은 효과를 낼 수 있었다.

## 6. 해결과 검증

- 해결책과 고른 이유: 원칙 글에 이미 있던 '지문마다 한 번' 장치를 나머지 다섯 덩어리에 넓힘(새 판정 하나 `scv_mp_rules_show`, 명령 `model-prompting.sh rules`). 경고가 남은 턴 · 지문이 바뀐 턴은 전문이라 흐려짐을 막는 장치가 그대로 있음. 시간 · 크기로 끊는 방식보다 기준값이 필요 없음. 숫자 상한은 검사 기본값을 '안 셈'으로 바꾸고 문구에서 숫자를 뺌(함수의 상한 인자는 남김).
- 고치기 전후 값: 시험 환경 같은 세션 둘째 턴 2,608 B → 922 B. 두 실제 세션 기록 재계산 턴당 4.3–6.0 KB → 1.6–2.8 KB. 헤드리스 비교 8턴: 어김 A 2/16 · B 1/8.
- 부작용과 회귀 시험: 새 시험 7개(맥 · 리눅스 · 코덱스 사본), 전체 실행 118개 중 처음 4개 실패 — 고정 지문 1(문구 변경), 커밋 뒤 검사 1, 같은 세션에서 안내 줄을 여러 번 보는 시험 1(그 시험만 SCV_RULES_ONCE=off), 부하 때 재는 시험 1(혼자 통과). 고친 뒤 모두 통과.

## 7. 배운 것

- 다음에 같은 문제를 만나면 진단하는 법: 대화 기록에서 사람 턴마다 붙은 훅 글을 덩어리별로 나눠 크기를 재고, 같은 글이 매 턴 반복되는지 본다. 바꾸기 전에 기록으로 '바꿨다면'을 다시 계산하고, 짧은 헤드리스 비교로 규칙 어김을 견준다.
- 다른 곳에도 쓸 수 있는 것: 매 턴 싣는 글은 '한 번 + 어겼을 때 다시'로 충분한 경우가 많음. 헤드리스 비교 시험은 호출마다 시간 제한을 두어야 함(가끔 5분 멈춤).
