# 마무리 보고 — 기어는 모델 없이 바로 돌고, 대화 턴은 가볍게 — 어긋나는 지시 정리

## 1. 문제

- 상황: 대시보드 0.3.2 와 본체 0.101.0 을 쓰는 긴 세션에서, 사용자가 입력창 위 줄의 기어를 쓰게 해서 요청을 보냄(2026-11-24).
- 기대: [사용함]을 누르거나 기어 명령을 치면 곧바로 기어가 돌고, 토큰을 거의 쓰지 않는다.
- 실제: [사용함]과 [쓰기]는 채팅을 한 줄 보낼 뿐이라 모델이 한 턴을 통째로 돈다. 기어 줄이 붙은 요청 한 턴: 3.6분 · 모델 호출 10번 · 도구 14번 · 쓴 글 13,750 토큰 · 캐시에서 다시 읽은 양 약 828만 토큰.
- 재현 조건: 기어가 있는 프로젝트에서 입력창에 그 기어의 낱말이 든 글을 치고 그대로 보낸다(또는 [사용함]). 세션이 길수록 호출마다 다시 읽는 양이 커져 더 느리다.

## 2. 관찰

- 관찰한 사실과 측정값: 세션 기록에서 턴마다 센 값(같은 세션, 22시대): 아무 일 없는 올리기 명령 턴 — 호출 3번 · 1.2~1.8분 · 쓴 글 약 1,500 토큰. 기어 줄이 붙은 요청 턴 — 호출 10번 · 3.6분. 호출 한 번이 캐시에서 다시 읽는 양은 약 83만 토큰(828만 ÷ 10). 매 턴 훅이 싣는 글은 약 8.4KB(시험 값 8,452B).
- 정상일 때와 차이: 창의 [바로 실행](표시 pure 인 기어)은 모델을 거치지 않아 호출 0번이다. 같은 기어라도 대화로 가면 SCV 의 턴 절차(도움말 부르기 · 등록 · 기록 · 마무리 · 끝 보고)를 다 거친다.

## 3. 가설

- H1: 느린 이유의 큰 몫은 세션 크기다 — 호출마다 83만 토큰을 다시 읽는다.
- H2: 기어 요청이어도 턴 절차가 보통 턴과 같아 호출 수가 준다는 보장이 없다 — 도움말 · 등록 · 기록 · 마무리 · 끝 보고가 각각 호출을 만든다.
- H3: 창이 직접 돌릴 수 있는 범위가 좁다(pure · 30초) — 이 컴퓨터에만 영향을 주는 기어도 대화로 보낸다.

## 4. 실험

- 방법과 같게 둔 것: 작은 새 프로젝트 둘(같은 기어 하나 — 대문자로 바꾸고 글자 수 세기), 화면 없는 새 세션 한 번씩, 같은 모델, 같은 요청 글(요청 한 줄 + 창이 붙이는 기어 한 줄). 한쪽은 설치본(0.101.0), 다른 쪽은 설치본 사본에 고친 본체를 덮어쓴 것. 세션 기록에서 모델 호출 수 · 도구 호출 수 · 쓴 토큰 · 걸린 시간을 셈.
- 결과와 가설별 판정: 바꾸기 전 — 모델 호출 8번 · 도구 9번 · 쓴 토큰 2,814 · 72.1초(도구 9번 가운데 8번이 도움말 · 규약 읽기 · 표시 · 등록 · 기어 액션). H2 맞음 — 작은 세션에서도 절차만으로 호출이 8번. H1 은 이 실험과 따로 맞음(큰 세션의 같은 요청은 10번 · 3.6분 — 호출 수는 비슷하고 호출마다의 시간이 다름). H3 은 대시보드 쪽에서 확인(창 직접 실행은 보낸 글 0번).

## 5. 원인

- 직접 원인과 일어난 길: 기어 요청도 보통 턴과 같은 글(약 7.7KB — 도움말 먼저 · 등록 · 답 모양 · 끝 보고)이 실리고 같은 검사를 받는다. 모델은 그 글대로 도움말 → 규약 읽기 → 표시 → 등록 → 기어 액션 → 실행 → 긴 답을 차례로 하고, 걸음마다 모델 호출이 한 번씩 든다.
- 근본 원인: 기어는 "정해 둔 일을 그대로 돌리는 것"인데, 턴 절차는 "요청을 새로 해석하는 일"을 기준으로 짜여 있었다. 창의 버튼도 실행이 아니라 채팅을 보내는 것이었다.

## 6. 해결과 검증

- 해결책과 고른 이유: (1) 기어 턴의 가벼운 길 — 매 턴 훅이 기어 요청을 가려 세 줄 안내만 싣고(값 안내를 훅이 미리 읽어 실음), 턴 끝 검사는 인용 · 끝 보고 · 계획 기록을 요구하지 않는다. 쓰기 전 검사는 그대로 둬서 가벼운 길이 보통 요청의 빠져나갈 구멍이 되지 않게 했다. (2) 창이 기어를 직접 돌림 — 값은 버튼 · 입력 칸으로, 오래 도는 실행과 멈춤, 밖으로 나가는 기어는 확인 뒤에(대시보드 0.4.0). (3) 어긋나는 지시 열 곳을 표로 뽑아 고침. (4) 대화가 길어지면 기록으로 바꿔 끼워 가볍게 함(대시보드 0.3.3). (5) 그림 도구가 있는 세션에서는 표 · 화살표 줄이 그림을 갈음하지 못하게 함.
- 고치기 전후 값: 같은 기어 요청 한 턴 — 모델 호출 8 → 2번, 도구 9 → 1번, 쓴 토큰 2,814 → 379, 72.1초 → 20.0초. 매 턴 글 — 보통 턴 약 7.7KB, 기어 턴 약 0.75KB. 대화 가볍게 하기 — 화면 없는 실제 실행 한 번에 45,301 → 367 토큰, 0.014초, 뒤 질문에 기록에만 있던 낱말을 맞게 답함. 그림 알림 — 실제 기록 두 개에 다시 돌리면 67턴 중 13턴 · 17턴 중 5턴.
- 부작용과 회귀 시험: 기어 턴에서는 인용 · 끝 보고 · 대화 기록 파일의 턴 적기가 없다 — 대신 실행기가 저널에 한 줄을 남긴다. 기어가 파일을 바꿔도 계획 기록을 요구하지 않는다(기록 파일에 한 줄만). 회귀 시험: `core/tests/test-gear-turn.sh` T1–T6(보통 턴은 끈 것과 같은 글 · 쓰기는 거절), `test-instruction-conflicts.sh` T10–T11, `test-picture-rule.sh` T52, `test-turn-plan-check.sh` T17b, 대시보드 시험 202개.

## 7. 배운 것

- 다음에 같은 문제를 만나면 진단하는 법: "느리다 · 토큰을 많이 쓴다"는 말을 들으면 세션 기록에서 그 턴의 모델 호출 수와 호출마다 한 일을 먼저 센다. 호출 수가 많으면 절차의 문제고, 호출 수는 적은데 느리면 세션 크기의 문제다. 고친 뒤에는 새 세션에서 같은 요청으로 전 · 후를 한 번씩 잰다.
- 다른 곳에도 쓸 수 있는 것: 모델이 따로 부르던 읽기 명령을 훅이 미리 읽어 실어 주면 호출이 한 번 준다(값 안내를 미리 실으니 4번 → 2번). 안내 글이 모호하면 그만큼 헛도는 호출이 생긴다 — "넣을 자료는 표준 입력으로, 인자가 아니다"처럼 틀리기 쉬운 곳을 글에 적는다. 모드가 스스로 부른 일은 자기 처리기를 건너뛴다 — 다른 길(명령 실행)로 불러야 자기 처리기가 받는다.
