# 재는 명령과 느려지면 막기 — 순수함수가 기본, 그다음 합성 함수

## Summary

SCV 에는 순수함수의 성능과 메모리를 재는 도구도, 느려지는 것을 막는 도구도 없다.
명령 하나(함수 하나를 예시 입력으로 돌리는 것)의 벽시계 · CPU 시간 · 메모리 · GPU 사용 · 띄운 외부 명령 수 · 입력을 4배로 늘렸을 때의 배수를 재는 명령을 만들고, 고친 코드가 한도를 넘어 느려지면 실패시킨다.
순수함수 하나하나가 성능과 메모리 효율을 갖추는 것이 기본이고, 그다음에 그것을 엮은 합성 함수를 같은 틀로 잰다.

## Goals / Non-Goals

- **Goals**
  - 재는 명령이 명령 하나에 대해 일곱 값을 낸다: 벽시계 · CPU 시간 · 메모리 최고치 · GPU 사용 시간 · GPU 메모리 · 띄운 외부 명령 수 · 입력 4배 때의 배수.
  - 판정에 쓸 잣대를 언어가 아니라 그 명령이 실제로 쓴 것으로 고른다: GPU 를 썼거나 벽시계가 CPU 시간보다 훨씬 크면 벽시계 · GPU 값으로, 아니면 CPU 시간으로.
  - 사전에 오른 순수함수를 먼저 재고, 그다음 합성 함수(순수함수를 엮은 것)를 묶음 전체로 잰다.
  - 고치기 전과 후의 코드를 같은 컴퓨터에서 번갈아 재서, 한도를 넘어 느려지거나 메모리를 더 쓰면 실패한다.
  - 지금 이미 한도를 넘는 곳은 목록으로 두고, 늘면 실패 · 줄면 목록에서 내린다.
  - 한도를 넘었지만 맞는 변경이면, 잰 값을 보이고 선택 창에서 사용자가 정한다. 답은 계획 기록에 남는다.
  - 도는 때: 순수함수를 고친 턴의 끝(바뀐 함수만)과 계획을 끝내기 전(전체).
- **Non-Goals**
  - 엮는 순서 · 방식을 더 좋은 것으로 고치는 일(다음 계획 — 규칙 변환과 순서 계산)
  - CI 에서 재기
  - 어제 정한 두 열쇠 승인 절차 · 판정 대기 목록
  - 옛 함수 337개의 선언 채우기

## Approach Overview

- **재는 실행기** — 잴 명령을 밖에서 감싼다. 벽시계와 CPU 시간(자식 포함)은 셸에서, 메모리 최고치는 운영체제의 시간 재는 명령에서, GPU 사용률과 GPU 메모리는 실행 중에 짧은 간격으로 읽는다. 2026-11-11 이 맥에서 관리자 권한 없이 다섯 값이 모두 재졌다(GPU 일이 10배 커져도 CPU 시간은 0.75 → 0.77초로 그대로였다).
  - GPU 읽기: 맥은 확인된 방법을 쓴다. 리눅스의 NVIDIA 는 같은 자리에 그 도구를 부르는 길을 두되, 사용자가 정한 대로 "맥에서 되면 된다고 본다" — 보고에는 "리눅스에서는 돌려 보지 않음"이라고 적는다.
  - GPU 를 썼다는 신호(벽시계 ÷ CPU 시간이 큼)가 있는데 GPU 를 읽을 도구가 없으면 "GPU 를 재지 못함"으로 적는다.
- **순수함수 재기** — 사전의 예시 입력으로 여러 번 돌려 한 번에 드는 값을 얻는다(2026-11-11: 수백 번 반복하면 1 ~ 2% 안에서 같았다). 입력을 4배로 늘려 한 번 더 재서 배수를 낸다. 늘릴 수 없는 예시는 "늘려 재지 못함"으로 적는다.
- **외부 명령 수** — 시간과 따로, 한 번 더 돌려 센다(세는 장치가 시간을 흐리기 때문). 입력이 늘 때 수가 느는지를 본다.
- **합성 함수** — 무엇을 합성 함수로 볼지는 5단계에서 실제 코드를 보고 정해 사용자에게 묻는다. 묶음 전체의 값과 단계 값의 합을 함께 보인다.
- **막기** — 고친 함수만 앞 코드와 번갈아 잰다. 숫자(2배 등)는 1단계의 측정을 보고 제안해 사용자에게 확인받는다. 답이 달라진 예시는 비교에서 뺀다(다른 일을 하게 된 것이므로).
- **지나가는 길** — 한도를 넘으면 잰 값(앞뒤 값 · 배수 · 느려진 함수 이름)을 선택 창으로 보이고 사용자가 정한다. 지금 있는 "해로운 변경은 먼저 묻기" 규칙에 잰 값을 붙이는 것이다.

### 정한 한도 (2026-11-11 — 1단계 측정을 보고 사용자가 선택 창에서 정함)

기준은 언제나 "고치기 전의 같은 함수를 같은 입력으로 돌린 값"이다. 새 함수는 비교할 앞 값이 없어 값만 적는다.

| 잣대 | 넘는다는 것 | 넘으면 |
|---|---|---|
| 시간 | 앞뒤 여섯 쌍의 가운데값 비율 > 1.2배 | 멈추고 알림 |
| 입력 4배 배수 | 시간이 8배를 넘음 | 이미 넘는 것은 목록, 새로 넘거나 더 나빠지면 멈춤 |
| 다른 프로그램을 부른 횟수 | 앞보다 1번이라도 늚 | 멈추고 알림 |
| 메모리(프로세스 · GPU) | 1.2배를 넘고 1MB 넘게 늚 | 멈추고 알림 |

- 근거(실측): 같은 코드를 번갈아 여섯 쌍 재면 가운데값 비율이 조용할 때 0.99 ~ 1.01, 붐빌 때 0.99 ~ 1.05. 한 번만 재면 붐빌 때 1.13 ~ 2.0배로 늘어 쓸 수 없다. 부른 횟수는 세 조건에서 완전히 같았다. 메모리는 작은 함수에서 0.3MB 쯤 저절로 달라진다.
- "멈추고 알림"은 선택 창이다. 그 창은 낱말이 아니라 실제 앞뒤 값으로 묻는다(예: "전 1번 → 후 100번", "1.9MB → 37MB") — 2026-11-11 에 낱말만 던진 물음이 두 번 되돌아왔다.

### 정한 것 — 무엇을 엮은 함수(합성 함수)로 보는가 (2026-11-11, 5단계에서 사용자가 정함)

- 사전의 순수함수 가운데 **다른 사전 함수를 2개 이상 부르는 함수**. 기계가 코드에서 찾는다(목록을 손으로 두지 않는다).
- 2026-11-11 코드에서 센 값: 사전 346개 중 1개 이상 부름 78 · 2개 이상 29 · 3개 이상 11.
- 표에는 엮은 함수의 값과 그것이 부르는 함수들의 값을 나란히 보인다. 실제 예: '하지 않기로 한 일과 겹치는지 찾기'(넷을 엮음)는 한 번에 54ms, 입력 4배에 234ms(bash 3.2).
- 명령 전체(읽기 · 쓰기까지 낀 가장 바깥 엮음)를 재는 것은 이번에 넣지 않는다 — `run -- <명령>` 으로 손으로는 잴 수 있다.

### 정한 것 — 언제 얼마나 재고, 무엇과 견주는가 (2026-11-11, 5단계를 시작하기 전에 사용자가 정함)

- 실측: 함수 하나를 한 번 재는 데 1 ~ 4초. 꼼꼼히(앞뒤 여섯 쌍 + 입력 4배) 재면 함수 하나에 35 ~ 60초인데, 턴 끝 검사는 전체가 60초 안에 끝나야 한다.
- **턴 끝은 빠르게**: 고친 함수마다 부른 횟수(흔들림 없음)와 시간 세 쌍만. 한도를 넘으면 그 함수만 여섯 쌍으로 다시 재서 확인한 뒤 멈춘다. 시간이 모자라 다 못 재면 "몇 개를 못 쟀다"고 알린다.
- **계획 끝은 꼼꼼히**: 계획을 끝내기 전에 여섯 쌍 · 입력 4배 · 메모리를 한 번 돌린다.
- **견주는 기준**: 이 일을 시작하기 전의 코드(작업 가지가 갈라진 지점). 조금씩 여러 번 느려져도 합쳐서 잡히고(1.15배 세 번 = 1.52배), 단계마다 커밋해도 놓치지 않는다. 사용자가 받아들인 변경은 그때의 값을 적어 두어 같은 것을 다시 묻지 않는다.

### 재면서 알게 된 것 (3 · 4단계)

- 같은 함수가 셸에 따라 열 배 넘게 다르다: 낱말 나누기가 bash 3.2 에서 한 번 22ms · 입력 4배에 17배, bash 5 에서 1.8ms · 6 ~ 7배. 잰 셸을 결과에 적고, 앞뒤는 같은 셸로 견준다.
- 지역 설정도 값을 바꾼다(같은 함수가 bash 3.2 에서 C 일 때 22ms, UTF-8 일 때 9.7ms).
- 이 맥의 GPU 값은 컴퓨터 전체의 값이라, 아무 일도 안 해도 사용률 7 ~ 17% · 메모리 +0 ~ 56MB 가 읽힌다. GPU 를 썼다고 보는 선은 메모리 +200MB 또는 사용률이 시작 전보다 30%p 오름으로 잡았다(GPU 작업은 +1.07 ~ 1.57GB · 35 ~ 92%).

## 순수함수 · 파이프라인 (Pure functions & pipeline)

```
flow(
  read_catalog,        // 사전 파일 → 사전 글                                   (부수효과: 읽기)
  pb_targets,          // 사전 글 · 바뀐 함수 목록 → 잴 목록(함수 · 예시 입력 · 4배 입력)
  run_measured,        // 잴 항목 → 잰 값 일곱                                   (부수효과: 실행 · GPU 읽기)
  pb_pick_measure,     // 잰 값 → 판정 잣대(cpu | wall-gpu | unmeasured)
  pb_scale_ratio,      // 1배 값 · 4배 값 → 배수
  pb_compare,          // 앞 값 · 뒤 값 · 한도 → 판정 줄들
  pb_baseline_next,    // 기준 목록 · 판정 줄들 → 새 기준 목록 · 실패 줄들
  pb_render,           // 잰 값 · 판정 → 표 글
  write_out,           // 표 · 기준 목록 → 화면 · 파일 · 종료 코드              (부수효과: 쓰기)
)
```

| # | 단계 | 하는 일 | 받는 값 → 돌려주는 값 | 순수/부수효과 |
|---|---|---|---|---|
| 1 | `read_catalog` | 순수함수 사전을 읽는다 | 사전 파일 → 사전 글 | 부수효과 (입구) |
| 2 | `pb_targets` | 잴 함수와 예시 입력 · 4배 입력을 정한다 | 사전 글 · 바뀐 함수 → 잴 목록 | 순수 |
| 3 | `run_measured` | 명령을 돌려 일곱 값을 잰다 | 잴 항목 → 잰 값 | 부수효과 (입구) |
| 4 | `pb_pick_measure` | 실제로 쓴 것을 보고 판정 잣대를 고른다 | 잰 값 → 잣대 이름 | 순수 |
| 5 | `pb_scale_ratio` | 입력 4배 때 몇 배가 됐는지 낸다 | 1배 값 · 4배 값 → 배수 | 순수 |
| 6 | `pb_compare` | 앞뒤 값과 한도로 느려졌는지 가린다 | 앞 값 · 뒤 값 · 한도 → 판정 줄들 | 순수 |
| 7 | `pb_baseline_next` | 기준 목록을 늘면 실패 · 줄면 내림으로 옮긴다 | 기준 목록 · 판정 → 새 목록 · 실패 줄들 | 순수 |
| 8 | `pb_render` | 표 글을 만든다 | 잰 값 · 판정 → 표 글 | 순수 |
| 9 | `write_out` | 표와 기준 목록을 쓰고 종료 코드를 낸다 | 표 · 목록 → 화면 · 파일 | 부수효과 (출구) |

- 부수효과 위치: 1 · 3(입구), 9(출구). 판정은 4 ~ 8 의 순수 함수가 한다.
- 재사용: 오늘 만든 CPU 시간 재는 함수(`core/tests/lib/cpu-time.sh`)의 방식, 순수함수 사전, 턴 끝 검사의 "이 세션이 바꾼 파일" 목록, 선택 창 답 기록.

### 합성 설계 체크리스트 (이 계획 자신)

| # | 물음 | 답 | 근거 |
|---|---|---|---|
| 1 | 각 단계가 요소 단위 단항 순수 함수인가 | 예 | 2 · 4 ~ 8 은 잴 항목 하나(또는 그 값)를 받아 값을 낸다 |
| 3 | 요소 단위로 먼저 합성한 뒤 순회는 한 번만 하는가 | 예 | 잴 목록을 한 번 돌며 4 → 5 → 6 을 항목마다 잇는다 |
| 5 | 큰 데이터나 조기 종료가 있으면 지연 평가를 쓰는가 | 예 | 바뀐 함수만 잴 때 목록을 다 만들지 않고 해당 항목만 흘려보낸다 |
| 7 | 부수효과가 파이프라인 양 끝에만 있는가 | 예 | 실행과 읽기는 1 · 3, 쓰기는 9 |
| 10 | 핫패스는 측정한 뒤에 최적화했는가 | 예 | 1단계가 재는 방법 자체를 먼저 잰다 |
| 그 밖 | 2 · 4 · 6 · 8 · 9 | 해당 없음 | 비동기 단계와 구조 공유가 필요한 큰 값이 없다 |

## Guardrails

- 한도 숫자를 측정 없이 정하지 않는다 — 1단계의 값을 사용자에게 보이고 정한다.
- GPU 를 쓴 명령을 CPU 시간으로 판정하지 않는다. 잴 도구가 없으면 "재지 못함"이지 통과가 아니다.
- 재는 명령은 잰 코드를 바꾸지 않는다. 느려진 것을 고치는 것은 모델과 사용자의 일이다.
- 턴 끝 훅을 느리게 하지 않는다: 순수함수를 고치지 않은 턴은 0번 실행, 고친 턴도 바뀐 함수만.
- 맥(BSD) · 리눅스(GNU), bash 3.2 에서 돈다. 리눅스 GPU 는 "돌려 보지 않음"으로 적는다.
- 기준 목록을 손으로 고쳐 지나가는 길을 만들지 않는다 — 지나가는 길은 선택 창 답 하나뿐이다.

- TESTS.md 의 시나리오 17개 통과
- 사전에 오른 순수함수 전체를 한 번 잰 표를 사용자에게 보였다(잰 수 · 못 잰 수와 이유 포함)
- 2026-11-11 에 본 두 가지가 표에 그대로 나온다: 낱말 나누기 함수의 "4배 입력에 약 12배", GPU 작업의 "CPU 시간은 그대로인데 벽시계와 GPU 값이 커짐"
- 전체 시험 bash 3.2 · bash 5 통과

1. 순수함수 10개와 GPU 작업 하나로 재는 방법을 검증하고(흔들림 · 메모리 · 외부 명령 수), 한도 숫자를 제안해 사용자에게 보임 — 재는 방법부터 잰다
2. 사전에서 잴 목록과 4배 입력을 만듦 — `read_catalog`, `pb_targets`
3. 명령을 감싸 일곱 값을 재는 실행기 — `run_measured`
4. 판정 잣대 고르기와 입력 배수 — `pb_pick_measure`, `pb_scale_ratio`
5. 무엇을 합성 함수로 볼지 코드로 정해 사용자에게 묻고, 묶음 전체를 잼 — `pb_targets`, `run_measured`
6. 표 — `pb_render`
7. 앞뒤 번갈아 재기 · 한도 판정 · 기준 목록 · 선택 창으로 지나가는 길 — `pb_compare`, `pb_baseline_next`, `write_out`
8. 턴 끝(바뀐 함수만)과 계획 끝(전체)에 이음 — `write_out`
9. 전체를 한 번 재서 사용자에게 보이고, 문서 · 변경 기록 · 버전을 맞춤 — 표를 그대로 보인다

## Risks / Open Questions

- 셸 함수의 메모리는 셸 자신의 기본 메모리에 묻힐 수 있다. 1단계에서 재 보고, 차이가 안 보이면 "셸 함수의 메모리는 큰 입력에서만 뜻이 있다"고 그대로 보고한다.
- 외부 명령 수를 세는 장치가 맥 기본 bash 에서 되는지 1단계에서 확인한다. 안 되면 대신 쓸 방법과 함께 보고한다.
- 이 맥의 GPU 값은 컴퓨터 전체의 값이다(다른 앱 때문에 시작 전에도 0 ~ 29%). 앞뒤를 번갈아 재서 줄이지만 프로세스별 값은 아니다.
- 리눅스 GPU 는 돌려 보지 않는다(사용자 결정: 맥에서 되면 된다고 봄).
- 예시 입력이 작아 큰 데이터의 차이는 4배 입력으로만 본다. 4배로도 안 드러나는 느려짐은 못 잡는다.
- 무엇을 합성 함수로 볼지는 아직 정해지지 않았다(5단계).
