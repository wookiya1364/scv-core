# 합성 설계 원칙을 SCV 계약에 넣기 — 원칙 · 언어별 표 · 체크리스트

## Summary

SCV 는 순수함수와 파이프라인을 요구하지만, 그것을 "어떻게 묶어야 빠르고 메모리를 덜 쓰는가"는 어디에도 적혀 있지 않다.
사용자가 준 순수 함수 합성 설계 가이드의 핵심 — 요소 단위로 합성하고 순회는 한 번, 언어별 수단 표, 체크리스트 10개 — 을 SCV 계약으로 옮긴다.
단위 순수함수뿐 아니라 그것을 묶은 합성 함수도 대상이다. 계획을 쓸 때와 끝낼 때 체크리스트에 근거를 붙여 답하게 한다.

## Goals / Non-Goals

- **Goals**
  - 계약 문서에 세 절이 생긴다: 합성 원칙(요소 단위 합성 · 순회 한 번 · 중간 모음 없애기 · 지연 평가 · 구조 공유) · 언어별 수단 표(언어 9개) · SCV 가 막는 것과 못 막는 것.
  - 계획서의 순수함수 절에 체크리스트 10개의 답 칸이 생기고, 답마다 근거(파일과 줄, 또는 "해당 없음"과 이유)를 적는다.
  - 계획을 끝낼 때(보관 전) 같은 체크리스트를 실제 코드로 다시 답한다.
  - 답이 빠졌거나 근거가 없는 계획은 기획서를 만들 때 경고가 한 줄씩 나온다.
- **Non-Goals**
  - 함수의 시간 · 메모리를 재는 명령(다음 계획)
  - 느려지면 실패시키는 검사
  - 옛 함수들을 원칙대로 고쳐 쓰는 일
  - 다른 언어의 린트 규칙을 SCV 가 싣는 일

## Approach Overview

- **계약 문서** — 새 문서 하나(`core/contracts/composition.md`)에 가이드의 3장(원칙) · 5장(언어별 표) · 6장(체크리스트)을 SCV 의 말로 옮긴다. 가이드를 통째로 베끼지 않고, SCV 가 요구하는 것만 번호를 붙여 적는다. 기존 `purity.md` 는 이 문서를 가리키는 한 줄만 더한다.
  - 셸에 대한 절을 따로 둔다: SCV 자신의 코드는 셸이라 "순회 한 번"이 "외부 명령을 줄마다 띄우지 않는다 · 같은 글을 여러 번 훑지 않는다"로 읽힌다.
  - "SCV 가 막는 것과 못 막는 것" 절: 최대 성능은 증명할 수 없다는 것, 그 대신 하는 세 가지(입력을 늘려 재기 · 체크리스트 · 다른 짜임과 겨루기 — 재는 수단은 다음 계획)를 적는다.
- **계획서** — 계획 템플릿의 `순수함수 · 파이프라인` 절 아래에 체크리스트 표(번호 · 답 · 근거)를 둔다. 합성 함수(단계를 묶은 것)가 있으면 그 이름을 적고 "순회는 어디서 한 번 하는가"에 답한다.
- **끝낼 때** — 작업 규약의 보관 전 단계에서 같은 표를 실제 코드로 다시 채운다(계획 때의 답과 달라졌으면 달라진 줄을 적는다).
- **경고** — 기획서를 만드는 도구의 검사(지금 "예외처리 섹션이 없습니다" 같은 경고를 내는 자리)에 두 가지를 더한다: 체크리스트 표가 없음 · 답은 있는데 근거 칸이 빔. 막지 않는다.

## 순수함수 · 파이프라인 (Pure functions & pipeline)

```
flow(
  read_plan,              // 계획 폴더 → 계획서 글                         (부수효과: 읽기)
  checklist_rows,         // 계획서 글 → 체크리스트 줄들(번호 · 답 · 근거)
  checklist_problems,     // 체크리스트 줄들 → 문제 줄들(표 없음 · 답 없음 · 근거 없음)
  render_warnings,        // 문제 줄들 → 경고 글
)
```

| # | 단계 | 하는 일 | 받는 값 → 돌려주는 값 | 순수/부수효과 |
|---|---|---|---|---|
| 1 | `read_plan` | 계획서를 읽는다 | 계획 폴더 → 계획서 글 | 부수효과 (입구) |
| 2 | `checklist_rows` | 계획서에서 체크리스트 표의 줄을 꺼낸다 | 계획서 글 → 줄들(번호 · 답 · 근거) | 순수 |
| 3 | `checklist_problems` | 빠진 답과 빈 근거를 찾는다 | 줄들 → 문제 줄들 | 순수 |
| 4 | `render_warnings` | 문제를 경고 글로 만든다 | 문제 줄들 → 경고 글 | 순수 |

- 부수효과 위치: 1(읽기)뿐. 경고를 화면에 찍는 것은 기획서 도구의 기존 출구가 한다.
- 재사용: 기획서 도구의 기존 검사 틀과 경고 출구.

### 합성 설계 체크리스트 (이 계획 자신)

| # | 물음 | 답 | 근거 |
|---|---|---|---|
| 1 | 각 단계가 요소 단위 단항 순수 함수인가 | 예 | 2 ~ 4단계는 값 하나를 받아 값 하나를 낸다 |
| 3 | 요소 단위로 먼저 합성한 뒤 순회는 한 번만 하는가 | 예 | 줄들을 한 번 훑으며 문제를 모은다(3단계) |
| 7 | 부수효과가 파이프라인 양 끝에만 있는가 | 예 | 읽기는 1단계, 출력은 기존 출구 |
| 그 밖 | 2 · 4 · 5 · 6 · 8 · 9 · 10 | 해당 없음 | 작은 글(계획서 한 장)을 한 번 훑는 일이라 지연 평가 · 구조 공유 · 비동기 단계가 없다 |

## Guardrails

- 가이드의 문장을 통째로 옮기지 않는다 — SCV 가 요구하는 것을 번호로 적고, 원문은 원자료로 남긴다.
- 체크리스트는 경고까지다. 답이 없다고 계획 만들기나 보관을 막지 않는다.
- "최대 성능을 보장한다"는 말을 어디에도 쓰지 않는다 — 못 막는 것을 그대로 적는다.
- 매 턴 안내에 글을 더하지 않는다(계약 문서와 계획 절차에만).
- 언어별 표의 칸은 짧은 낱말로(문서 표에 줄글을 넣지 않는다).

## Exit criteria

- TESTS.md 의 시나리오 12개 통과
- 계약 문서에 가이드의 핵심 낱말(순회 · 지연 평가 · 구조 공유 · 단항 · 중간 모음 · 언어별)이 있다(지금은 0번)
- 이 계획 자신의 체크리스트 표로 기획서를 만들었을 때 체크리스트 경고가 0줄
- 분량 한도 시험과 전체 시험 통과

## Suggested path

1. 지금의 계획 템플릿 · 작업 규약 · 기획서 검사가 어디서 무엇을 요구하는지 확인 — 고칠 자리를 정한다
2. 계약 문서를 쓰고 기존 순수성 문서가 가리키게 함 — 문서 세 절과 셸 절을 쓴다
3. 계획 템플릿에 체크리스트 표를 넣고 작업 규약의 보관 전 단계에 다시 답하기를 넣음 — 계획 절차를 고친다
4. 기획서 검사에 경고 둘을 더함 — `checklist_rows`, `checklist_problems`, `render_warnings`
5. 문서 · 변경 기록 · 버전 · 분량 한도 확인 — 문서와 버전을 맞춘다
6. 전체 시험을 두 bash 로 돌림 — 새로 실패한 것이 없는지 본다

## Risks / Open Questions

- 체크리스트 답은 모델이 쓴다. 근거 칸을 요구해 빈말을 줄이지만, 근거가 맞는지는 기계가 보지 못한다 — 재는 명령(다음 계획)이 그 일부를 숫자로 대신한다.
- 계획 템플릿이 길어진다(표 하나). 분량 한도에 걸리면 표를 짧은 꼴(해당하는 번호만)로 줄인다.
- 기획서 검사는 래퍼 저장소에도 실리는 도구라, 래퍼 쪽 시험이 경고 문구를 고정하고 있는지 확인이 필요하다.
