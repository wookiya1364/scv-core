# 실사용 보고 판정기를 구조 규칙으로 — 보이고 물었나를 바르게 세기

## Summary

실체 보여 주기의 실사용 보고는 결과물이 바뀐 턴마다 '실제 결과를 보이고 계속 · 고칠 점을 물었나'를 판정기로 센다. 그런데
지금 판정기는 정답 표본 40턴의 '보이고 물음' 15개를 하나도 잡지 못한다(0/15) — 확인 질문에 '계속' 쪽 단서와 '고칠' 쪽 단서가
둘 다 있어야 잡기 때문이다. 10월 10일에 시도한 순서 판정(잡음 14 · 잘못 잡음 7)과 좁힌 판정(12 · 5)은 기준(잘못 잡음 2 이하)에
못 미쳐 미뤘다(사용자 결정 '측정은 판정자가, 계산기는 나중에'). 잘못 잡은 7개는 모두 '실행 뒤 묻지 않음 · 편집 앞 질문 ·
편집 뒤 실행 없이 다른 질문 · 실제 값 없이 물음' 가운데 하나였다. 그래서 판정을 기록의 구조로 바꾼다 — 첫 편집 뒤에 실행이
있고, 그 실행 뒤에 묻기가 있으며, 묻는 글 · 창이나 바로 앞 글에 그 실행 출력의 줄 · 숫자가 그대로 들어 있을 때만 '보여 줌'.
새 표본(보이고 물음 20 · 아님 20, 정답을 먼저 고정)에서 한 번만 재어 잘못 잡음 0 · 18/20 이상을 넘어야 한다.

## Goals / Non-Goals

- **Goals**
  1. **판정 규칙**: 결과물이 바뀐 턴에서 세 조건 — (가) 첫 편집 뒤 실행, (나) 그 실행 뒤 묻기(선택 창, 또는 끝 문단의 글 질문),
     (다) 묻는 글 · 창이나 바로 앞 글에 그 실행 출력의 줄 · 숫자가 그대로 — 을 모두 만족할 때만 '보여 줌'으로 센다.
  2. **실행 출력 읽기**: (다)를 가를 만큼만 실행 결과를 기록에서 읽는다. 보고가 내는 것은 지금처럼 숫자 · 날짜뿐이다.
  3. **새 표본**: 10월 9일 이후 이 저장소의 사용자 세션과 지난 측정 18번의 옮겨 둔 기록에서 편집이 있는 턴을 80개쯤 무작위
     (시드 고정)로 뽑는다. 정답은 지난번과 같은 가린 판정(방식을 모르는 새 Claude, 같은 질문)으로 먼저 매기고, 그중
     '보이고 물음' 20 · '아님' 20 을 골라 40턴을 만든다. 예전 40턴은 참고로만 쓴다.
  4. **한 번 재기**: 판정기를 다 만든 뒤 새 표본을 한 번만 열어 잰다 — 잘못 잡음 0 · '보이고 물음' 20개 중 18개 이상.
  5. **속도**: 같은 기록 묶음에서 보고 시간이 지금 판정기의 2배 안이다(맥 기본 bash 3.2).
- **Non-Goals**
  - 실사용 보고(T10) 돌리기 — 기간과 판단 기준(유지 · 끄기 · 빼기)을 따로 정해 돌린다.
  - 매 턴 안내 문구 · 실체 보여 주기 계약 · 스위치 바꾸기.
  - 판정자(모델)를 보고에 넣기 — 이 계획이 기준에 못 미치면 '둘 다(규칙이 확실한 턴은 규칙, 애매한 턴만 판정자)'를
    사용자와 정한다.
  - 코덱스 기록에서의 정확도 재기(표본에 코덱스 기록이 없다).

## Approach Overview

지금 보고는 기록 읽기 → 사람 턴 나누기 → 턴마다 판정 → 기간별 세기 → 글로 내기의 다섯 단계다(코어의 실체 보여 주기
라이브러리와 보고 스크립트). 바꾸는 곳은 둘이다. 기록 읽기는 지금 도구 결과 줄을 건너뛰므로, 실행(명령) 결과의 내용을
판정에 필요한 만큼 함께 읽게 한다. 턴마다 판정은 '확인 질문 단서 두 개' 대신 세 조건(가 · 나 · 다)으로 '보여 줌'을 가른다 —
(다)는 실행 출력과 묻는 글 · 창을 맞대어 보는 새 순수 단계로 둔다. 바뀜 · 완료 · 수정 요구 · 확인 질문 수 같은 다른 칸의
뜻은 그대로다.

검증은 두 겹이다. 저장소 안에서는 만든 고정 기록(대화 내용 없음)으로 세 조건의 경계 · 끄면 같음 · 출력 모양 · bash 3.2 와
리눅스의 같은 결과 · 속도를 검사한다. 저장소 밖 측정 장치에서는 새 표본을 가린 판정으로 먼저 고정한 뒤, 판정기를 다
만들고 한 번만 잰다. 기준(잘못 잡음 0 · 18/20 · 시간 2배)과 절차는 표본을 열기 전에 측정 기준 문서에 적는다.

## 순수함수 · 파이프라인 (Pure functions & pipeline)

```
flow(
  scv_show_real_entries,   // 기록 JSONL 줄 → 사건 줄(편집 E · 실행 R · 기타 O · 창 C/K · 글 T) + 실행 출력 조각   ← 바꿈
  scv_show_real_split,     // 사건 줄 → 사람 턴 줄
  (새) 출력 인용 판정,      // 실행 출력 조각 + 묻는 글 · 창 → 줄 · 숫자가 그대로 들어 있나(1|0)                    ← 새 단계
  scv_show_real_classify,  // 턴 줄 → 턴별 판정(바뀜 · 보여 줌 · 완료 · 수정 요구 · 확인 질문 수)               ← 보여 줌 규칙만 바꿈
  scv_show_real_count,     // 판정 줄 + 기간 → 기간별 수
  scv_show_real_render,    // 수 → 보고 글
)
```

| # | 단계 | 받는 값 → 돌려주는 값 | 순수/부수효과 |
|---|---|---|---|
| 1 | 기록 읽기 | 세션 기록 JSONL 줄 → 사건 줄 + 실행 출력 조각 | 순수 (파일 읽기는 보고 스크립트) |
| 2 | 턴 나누기 | 사건 줄 → 사람 턴 줄 | 순수 |
| 3 | 출력 인용 판정 (새) | 실행 출력 조각 + 묻는 글 · 창 → 1 \| 0 | 순수 |
| 4 | 턴 판정 | 턴 줄 → 바뀜 · 보여 줌 · 완료 · 수정 요구 · 확인 수 | 순수 |
| 5 | 기간별 세기 | 판정 줄 + 기간 → 수 | 순수 |
| 6 | 글로 내기 | 수 → 보고 글 | 부수효과 (출구: 화면 출력) |

- 부수효과 위치: 보고 스크립트의 입구(세션 기록 파일 찾기 · 읽기, 지역 시각)와 출구(화면 출력)뿐이다.
- 재사용: 턴 나누기 · 기간별 세기 · 글로 내기와 질문 판정(글 질문 여부)은 그대로 쓴다.

## Guardrails

- frontmatter `invariants:` 넷을 지킨다 — 끄면 바이트 단위로 같음, 안내 · 계약 문구 그대로, 보고는 숫자 · 날짜만, 맥 bash 3.2 와
  리눅스 같은 결과.
- 새 표본은 판정기를 다 만들기 전에 열지 않는다 — 표본 · 정답 파일은 만든 뒤 내용을 읽지 않고, 평가 스크립트가 낸 숫자만 본다.
  판정기 개발에는 예전 40턴과 직접 만든 고정 기록을 쓴다.
- 기준(잘못 잡음 0 · 18/20 이상 · 시간 2배 안)과 정답 매기기 절차(판정자 질문 · 설정 · 뽑기 시드 · 고르기 규칙)는 표본을 열기
  전에 측정 기준 문서에 고정하고, 결과를 본 뒤 바꾸지 않는다.
- 새 표본은 한 번만 잰다 — 못 넘으면 같은 표본으로 고쳐 다시 재지 않고 멈춰 보고한다.
- 표본 · 정답 · 대화 내용은 저장소 밖(측정 장치 폴더)에 둔다. 저장소의 검사는 만든 고정 기록만 쓴다.
- 정답 매기기는 판정자 호출을 80번쯤 쓴다 — 시작 전에 주간 사용량을 보고, 한도에 닿으면 멈춘다.
- 실사용 보고(T10)는 이 계획에서 돌리지 않는다.

## 예외처리 (Edge cases)

- **편집 도구 없이 명령으로만 파일을 바꾼 턴**: 지금처럼 바뀜 0 — 보여 줌도 0 (T8).
- **선택 창이 없는 호스트**: 끝 문단의 글 질문도 묻기로 센다 (T7).
- **결과물 변화 없음 · 자동 입력 · 하위 에이전트 줄**: 지금 판정기와 같은 뜻 (T9).
- **아주 짧은 값(예: '0', '1')만 겹침**: 우연한 일치일 수 있다 — 잘못 잡음으로 이어지면 새 표본 기준(0)에서 드러난다.
- **새 표본 후보에 '보이고 물음'이 20개가 안 됨**: 후보를 늘리고 그 사실을 결과에 적는다 — 기준은 그대로.
- **판정자가 답하지 못함 · 주간 사용량 한도**: 멈추고 보고한다(측정 절차).

## Exit criteria

- All TESTS.md scenarios pass (맥 · 리눅스 CI).
- 새 표본 40턴을 한 번 잰 결과가 잘못 잡음 0 · '보이고 물음' 20개 중 18개 이상이다.
- 같은 기록 묶음에서 보고 시간이 지금 판정기의 2배 안이다(맥 기본 bash 3.2).
- 하나라도 못 넘으면 멈추고 보고한다 — 다음 길('둘 다')은 사용자와 정한다.

## Suggested path

1. 기준 · 절차 고정: 정답 매기기 질문 · 판정자 설정 · 뽑기 시드 · 20 · 20 고르기 규칙 · 통과 기준을 측정 기준 문서에 적는다.
2. 새 표본 만들기: 편집 턴 후보 ~80개 뽑기 → 가린 판정으로 정답 → '보이고 물음' 20 · '아님' 20 고르기(내용은 열지 않음).
3. 판정 규칙 구현: 기록 읽기에 실행 출력 조각을 더하고, 출력 인용 판정을 새 순수 단계로, 턴 판정의 '보여 줌'을 세 조건으로.
4. 단위 검사: 세 조건 각각의 경계, 끄면 같음, 보고 출력 모양, bash 3.2 · 리눅스 같은 결과, 속도.
5. 새 표본 한 번 재기 → 기준 판정 → 넘으면 보관 · PR, 못 넘으면 멈추고 보고.

## Risks / Open Questions

- 정답도 판정자(모델)의 판단이다 — 판정자가 틀린 턴이 있을 수 있고, 사람이 다시 보지는 않는다.
- '줄 · 숫자 그대로'에서 아주 짧은 값(예: '0', '1')이 우연히 겹치면 잘못 잡음이 날 수 있다 — 기준이 잘못 잡음 0 이라 민감하다.
- 실행 출력을 읽으면 보고가 느려질 수 있다 — 0.66.0 에서 bash 3.2 의 긴 한글 처리와 jq 정규식 비용으로 크게 느려진 적이 있다.
- 10월 9일 이후 기록에서 '보이고 물음' 턴이 20개가 안 될 수 있다 — 그러면 후보를 늘리고 그 사실을 결과에 적는다(기준은 그대로).
- 코덱스 기록은 표본에 없어, 코덱스에서의 정확도는 재지 않는다(남는 한계).
- 기준이 엄격해 규칙만으로는 못 넘을 수 있다 — 그때는 멈추고 '둘 다'를 사용자와 정한다.
