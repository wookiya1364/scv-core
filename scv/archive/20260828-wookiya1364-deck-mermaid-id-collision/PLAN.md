# 기획서 그림이 서로 겹친다 — 그림마다 다른 id, 그리고 빈 그림 없애기

## Summary

기획서를 열면 그림들이 서로 겹치고, 그중 하나는 빈 채로 나온다. 두 증상처럼 보이지만
**뿌리는 하나다** — 머메이드가 그림 id 를 시각에서 만들어, 같은 순간에 그려진 두
그림이 같은 id 를 받는다. 뒤진 쪽은 빈 그림이 되고, 살아남은 쪽의 스타일과 화살촉은
문서 전체에 번진다. 여기에 정적 렌더 단계가 모든 id 를 하나로 뭉개 놓아 굳어졌다.

## Goals / Non-Goals

- **Goals**
  - 한 문서 안의 그림들이 서로 다른 id 를 갖게 한다.
  - 그러면서도 같은 입력이면 산출물이 바이트 단위로 같다는 기존 성질을 지킨다.
  - 같은 그림은 문서에서의 **위치가 바뀌어도** 같은 id 를 갖게 한다 — 중간에 한 장
    끼워 넣어도 나머지 그림의 산출물이 흔들리지 않는다.
  - 화면설계 시트 안의 그림이 내용과 크기를 갖춘 채로 나오게 한다.

- **Non-Goals**
  - 덱의 시각 디자인 변경 — 색·여백·글꼴은 건드리지 않는다.
  - 머메이드 버전 올리기.
  - 화면설계 시트의 스키마 변경 — 작성 문법은 그대로다.
  - 정적 렌더가 실패했을 때의 물러남 정책 변경 — 지금처럼 CDN 판을 남긴다.

## Approach Overview

두 결함은 기획서가 만들어지는 마지막 단계에서 함께 나온다.

**결함 1 — 같은 id.** 정적 렌더는 머메이드가 붙인 빌드 시각 기반 id 를 고정 문자열
하나로 바꾼다. 그렇게 한 이유가 코드 주석에 남아 있다: 이 산출물은 계획을 승격할
때마다 커밋되는데, 빌드마다 달라지는 id 를 그대로 두면 내용이 같아도 파일이 매번
달라진다. 의도는 옳았고 결과가 과했다 — **안정성과 유일성을 동시에 만족시켜야 하는데
안정성만 취했다.**

해결 방향은 id 를 **그림의 내용에서** 만드는 것이다. 같은 그림이면 언제 빌드해도 같은
값이고, 다른 그림이면 다른 값이며, 문서에서의 위치와 무관하다. 순번은 안정성은 주지만
중간 삽입 한 번에 뒤 그림이 전부 밀려 산출물 차이가 커지므로 택하지 않는다.

**결함 2 — 빈 그림. 그리고 두 결함은 같은 뿌리였다.**

이 절은 원인을 확정한 뒤 다시 썼다. 처음 세운 가설은 "시트 안에서 폭이 0으로
측정된다" 였고 **그것은 틀렸다**. 실제로 재 보니 그 컨테이너의 폭은 550px 로 멀쩡했다.
앞서 배제한 두 가설(원본 손상·페이지 숨김)과 함께, 이 세 번째 가설도 측정이 기각했다.

진짜 원인은 **머메이드가 그림 id 를 시각에서 만든다**는 것이다. 같은 밀리초에 그려진
두 그림이 같은 id 를 받는다. 실측으로 잡았다 — 세 장짜리 문서에서 2번과 3번이 둘 다
`mermaid-1787895796165` 였다. 뒤진 쪽은 자기 id 로 앞 그림의 요소를 집어 빈 SVG 로
끝난다. 그래서 **겹침과 빈 그림은 두 증상이 아니라 한 원인의 두 얼굴**이다.

여기에 정적 단계의 고정 id 가 겹쳐 상황이 굳었다. 고칠 곳도 두 군데다: 그리는 쪽은
머메이드에 결정적 id 를 쓰게 하고(충돌 제거 + 시각 의존 제거), 굽는 쪽은 최종 id 를
그림 내용에서 만든다(유일성 + 위치 무관성).

**첫 항목을 "고치기" 가 아니라 "재기" 로 둔 것이 이 계획에서 가장 값어치 있는
판단이었다.** 유력해 보이던 가설이 측정 한 번에 무너졌고, 그대로 고쳤다면 엉뚱한
곳을 손봤을 것이다.

## 순수함수 · 파이프라인 (Pure functions & pipeline)

```
flow(
  extractSvgs,      // 문서 HTML → 그림 조각 목록
  deriveId,         // 그림 조각 → 그 그림의 고유 id
  rewriteRefs,      // (그림 조각, id) → id 참조가 바뀐 조각
  applySize,        // 그림 조각 → 크기가 실린 조각
  spliceBack,       // (문서 HTML, 조각들) → 문서 HTML
)
```

| # | 단계 | 받는 값 → 돌려주는 값 | 순수/부수효과 |
|---|---|---|---|
| 1 | `extractSvgs` | 문서 HTML → 그림 조각 목록 | 순수 |
| 2 | `deriveId` | 그림 조각 → 고유 id 문자열 | 결정적 변환 (해싱 도구 사용 가능) |
| 3 | `rewriteRefs` | (조각, id) → 스타일·마커 참조가 새 id 로 바뀐 조각 | 순수 |
| 4 | `applySize` | 조각 → 크기 정보가 실린 조각 | 순수 |
| 5 | `spliceBack` | (문서 HTML, 조각들) → 완성된 문서 HTML | 순수 |

- 부수효과 위치: 파이프라인 바깥. 브라우저를 띄워 문서를 얻는 일과 파일로 쓰는 일만
  효과부가 맡고, 위 다섯 단계는 문자열만 다룬다.
- 재사용: 색을 벗기고 크기를 싣는 기존 처리는 그대로 두고, 그 앞에 `deriveId` 만
  갈아 끼운다. 조각을 훑는 방식도 지금 것을 그대로 쓴다.

## Guardrails

- **바이트 안정성이 이 변경의 계약이다.** 같은 입력으로 두 번 빌드해 산출물이 다르면
  실패다. 시각·난수·빌드 순번에서 값을 만들지 않는다.
- **색 벗기기 처리를 건드리지 않는다.** 머메이드가 세 가지 방식으로 색을 굽고 그것을
  벗겨야 덱이 다시 칠할 수 있다는 기존 이유는 그대로다. id 를 만드는 부분만 바꾼다.
- **물러남 정책을 유지한다.** 브라우저가 없거나 CDN 이 막히면 지금처럼 CDN 판을 남기고
  실패로 취급하지 않는다.
- **원인 확정 전에 고치지 않는다.** 이 항목이 이번에 실제로 값을 했다 — 유력하던
  가설(폭 0)이 측정 한 번에 무너졌고, 재지 않았다면 엉뚱한 곳을 손봤을 것이다.
- **화면설계 시트의 작성 문법을 바꾸지 않는다.** 이미 쓰인 계획서들이 그대로 열려야
  한다.
- whitespace 계약: 줄 끝 공백 금지, 파일 끝 빈 줄 금지.

## 성공지표 (Metrics)

| 지표 | 지금 (baseline) | 목표 (target) | 어떻게 재나 |
|---|---|---|---|
| 한 문서에서 서로 다른 그림 id 수 | 3장 모두 같은 id 1개 | 그림 수와 같음 | 산출물에서 id 를 세어 본다 |
| 내용 없이 나오는 그림 | 화면설계 시트의 그림 (실측 1장) | 0장 | 빈 그래픽 표식을 센다 |
| 크기 정보 없는 그림 | 1장 (폭이 100% 로 남음) | 0장 | 크기 속성 유무를 본다 |
| 같은 입력 재빌드 시 산출물 차이 | 0 (이미 안정) | 0 (유지) | 두 번 빌드해 해시 비교 |
| 중간 삽입 시 나머지 그림의 차이 | 해당 없음 (전부 같은 id 라 무의미) | 0 | 그림 한 장을 앞에 끼우고 뒤 그림 조각을 비교 |

## 예외처리 (Edge cases)

- **그림이 한 장뿐인 문서** → id 는 여전히 내용에서 나온다. 특별 취급 없음.
- **완전히 같은 그림이 한 문서에 두 번** → 내용이 같으므로 id 도 같아진다. 이 경우
  참조가 첫 번째로 몰리므로, 같은 값이 이미 쓰였는지 보고 구분자를 덧붙인다.
- **머메이드 markup 이 바뀌어 id 를 못 찾음** → 지금처럼 그 조각을 건드리지 않고
  넘어간다 (fail open).
- **브라우저 없음 · CDN 막힘** → 정적 렌더를 건너뛰고 CDN 판을 남긴다. 변경 없음.
- **크기 정보가 없는 그림** → 원인 확정 뒤 결정. 크기를 만들어 낼 수 없다면 그 사실을
  한 줄로 알리고 넘어가되, 다른 절을 덮지는 않게 한다.
- **화면설계 시트 없이 그림만 있는 계획서** → 지금과 동일하게 동작해야 한다.

## Exit criteria

- TESTS.md 시나리오가 모두 통과한다.
- 기존 덱 검사 네 종이 계속 통과한다.
- 실제 기획서를 열었을 때 그림이 겹치지 않는다 (사람 눈으로 한 번 확인).
- 빈 그림이 없다.
- 같은 입력으로 두 번 빌드한 산출물의 해시가 같다.
- 템플릿 지문이 갱신돼 있다.

## Suggested path

1. **원인 확정 먼저.** 그림이 그려질 때의 실제 값을 찍는다. (완료 — 폭은 550px 로
   멀쩡했고, 진짜 원인은 머메이드의 시각 기반 id 충돌이었다.)
2. 그리는 쪽: 머메이드에 결정적 id 를 쓰게 한다 — 충돌이 사라지고 빈 그림도 사라진다.
3. 굽는 쪽: 최종 id 를 그림 내용에서 만든다. 같은 값이 겹치면 구분자를 붙인다.
4. 검사를 쓴다 — id 유일성, 위치 무관성, 재빌드 동일성, 빈 그림 없음.
5. 기존 덱 검사 네 종이 초록인지 확인한다.
6. 템플릿 지문을 다시 계산하고 변경 이력을 남긴다.

## Risks / Open Questions

- **빈 그림의 원인은 확정됐고, 처음 가설은 틀렸다.** 폭이 0일 것이라 보았으나 550px
  이었다. 세 번째로 세운 가설까지 측정이 기각했고, 그제야 id 충돌이 드러났다.
- **결정적 id 는 머메이드의 설정에 기댄다.** 머메이드가 이 동작을 바꾸면 빈 그림이
  돌아올 수 있다. 여러 장 재료를 쓰는 검사가 그때 잡아 준다.
- **내용에서 뽑은 id 는 길다.** 산출물이 조금 커진다. 그림 하나당 몇 십 바이트 수준이라
  받아들일 만하다고 보지만, 실제 증가폭은 구현 뒤 확인한다.
- **같은 그림이 두 번 나오는 경우**를 구분자로 처리하면, 그 문서에서 그림 순서를 바꿀 때
  구분자가 옮겨 붙어 두 조각이 달라질 수 있다. 드문 경우라 받아들이되 검사로 드러낸다.
