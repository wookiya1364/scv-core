# 강제를 preflight 로 — 진단은 주입하고 되돌림은 없앤다

## Summary

0.39.0 의 강제는 동작하지만 값이 너무 비싸다. 되돌림이 **응답 종료 시점**에 걸리는
탓에, 모델이 본문을 다 쓴 뒤에 되돌려지고 되돌릴 때마다 본문을 통째로 다시 쓴다.
강제 지점을 턴의 **시작**으로 옮긴다: 프롬프트 훅이 상태 진단을 직접 주입하고,
되돌림은 없앤다. 본문은 항상 한 번만 나간다.

## Goals / Non-Goals

- **Goals**
  - 한 턴에 본문이 **한 번만** 생성되게 한다.
  - 매 턴 SCV 의 현재 상태가 컨텍스트에 들어와 있게 한다 (진단 주입).
  - 앞을 보는 턴은 대화 모드로, 뒤를 보는 턴은 아카이브 검색으로 가게 안내한다.
  - 강제 동작 여부를 화면에서 계속 구분할 수 있게 한다 (표시줄 유지).
  - 가드를 다시 의존성 없는 파일로 되돌린다.

- **Non-Goals**
  - help 프로토콜 본문 변경 — 세 모드의 문법은 그대로다.
  - 주입 내용을 사람이 읽기 좋게 다시 쓰는 것 — 진단 출력을 그대로 싣는다.
  - 다른 SCV 액션의 호출 유도 — 이번 범위는 help 의 세 모드뿐이다.
  - 스위치 이름 변경 — 뜻만 바뀐다 (되돌림 → preflight).

## Approach Overview

**무엇이 잘못됐나.** 목적을 잘못 잡았다. 목적은 "스킬이 호출되는 것" 이 아니라
**"이 턴에 SCV 의 현재 상태가 들어와 있는 것"** 이었다. 호출은 수단일 뿐이었는데,
그 수단을 강제하느라 목적보다 비싼 값을 치렀다.

값의 크기가 그것을 말해 준다. 상태 점검 출력은 전체 5,898바이트이고 그중 진단은
3,148바이트다. 되돌림 한 번은 **모델 턴 하나** — 그 시점 대화 전체의 재처리와 본문
재생성이 모두 들어간다. 3KB 를 아끼려다 그보다 훨씬 큰 것을 반복해서 썼다.

**강제 지점이 턴의 끝이었던 것이 구조적 원인이다.** 일이 이미 끝난 뒤에 다시 시키면
그 일이 통째로 반복된다. 시작으로 옮기면 반복할 일 자체가 없다.

**새 모양.** 프롬프트 훅이 세 가지를 싣는다.

1. **진단** (약 3KB) — 상태 점검 출력에서 진단 부분만. 앞의 SCV 개요와 명령 목록
   2,823바이트는 매번 같은 내용이라 뺀다.
2. **분류 지침** — 앞을 보는 턴이면 대화 모드, 뒤를 보는 턴이면 아카이브 검색,
   둘 다 아니면 주입된 진단만 보고 바로 답한다.
3. **표시줄** — 한 줄. 최초 문제 제기가 "되는지 안 되는지 구분이 안 간다" 였고,
   그 답은 되돌림이 아니라 이 줄이었다.

**되돌림이 사라지는 이유는 둘이다.** 첫째, 세 갈래가 모두 정당한 결과가 되면
"부르지 않은 것이 잘못" 이라는 전제가 무너진다. 둘째, "이 턴이 대화 모드였어야
했다" 는 판단은 **모델의 것**이라 위조 불가한 근거가 되지 못한다. 분류는 모델이
하는데 강제는 모델을 믿을 수 없다는 비대칭이 있고, 그 위에는 강제를 세울 수 없다.

**따라오는 정리.** 되돌림이 없으면 영수증을 읽는 두 번째 소비자도 없다. 가드가
라이브러리를 읽을 이유가 사라지므로 원래의 의존성 없는 모습으로 되돌린다 —
제품에서 가장 위험한 파일의 위험이 도로 줄어든다. 가드 계약에서 "두 번째 소비자"
절도 함께 걷는다.

## 순수함수 · 파이프라인 (Pure functions & pipeline)

```
flow(
  readSwitches,      // 설정 → 스위치 두 개
  runProbe,          // (없음) → 상태 점검 전체 출력
  trimToDiagnosis,   // 전체 출력 → 진단 부분만
  renderBanner,      // 스위치 → 표시줄 한 줄
  renderRouting,     // (없음) → 분류 지침 블록
  emitLines,         // 텍스트들 → 표준출력
)
```

| # | 단계 | 받는 값 → 돌려주는 값 | 순수/부수효과 |
|---|---|---|---|
| 1 | `readSwitches` | 설정 파일 → (라우팅 스위치, preflight 스위치) | 부수효과 (입구) |
| 2 | `runProbe` | 없음 → 상태 점검 전체 출력 | 부수효과 (입구) |
| 3 | `trimToDiagnosis` | 전체 출력 → 진단 부분만 | 순수 |
| 4 | `renderBanner` | 스위치 → 표시줄 한 줄 | 순수 |
| 5 | `renderRouting` | 없음 → 분류 지침 블록 | 순수 |
| 6 | `emitLines` | 텍스트들 → 표준출력 | 부수효과 (출구) |

- 부수효과 위치: 설정 읽기와 점검 실행이 입구, 출력이 출구. 가운데 세 단계는
  문자열만 다룬다 — 그래서 점검 출력을 고정 입력으로 주면 잘라내기와 문구 생성을
  훅 없이 그대로 시험할 수 있다.
- 재사용: 스위치 해석은 기존 것을 그대로 쓴다. 삭제되는 것은 되돌림 판정·회차별
  문구·턴 상태 경로다.

## Guardrails

- **본문이 두 번 생성되면 실패다.** 이 계획의 존재 이유다. 어떤 경로로도 추가
  생성이 일어나서는 안 된다.
- **응답 종료 훅은 되돌리지 않는다.** 조건부로도 남기지 않는다 — 조건이 생기면
  그 조건을 판정할 근거가 다시 필요해지고, 그 근거는 없다.
- **세션을 막지 않는다.** 점검 실행이 실패하거나 느려도 훅은 조용히 넘어간다.
  기존 NON-BLOCKING 보장이 여기서도 상한이다.
- **점검 실행이 매 턴 돈다는 점을 잊지 않는다.** 실측 0.45초. 이보다 크게 느려지면
  주입을 줄이는 쪽을 먼저 본다.
- **가드에 새 의존성을 남기지 않는다.** 되돌림과 함께 들어갔던 라이브러리 참조를
  걷어 원래대로 되돌린다.
- **저널 기록 모양을 되돌린다.** 기록을 함수로 감쌌던 것은 되돌림 순서 때문이었다.
  되돌림이 없으면 그 구조도 필요 없다.
- **옛 계획을 supersedes 로 선언한다.** 그 계획의 테스트는 "되돌린다" 를 단언하므로,
  선언하지 않으면 누적 회귀가 그 슬러그에서 실패한다.
- whitespace 계약: 줄 끝 공백 금지, 파일 끝 빈 줄 금지.

## 예외처리 (Edge cases)

- **점검 실행이 실패한다** → 진단 없이 표시줄과 지침만 낸다. 막지 않는다.
- **점검이 느리다** → 그대로 기다린다. 시간 제한을 두어 잘라내면 반쪽 진단이
  들어가 더 나쁘다. 느려지면 주입량을 줄이는 쪽으로 고친다.
- **진단 구간을 못 찾는다** (점검 출력 형식이 바뀜) → 자르지 않고 전체를 싣는다.
  많이 싣는 쪽이 아무것도 안 싣는 쪽보다 낫다.
- **앞도 뒤도 아닌 턴** → 추가 호출 없이 바로 답한다. 정당한 결과다.
- **이미 다른 SCV 액션이 실린 턴** → 그 프로토콜을 계속한다. 기존 계약 그대로.
- **스위치 두 개가 다른 상태** (라우팅 켬 + preflight 끔) → 기존 라우팅 안내만
  나가고 진단·표시줄은 없다.
- **scv 폴더 없음 · 읽기 도구 없음** → 아무 출력도 없다.

## Exit criteria

- TESTS.md 시나리오가 모두 통과한다.
- 기존 검사가 계속 통과한다 (저널·항상라우팅·가드·설정·순수성·공백·지문).
- 누적 회귀가 초록이다 — 옛 슬러그가 supersedes 로 건너뛰어진다.
- 실제 대화에서 본문이 한 번만 나가는 것을 사람이 확인한다.
- 템플릿 지문이 갱신돼 있다.

## Suggested path

1. 되돌림을 걷는다 — 응답 종료 훅의 강제 블록 삭제, 저널 기록 구조 원복.
2. 가드와 가드 계약을 되돌린다 (라이브러리 의존 제거).
3. 판정부에서 되돌림용 함수를 걷고 잘라내기·문구 생성만 남긴다.
4. 프롬프트 훅을 preflight 로 바꾼다 — 진단 주입 + 분류 지침 + 표시줄.
5. 검사를 다시 쓴다 (되돌림 단언 → 주입·무되돌림 단언).
6. 지문을 다시 계산하고 변경 이력을 남긴다.

## Risks / Open Questions

- **매 턴 점검 실행이 새 비용이다.** 0.45초와 3KB. 되돌림 한 번보다 훨씬 싸지만

- **분류가 틀릴 수 있다.** 앞을 보는 턴인데 그냥 답하고 넘어갈 수 있다. 강제
  수단이 없으므로 그때는 사용자가 직접 부르면 된다 — 잘못 부르는 쪽보다 낫다.

  를 뜻한다. 설명 문구와 변경 이력에 그 사실을 적는다.

# Test Plan — 강제를 preflight 로

## Overview

이 계획의 핵심 단언은 **부정형**이다: 응답 종료 훅이 어떤 경우에도 되돌리지
않는다. 그래서 검사의 절반은 "무엇이 일어나지 않는가" 를 본다. 앞선 계획의 검사가
"되돌린다" 를 단언했으므로, 그 단언을 뒤집는 것이 이 문서의 일이다.

나머지 절반은 주입을 본다. 무엇이 들어가고(진단·지침·표시줄), 무엇이 빠지는가
(개요·명령 목록). 훅을 직접 실행해 표준출력과 종료 코드로 판정한다.

## Test scenarios

### T1. 응답 종료 훅이 되돌리지 않는다

이 계획이 존재하는 이유다. 앞 계획에서 되돌림이 나오던 바로 그 상황을 그대로
재현하고, 이번에는 나오지 않는 것을 본다.

- **Setup**: scv 폴더가 있는 임시 프로젝트. 스위치 기본값. 프롬프트 훅을 먼저
  실행한다. 영수증 저장소는 비어 있다 (help 를 부르지 않은 상태).
- **Run**: 종료 훅을 실행한다.
- **Expected**: 차단 결정이 없다.
- **Pass criterion**: 표준출력에 차단 결정이 없고 종료 코드가 0.

### T2. 여러 번 실행해도 되돌리지 않는다

- **Setup**: T1 과 같다.
- **Run**: 종료 훅을 연속 5회 실행한다.
- **Expected**: 매번 차단 결정이 없다.
- **Pass criterion**: 5회 모두 출력에 차단 결정이 없다. 회차가 쌓여도 달라지지
  않는다는 것이 요점이다.

### T3. 매 턴 진단이 주입된다

- **Setup**: scv 폴더가 있는 임시 프로젝트.
- **Run**: 프롬프트 훅을 실행한다.
- **Expected**: 출력에 프로젝트 진단 내용이 실린다.
- **Pass criterion**: 진단 구간을 알아볼 수 있는 표지가 출력에 있다.

### T4. 개요와 명령 목록은 주입되지 않는다

매번 같은 내용이라 뺀 것이므로, 실제로 빠졌는지 본다.

- **Setup**: T3 과 같다.
- **Run**: 프롬프트 훅 출력과 상태 점검 전체 출력을 비교한다.
- **Expected**: 점검 전체에는 있고 훅 출력에는 없는 구간이 존재한다 (개요·명령
  목록).
- **Pass criterion**: 훅 출력이 점검 전체 출력보다 짧고, 명령 목록 표지가 훅
  출력에 없다.

### T5. 분류 지침이 세 갈래를 모두 말한다

- **Setup**: T3 과 같다.
- **Run**: 프롬프트 훅 출력을 본다.
- **Expected**: 앞을 보는 턴·뒤를 보는 턴·둘 다 아닌 턴에 대한 지침이 모두 있다.
- **Pass criterion**: 세 갈래가 각각 출력에서 확인된다. 셋째 갈래가 빠지면 모델이
  모든 턴을 둘 중 하나로 밀어넣게 되므로, 그 항목이 특히 중요하다.

### T6. 표시줄이 매 턴 나온다

- **Setup**: T3 과 같다.
- **Run**: 프롬프트 훅을 두 번 실행한다.
- **Expected**: 두 번 다 표시줄이 나온다.
- **Pass criterion**: 두 실행 모두 표시줄 표지가 출력에 있다.

### T7. preflight 스위치를 끄면 주입도 표시줄도 없다

- **Setup**: 설정에서 preflight 스위치를 off 로 둔다. 라우팅 스위치는 켜 둔다.
- **Run**: 프롬프트 훅과 종료 훅을 차례로 실행한다.
- **Expected**: 진단·지침·표시줄이 모두 없다. 기존 라우팅 안내는 그대로 나온다.
  종료 훅은 되돌리지 않는다.
- **Pass criterion**: 세 가지가 출력에 없고, 라우팅 안내는 있으며, 차단 결정이 없다.

### T8. 전체 라우팅 스위치를 끄면 아무것도 없다

- **Setup**: 라우팅 스위치를 off 로 둔다.
- **Run**: 프롬프트 훅을 실행한다.
- **Expected**: 라우팅 안내·진단·지침·표시줄이 모두 없다.
- **Pass criterion**: 네 가지가 모두 출력에 없다.

### T9. scv 폴더가 없으면 아무 출력도 없다

- **Setup**: scv 폴더가 없는 임시 폴더.
- **Run**: 프롬프트 훅과 종료 훅을 차례로 실행한다.
- **Expected**: 두 훅 모두 조용히 끝난다.
- **Pass criterion**: 표준출력이 비어 있고 종료 코드 0.

### T10. 점검 실행이 실패해도 막지 않는다

- **Setup**: 상태 점검을 실행할 수 없는 환경을 만든다.
- **Run**: 프롬프트 훅을 실행한다.
- **Expected**: 진단 없이 표시줄과 지침만 나오고 정상 종료한다.
- **Pass criterion**: 종료 코드 0, 표시줄 있음, 훅이 죽지 않음.

### T11. 저널 기록이 이번 변경 이전과 같다

- **Setup**: 기존 저널 검사가 쓰는 페이로드를 그대로 쓴다.
- **Run**: 기존 저널 검사를 실행한다.
- **Expected**: 전부 통과한다.
- **Pass criterion**: 기존 저널 검사가 초록이다. 한 턴에 한 줄이라는 성질이
  되돌림 제거 뒤에도 유지되는지를 본다.

### T12. 가드가 라이브러리를 읽지 않는다

- **Setup**: 판정부 라이브러리 파일을 읽을 수 없게 만든다.
- **Run**: 가드를 발행 모드로 실행하고 영수증이 남는지 본다.
- **Expected**: 라이브러리가 없어도 평소처럼 영수증을 남긴다.
- **Pass criterion**: 영수증이 기록되고 가드가 정상 종료한다. 가드가 다시 홀로
  서는지를 보는 항목이다.

### T13. 되돌림용 함수가 남아 있지 않다

- **Setup**: 없음.
- **Run**: 판정부 라이브러리를 훑는다.
- **Expected**: 되돌림 판정·회차별 문구·턴 상태 경로 함수가 없다.
- **Pass criterion**: 해당 함수 이름이 하나도 정의돼 있지 않다. 코드가 남아 있으면
  다음 사람이 다시 켤 수 있고, 그러면 같은 비용이 돌아온다.

### T14. 판정부가 순수성 계약을 지킨다

- **Setup**: 없음.
- **Run**: 순수성 검사기를 판정부 파일에 돌린다.
- **Expected**: 위반 0건.
- **Pass criterion**: 검사기가 통과를 보고한다.

### T15. 옛 계획이 회귀에서 건너뛰어진다

- **Setup**: 이 계획이 아카이브된 뒤.
- **Run**: 누적 회귀를 실행한다.
- **Expected**: 대체된 슬러그가 건너뛰어지고 회귀가 초록이다.
- **Pass criterion**: 실패 0건. 이 선언을 빠뜨리면 옛 슬러그의 "되돌린다" 단언이
  실패하므로, 그 사실을 검사로 못 박는다.

### T16. 실제 대화에서 본문이 한 번만 나간다 (사람 확인)

기계로 판정하기 어려워 따로 둔다.

- **Run**: 평범한 대화를 몇 턴 한다.
- **Expected**: 답이 한 번만 생성되고, 같은 내용이 반복되지 않는다.
- **Pass criterion**: 사람이 확인하고 보고한다.

# 강제를 preflight 로 — 진단은 주입하고 되돌림은 없앤다

## Summary

0.39.0 의 강제는 동작하지만 값이 너무 비싸다. 되돌림이 **응답 종료 시점**에 걸리는
탓에, 모델이 본문을 다 쓴 뒤에 되돌려지고 되돌릴 때마다 본문을 통째로 다시 쓴다.
강제 지점을 턴의 **시작**으로 옮긴다: 프롬프트 훅이 상태 진단을 직접 주입하고,
되돌림은 없앤다. 본문은 항상 한 번만 나간다.

## Goals / Non-Goals

- **Goals**
  - 한 턴에 본문이 **한 번만** 생성되게 한다.
  - 매 턴 SCV 의 현재 상태가 컨텍스트에 들어와 있게 한다 (진단 주입).
  - 앞을 보는 턴은 대화 모드로, 뒤를 보는 턴은 아카이브 검색으로 가게 안내한다.
  - 강제 동작 여부를 화면에서 계속 구분할 수 있게 한다 (표시줄 유지).
  - 가드를 다시 의존성 없는 파일로 되돌린다.

- **Non-Goals**
  - help 프로토콜 본문 변경 — 세 모드의 문법은 그대로다.
  - 주입 내용을 사람이 읽기 좋게 다시 쓰는 것 — 진단 출력을 그대로 싣는다.
  - 다른 SCV 액션의 호출 유도 — 이번 범위는 help 의 세 모드뿐이다.
  - 스위치 이름 변경 — 뜻만 바뀐다 (되돌림 → preflight).

## Approach Overview

**무엇이 잘못됐나.** 목적을 잘못 잡았다. 목적은 "스킬이 호출되는 것" 이 아니라
**"이 턴에 SCV 의 현재 상태가 들어와 있는 것"** 이었다. 호출은 수단일 뿐이었는데,
그 수단을 강제하느라 목적보다 비싼 값을 치렀다.

값의 크기가 그것을 말해 준다. 상태 점검 출력은 전체 5,898바이트이고 그중 진단은
3,148바이트다. 되돌림 한 번은 **모델 턴 하나** — 그 시점 대화 전체의 재처리와 본문
재생성이 모두 들어간다. 3KB 를 아끼려다 그보다 훨씬 큰 것을 반복해서 썼다.

**강제 지점이 턴의 끝이었던 것이 구조적 원인이다.** 일이 이미 끝난 뒤에 다시 시키면
그 일이 통째로 반복된다. 시작으로 옮기면 반복할 일 자체가 없다.

**새 모양.** 프롬프트 훅이 세 가지를 싣는다.

1. **진단** (약 3KB) — 상태 점검 출력에서 진단 부분만. 앞의 SCV 개요와 명령 목록
   2,823바이트는 매번 같은 내용이라 뺀다.
2. **분류 지침** — 앞을 보는 턴이면 대화 모드, 뒤를 보는 턴이면 아카이브 검색,
   둘 다 아니면 주입된 진단만 보고 바로 답한다.
3. **표시줄** — 한 줄. 최초 문제 제기가 "되는지 안 되는지 구분이 안 간다" 였고,
   그 답은 되돌림이 아니라 이 줄이었다.

**되돌림이 사라지는 이유는 둘이다.** 첫째, 세 갈래가 모두 정당한 결과가 되면
"부르지 않은 것이 잘못" 이라는 전제가 무너진다. 둘째, "이 턴이 대화 모드였어야
했다" 는 판단은 **모델의 것**이라 위조 불가한 근거가 되지 못한다. 분류는 모델이
하는데 강제는 모델을 믿을 수 없다는 비대칭이 있고, 그 위에는 강제를 세울 수 없다.

**따라오는 정리.** 되돌림이 없으면 영수증을 읽는 두 번째 소비자도 없다. 가드가
라이브러리를 읽을 이유가 사라지므로 원래의 의존성 없는 모습으로 되돌린다 —
제품에서 가장 위험한 파일의 위험이 도로 줄어든다. 가드 계약에서 "두 번째 소비자"
절도 함께 걷는다.

## 순수함수 · 파이프라인 (Pure functions & pipeline)

```
flow(
  readSwitches,      // 설정 → 스위치 두 개
  runProbe,          // (없음) → 상태 점검 전체 출력
  trimToDiagnosis,   // 전체 출력 → 진단 부분만
  renderBanner,      // 스위치 → 표시줄 한 줄
  renderRouting,     // (없음) → 분류 지침 블록
  emitLines,         // 텍스트들 → 표준출력
)
```

| # | 단계 | 받는 값 → 돌려주는 값 | 순수/부수효과 |
|---|---|---|---|
| 1 | `readSwitches` | 설정 파일 → (라우팅 스위치, preflight 스위치) | 부수효과 (입구) |
| 2 | `runProbe` | 없음 → 상태 점검 전체 출력 | 부수효과 (입구) |
| 3 | `trimToDiagnosis` | 전체 출력 → 진단 부분만 | 순수 |
| 4 | `renderBanner` | 스위치 → 표시줄 한 줄 | 순수 |
| 5 | `renderRouting` | 없음 → 분류 지침 블록 | 순수 |
| 6 | `emitLines` | 텍스트들 → 표준출력 | 부수효과 (출구) |

- 부수효과 위치: 설정 읽기와 점검 실행이 입구, 출력이 출구. 가운데 세 단계는
  문자열만 다룬다 — 그래서 점검 출력을 고정 입력으로 주면 잘라내기와 문구 생성을
  훅 없이 그대로 시험할 수 있다.
- 재사용: 스위치 해석은 기존 것을 그대로 쓴다. 삭제되는 것은 되돌림 판정·회차별
  문구·턴 상태 경로다.

## Guardrails

- **본문이 두 번 생성되면 실패다.** 이 계획의 존재 이유다. 어떤 경로로도 추가
  생성이 일어나서는 안 된다.
- **응답 종료 훅은 되돌리지 않는다.** 조건부로도 남기지 않는다 — 조건이 생기면
  그 조건을 판정할 근거가 다시 필요해지고, 그 근거는 없다.
- **세션을 막지 않는다.** 점검 실행이 실패하거나 느려도 훅은 조용히 넘어간다.
  기존 NON-BLOCKING 보장이 여기서도 상한이다.
- **점검 실행이 매 턴 돈다는 점을 잊지 않는다.** 실측 0.45초. 이보다 크게 느려지면
  주입을 줄이는 쪽을 먼저 본다.
- **가드에 새 의존성을 남기지 않는다.** 되돌림과 함께 들어갔던 라이브러리 참조를
  걷어 원래대로 되돌린다.
- **저널 기록 모양을 되돌린다.** 기록을 함수로 감쌌던 것은 되돌림 순서 때문이었다.
  되돌림이 없으면 그 구조도 필요 없다.
- **옛 계획을 supersedes 로 선언한다.** 그 계획의 테스트는 "되돌린다" 를 단언하므로,
  선언하지 않으면 누적 회귀가 그 슬러그에서 실패한다.
- whitespace 계약: 줄 끝 공백 금지, 파일 끝 빈 줄 금지.

| 지표 | 지금 (baseline) | 목표 (target) | 어떻게 재나 |
|---|---|---|---|
| 한 턴의 본문 생성 횟수 | 되돌린 횟수만큼 (실측 여러 번) | 항상 1 | 되돌림 결정이 아예 나오지 않는지 본다 |
| 턴당 주입 크기 | 안내 약 8줄 | 진단 약 3KB + 지침 | 프롬프트 훅 출력 바이트 |

## 예외처리 (Edge cases)

- **점검 실행이 실패한다** → 진단 없이 표시줄과 지침만 낸다. 막지 않는다.
- **점검이 느리다** → 그대로 기다린다. 시간 제한을 두어 잘라내면 반쪽 진단이
  들어가 더 나쁘다. 느려지면 주입량을 줄이는 쪽으로 고친다.
- **진단 구간을 못 찾는다** (점검 출력 형식이 바뀜) → 자르지 않고 전체를 싣는다.
  많이 싣는 쪽이 아무것도 안 싣는 쪽보다 낫다.
- **앞도 뒤도 아닌 턴** → 추가 호출 없이 바로 답한다. 정당한 결과다.
- **이미 다른 SCV 액션이 실린 턴** → 그 프로토콜을 계속한다. 기존 계약 그대로.
- **스위치 두 개가 다른 상태** (라우팅 켬 + preflight 끔) → 기존 라우팅 안내만
  나가고 진단·표시줄은 없다.
- **scv 폴더 없음 · 읽기 도구 없음** → 아무 출력도 없다.

## Exit criteria

- TESTS.md 시나리오가 모두 통과한다.
- 기존 검사가 계속 통과한다 (저널·항상라우팅·가드·설정·순수성·공백·지문).
- 누적 회귀가 초록이다 — 옛 슬러그가 supersedes 로 건너뛰어진다.
- 실제 대화에서 본문이 한 번만 나가는 것을 사람이 확인한다.
- 템플릿 지문이 갱신돼 있다.

## Suggested path

1. 되돌림을 걷는다 — 응답 종료 훅의 강제 블록 삭제, 저널 기록 구조 원복.
2. 가드와 가드 계약을 되돌린다 (라이브러리 의존 제거).
3. 판정부에서 되돌림용 함수를 걷고 잘라내기·문구 생성만 남긴다.
4. 프롬프트 훅을 preflight 로 바꾼다 — 진단 주입 + 분류 지침 + 표시줄.
5. 검사를 다시 쓴다 (되돌림 단언 → 주입·무되돌림 단언).
6. 지문을 다시 계산하고 변경 이력을 남긴다.

# Test Plan — 강제를 preflight 로

## Overview

이 계획의 핵심 단언은 **부정형**이다: 응답 종료 훅이 어떤 경우에도 되돌리지
않는다. 그래서 검사의 절반은 "무엇이 일어나지 않는가" 를 본다. 앞선 계획의 검사가
"되돌린다" 를 단언했으므로, 그 단언을 뒤집는 것이 이 문서의 일이다.

나머지 절반은 주입을 본다. 무엇이 들어가고(진단·지침·표시줄), 무엇이 빠지는가
(개요·명령 목록). 훅을 직접 실행해 표준출력과 종료 코드로 판정한다.

## Test scenarios

### T1. 응답 종료 훅이 되돌리지 않는다

이 계획이 존재하는 이유다. 앞 계획에서 되돌림이 나오던 바로 그 상황을 그대로
재현하고, 이번에는 나오지 않는 것을 본다.

- **Setup**: scv 폴더가 있는 임시 프로젝트. 스위치 기본값. 프롬프트 훅을 먼저
  실행한다. 영수증 저장소는 비어 있다 (help 를 부르지 않은 상태).
- **Run**: 종료 훅을 실행한다.
- **Expected**: 차단 결정이 없다.
- **Pass criterion**: 표준출력에 차단 결정이 없고 종료 코드가 0.

### T2. 여러 번 실행해도 되돌리지 않는다

- **Setup**: T1 과 같다.
- **Run**: 종료 훅을 연속 5회 실행한다.
- **Expected**: 매번 차단 결정이 없다.
- **Pass criterion**: 5회 모두 출력에 차단 결정이 없다. 회차가 쌓여도 달라지지
  않는다는 것이 요점이다.

### T3. 매 턴 진단이 주입된다

- **Setup**: scv 폴더가 있는 임시 프로젝트.
- **Run**: 프롬프트 훅을 실행한다.
- **Expected**: 출력에 프로젝트 진단 내용이 실린다.
- **Pass criterion**: 진단 구간을 알아볼 수 있는 표지가 출력에 있다.

### T4. 개요와 명령 목록은 주입되지 않는다

매번 같은 내용이라 뺀 것이므로, 실제로 빠졌는지 본다.

- **Setup**: T3 과 같다.
- **Run**: 프롬프트 훅 출력과 상태 점검 전체 출력을 비교한다.
- **Expected**: 점검 전체에는 있고 훅 출력에는 없는 구간이 존재한다 (개요·명령
  목록).
- **Pass criterion**: 훅 출력이 점검 전체 출력보다 짧고, 명령 목록 표지가 훅
  출력에 없다.

### T5. 분류 지침이 세 갈래를 모두 말한다

- **Setup**: T3 과 같다.
- **Run**: 프롬프트 훅 출력을 본다.
- **Expected**: 앞을 보는 턴·뒤를 보는 턴·둘 다 아닌 턴에 대한 지침이 모두 있다.
- **Pass criterion**: 세 갈래가 각각 출력에서 확인된다. 셋째 갈래가 빠지면 모델이
  모든 턴을 둘 중 하나로 밀어넣게 되므로, 그 항목이 특히 중요하다.

### T6. 표시줄이 매 턴 나온다

- **Setup**: T3 과 같다.
- **Run**: 프롬프트 훅을 두 번 실행한다.
- **Expected**: 두 번 다 표시줄이 나온다.
- **Pass criterion**: 두 실행 모두 표시줄 표지가 출력에 있다.

### T7. preflight 스위치를 끄면 주입도 표시줄도 없다

- **Setup**: 설정에서 preflight 스위치를 off 로 둔다. 라우팅 스위치는 켜 둔다.
- **Run**: 프롬프트 훅과 종료 훅을 차례로 실행한다.
- **Expected**: 진단·지침·표시줄이 모두 없다. 기존 라우팅 안내는 그대로 나온다.
  종료 훅은 되돌리지 않는다.
- **Pass criterion**: 세 가지가 출력에 없고, 라우팅 안내는 있으며, 차단 결정이 없다.

### T8. 전체 라우팅 스위치를 끄면 아무것도 없다

- **Setup**: 라우팅 스위치를 off 로 둔다.
- **Run**: 프롬프트 훅을 실행한다.
- **Expected**: 라우팅 안내·진단·지침·표시줄이 모두 없다.
- **Pass criterion**: 네 가지가 모두 출력에 없다.

### T9. scv 폴더가 없으면 아무 출력도 없다

- **Setup**: scv 폴더가 없는 임시 폴더.
- **Run**: 프롬프트 훅과 종료 훅을 차례로 실행한다.
- **Expected**: 두 훅 모두 조용히 끝난다.
- **Pass criterion**: 표준출력이 비어 있고 종료 코드 0.

### T10. 점검 실행이 실패해도 막지 않는다

- **Setup**: 상태 점검을 실행할 수 없는 환경을 만든다.
- **Run**: 프롬프트 훅을 실행한다.
- **Expected**: 진단 없이 표시줄과 지침만 나오고 정상 종료한다.
- **Pass criterion**: 종료 코드 0, 표시줄 있음, 훅이 죽지 않음.

### T11. 저널 기록이 이번 변경 이전과 같다

- **Setup**: 기존 저널 검사가 쓰는 페이로드를 그대로 쓴다.
- **Run**: 기존 저널 검사를 실행한다.
- **Expected**: 전부 통과한다.
- **Pass criterion**: 기존 저널 검사가 초록이다. 한 턴에 한 줄이라는 성질이
  되돌림 제거 뒤에도 유지되는지를 본다.

### T12. 가드가 라이브러리를 읽지 않는다

- **Setup**: 판정부 라이브러리 파일을 읽을 수 없게 만든다.
- **Run**: 가드를 발행 모드로 실행하고 영수증이 남는지 본다.
- **Expected**: 라이브러리가 없어도 평소처럼 영수증을 남긴다.
- **Pass criterion**: 영수증이 기록되고 가드가 정상 종료한다. 가드가 다시 홀로
  서는지를 보는 항목이다.

### T13. 되돌림용 함수가 남아 있지 않다

- **Setup**: 없음.
- **Run**: 판정부 라이브러리를 훑는다.
- **Expected**: 되돌림 판정·회차별 문구·턴 상태 경로 함수가 없다.
- **Pass criterion**: 해당 함수 이름이 하나도 정의돼 있지 않다. 코드가 남아 있으면
  다음 사람이 다시 켤 수 있고, 그러면 같은 비용이 돌아온다.

### T14. 판정부가 순수성 계약을 지킨다

- **Setup**: 없음.
- **Run**: 순수성 검사기를 판정부 파일에 돌린다.
- **Expected**: 위반 0건.
- **Pass criterion**: 검사기가 통과를 보고한다.

### T15. 옛 계획이 회귀에서 건너뛰어진다

- **Setup**: 이 계획이 아카이브된 뒤.
- **Run**: 누적 회귀를 실행한다.
- **Expected**: 대체된 슬러그가 건너뛰어지고 회귀가 초록이다.
- **Pass criterion**: 실패 0건. 이 선언을 빠뜨리면 옛 슬러그의 "되돌린다" 단언이
  실패하므로, 그 사실을 검사로 못 박는다.

### T16. 실제 대화에서 본문이 한 번만 나간다 (사람 확인)

기계로 판정하기 어려워 따로 둔다.

- **Setup**: 갱신된 플러그인이 적용된 세션.
- **Run**: 평범한 대화를 몇 턴 한다.
- **Expected**: 답이 한 번만 생성되고, 같은 내용이 반복되지 않는다.
- **Pass criterion**: 사람이 확인하고 보고한다.
