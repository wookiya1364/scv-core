# Test Plan — 번호식 화면설계서 — 그림이 주인공인 기획서

## Overview

기획서를 열었을 때 **그림이 먼저 보이고 설명이 번호로 그림에 매달리는지**를
검증한다. 새로 생기는 것(마커·사이드바·페이지 코드·BE 큰 그림·밀도 경고·재료
필수화)이 실제로 나오는지, 그리고 **기존 기획서가 하나도 달라지지 않는지**를
같은 무게로 확인한다. 후자가 없으면 이 변경은 기존 문서 30여 건을 조용히
망가뜨릴 수 있다.

새 검사는 `core/tests/test-deck-numbered-spec.sh` 에 모으고, 기존 deck 계약
(`core/tests/test-deck-doc.sh`)은 **수정하지 않고 그대로 통과**해야 한다.

## Test scenarios

### T1. 번호 마커가 그림 위에 표시된다 (FE)

- **Setup**: 화면 목업 블록을 담은 임시 마크다운을 만든다. 컴포넌트 3개에 각각
  번호 1·2·3을 부여한다 (예: 이메일 입력칸, 비밀번호 입력칸, 약관 체크박스).
- **Run**: 그 파일로 기획서를 만든다 (문서 형태, 원문 패널 제외 렌더로 검사해
  원문 마크다운 쪽 문자열에 우연히 걸리지 않게 한다).
- **Expected**: 목업 안에 번호 마커 1·2·3이 각 컴포넌트에 붙어 렌더된다.
- **Pass criterion**: 렌더 결과에서 마커 요소 3개가 확인되고, 각 마커의 번호가
  1·2·3이다.

### T2. 액션 요소는 문자 마커로 구분된다 (FE)

- **Setup**: T1 파일에 버튼 2개를 추가하고 각각 문자 마커 A·B를 부여한다.
- **Run**: 기획서를 만든다.
- **Expected**: 버튼에는 숫자가 아니라 문자 마커 A·B가 붙는다. 숫자 마커와
  문자 마커가 서로 다른 계열로 구분된다.
- **Pass criterion**: 문자 마커 A·B가 렌더되고, 숫자 마커 집합과 겹치지 않는다.

### T3. 번호별 상세가 그림 오른쪽에 붙는다 (FE — 역할 + 액션 두 묶음)

- **Setup**: T2 파일에 번호별 상세를 쓴다 — 1·2·3 에는 컴포넌트 역할(예:
  "이메일 입력칸: 320자 초과 입력 막음, 포커스 아웃 시 형식 검사"), A·B 에는
  액션 동작(예: "회원가입 버튼: 모든 필수 항목 충족 시 활성화").
- **Run**: 기획서를 만든다.
- **Expected**: 그림 옆에 상세 목록이 **역할 묶음**과 **액션 묶음**으로 나뉘어
  렌더된다. 각 항목이 자기 마커 번호를 달고 있다.
- **Pass criterion**: 역할 묶음에 1·2·3 항목이, 액션 묶음에 A·B 항목이 각각
  들어 있고, 작성한 설명 문구가 그대로 나온다.

### T4. 지어내지 않는다 (충실도)

- **Setup**: 컴포넌트 3개 중 **2개에만** 번호별 상세를 쓴다 (1·2만, 3은 비움).
- **Run**: 기획서를 만든다.
- **Expected**: 3번에 대한 설명이 **비어 있거나 생략**된다. 렌더러가 "3번은
  아마 이런 역할" 같은 문구를 만들어내지 않는다.
- **Pass criterion**: 렌더 결과의 상세 묶음에 작성하지 않은 3번 설명 텍스트가
  존재하지 않는다.

### T5. 페이지 이름과 식별 코드가 그림 위에 나온다

- **Setup**: 화면 목업에 페이지 이름("회원가입 페이지")과 식별 코드
  ("FO-SU-02-01")를 부여한다.
- **Run**: 기획서를 만든다.
- **Expected**: 그림 위쪽에 페이지 이름과 식별 코드가 함께 표시된다.
- **Pass criterion**: 두 값이 모두 렌더 결과에 나타나며, 목업 프레임 바깥이
  아니라 해당 화면 블록에 속해 있다.

### T6. 이동 대상 상호참조가 표현된다

- **Setup**: 액션 상세에 이동 대상 코드를 쓴다 (예: "회원가입 완료 시
  FO-SU-02-02 로 이동").
- **Run**: 기획서를 만든다.
- **Expected**: 이동 대상 코드가 액션 설명 안에 그대로 표시된다.
- **Pass criterion**: 해당 코드 문자열이 액션 묶음 안에서 확인된다.

### T7. BE — 화면이 없는 계획도 같은 골자로 그려진다

- **Setup**: 화면 목업 없이 구성도(다이어그램)를 담은 마크다운을 만들고, 그
  구성 요소에 번호를 붙인 뒤 번호별로 API·함수 역할을 쓴다 (예: "1. 인증 API —
  이메일·비밀번호를 받아 토큰을 돌려준다").
- **Run**: 기획서를 만든다.
- **Expected**: 큰 그림(구성도) 옆에 **FE와 같은 형태의** 번호별 상세가 붙는다.
- **Pass criterion**: 구성도가 렌더되고, 그 옆 상세 묶음에 번호별 API·함수 설명이
  들어 있으며, FE 사례(T3)와 **같은 구조**(같은 사이드바 형태)로 렌더된다.

### T8. 마커 없는 기존 목업은 지금과 똑같이 렌더된다 (하위 호환 — 회귀 방지)

- **Setup**: 마커·상세·페이지 코드가 **전혀 없는** 기존 형태의 화면 목업
  마크다운을 준비한다.
- **Run**: 변경 전후로 같은 입력을 렌더해 결과를 비교한다. (변경 전 결과는
  현재 코드로 미리 만들어 보관한다.)
- **Expected**: 결과가 **동일**하다. 빈 사이드바나 빈 마커 자리가 생기지 않는다.
- **Pass criterion**: 두 렌더 결과의 본문이 일치한다.

### T9. 그림 없는 기획서는 경고로 드러난다

- **Setup**: 그림(화면 목업·다이어그램)이 하나도 없는 글만 있는 마크다운을
  준비한다.
- **Run**: 기획서를 만든다.
- **Expected**: 품질 검사 경고에 **그림이 없다**는 항목이 나온다. 그래도
  기획서 파일은 정상적으로 만들어진다 (막지 않는다).
- **Pass criterion**: 경고 출력에 해당 항목이 존재하고, 종료 코드는 0이며,
  결과 HTML 파일이 생성된다.

### T10. 그림이 있으면 그 경고는 뜨지 않는다 (거짓 경고 방지)

- **Setup**: 다이어그램이 하나 있는 마크다운을 준비한다.
- **Run**: 기획서를 만든다.
- **Expected**: 그림 없음 경고가 **뜨지 않는다**.
- **Pass criterion**: 경고 출력에 해당 항목이 없다.

### T11. 계획 작성 지침이 양식 재료를 요구한다

- **Setup**: 계획 작성 지침 문서를 대상으로 한다.
- **Run**: 지침에 양식 재료(큰 그림 + 번호별 상세) 요구와 **빠졌을 때 경고하고
  진행**한다는 규칙이 명시돼 있는지 확인한다.
- **Expected**: 두 규칙이 모두 문서에 존재한다. "재료 없으면 중단"이라는 문구는
  없어야 한다 (막지 않기로 한 결정).
- **Pass criterion**: 요구 규칙과 경고-진행 규칙이 확인되고, 중단 규칙은 없다.

### T12. 기존 deck 계약이 그대로 통과한다 (회귀)

- **Setup**: 없음.
- **Run**: 기존 deck 문서 테스트와 정적 다이어그램 테스트를 그대로 실행한다.
- **Expected**: 전부 통과. 기존 테스트 파일은 수정되지 않았다.
- **Pass criterion**: 두 테스트 스크립트가 exit 0.

### T13. 아카이브된 기획서를 다시 만들어도 지금과 같이 열린다

- **Setup**: 아카이브된 계획 폴더 하나(예: 최근 것)를 고른다.
- **Run**: 그 폴더로 기획서를 다시 만든다.
- **Expected**: 정상적으로 만들어지고, 새 양식 때문에 깨지거나 빈 사이드바가
  끼어들지 않는다.
- **Pass criterion**: 생성이 exit 0 이고, 결과에 빈 상세 사이드바가 없다.

### T19. 검증 메시지 표가 그림 아래에 나온다

- **Setup**: 화면 목업에 검증 규칙 2건을 쓴다. 한 건은 여러 번호에 걸치게 한다
  (예: 이메일 형식 오류 — 입력칸 ①과 제출 버튼 Ⓐ 양쪽).
- **Run**: 기획서를 만든다.
- **Expected**: 그림 아래에 표가 나오고, 머리글은 체크 시점 / 조건 / 메시지 /
  노출 유형이며, 여러 번호에 걸친 규칙이 한 행에 그 번호들을 함께 표시한다.
- **Pass criterion**: 표가 렌더되고 규칙 수만큼 행이 있으며, 여러 번호 표기가 보인다.

### T20. 컴포넌트 상태 변형이 그림 아래 띠로 나온다

- **Setup**: 같은 번호의 컴포넌트에 상태 2개(기본 / Invalid)를 쓴다.
- **Run**: 기획서를 만든다.
- **Expected**: 그림 아래에 상태 띠가 나오고, 각 상태에 이름과 번호가 붙는다.
- **Pass criterion**: 상태 칸이 쓴 개수만큼 렌더된다.

### T21. 번호별 상세가 파이프라인 단계와 이어진다

- **Setup**: 번호별 상세에 파이프라인 단계 이름을 단다 (기능 2개 + 액션 1개).
- **Run**: 기획서를 만든다.
- **Expected**: 각 항목 제목 옆에 단계 이름 태그가 붙는다.
- **Pass criterion**: 단계 태그가 3개 렌더되고 단계 이름이 그대로 나온다.

### T22. 마커를 안 쓰면 자동으로 번호가 붙는다 (기본 동작)

- **Setup**: 컴포넌트에 번호를 **하나도 쓰지 않은** 화면 목업을 만든다. 캡션
  (헤더)과 입력칸 2개, 버튼 2개를 넣는다.
- **Run**: 기획서를 만든다.
- **Expected**: 입력칸은 1·2, 버튼은 A·B를 자동으로 받는다. **캡션은 번호를 받지
  않는다** (받으면 실제 항목의 번호가 밀린다). 짝 검사가 오탐 경고를 내지 않는다.
- **Pass criterion**: 마커가 정확히 4개이고 숫자·문자 계열이 각각 맞으며,
  "그림에 없는 번호" 경고가 뜨지 않는다.

### T23. 자동 번호를 끌 수 있다

- **Setup**: T22 문서에 자동 번호 끄기를 지정한다.
- **Run**: 기획서를 만든다.
- **Expected**: 마커가 하나도 붙지 않는다. 검증 표 등 나머지는 그대로 나온다.
- **Pass criterion**: 마커 0개, 검증 표는 존재.

### T24. 스크롤 영역은 하나뿐이다 (이중 스크롤 금지)

- **Setup**: 기획서 하나를 만든다.
- **Run**: 결과 문서의 스크롤 설정을 확인한다.
- **Expected**: 문서 껍데기 안쪽 한 곳만 스크롤한다. 그 뒤의 바깥 문서는
  스크롤하지 않는다(스크롤바가 하나만 보인다). 인쇄할 때는 이 제약이 풀려
  내용이 잘리지 않는다.
- **Pass criterion**: 바깥 문서 스크롤 차단과 스크롤 체이닝 차단이 확인되고,
  안쪽 스크롤 영역은 그대로이며, 인쇄 규칙에 되돌림이 들어 있다.

### T25. BE 최상단에 "어느 화면이 부르는가"가 나온다

- **Setup**: BE 화면설계서에 호출 화면 1건을 쓴다 (화면 이름·코드·요소·시점).
- **Run**: 기획서를 만든다.
- **Expected**: 표가 **그림보다 위에** 나온다. 백엔드 독자의 첫 질문이 "누가 나를
  부르나"이기 때문이다.
- **Pass criterion**: 표의 내용이 모두 렌더되고, 위치가 그림보다 앞선다.

### T26. 큰 그림을 여러 장(구성 + 순서) 그릴 수 있다

- **Setup**: 큰 그림을 2장 쓴다 — 구성도 하나, 순서도 하나. 각 장에 이름을 단다.
- **Run**: 기획서를 만든다.
- **Expected**: 두 장이 모두 렌더되고 각 장에 이름표가 붙는다.
- **Pass criterion**: 다이어그램 2개, 이름표 존재, 순서도 문법이 그대로 실린다.

### T27. 상태 띠를 테이블 스키마로 쓸 수 있다

- **Setup**: 상태 띠 제목을 "데이터 모양 (테이블 스키마)"로 바꾸고, 표의 컬럼과
  비고를 담은 카드를 1장 쓴다.
- **Run**: 기획서를 만든다.
- **Expected**: 바꾼 제목이 나오고 FE 기본 제목("컴포넌트 상태")은 나오지 않는다.
- **Pass criterion**: 제목이 교체되고 컬럼 내용이 렌더된다.

### T28. 실패·응답 표를 직접 정한 컬럼으로 쓸 수 있다

- **Setup**: 검증표를 컬럼 직접 지정 형태로 쓴다 (번호 / 조건 / 응답 / 본문·메시지
  / 기록·데이터 영향), 규칙 2건.
- **Run**: 기획서를 만든다.
- **Expected**: 바꾼 제목과 컬럼으로 표가 나오고 규칙이 2행이다.
- **Pass criterion**: 제목·컬럼이 그대로이고, 해당 표의 행이 정확히 2개다
  (같은 표 부품을 쓰는 호출 화면 표와 섞어 세지 않는다).

### T29. 순서도 글자가 배경에 묻히지 않는다 (대비)

- **Setup**: 없음 — 렌더러의 색 규칙을 대상으로 한다.
- **Run**: 순서도 요소별 색 규칙이 있는지 확인한다.
- **Expected**: 메시지 글자, else 분기 라벨, 참여자 상자에 각각 규칙이 있다.
- **Pass criterion**: 세 규칙이 모두 존재한다.

## How to run

```bash
bash -euo pipefail -c '
fail() { echo "FAIL: $1"; exit 1; }
bash core/tests/test-deck-numbered-spec.sh >/dev/null || fail "T1-T11,T13 번호식 화면설계서"
bash core/tests/test-deck-doc.sh >/dev/null || fail "T12 기존 deck 문서 계약"
bash core/tests/test-deck-static-mermaid.sh >/dev/null || fail "T12 정적 다이어그램 계약"
echo "ALL GATES OK"
'
```

## Pass criteria

- 위 블록 exit 0.
- T8(하위 호환)과 T12(기존 계약)가 통과 — 기존 기획서가 달라지지 않았다.
- T4(지어내지 않음)가 통과 — 결정적 변환 원칙이 지켜졌다.
- FE 예시(T1–T6)와 BE 예시(T7)를 **실제로 열어 눈으로 확인** — 그림이 먼저
  보이고 설명이 번호로 그림에 매달려 있다.
