번호식 화면설계서 — 그림이 주인공인 기획서

Summary

기획서를 열었을 때 큰 그림 한 장이 먼저 보이고, 설명은 번호를 달고 그림 옆에 붙는 형태로 바꾼다. 지금은 화면을 열면 검은 배경에 문장 몇 줄뿐이라 "기획서"가 아니라 "폰트 큰 마크다운"으로 읽힌다. 실무에서 쓰는 화면설계서 양식(그림에 ①②③, 우측에 번호별 상세)을 그대로 도입해, 그림이 없으면 기획서가 성립하지 않게 만든다.

Goals / Non-Goals

  • Goals
    • 기획서의 기본 형태를 큰 그림 + 번호 마커 + 번호별 상세 사이드바로 바꾼다.
    • FE(화면 있음): 컴포넌트 역할 + 액션(버튼 등) 동작을 번호로 나눠 기술한다.
    • BE(화면 없음): 구성도·흐름도에 번호를 달고 API·함수의 역할을 기술한다.
    • 페이지 식별 코드와 이동 대상 상호참조(이 버튼을 누르면 어느 화면으로)를 기획서 안에서 표현할 수 있게 한다.
    • 계획을 세울 때 이 재료(그림 + 번호별 상세)를 필수로 요구한다. 빠졌으면 경고하고 진행한다.
    • 그림이 하나도 없는 기획서는 경고로 드러난다 (지금은 조용히 통과).
    • 검증 메시지 표 — 한 규칙이 여러 번호에 걸릴 때 어디서 무슨 문구가 뜨는지 한 표에서 추적된다 (샘플의 "체크 시점 / 조건 / 메시지 / 노출 유형").
    • 컴포넌트 상태 변형 — 기본·입력 중·Invalid 같은 상태를 그림 아래 띠로 보인다.
    • 파이프라인 단계 연결 — 번호별 상세가 계획의 파이프라인 단계 이름을 달아, 계획·화면·구현이 한 줄로 꿰인다.
    • 마커 자동 번호 — 지시하지 않으면 읽는 순서대로 번호(①②③)와 문자(ⒶⒷ)를 자동으로 붙인다. 손으로 쓴 번호가 항상 우선한다.
    • BE — 호출 화면 표 — 어느 화면의 어느 요소가 이 API를 부르는지 맨 위에 적는다. 백엔드만 보는 사람이 화면 없이 구현하다 헤매는 것을 막는다.
    • BE — 순서도 — 구성도와 별개로 요청 하나가 어떻게 처리되는지(분기 포함)를 그림으로 그린다. 큰 그림을 여러 장 실을 수 있게 한다.
    • BE — 테이블 스키마 카드 — FE의 상태 띠 자리에 표의 컬럼·인덱스·증가 양상을 싣는다.
    • BE — 실패·응답 표 — FE의 검증 메시지 표를 컬럼만 바꿔 재사용한다 (번호 / 조건 / 응답 / 본문·메시지 / 기록·데이터 영향).
  • Non-Goals
    • 이미 아카이브된 계획 30여 건의 재작성 — 앞으로 쓰는 계획부터 적용한다. 과거 문서는 지금과 똑같이 열린다.
    • 인프라·데이터·운영 등 나머지 영역의 전용 양식 — 기본 골자는 같으므로 FE/BE에서 골자가 검증되면 다음에 확장한다. 이번엔 두 영역만.
    • 상태 변형을 모든 컴포넌트에 강제하는 것 — 규칙이 실제로 있는 컴포넌트에만 쓴다. 기본 모습만 반복하는 상태 띠는 의미가 없다.
    • 목업을 실제 동작하는 화면으로 만드는 것 — 목업은 정지된 그림이다.
    • 실제 스크린샷 사용 — 와이어프레임(구조만 보여주는 중립 그림)이다.
    • 슬라이드 형태(발표용) 개편 — 이번 대상은 읽는 문서 형태다.

Approach Overview

두 군데를 건드린다. 그림을 그리는 쪽(렌더러)과 재료를 요구하는 쪽(계획 작성 지침)이다. 밀도 문제의 원인이 "렌더러가 아니라 공급"이었으므로 둘 다 필요하다.

  1. 마커와 사이드바를 렌더러에 추가한다. 현재 화면 목업은 컴포넌트를 위에서 아래로 그릴 뿐, 번호 개념이 없다. 여기에 마커가 없는 기존 목업은 지금과 똑같이 그려진다(하위 호환).
    • 각 컴포넌트가 자기 번호를 가질 수 있게 하고 (그림 위에 ①②③ 표시),
    • 액션 요소는 문자 마커(ⒶⒷ)로 구분하며,
    • 그림 오른쪽에 번호별 상세 목록(역할 설명 / 액션 설명 두 묶음)을 붙이고,
    • 그림 위에 페이지 이름과 식별 코드 줄을 얹는다.
  2. BE용 큰 그림에도 같은 골자를 적용한다. 화면이 없는 계획은 구성도·흐름도가 "큰 그림" 자리를 대신한다. 다이어그램의 각 요소에 번호를 달고, 같은 형태의 우측 상세(이 API는 무엇을 받고 무엇을 하는가 / 이 함수의 역할)를 붙인다. FE와 시각적으로 같은 틀이어야 한다 — 영역이 달라도 골자는 같다는 요구가 여기서 검증된다.
  3. 계획 작성 단계에서 이 재료를 요구한다. 계획을 만들 때 화면(또는 구성도)과 번호별 상세를 함께 쓰도록 필수화한다. 빠졌으면 무엇이 비었는지 알리고 진행한다 — 지어내지 않는다.
  4. 품질 검사에 밀도 항목을 넣는다. 지금 검사는 "이 절이 있는가"만 본다. 여기에 그림이 한 장도 없는가를 더한다. 진단에서 최근 기획서 8건 연속 그림 0개가 조용히 통과한 것이 이 검사의 공백 때문이다.

설계 판단 — 어디에 둘 것인가. 마커·사이드바를 그리는 규칙은 **코드(렌더러)**에 둔다. 작성 지시문에 두면 이미 만들어진 문서는 영원히 옛 모습으로 남고 코드를 고쳐도 안 바뀐다 — 색 팔레트를 지시문에 박았다가 겪은 문제와 같은 함정이다. 지시문에는 "재료를 요구하는 규칙"만 둔다.

순수함수 · 파이프라인 (Pure functions & pipeline)

기획서를 만드는 일 자체가 파이프라인이다. 각 단계는 받은 값만 보고 결과를 돌려주며, 파일을 읽고 쓰는 일은 입구와 출구에만 있다.

flow(
  readSource,        // 경로 → 원문 마크다운          [부수효과 · 입구]
  mdToDeck,          // 원문 → 블록 배열 + 경고 목록   [순수]
  renderBlocks,      // 블록 배열 → HTML 조각          [순수]
  renderScreen,      // 화면 블록 → 목업·마커·상세     [순수]
  assembleHtml,      // HTML 조각 → 자체완결 문서      [순수]
  writeDeck,         // 문서 → 파일                    [부수효과 · 출구]
)
#단계받는 값 → 돌려주는 값순수/부수효과
1readSource경로 → 원문 마크다운부수효과 (입구)
2mdToDeck원문 → 블록 배열 + 경고 목록순수
3renderBlocks블록 배열 → HTML 조각순수
4renderScreen화면 블록 → 목업 + 마커 + 상세순수
5assembleHtmlHTML 조각 → 자체완결 문서순수
6writeDeck문서 → 파일부수효과 (출구)
부수효과 위치파일 읽기(1)와 파일 쓰기(6)뿐이다. 2~5는 같은 입력이면 항상 같은 출력이라 결과를 그대로 비교할 수 있다 — 하위 호환을 바이트 단위로 검증할 수 있는 이유가 이것이다.
재사용마커·상세를 그리는 단계(4)는 화면(FE)과 구성도(BE)가 같은 단계를 그대로 쓴다. 영역이 달라도 골자가 같은 것이 이 재사용의 결과다.
A/B 검증어느 한 단계만 바꿔 끼우면 나머지는 그대로 두고 비교할 수 있다.

Guardrails

  • 순수함수·파이프라인을 지킨다. 각 단계는 받은 값만 보고 결과를 돌려주며, 파일·네트워크·시각을 만지는 일은 입구와 출구에만 둔다. 중간 단계에 부수효과를 넣지 않는다.
  • 결정적 변환을 깨지 않는다. 번호별 설명은 작성자가 쓴 것만 나온다. 렌더러가 "이 버튼은 아마 이런 역할일 것"이라고 지어내지 않는다.
  • 하위 호환. 마커가 없는 기존 화면 목업은 지금과 픽셀 단위로 같게 그려진다. 기존 기획서를 다시 만들었을 때 달라지면 안 된다.
  • 아카이브된 계획은 건드리지 않는다. 과거 문서를 열면 지금과 같이 보인다.
  • 막지 않는다. 재료가 없으면 경고만 하고 기획서는 만들어진다.
  • 그림 없이 만들어진 기획서도 여전히 만들어진다 — 경고로 드러날 뿐이다.
  • 원문 마크다운은 계속 결과물에 동봉된다 (렌더링과 원본이 항상 일치).
  • 마커 개수가 많아져도 그림이 읽을 수 없게 뭉개지면 안 된다 — 한 화면의 마커 수에 실용적 상한을 두고, 넘으면 알린다.
  • 스크롤 영역은 하나뿐이다. 문서 껍데기가 스크롤을 갖고, 그 뒤의 바깥 문서는 스크롤하지 않는다. 스크롤바가 둘이면 휠이 어디에 먹을지 알 수 없다. 인쇄할 때는 이 제약을 풀어 내용이 잘리지 않게 한다.

Exit criteria

  • TESTS.md 시나리오 전부 통과.
  • FE 예시 하나와 BE 예시 하나를 실제로 만들어 열었을 때, 그림이 먼저 보이고 번호별 설명이 그림 옆에 붙어 있다.
  • 마커 없는 기존 목업을 다시 만들었을 때 결과가 이전과 같다.
  • 그림 없는 기획서를 만들면 경고가 뜬다.
  • 아카이브된 기획서 하나를 다시 만들어도 지금과 같이 열린다.

Suggested path

  1. 화면 목업에 번호·문자 마커를 추가한다 (그림 위 표시 + 컴포넌트별 번호).
  2. 그림 오른쪽에 번호별 상세 사이드바(역할 묶음 / 액션 묶음)를 붙인다.
  3. 그림 위에 페이지 이름 + 식별 코드 줄과 이동 대상 상호참조를 넣는다.
  4. BE용 큰 그림(구성도·흐름도)에 같은 마커·사이드바 골자를 적용한다.
  5. 품질 검사에 그림 0장 경고를 추가한다.
  6. 계획 작성 지침에 양식 재료 필수화(빠지면 경고)를 넣는다.
  7. 검증 메시지 표를 그림 아래에 붙인다 (규칙 하나가 여러 번호에 걸릴 수 있게).
  8. 컴포넌트 상태 변형을 그림 아래 띠로 붙인다.
  9. 번호별 상세에 파이프라인 단계 이름을 달 수 있게 한다.
  10. 마커 자동 번호를 기본으로 켠다 — 변환 단계에서 붙여 검사와 화면이 같은 번호를 보게 한다. 손으로 쓴 번호가 우선하고, 캡션은 번호를 받지 않는다.
  11. 스크롤 영역을 하나로 고정한다 (바깥 문서 스크롤 차단, 인쇄 시 해제).
  12. BE 심화 — 호출 화면 표(최상단), 큰 그림 여러 장(구성 + 순서), 상태 띠를 테이블 스키마로, 검증표를 실패·응답 표로 재사용. 오른쪽 상세는 역할과 입출력만 남겨 FE만큼 가볍게 만든다.
  13. 순서도 대비를 잡는다 — 순서도 전용 색 규칙이 없으면 글자가 배경에 묻힌다.
  14. FE·BE 예시를 각각 만들어 눈으로 확인하고, 기존 목업의 하위 호환을 확인한다.

예외처리 (Edge cases)

번호를 붙였는데 그 번호의 설명이 없다→ 그 항목은 비워 둔다. 지어내지 않는다 (T4).

마커가 너무 많다→ 실용적 상한을 넘으면 알린다. 그림이 뭉개지는 것을 막기 위함이다.
마커가 하나도 없는 기존 목업→ 지금과 똑같이 그린다. 빈 사이드바가 생기지 않는다 (T8).
그림이 하나도 없는 계획→ 경고로 드러나되 기획서는 만들어진다 (T9).
화면이 좁을 때→ 사이드바를 그림 옆에 두면 그림이 찌그러지므로, 좁은 화면에서는 그림 아래로 내린다.
인쇄(PDF)→ 마커와 사이드바가 끊기지 않게 배치한다. 실제 인쇄로 확인한다.
BE 계획에 구성도가 없다→ 화면도 구성도도 없으면 그림 0장 경고에 걸린다.
번호 문자가 특수문자라 깨질 때→ 표시가 깨지지 않는 방식으로 그린다.
아카이브된 계획을 다시 만들 때→ 새 양식 때문에 깨지지 않는다 (T13).

  • 그림이 좁아진다 → 실제로 재발했고, 고쳤다. 다이어그램을 옆 칸(약 430px)에 넣자 800px짜리 구성도가 절반 크기로 줄어 8/13과 똑같이 글자가 뭉갰다. 그래서 다이어그램일 때는 그림이 전체 폭을 쓰고 번호별 상세가 아래로 내려가도록 했다. 와이어프레임은 옆 칸이 적당하므로 그대로 옆에 둔다. 골자(큰 그림 + 번호
    • 번호별 상세)는 두 경우 모두 같다.

  • BE의 큰 그림에 번호 붙이는 법 → 작성자가 구성도 노드 이름에 직접 번호를 넣는다(가장 단순하고, 렌더러가 위치를 지어내지 않는다).
  • 마커 수 상한 → 한 그림당 20개. 넘으면 경고한다.
  • 이중 스크롤 → 실측으로 확인했다. 바깥 문서가 껍데기보다 6px 커서 스크롤바가 둘이었다. 껍데기만 스크롤을 갖도록 못박고, 인쇄 시에는 풀었다.
  • 순서도 글자가 묻히는 문제 → 이 프로젝트는 다이어그램을 자체 색 규칙으로 칠하는데, 그 규칙이 흐름도 전용이었다. 순서도는 밝은 배경을 전제한 기본색이 그대로 남아 글자가 안 보였다. 순서도 전용 규칙을 같은 자리에 추가했다. (중간에 목업 안 다이어그램 배경을 투명하게 만든 것이 이 문제를 키웠다 — 되돌렸다.)

Test scenarios

T1. 번호 마커가 그림 위에 표시된다 (FE)

Setup화면 목업 블록을 담은 임시 마크다운을 만든다. 컴포넌트 3개에 각각 번호 1·2·3을 부여한다 (예: 이메일 입력칸, 비밀번호 입력칸, 약관 체크박스).
Run그 파일로 기획서를 만든다 (문서 형태, 원문 패널 제외 렌더로 검사해 원문 마크다운 쪽 문자열에 우연히 걸리지 않게 한다).
Expected목업 안에 번호 마커 1·2·3이 각 컴포넌트에 붙어 렌더된다.
Pass criterion렌더 결과에서 마커 요소 3개가 확인되고, 각 마커의 번호가 1·2·3이다.

T2. 액션 요소는 문자 마커로 구분된다 (FE)

SetupT1 파일에 버튼 2개를 추가하고 각각 문자 마커 A·B를 부여한다.
Run기획서를 만든다.
Expected버튼에는 숫자가 아니라 문자 마커 A·B가 붙는다. 숫자 마커와 문자 마커가 서로 다른 계열로 구분된다.
Pass criterion문자 마커 A·B가 렌더되고, 숫자 마커 집합과 겹치지 않는다.

T3. 번호별 상세가 그림 오른쪽에 붙는다 (FE — 역할 + 액션 두 묶음)

SetupT2 파일에 번호별 상세를 쓴다 — 1·2·3 에는 컴포넌트 역할(예: "이메일 입력칸: 320자 초과 입력 막음, 포커스 아웃 시 형식 검사"), A·B 에는 액션 동작(예: "회원가입 버튼: 모든 필수 항목 충족 시 활성화").
Run기획서를 만든다.
Expected그림 옆에 상세 목록이 역할 묶음과 액션 묶음으로 나뉘어 렌더된다. 각 항목이 자기 마커 번호를 달고 있다.
Pass criterion역할 묶음에 1·2·3 항목이, 액션 묶음에 A·B 항목이 각각 들어 있고, 작성한 설명 문구가 그대로 나온다.

T4. 지어내지 않는다 (충실도)

Setup컴포넌트 3개 중 2개에만 번호별 상세를 쓴다 (1·2만, 3은 비움).
Run기획서를 만든다.
Expected3번에 대한 설명이 비어 있거나 생략된다. 렌더러가 "3번은 아마 이런 역할" 같은 문구를 만들어내지 않는다.
Pass criterion렌더 결과의 상세 묶음에 작성하지 않은 3번 설명 텍스트가 존재하지 않는다.

T5. 페이지 이름과 식별 코드가 그림 위에 나온다

Setup화면 목업에 페이지 이름("회원가입 페이지")과 식별 코드 ("FO-SU-02-01")를 부여한다.
Run기획서를 만든다.
Expected그림 위쪽에 페이지 이름과 식별 코드가 함께 표시된다.
Pass criterion두 값이 모두 렌더 결과에 나타나며, 목업 프레임 바깥이 아니라 해당 화면 블록에 속해 있다.

T6. 이동 대상 상호참조가 표현된다

Setup액션 상세에 이동 대상 코드를 쓴다 (예: "회원가입 완료 시 FO-SU-02-02 로 이동").
Run기획서를 만든다.
Expected이동 대상 코드가 액션 설명 안에 그대로 표시된다.
Pass criterion해당 코드 문자열이 액션 묶음 안에서 확인된다.

T7. BE — 화면이 없는 계획도 같은 골자로 그려진다

Setup화면 목업 없이 구성도(다이어그램)를 담은 마크다운을 만들고, 그 구성 요소에 번호를 붙인 뒤 번호별로 API·함수 역할을 쓴다 (예: "1. 인증 API — 이메일·비밀번호를 받아 토큰을 돌려준다").
Run기획서를 만든다.
Expected큰 그림(구성도) 옆에 FE와 같은 형태의 번호별 상세가 붙는다.
Pass criterion구성도가 렌더되고, 그 옆 상세 묶음에 번호별 API·함수 설명이 들어 있으며, FE 사례(T3)와 같은 구조(같은 사이드바 형태)로 렌더된다.

T8. 마커 없는 기존 목업은 지금과 똑같이 렌더된다 (하위 호환 — 회귀 방지)

Setup마커·상세·페이지 코드가 전혀 없는 기존 형태의 화면 목업 마크다운을 준비한다.
Run변경 전후로 같은 입력을 렌더해 결과를 비교한다. (변경 전 결과는 현재 코드로 미리 만들어 보관한다.)
Expected결과가 동일하다. 빈 사이드바나 빈 마커 자리가 생기지 않는다.
Pass criterion두 렌더 결과의 본문이 일치한다.

T9. 그림 없는 기획서는 경고로 드러난다

Setup그림(화면 목업·다이어그램)이 하나도 없는 글만 있는 마크다운을 준비한다.
Run기획서를 만든다.
Expected품질 검사 경고에 그림이 없다는 항목이 나온다. 그래도 기획서 파일은 정상적으로 만들어진다 (막지 않는다).
Pass criterion경고 출력에 해당 항목이 존재하고, 종료 코드는 0이며, 결과 HTML 파일이 생성된다.

T10. 그림이 있으면 그 경고는 뜨지 않는다 (거짓 경고 방지)

Setup다이어그램이 하나 있는 마크다운을 준비한다.
Run기획서를 만든다.
Expected그림 없음 경고가 뜨지 않는다.
Pass criterion경고 출력에 해당 항목이 없다.

T11. 계획 작성 지침이 양식 재료를 요구한다

Setup계획 작성 지침 문서를 대상으로 한다.
Run지침에 양식 재료(큰 그림 + 번호별 상세) 요구와 빠졌을 때 경고하고 진행한다는 규칙이 명시돼 있는지 확인한다.
Expected두 규칙이 모두 문서에 존재한다. "재료 없으면 중단"이라는 문구는 없어야 한다 (막지 않기로 한 결정).
Pass criterion요구 규칙과 경고-진행 규칙이 확인되고, 중단 규칙은 없다.

T12. 기존 deck 계약이 그대로 통과한다 (회귀)

Setup없음.
Run기존 deck 문서 테스트와 정적 다이어그램 테스트를 그대로 실행한다.
Expected전부 통과. 기존 테스트 파일은 수정되지 않았다.
Pass criterion두 테스트 스크립트가 exit 0.

T13. 아카이브된 기획서를 다시 만들어도 지금과 같이 열린다

Setup아카이브된 계획 폴더 하나(예: 최근 것)를 고른다.
Run그 폴더로 기획서를 다시 만든다.
Expected정상적으로 만들어지고, 새 양식 때문에 깨지거나 빈 사이드바가 끼어들지 않는다.
Pass criterion생성이 exit 0 이고, 결과에 빈 상세 사이드바가 없다.

T19. 검증 메시지 표가 그림 아래에 나온다

Setup화면 목업에 검증 규칙 2건을 쓴다. 한 건은 여러 번호에 걸치게 한다 (예: 이메일 형식 오류 — 입력칸 ①과 제출 버튼 Ⓐ 양쪽).
Run기획서를 만든다.
Expected그림 아래에 표가 나오고, 머리글은 체크 시점 / 조건 / 메시지 / 노출 유형이며, 여러 번호에 걸친 규칙이 한 행에 그 번호들을 함께 표시한다.
Pass criterion표가 렌더되고 규칙 수만큼 행이 있으며, 여러 번호 표기가 보인다.

T20. 컴포넌트 상태 변형이 그림 아래 띠로 나온다

Setup같은 번호의 컴포넌트에 상태 2개(기본 / Invalid)를 쓴다.
Run기획서를 만든다.
Expected그림 아래에 상태 띠가 나오고, 각 상태에 이름과 번호가 붙는다.
Pass criterion상태 칸이 쓴 개수만큼 렌더된다.

T21. 번호별 상세가 파이프라인 단계와 이어진다

Setup번호별 상세에 파이프라인 단계 이름을 단다 (기능 2개 + 액션 1개).
Run기획서를 만든다.
Expected각 항목 제목 옆에 단계 이름 태그가 붙는다.
Pass criterion단계 태그가 3개 렌더되고 단계 이름이 그대로 나온다.

T22. 마커를 안 쓰면 자동으로 번호가 붙는다 (기본 동작)

Setup컴포넌트에 번호를 하나도 쓰지 않은 화면 목업을 만든다. 캡션 (헤더)과 입력칸 2개, 버튼 2개를 넣는다.
Run기획서를 만든다.
Expected입력칸은 1·2, 버튼은 A·B를 자동으로 받는다. 캡션은 번호를 받지 않는다 (받으면 실제 항목의 번호가 밀린다). 짝 검사가 오탐 경고를 내지 않는다.
Pass criterion마커가 정확히 4개이고 숫자·문자 계열이 각각 맞으며, "그림에 없는 번호" 경고가 뜨지 않는다.

T23. 자동 번호를 끌 수 있다

SetupT22 문서에 자동 번호 끄기를 지정한다.
Run기획서를 만든다.
Expected마커가 하나도 붙지 않는다. 검증 표 등 나머지는 그대로 나온다.
Pass criterion마커 0개, 검증 표는 존재.

T24. 스크롤 영역은 하나뿐이다 (이중 스크롤 금지)

Setup기획서 하나를 만든다.
Run결과 문서의 스크롤 설정을 확인한다.
Expected문서 껍데기 안쪽 한 곳만 스크롤한다. 그 뒤의 바깥 문서는 스크롤하지 않는다(스크롤바가 하나만 보인다). 인쇄할 때는 이 제약이 풀려 내용이 잘리지 않는다.
Pass criterion바깥 문서 스크롤 차단과 스크롤 체이닝 차단이 확인되고, 안쪽 스크롤 영역은 그대로이며, 인쇄 규칙에 되돌림이 들어 있다.

T25. BE 최상단에 "어느 화면이 부르는가"가 나온다

SetupBE 화면설계서에 호출 화면 1건을 쓴다 (화면 이름·코드·요소·시점).
Run기획서를 만든다.
Expected표가 그림보다 위에 나온다. 백엔드 독자의 첫 질문이 "누가 나를 부르나"이기 때문이다.
Pass criterion표의 내용이 모두 렌더되고, 위치가 그림보다 앞선다.

T26. 큰 그림을 여러 장(구성 + 순서) 그릴 수 있다

Setup큰 그림을 2장 쓴다 — 구성도 하나, 순서도 하나. 각 장에 이름을 단다.
Run기획서를 만든다.
Expected두 장이 모두 렌더되고 각 장에 이름표가 붙는다.
Pass criterion다이어그램 2개, 이름표 존재, 순서도 문법이 그대로 실린다.

T27. 상태 띠를 테이블 스키마로 쓸 수 있다

Setup상태 띠 제목을 "데이터 모양 (테이블 스키마)"로 바꾸고, 표의 컬럼과 비고를 담은 카드를 1장 쓴다.
Run기획서를 만든다.
Expected바꾼 제목이 나오고 FE 기본 제목("컴포넌트 상태")은 나오지 않는다.
Pass criterion제목이 교체되고 컬럼 내용이 렌더된다.

T28. 실패·응답 표를 직접 정한 컬럼으로 쓸 수 있다

Setup검증표를 컬럼 직접 지정 형태로 쓴다 (번호 / 조건 / 응답 / 본문·메시지 / 기록·데이터 영향), 규칙 2건.

Pass criterion제목·컬럼이 그대로이고, 해당 표의 행이 정확히 2개다 (같은 표 부품을 쓰는 호출 화면 표와 섞어 세지 않는다).

T29. 순서도 글자가 배경에 묻히지 않는다 (대비)

# 번호식 화면설계서 — 그림이 주인공인 기획서

## Summary

기획서를 열었을 때 **큰 그림 한 장이 먼저 보이고, 설명은 번호를 달고 그림 옆에
붙는** 형태로 바꾼다. 지금은 화면을 열면 검은 배경에 문장 몇 줄뿐이라 "기획서"가
아니라 "폰트 큰 마크다운"으로 읽힌다. 실무에서 쓰는 화면설계서 양식(그림에 ①②③,
우측에 번호별 상세)을 그대로 도입해, 그림이 없으면 기획서가 성립하지 않게 만든다.

## Goals / Non-Goals

- **Goals**
  - 기획서의 기본 형태를 **큰 그림 + 번호 마커 + 번호별 상세 사이드바**로 바꾼다.
  - **FE**(화면 있음): 컴포넌트 역할 + 액션(버튼 등) 동작을 번호로 나눠 기술한다.
  - **BE**(화면 없음): 구성도·흐름도에 번호를 달고 API·함수의 역할을 기술한다.
  - 페이지 식별 코드와 **이동 대상 상호참조**(이 버튼을 누르면 어느 화면으로)를
    기획서 안에서 표현할 수 있게 한다.
  - 계획을 세울 때 이 재료(그림 + 번호별 상세)를 **필수로 요구**한다. 빠졌으면
    **경고하고 진행**한다.
  - 그림이 하나도 없는 기획서는 **경고로 드러난다** (지금은 조용히 통과).
  - **검증 메시지 표** — 한 규칙이 여러 번호에 걸릴 때 어디서 무슨 문구가 뜨는지
    한 표에서 추적된다 (샘플의 "체크 시점 / 조건 / 메시지 / 노출 유형").
  - **컴포넌트 상태 변형** — 기본·입력 중·Invalid 같은 상태를 그림 아래 띠로 보인다.
  - **파이프라인 단계 연결** — 번호별 상세가 계획의 파이프라인 단계 이름을 달아,
    계획·화면·구현이 한 줄로 꿰인다.
  - **마커 자동 번호** — 지시하지 않으면 읽는 순서대로 번호(①②③)와 문자(ⒶⒷ)를
    자동으로 붙인다. 손으로 쓴 번호가 항상 우선한다.
  - **BE — 호출 화면 표** — 어느 화면의 어느 요소가 이 API를 부르는지 맨 위에
    적는다. 백엔드만 보는 사람이 화면 없이 구현하다 헤매는 것을 막는다.
  - **BE — 순서도** — 구성도와 별개로 요청 하나가 어떻게 처리되는지(분기 포함)를
    그림으로 그린다. 큰 그림을 여러 장 실을 수 있게 한다.
  - **BE — 테이블 스키마 카드** — FE의 상태 띠 자리에 표의 컬럼·인덱스·증가
    양상을 싣는다.
  - **BE — 실패·응답 표** — FE의 검증 메시지 표를 컬럼만 바꿔 재사용한다
    (번호 / 조건 / 응답 / 본문·메시지 / 기록·데이터 영향).

- **Non-Goals**
  - **이미 아카이브된 계획 30여 건의 재작성** — 앞으로 쓰는 계획부터 적용한다.
    과거 문서는 지금과 똑같이 열린다.
  - **인프라·데이터·운영 등 나머지 영역의 전용 양식** — 기본 골자는 같으므로
    FE/BE에서 골자가 검증되면 다음에 확장한다. 이번엔 두 영역만.
  - **상태 변형을 모든 컴포넌트에 강제하는 것** — 규칙이 실제로 있는 컴포넌트에만
    쓴다. 기본 모습만 반복하는 상태 띠는 의미가 없다.
  - **목업을 실제 동작하는 화면으로 만드는 것** — 목업은 정지된 그림이다.
  - **실제 스크린샷 사용** — 와이어프레임(구조만 보여주는 중립 그림)이다.
  - 슬라이드 형태(발표용) 개편 — 이번 대상은 읽는 문서 형태다.

## Approach Overview

두 군데를 건드린다. **그림을 그리는 쪽**(렌더러)과 **재료를 요구하는 쪽**(계획 작성
지침)이다. 밀도 문제의 원인이 "렌더러가 아니라 공급"이었으므로 둘 다 필요하다.

1. **마커와 사이드바를 렌더러에 추가한다.**
   현재 화면 목업은 컴포넌트를 위에서 아래로 그릴 뿐, 번호 개념이 없다. 여기에
   - 각 컴포넌트가 **자기 번호를 가질 수 있게** 하고 (그림 위에 ①②③ 표시),
   - 액션 요소는 **문자 마커**(ⒶⒷ)로 구분하며,
   - 그림 **오른쪽에 번호별 상세 목록**(역할 설명 / 액션 설명 두 묶음)을 붙이고,
   - 그림 **위에 페이지 이름과 식별 코드** 줄을 얹는다.

   마커가 없는 기존 목업은 지금과 똑같이 그려진다(하위 호환).

2. **BE용 큰 그림에도 같은 골자를 적용한다.**
   화면이 없는 계획은 구성도·흐름도가 "큰 그림" 자리를 대신한다. 다이어그램의
   각 요소에 번호를 달고, 같은 형태의 우측 상세(이 API는 무엇을 받고 무엇을
   하는가 / 이 함수의 역할)를 붙인다. **FE와 시각적으로 같은 틀**이어야 한다 —
   영역이 달라도 골자는 같다는 요구가 여기서 검증된다.

3. **계획 작성 단계에서 이 재료를 요구한다.**
   계획을 만들 때 화면(또는 구성도)과 번호별 상세를 **함께 쓰도록 필수화**한다.
   빠졌으면 무엇이 비었는지 알리고 진행한다 — 지어내지 않는다.

4. **품질 검사에 밀도 항목을 넣는다.**
   지금 검사는 "이 절이 있는가"만 본다. 여기에 **그림이 한 장도 없는가**를
   더한다. 진단에서 최근 기획서 8건 연속 그림 0개가 조용히 통과한 것이 이
   검사의 공백 때문이다.

**설계 판단 — 어디에 둘 것인가.** 마커·사이드바를 그리는 규칙은 **코드(렌더러)**에
둔다. 작성 지시문에 두면 이미 만들어진 문서는 영원히 옛 모습으로 남고 코드를
고쳐도 안 바뀐다 — 색 팔레트를 지시문에 박았다가 겪은 문제와 같은 함정이다.
지시문에는 "재료를 요구하는 규칙"만 둔다.

## 순수함수 · 파이프라인 (Pure functions & pipeline)

기획서를 만드는 일 자체가 파이프라인이다. 각 단계는 받은 값만 보고 결과를
돌려주며, 파일을 읽고 쓰는 일은 **입구와 출구에만** 있다.

```
flow(
  readSource,        // 경로 → 원문 마크다운          [부수효과 · 입구]
  mdToDeck,          // 원문 → 블록 배열 + 경고 목록   [순수]
  renderBlocks,      // 블록 배열 → HTML 조각          [순수]
  renderScreen,      // 화면 블록 → 목업·마커·상세     [순수]
  assembleHtml,      // HTML 조각 → 자체완결 문서      [순수]
  writeDeck,         // 문서 → 파일                    [부수효과 · 출구]
)
```

| # | 단계 | 받는 값 → 돌려주는 값 | 순수/부수효과 |
|---|---|---|---|
| 1 | readSource | 경로 → 원문 마크다운 | 부수효과 (입구) |
| 2 | mdToDeck | 원문 → 블록 배열 + 경고 목록 | 순수 |
| 3 | renderBlocks | 블록 배열 → HTML 조각 | 순수 |
| 4 | renderScreen | 화면 블록 → 목업 + 마커 + 상세 | 순수 |
| 5 | assembleHtml | HTML 조각 → 자체완결 문서 | 순수 |
| 6 | writeDeck | 문서 → 파일 | 부수효과 (출구) |

- **부수효과 위치**: 파일 읽기(1)와 파일 쓰기(6)뿐이다. 2~5는 같은 입력이면
  항상 같은 출력이라 결과를 그대로 비교할 수 있다 — 하위 호환을 바이트 단위로
  검증할 수 있는 이유가 이것이다.
- **재사용**: 마커·상세를 그리는 단계(4)는 화면(FE)과 구성도(BE)가 **같은 단계를
  그대로** 쓴다. 영역이 달라도 골자가 같은 것이 이 재사용의 결과다.
- **A/B 검증**: 어느 한 단계만 바꿔 끼우면 나머지는 그대로 두고 비교할 수 있다.

## Guardrails

- **순수함수·파이프라인을 지킨다.** 각 단계는 받은 값만 보고 결과를 돌려주며,
  파일·네트워크·시각을 만지는 일은 입구와 출구에만 둔다. 중간 단계에 부수효과를
  넣지 않는다.
- **결정적 변환을 깨지 않는다.** 번호별 설명은 작성자가 쓴 것만 나온다. 렌더러가
  "이 버튼은 아마 이런 역할일 것"이라고 지어내지 않는다.
- **하위 호환.** 마커가 없는 기존 화면 목업은 지금과 픽셀 단위로 같게 그려진다.
  기존 기획서를 다시 만들었을 때 달라지면 안 된다.
- **아카이브된 계획은 건드리지 않는다.** 과거 문서를 열면 지금과 같이 보인다.
- **막지 않는다.** 재료가 없으면 경고만 하고 기획서는 만들어진다.
- 그림 없이 만들어진 기획서도 **여전히 만들어진다** — 경고로 드러날 뿐이다.
- 원문 마크다운은 계속 결과물에 동봉된다 (렌더링과 원본이 항상 일치).
- 마커 개수가 많아져도 그림이 읽을 수 없게 뭉개지면 안 된다 — 한 화면의 마커
  수에 실용적 상한을 두고, 넘으면 알린다.
- **스크롤 영역은 하나뿐이다.** 문서 껍데기가 스크롤을 갖고, 그 뒤의 바깥 문서는
  스크롤하지 않는다. 스크롤바가 둘이면 휠이 어디에 먹을지 알 수 없다. 인쇄할
  때는 이 제약을 풀어 내용이 잘리지 않게 한다.

## Exit criteria

- TESTS.md 시나리오 전부 통과.
- FE 예시 하나와 BE 예시 하나를 **실제로 만들어 열었을 때**, 그림이 먼저 보이고
  번호별 설명이 그림 옆에 붙어 있다.
- 마커 없는 기존 목업을 다시 만들었을 때 **결과가 이전과 같다**.
- 그림 없는 기획서를 만들면 **경고가 뜬다**.
- 아카이브된 기획서 하나를 다시 만들어도 **지금과 같이 열린다**.

## Suggested path

1. 화면 목업에 **번호·문자 마커**를 추가한다 (그림 위 표시 + 컴포넌트별 번호).
2. 그림 오른쪽에 **번호별 상세 사이드바**(역할 묶음 / 액션 묶음)를 붙인다.
3. 그림 위에 **페이지 이름 + 식별 코드** 줄과 **이동 대상 상호참조**를 넣는다.
4. **BE용 큰 그림**(구성도·흐름도)에 같은 마커·사이드바 골자를 적용한다.
5. 품질 검사에 **그림 0장 경고**를 추가한다.
6. 계획 작성 지침에 **양식 재료 필수화**(빠지면 경고)를 넣는다.
7. **검증 메시지 표**를 그림 아래에 붙인다 (규칙 하나가 여러 번호에 걸릴 수 있게).
8. **컴포넌트 상태 변형**을 그림 아래 띠로 붙인다.
9. 번호별 상세에 **파이프라인 단계 이름**을 달 수 있게 한다.
10. **마커 자동 번호**를 기본으로 켠다 — 변환 단계에서 붙여 검사와 화면이 같은
    번호를 보게 한다. 손으로 쓴 번호가 우선하고, 캡션은 번호를 받지 않는다.
11. **스크롤 영역을 하나로** 고정한다 (바깥 문서 스크롤 차단, 인쇄 시 해제).
12. **BE 심화** — 호출 화면 표(최상단), 큰 그림 여러 장(구성 + 순서), 상태 띠를
    테이블 스키마로, 검증표를 실패·응답 표로 재사용. 오른쪽 상세는 역할과
    입출력만 남겨 FE만큼 가볍게 만든다.
13. **순서도 대비**를 잡는다 — 순서도 전용 색 규칙이 없으면 글자가 배경에 묻힌다.
14. FE·BE 예시를 각각 만들어 눈으로 확인하고, 기존 목업의 하위 호환을 확인한다.

## 예외처리 (Edge cases)

- **번호를 붙였는데 그 번호의 설명이 없다** → 그 항목은 비워 둔다. 지어내지
  않는다 (T4).
- **설명은 썼는데 그림에 그 번호가 없다** → 짝이 맞지 않는다고 알린다.
  기획서는 그대로 만든다.
- **마커가 너무 많다** → 실용적 상한을 넘으면 알린다. 그림이 뭉개지는 것을
  막기 위함이다.
- **마커가 하나도 없는 기존 목업** → 지금과 똑같이 그린다. 빈 사이드바가
  생기지 않는다 (T8).
- **그림이 하나도 없는 계획** → 경고로 드러나되 기획서는 만들어진다 (T9).
- **화면이 좁을 때** → 사이드바를 그림 옆에 두면 그림이 찌그러지므로, 좁은
  화면에서는 그림 아래로 내린다.
- **인쇄(PDF)** → 마커와 사이드바가 끊기지 않게 배치한다. 실제 인쇄로 확인한다.
- **BE 계획에 구성도가 없다** → 화면도 구성도도 없으면 그림 0장 경고에 걸린다.
- **번호 문자가 특수문자라 깨질 때** → 표시가 깨지지 않는 방식으로 그린다.
- **아카이브된 계획을 다시 만들 때** → 새 양식 때문에 깨지지 않는다 (T13).

## Risks / Open Questions

**해소됨 (구현 중 실제 화면으로 확인)**

- **그림이 좁아진다** → 실제로 재발했고, 고쳤다. 다이어그램을 옆 칸(약 430px)에
  넣자 800px짜리 구성도가 절반 크기로 줄어 8/13과 똑같이 글자가 뭉갰다. 그래서
  **다이어그램일 때는 그림이 전체 폭을 쓰고 번호별 상세가 아래로 내려가도록**
  했다. 와이어프레임은 옆 칸이 적당하므로 그대로 옆에 둔다. 골자(큰 그림 + 번호
  + 번호별 상세)는 두 경우 모두 같다.
- **다이어그램이 상자를 뚫고 나가 잘리던 문제** → 기존에 다이어그램을 본문보다
  넓게 펼치는 장치가 있었는데, 목업 안에서는 그게 틀을 뚫었다. 목업 안에서만
  해제했다.
- **BE의 큰 그림에 번호 붙이는 법** → 작성자가 **구성도 노드 이름에 직접**
  번호를 넣는다(가장 단순하고, 렌더러가 위치를 지어내지 않는다).
- **마커 수 상한** → 한 그림당 20개. 넘으면 경고한다.
- **이중 스크롤** → 실측으로 확인했다. 바깥 문서가 껍데기보다 6px 커서 스크롤바가
  둘이었다. 껍데기만 스크롤을 갖도록 못박고, 인쇄 시에는 풀었다.
- **순서도 글자가 묻히는 문제** → 이 프로젝트는 다이어그램을 자체 색 규칙으로
  칠하는데, 그 규칙이 흐름도 전용이었다. 순서도는 밝은 배경을 전제한 기본색이
  그대로 남아 글자가 안 보였다. 순서도 전용 규칙을 같은 자리에 추가했다.
  (중간에 목업 안 다이어그램 배경을 투명하게 만든 것이 이 문제를 키웠다 — 되돌렸다.)

**남은 것**

- **인쇄(PDF)에서의 모습**은 아직 확인 안 됨. 인쇄 시 사이드바를 그림 아래로
  내리도록 규칙은 넣었으나, 실제 인쇄로 눈으로 본 것은 아니다.
- **나머지 영역(인프라·데이터·운영)** 은 이번 범위 밖 — FE/BE에서 골자가
  검증됐으므로 같은 틀로 확장하면 된다.

# Test Plan — 번호식 화면설계서 — 그림이 주인공인 기획서

## Overview

기획서를 열었을 때 **그림이 먼저 보이고 설명이 번호로 그림에 매달리는지**를
검증한다. 새로 생기는 것(마커·사이드바·페이지 코드·BE 큰 그림·밀도 경고·재료
필수화)이 실제로 나오는지, 그리고 **기존 기획서가 하나도 달라지지 않는지**를
같은 무게로 확인한다. 후자가 없으면 이 변경은 기존 문서 30여 건을 조용히
망가뜨릴 수 있다.

새 검사는 `core/tests/test-deck-numbered-spec.sh` 에 모으고, 기존 deck 계약
(`core/tests/test-deck-doc.sh`)은 **수정하지 않고 그대로 통과**해야 한다.

## Test scenarios

### T1. 번호 마커가 그림 위에 표시된다 (FE)

- **Setup**: 화면 목업 블록을 담은 임시 마크다운을 만든다. 컴포넌트 3개에 각각
  번호 1·2·3을 부여한다 (예: 이메일 입력칸, 비밀번호 입력칸, 약관 체크박스).
- **Run**: 그 파일로 기획서를 만든다 (문서 형태, 원문 패널 제외 렌더로 검사해
  원문 마크다운 쪽 문자열에 우연히 걸리지 않게 한다).
- **Expected**: 목업 안에 번호 마커 1·2·3이 각 컴포넌트에 붙어 렌더된다.
- **Pass criterion**: 렌더 결과에서 마커 요소 3개가 확인되고, 각 마커의 번호가
  1·2·3이다.

### T2. 액션 요소는 문자 마커로 구분된다 (FE)

- **Setup**: T1 파일에 버튼 2개를 추가하고 각각 문자 마커 A·B를 부여한다.
- **Run**: 기획서를 만든다.
- **Expected**: 버튼에는 숫자가 아니라 문자 마커 A·B가 붙는다. 숫자 마커와
  문자 마커가 서로 다른 계열로 구분된다.
- **Pass criterion**: 문자 마커 A·B가 렌더되고, 숫자 마커 집합과 겹치지 않는다.

### T3. 번호별 상세가 그림 오른쪽에 붙는다 (FE — 역할 + 액션 두 묶음)

- **Setup**: T2 파일에 번호별 상세를 쓴다 — 1·2·3 에는 컴포넌트 역할(예:
  "이메일 입력칸: 320자 초과 입력 막음, 포커스 아웃 시 형식 검사"), A·B 에는
  액션 동작(예: "회원가입 버튼: 모든 필수 항목 충족 시 활성화").
- **Run**: 기획서를 만든다.
- **Expected**: 그림 옆에 상세 목록이 **역할 묶음**과 **액션 묶음**으로 나뉘어
  렌더된다. 각 항목이 자기 마커 번호를 달고 있다.
- **Pass criterion**: 역할 묶음에 1·2·3 항목이, 액션 묶음에 A·B 항목이 각각
  들어 있고, 작성한 설명 문구가 그대로 나온다.

### T4. 지어내지 않는다 (충실도)

- **Setup**: 컴포넌트 3개 중 **2개에만** 번호별 상세를 쓴다 (1·2만, 3은 비움).
- **Run**: 기획서를 만든다.
- **Expected**: 3번에 대한 설명이 **비어 있거나 생략**된다. 렌더러가 "3번은
  아마 이런 역할" 같은 문구를 만들어내지 않는다.
- **Pass criterion**: 렌더 결과의 상세 묶음에 작성하지 않은 3번 설명 텍스트가
  존재하지 않는다.

### T5. 페이지 이름과 식별 코드가 그림 위에 나온다

- **Setup**: 화면 목업에 페이지 이름("회원가입 페이지")과 식별 코드
  ("FO-SU-02-01")를 부여한다.
- **Run**: 기획서를 만든다.
- **Expected**: 그림 위쪽에 페이지 이름과 식별 코드가 함께 표시된다.
- **Pass criterion**: 두 값이 모두 렌더 결과에 나타나며, 목업 프레임 바깥이
  아니라 해당 화면 블록에 속해 있다.

### T6. 이동 대상 상호참조가 표현된다

- **Setup**: 액션 상세에 이동 대상 코드를 쓴다 (예: "회원가입 완료 시
  FO-SU-02-02 로 이동").
- **Run**: 기획서를 만든다.
- **Expected**: 이동 대상 코드가 액션 설명 안에 그대로 표시된다.
- **Pass criterion**: 해당 코드 문자열이 액션 묶음 안에서 확인된다.

### T7. BE — 화면이 없는 계획도 같은 골자로 그려진다

- **Setup**: 화면 목업 없이 구성도(다이어그램)를 담은 마크다운을 만들고, 그
  구성 요소에 번호를 붙인 뒤 번호별로 API·함수 역할을 쓴다 (예: "1. 인증 API —
  이메일·비밀번호를 받아 토큰을 돌려준다").
- **Run**: 기획서를 만든다.
- **Expected**: 큰 그림(구성도) 옆에 **FE와 같은 형태의** 번호별 상세가 붙는다.
- **Pass criterion**: 구성도가 렌더되고, 그 옆 상세 묶음에 번호별 API·함수 설명이
  들어 있으며, FE 사례(T3)와 **같은 구조**(같은 사이드바 형태)로 렌더된다.

### T8. 마커 없는 기존 목업은 지금과 똑같이 렌더된다 (하위 호환 — 회귀 방지)

- **Setup**: 마커·상세·페이지 코드가 **전혀 없는** 기존 형태의 화면 목업
  마크다운을 준비한다.
- **Run**: 변경 전후로 같은 입력을 렌더해 결과를 비교한다. (변경 전 결과는
  현재 코드로 미리 만들어 보관한다.)
- **Expected**: 결과가 **동일**하다. 빈 사이드바나 빈 마커 자리가 생기지 않는다.
- **Pass criterion**: 두 렌더 결과의 본문이 일치한다.

### T9. 그림 없는 기획서는 경고로 드러난다

- **Setup**: 그림(화면 목업·다이어그램)이 하나도 없는 글만 있는 마크다운을
  준비한다.
- **Run**: 기획서를 만든다.
- **Expected**: 품질 검사 경고에 **그림이 없다**는 항목이 나온다. 그래도
  기획서 파일은 정상적으로 만들어진다 (막지 않는다).
- **Pass criterion**: 경고 출력에 해당 항목이 존재하고, 종료 코드는 0이며,
  결과 HTML 파일이 생성된다.

### T10. 그림이 있으면 그 경고는 뜨지 않는다 (거짓 경고 방지)

- **Setup**: 다이어그램이 하나 있는 마크다운을 준비한다.
- **Run**: 기획서를 만든다.
- **Expected**: 그림 없음 경고가 **뜨지 않는다**.
- **Pass criterion**: 경고 출력에 해당 항목이 없다.

### T11. 계획 작성 지침이 양식 재료를 요구한다

- **Setup**: 계획 작성 지침 문서를 대상으로 한다.
- **Run**: 지침에 양식 재료(큰 그림 + 번호별 상세) 요구와 **빠졌을 때 경고하고
  진행**한다는 규칙이 명시돼 있는지 확인한다.
- **Expected**: 두 규칙이 모두 문서에 존재한다. "재료 없으면 중단"이라는 문구는
  없어야 한다 (막지 않기로 한 결정).
- **Pass criterion**: 요구 규칙과 경고-진행 규칙이 확인되고, 중단 규칙은 없다.

### T12. 기존 deck 계약이 그대로 통과한다 (회귀)

- **Setup**: 없음.
- **Run**: 기존 deck 문서 테스트와 정적 다이어그램 테스트를 그대로 실행한다.
- **Expected**: 전부 통과. 기존 테스트 파일은 수정되지 않았다.
- **Pass criterion**: 두 테스트 스크립트가 exit 0.

### T13. 아카이브된 기획서를 다시 만들어도 지금과 같이 열린다

- **Setup**: 아카이브된 계획 폴더 하나(예: 최근 것)를 고른다.
- **Run**: 그 폴더로 기획서를 다시 만든다.
- **Expected**: 정상적으로 만들어지고, 새 양식 때문에 깨지거나 빈 사이드바가
  끼어들지 않는다.
- **Pass criterion**: 생성이 exit 0 이고, 결과에 빈 상세 사이드바가 없다.

### T19. 검증 메시지 표가 그림 아래에 나온다

- **Setup**: 화면 목업에 검증 규칙 2건을 쓴다. 한 건은 여러 번호에 걸치게 한다
  (예: 이메일 형식 오류 — 입력칸 ①과 제출 버튼 Ⓐ 양쪽).
- **Run**: 기획서를 만든다.
- **Expected**: 그림 아래에 표가 나오고, 머리글은 체크 시점 / 조건 / 메시지 /
  노출 유형이며, 여러 번호에 걸친 규칙이 한 행에 그 번호들을 함께 표시한다.
- **Pass criterion**: 표가 렌더되고 규칙 수만큼 행이 있으며, 여러 번호 표기가 보인다.

### T20. 컴포넌트 상태 변형이 그림 아래 띠로 나온다

- **Setup**: 같은 번호의 컴포넌트에 상태 2개(기본 / Invalid)를 쓴다.
- **Run**: 기획서를 만든다.
- **Expected**: 그림 아래에 상태 띠가 나오고, 각 상태에 이름과 번호가 붙는다.
- **Pass criterion**: 상태 칸이 쓴 개수만큼 렌더된다.

### T21. 번호별 상세가 파이프라인 단계와 이어진다

- **Setup**: 번호별 상세에 파이프라인 단계 이름을 단다 (기능 2개 + 액션 1개).
- **Run**: 기획서를 만든다.
- **Expected**: 각 항목 제목 옆에 단계 이름 태그가 붙는다.
- **Pass criterion**: 단계 태그가 3개 렌더되고 단계 이름이 그대로 나온다.

### T22. 마커를 안 쓰면 자동으로 번호가 붙는다 (기본 동작)

- **Setup**: 컴포넌트에 번호를 **하나도 쓰지 않은** 화면 목업을 만든다. 캡션
  (헤더)과 입력칸 2개, 버튼 2개를 넣는다.
- **Run**: 기획서를 만든다.
- **Expected**: 입력칸은 1·2, 버튼은 A·B를 자동으로 받는다. **캡션은 번호를 받지
  않는다** (받으면 실제 항목의 번호가 밀린다). 짝 검사가 오탐 경고를 내지 않는다.
- **Pass criterion**: 마커가 정확히 4개이고 숫자·문자 계열이 각각 맞으며,
  "그림에 없는 번호" 경고가 뜨지 않는다.

### T23. 자동 번호를 끌 수 있다

- **Setup**: T22 문서에 자동 번호 끄기를 지정한다.
- **Run**: 기획서를 만든다.
- **Expected**: 마커가 하나도 붙지 않는다. 검증 표 등 나머지는 그대로 나온다.
- **Pass criterion**: 마커 0개, 검증 표는 존재.

### T24. 스크롤 영역은 하나뿐이다 (이중 스크롤 금지)

- **Setup**: 기획서 하나를 만든다.
- **Run**: 결과 문서의 스크롤 설정을 확인한다.
- **Expected**: 문서 껍데기 안쪽 한 곳만 스크롤한다. 그 뒤의 바깥 문서는
  스크롤하지 않는다(스크롤바가 하나만 보인다). 인쇄할 때는 이 제약이 풀려
  내용이 잘리지 않는다.
- **Pass criterion**: 바깥 문서 스크롤 차단과 스크롤 체이닝 차단이 확인되고,
  안쪽 스크롤 영역은 그대로이며, 인쇄 규칙에 되돌림이 들어 있다.

### T25. BE 최상단에 "어느 화면이 부르는가"가 나온다

- **Setup**: BE 화면설계서에 호출 화면 1건을 쓴다 (화면 이름·코드·요소·시점).
- **Run**: 기획서를 만든다.
- **Expected**: 표가 **그림보다 위에** 나온다. 백엔드 독자의 첫 질문이 "누가 나를
  부르나"이기 때문이다.
- **Pass criterion**: 표의 내용이 모두 렌더되고, 위치가 그림보다 앞선다.

### T26. 큰 그림을 여러 장(구성 + 순서) 그릴 수 있다

- **Setup**: 큰 그림을 2장 쓴다 — 구성도 하나, 순서도 하나. 각 장에 이름을 단다.
- **Run**: 기획서를 만든다.
- **Expected**: 두 장이 모두 렌더되고 각 장에 이름표가 붙는다.
- **Pass criterion**: 다이어그램 2개, 이름표 존재, 순서도 문법이 그대로 실린다.

### T27. 상태 띠를 테이블 스키마로 쓸 수 있다

- **Setup**: 상태 띠 제목을 "데이터 모양 (테이블 스키마)"로 바꾸고, 표의 컬럼과
  비고를 담은 카드를 1장 쓴다.
- **Run**: 기획서를 만든다.
- **Expected**: 바꾼 제목이 나오고 FE 기본 제목("컴포넌트 상태")은 나오지 않는다.
- **Pass criterion**: 제목이 교체되고 컬럼 내용이 렌더된다.

### T28. 실패·응답 표를 직접 정한 컬럼으로 쓸 수 있다

- **Setup**: 검증표를 컬럼 직접 지정 형태로 쓴다 (번호 / 조건 / 응답 / 본문·메시지
  / 기록·데이터 영향), 규칙 2건.
- **Run**: 기획서를 만든다.
- **Expected**: 바꾼 제목과 컬럼으로 표가 나오고 규칙이 2행이다.
- **Pass criterion**: 제목·컬럼이 그대로이고, 해당 표의 행이 정확히 2개다
  (같은 표 부품을 쓰는 호출 화면 표와 섞어 세지 않는다).

### T29. 순서도 글자가 배경에 묻히지 않는다 (대비)

- **Setup**: 없음 — 렌더러의 색 규칙을 대상으로 한다.
- **Run**: 순서도 요소별 색 규칙이 있는지 확인한다.
- **Expected**: 메시지 글자, else 분기 라벨, 참여자 상자에 각각 규칙이 있다.
- **Pass criterion**: 세 규칙이 모두 존재한다.

# 번호식 화면설계서 — 그림이 주인공인 기획서

## Summary

기획서를 열었을 때 **큰 그림 한 장이 먼저 보이고, 설명은 번호를 달고 그림 옆에
붙는** 형태로 바꾼다. 지금은 화면을 열면 검은 배경에 문장 몇 줄뿐이라 "기획서"가
아니라 "폰트 큰 마크다운"으로 읽힌다. 실무에서 쓰는 화면설계서 양식(그림에 ①②③,
우측에 번호별 상세)을 그대로 도입해, 그림이 없으면 기획서가 성립하지 않게 만든다.

## Goals / Non-Goals

- **Goals**
  - 기획서의 기본 형태를 **큰 그림 + 번호 마커 + 번호별 상세 사이드바**로 바꾼다.
  - **FE**(화면 있음): 컴포넌트 역할 + 액션(버튼 등) 동작을 번호로 나눠 기술한다.
  - **BE**(화면 없음): 구성도·흐름도에 번호를 달고 API·함수의 역할을 기술한다.
  - 페이지 식별 코드와 **이동 대상 상호참조**(이 버튼을 누르면 어느 화면으로)를
    기획서 안에서 표현할 수 있게 한다.
  - 계획을 세울 때 이 재료(그림 + 번호별 상세)를 **필수로 요구**한다. 빠졌으면
    **경고하고 진행**한다.
  - 그림이 하나도 없는 기획서는 **경고로 드러난다** (지금은 조용히 통과).
  - **검증 메시지 표** — 한 규칙이 여러 번호에 걸릴 때 어디서 무슨 문구가 뜨는지
    한 표에서 추적된다 (샘플의 "체크 시점 / 조건 / 메시지 / 노출 유형").
  - **컴포넌트 상태 변형** — 기본·입력 중·Invalid 같은 상태를 그림 아래 띠로 보인다.
  - **파이프라인 단계 연결** — 번호별 상세가 계획의 파이프라인 단계 이름을 달아,
    계획·화면·구현이 한 줄로 꿰인다.
  - **마커 자동 번호** — 지시하지 않으면 읽는 순서대로 번호(①②③)와 문자(ⒶⒷ)를
    자동으로 붙인다. 손으로 쓴 번호가 항상 우선한다.
  - **BE — 호출 화면 표** — 어느 화면의 어느 요소가 이 API를 부르는지 맨 위에
    적는다. 백엔드만 보는 사람이 화면 없이 구현하다 헤매는 것을 막는다.
  - **BE — 순서도** — 구성도와 별개로 요청 하나가 어떻게 처리되는지(분기 포함)를
    그림으로 그린다. 큰 그림을 여러 장 실을 수 있게 한다.
  - **BE — 테이블 스키마 카드** — FE의 상태 띠 자리에 표의 컬럼·인덱스·증가
    양상을 싣는다.
  - **BE — 실패·응답 표** — FE의 검증 메시지 표를 컬럼만 바꿔 재사용한다
    (번호 / 조건 / 응답 / 본문·메시지 / 기록·데이터 영향).

- **Non-Goals**
  - **이미 아카이브된 계획 30여 건의 재작성** — 앞으로 쓰는 계획부터 적용한다.
    과거 문서는 지금과 똑같이 열린다.
  - **인프라·데이터·운영 등 나머지 영역의 전용 양식** — 기본 골자는 같으므로
    FE/BE에서 골자가 검증되면 다음에 확장한다. 이번엔 두 영역만.
  - **상태 변형을 모든 컴포넌트에 강제하는 것** — 규칙이 실제로 있는 컴포넌트에만
    쓴다. 기본 모습만 반복하는 상태 띠는 의미가 없다.
  - **목업을 실제 동작하는 화면으로 만드는 것** — 목업은 정지된 그림이다.
  - **실제 스크린샷 사용** — 와이어프레임(구조만 보여주는 중립 그림)이다.
  - 슬라이드 형태(발표용) 개편 — 이번 대상은 읽는 문서 형태다.

## Approach Overview

두 군데를 건드린다. **그림을 그리는 쪽**(렌더러)과 **재료를 요구하는 쪽**(계획 작성
지침)이다. 밀도 문제의 원인이 "렌더러가 아니라 공급"이었으므로 둘 다 필요하다.

1. **마커와 사이드바를 렌더러에 추가한다.**
   현재 화면 목업은 컴포넌트를 위에서 아래로 그릴 뿐, 번호 개념이 없다. 여기에
   - 각 컴포넌트가 **자기 번호를 가질 수 있게** 하고 (그림 위에 ①②③ 표시),
   - 액션 요소는 **문자 마커**(ⒶⒷ)로 구분하며,
   - 그림 **오른쪽에 번호별 상세 목록**(역할 설명 / 액션 설명 두 묶음)을 붙이고,
   - 그림 **위에 페이지 이름과 식별 코드** 줄을 얹는다.

   마커가 없는 기존 목업은 지금과 똑같이 그려진다(하위 호환).

2. **BE용 큰 그림에도 같은 골자를 적용한다.**
   화면이 없는 계획은 구성도·흐름도가 "큰 그림" 자리를 대신한다. 다이어그램의
   각 요소에 번호를 달고, 같은 형태의 우측 상세(이 API는 무엇을 받고 무엇을
   하는가 / 이 함수의 역할)를 붙인다. **FE와 시각적으로 같은 틀**이어야 한다 —
   영역이 달라도 골자는 같다는 요구가 여기서 검증된다.

3. **계획 작성 단계에서 이 재료를 요구한다.**
   계획을 만들 때 화면(또는 구성도)과 번호별 상세를 **함께 쓰도록 필수화**한다.
   빠졌으면 무엇이 비었는지 알리고 진행한다 — 지어내지 않는다.

4. **품질 검사에 밀도 항목을 넣는다.**
   지금 검사는 "이 절이 있는가"만 본다. 여기에 **그림이 한 장도 없는가**를
   더한다. 진단에서 최근 기획서 8건 연속 그림 0개가 조용히 통과한 것이 이
   검사의 공백 때문이다.

**설계 판단 — 어디에 둘 것인가.** 마커·사이드바를 그리는 규칙은 **코드(렌더러)**에
둔다. 작성 지시문에 두면 이미 만들어진 문서는 영원히 옛 모습으로 남고 코드를
고쳐도 안 바뀐다 — 색 팔레트를 지시문에 박았다가 겪은 문제와 같은 함정이다.
지시문에는 "재료를 요구하는 규칙"만 둔다.

## 순수함수 · 파이프라인 (Pure functions & pipeline)

기획서를 만드는 일 자체가 파이프라인이다. 각 단계는 받은 값만 보고 결과를
돌려주며, 파일을 읽고 쓰는 일은 **입구와 출구에만** 있다.

```
flow(
  readSource,        // 경로 → 원문 마크다운          [부수효과 · 입구]
  mdToDeck,          // 원문 → 블록 배열 + 경고 목록   [순수]
  renderBlocks,      // 블록 배열 → HTML 조각          [순수]
  renderScreen,      // 화면 블록 → 목업·마커·상세     [순수]
  assembleHtml,      // HTML 조각 → 자체완결 문서      [순수]
  writeDeck,         // 문서 → 파일                    [부수효과 · 출구]
)
```

| # | 단계 | 받는 값 → 돌려주는 값 | 순수/부수효과 |
|---|---|---|---|
| 1 | readSource | 경로 → 원문 마크다운 | 부수효과 (입구) |
| 2 | mdToDeck | 원문 → 블록 배열 + 경고 목록 | 순수 |
| 3 | renderBlocks | 블록 배열 → HTML 조각 | 순수 |
| 4 | renderScreen | 화면 블록 → 목업 + 마커 + 상세 | 순수 |
| 5 | assembleHtml | HTML 조각 → 자체완결 문서 | 순수 |
| 6 | writeDeck | 문서 → 파일 | 부수효과 (출구) |

- **부수효과 위치**: 파일 읽기(1)와 파일 쓰기(6)뿐이다. 2~5는 같은 입력이면
  항상 같은 출력이라 결과를 그대로 비교할 수 있다 — 하위 호환을 바이트 단위로
  검증할 수 있는 이유가 이것이다.
- **재사용**: 마커·상세를 그리는 단계(4)는 화면(FE)과 구성도(BE)가 **같은 단계를
  그대로** 쓴다. 영역이 달라도 골자가 같은 것이 이 재사용의 결과다.
- **A/B 검증**: 어느 한 단계만 바꿔 끼우면 나머지는 그대로 두고 비교할 수 있다.

## Guardrails

- **순수함수·파이프라인을 지킨다.** 각 단계는 받은 값만 보고 결과를 돌려주며,
  파일·네트워크·시각을 만지는 일은 입구와 출구에만 둔다. 중간 단계에 부수효과를
  넣지 않는다.
- **결정적 변환을 깨지 않는다.** 번호별 설명은 작성자가 쓴 것만 나온다. 렌더러가
  "이 버튼은 아마 이런 역할일 것"이라고 지어내지 않는다.
- **하위 호환.** 마커가 없는 기존 화면 목업은 지금과 픽셀 단위로 같게 그려진다.
  기존 기획서를 다시 만들었을 때 달라지면 안 된다.
- **아카이브된 계획은 건드리지 않는다.** 과거 문서를 열면 지금과 같이 보인다.
- **막지 않는다.** 재료가 없으면 경고만 하고 기획서는 만들어진다.
- 그림 없이 만들어진 기획서도 **여전히 만들어진다** — 경고로 드러날 뿐이다.
- 원문 마크다운은 계속 결과물에 동봉된다 (렌더링과 원본이 항상 일치).
- 마커 개수가 많아져도 그림이 읽을 수 없게 뭉개지면 안 된다 — 한 화면의 마커
  수에 실용적 상한을 두고, 넘으면 알린다.
- **스크롤 영역은 하나뿐이다.** 문서 껍데기가 스크롤을 갖고, 그 뒤의 바깥 문서는
  스크롤하지 않는다. 스크롤바가 둘이면 휠이 어디에 먹을지 알 수 없다. 인쇄할
  때는 이 제약을 풀어 내용이 잘리지 않게 한다.

## Exit criteria

- TESTS.md 시나리오 전부 통과.
- FE 예시 하나와 BE 예시 하나를 **실제로 만들어 열었을 때**, 그림이 먼저 보이고
  번호별 설명이 그림 옆에 붙어 있다.
- 마커 없는 기존 목업을 다시 만들었을 때 **결과가 이전과 같다**.
- 그림 없는 기획서를 만들면 **경고가 뜬다**.
- 아카이브된 기획서 하나를 다시 만들어도 **지금과 같이 열린다**.

## Suggested path

1. 화면 목업에 **번호·문자 마커**를 추가한다 (그림 위 표시 + 컴포넌트별 번호).
2. 그림 오른쪽에 **번호별 상세 사이드바**(역할 묶음 / 액션 묶음)를 붙인다.
3. 그림 위에 **페이지 이름 + 식별 코드** 줄과 **이동 대상 상호참조**를 넣는다.
4. **BE용 큰 그림**(구성도·흐름도)에 같은 마커·사이드바 골자를 적용한다.
5. 품질 검사에 **그림 0장 경고**를 추가한다.
6. 계획 작성 지침에 **양식 재료 필수화**(빠지면 경고)를 넣는다.
7. **검증 메시지 표**를 그림 아래에 붙인다 (규칙 하나가 여러 번호에 걸릴 수 있게).
8. **컴포넌트 상태 변형**을 그림 아래 띠로 붙인다.
9. 번호별 상세에 **파이프라인 단계 이름**을 달 수 있게 한다.
10. **마커 자동 번호**를 기본으로 켠다 — 변환 단계에서 붙여 검사와 화면이 같은
    번호를 보게 한다. 손으로 쓴 번호가 우선하고, 캡션은 번호를 받지 않는다.
11. **스크롤 영역을 하나로** 고정한다 (바깥 문서 스크롤 차단, 인쇄 시 해제).
12. **BE 심화** — 호출 화면 표(최상단), 큰 그림 여러 장(구성 + 순서), 상태 띠를
    테이블 스키마로, 검증표를 실패·응답 표로 재사용. 오른쪽 상세는 역할과
    입출력만 남겨 FE만큼 가볍게 만든다.
13. **순서도 대비**를 잡는다 — 순서도 전용 색 규칙이 없으면 글자가 배경에 묻힌다.
14. FE·BE 예시를 각각 만들어 눈으로 확인하고, 기존 목업의 하위 호환을 확인한다.

## 예외처리 (Edge cases)

- **번호를 붙였는데 그 번호의 설명이 없다** → 그 항목은 비워 둔다. 지어내지
  않는다 (T4).
- **설명은 썼는데 그림에 그 번호가 없다** → 짝이 맞지 않는다고 알린다.
  기획서는 그대로 만든다.
- **마커가 너무 많다** → 실용적 상한을 넘으면 알린다. 그림이 뭉개지는 것을
  막기 위함이다.
- **마커가 하나도 없는 기존 목업** → 지금과 똑같이 그린다. 빈 사이드바가
  생기지 않는다 (T8).
- **그림이 하나도 없는 계획** → 경고로 드러나되 기획서는 만들어진다 (T9).
- **화면이 좁을 때** → 사이드바를 그림 옆에 두면 그림이 찌그러지므로, 좁은
  화면에서는 그림 아래로 내린다.
- **인쇄(PDF)** → 마커와 사이드바가 끊기지 않게 배치한다. 실제 인쇄로 확인한다.
- **BE 계획에 구성도가 없다** → 화면도 구성도도 없으면 그림 0장 경고에 걸린다.
- **번호 문자가 특수문자라 깨질 때** → 표시가 깨지지 않는 방식으로 그린다.
- **아카이브된 계획을 다시 만들 때** → 새 양식 때문에 깨지지 않는다 (T13).

## Risks / Open Questions

**해소됨 (구현 중 실제 화면으로 확인)**

- **그림이 좁아진다** → 실제로 재발했고, 고쳤다. 다이어그램을 옆 칸(약 430px)에
  넣자 800px짜리 구성도가 절반 크기로 줄어 8/13과 똑같이 글자가 뭉갰다. 그래서
  **다이어그램일 때는 그림이 전체 폭을 쓰고 번호별 상세가 아래로 내려가도록**
  했다. 와이어프레임은 옆 칸이 적당하므로 그대로 옆에 둔다. 골자(큰 그림 + 번호
  + 번호별 상세)는 두 경우 모두 같다.
- **다이어그램이 상자를 뚫고 나가 잘리던 문제** → 기존에 다이어그램을 본문보다
  넓게 펼치는 장치가 있었는데, 목업 안에서는 그게 틀을 뚫었다. 목업 안에서만
  해제했다.
- **BE의 큰 그림에 번호 붙이는 법** → 작성자가 **구성도 노드 이름에 직접**
  번호를 넣는다(가장 단순하고, 렌더러가 위치를 지어내지 않는다).
- **마커 수 상한** → 한 그림당 20개. 넘으면 경고한다.
- **이중 스크롤** → 실측으로 확인했다. 바깥 문서가 껍데기보다 6px 커서 스크롤바가
  둘이었다. 껍데기만 스크롤을 갖도록 못박고, 인쇄 시에는 풀었다.
- **순서도 글자가 묻히는 문제** → 이 프로젝트는 다이어그램을 자체 색 규칙으로
  칠하는데, 그 규칙이 흐름도 전용이었다. 순서도는 밝은 배경을 전제한 기본색이
  그대로 남아 글자가 안 보였다. 순서도 전용 규칙을 같은 자리에 추가했다.
  (중간에 목업 안 다이어그램 배경을 투명하게 만든 것이 이 문제를 키웠다 — 되돌렸다.)

**남은 것**

- **인쇄(PDF)에서의 모습**은 아직 확인 안 됨. 인쇄 시 사이드바를 그림 아래로
  내리도록 규칙은 넣었으나, 실제 인쇄로 눈으로 본 것은 아니다.
- **나머지 영역(인프라·데이터·운영)** 은 이번 범위 밖 — FE/BE에서 골자가
  검증됐으므로 같은 틀로 확장하면 된다.

# Test Plan — 번호식 화면설계서 — 그림이 주인공인 기획서

## Overview

기획서를 열었을 때 **그림이 먼저 보이고 설명이 번호로 그림에 매달리는지**를
검증한다. 새로 생기는 것(마커·사이드바·페이지 코드·BE 큰 그림·밀도 경고·재료
필수화)이 실제로 나오는지, 그리고 **기존 기획서가 하나도 달라지지 않는지**를
같은 무게로 확인한다. 후자가 없으면 이 변경은 기존 문서 30여 건을 조용히
망가뜨릴 수 있다.

새 검사는 `core/tests/test-deck-numbered-spec.sh` 에 모으고, 기존 deck 계약
(`core/tests/test-deck-doc.sh`)은 **수정하지 않고 그대로 통과**해야 한다.

## Test scenarios

### T1. 번호 마커가 그림 위에 표시된다 (FE)

- **Setup**: 화면 목업 블록을 담은 임시 마크다운을 만든다. 컴포넌트 3개에 각각
  번호 1·2·3을 부여한다 (예: 이메일 입력칸, 비밀번호 입력칸, 약관 체크박스).
- **Run**: 그 파일로 기획서를 만든다 (문서 형태, 원문 패널 제외 렌더로 검사해
  원문 마크다운 쪽 문자열에 우연히 걸리지 않게 한다).
- **Expected**: 목업 안에 번호 마커 1·2·3이 각 컴포넌트에 붙어 렌더된다.
- **Pass criterion**: 렌더 결과에서 마커 요소 3개가 확인되고, 각 마커의 번호가
  1·2·3이다.

### T2. 액션 요소는 문자 마커로 구분된다 (FE)

- **Setup**: T1 파일에 버튼 2개를 추가하고 각각 문자 마커 A·B를 부여한다.
- **Run**: 기획서를 만든다.
- **Expected**: 버튼에는 숫자가 아니라 문자 마커 A·B가 붙는다. 숫자 마커와
  문자 마커가 서로 다른 계열로 구분된다.
- **Pass criterion**: 문자 마커 A·B가 렌더되고, 숫자 마커 집합과 겹치지 않는다.

### T3. 번호별 상세가 그림 오른쪽에 붙는다 (FE — 역할 + 액션 두 묶음)

- **Setup**: T2 파일에 번호별 상세를 쓴다 — 1·2·3 에는 컴포넌트 역할(예:
  "이메일 입력칸: 320자 초과 입력 막음, 포커스 아웃 시 형식 검사"), A·B 에는
  액션 동작(예: "회원가입 버튼: 모든 필수 항목 충족 시 활성화").
- **Run**: 기획서를 만든다.
- **Expected**: 그림 옆에 상세 목록이 **역할 묶음**과 **액션 묶음**으로 나뉘어
  렌더된다. 각 항목이 자기 마커 번호를 달고 있다.
- **Pass criterion**: 역할 묶음에 1·2·3 항목이, 액션 묶음에 A·B 항목이 각각
  들어 있고, 작성한 설명 문구가 그대로 나온다.

### T4. 지어내지 않는다 (충실도)

- **Setup**: 컴포넌트 3개 중 **2개에만** 번호별 상세를 쓴다 (1·2만, 3은 비움).
- **Run**: 기획서를 만든다.
- **Expected**: 3번에 대한 설명이 **비어 있거나 생략**된다. 렌더러가 "3번은
  아마 이런 역할" 같은 문구를 만들어내지 않는다.
- **Pass criterion**: 렌더 결과의 상세 묶음에 작성하지 않은 3번 설명 텍스트가
  존재하지 않는다.

### T5. 페이지 이름과 식별 코드가 그림 위에 나온다

- **Setup**: 화면 목업에 페이지 이름("회원가입 페이지")과 식별 코드
  ("FO-SU-02-01")를 부여한다.
- **Run**: 기획서를 만든다.
- **Expected**: 그림 위쪽에 페이지 이름과 식별 코드가 함께 표시된다.
- **Pass criterion**: 두 값이 모두 렌더 결과에 나타나며, 목업 프레임 바깥이
  아니라 해당 화면 블록에 속해 있다.

### T6. 이동 대상 상호참조가 표현된다

- **Setup**: 액션 상세에 이동 대상 코드를 쓴다 (예: "회원가입 완료 시
  FO-SU-02-02 로 이동").
- **Run**: 기획서를 만든다.
- **Expected**: 이동 대상 코드가 액션 설명 안에 그대로 표시된다.
- **Pass criterion**: 해당 코드 문자열이 액션 묶음 안에서 확인된다.

### T7. BE — 화면이 없는 계획도 같은 골자로 그려진다

- **Setup**: 화면 목업 없이 구성도(다이어그램)를 담은 마크다운을 만들고, 그
  구성 요소에 번호를 붙인 뒤 번호별로 API·함수 역할을 쓴다 (예: "1. 인증 API —
  이메일·비밀번호를 받아 토큰을 돌려준다").
- **Run**: 기획서를 만든다.
- **Expected**: 큰 그림(구성도) 옆에 **FE와 같은 형태의** 번호별 상세가 붙는다.
- **Pass criterion**: 구성도가 렌더되고, 그 옆 상세 묶음에 번호별 API·함수 설명이
  들어 있으며, FE 사례(T3)와 **같은 구조**(같은 사이드바 형태)로 렌더된다.

### T8. 마커 없는 기존 목업은 지금과 똑같이 렌더된다 (하위 호환 — 회귀 방지)

- **Setup**: 마커·상세·페이지 코드가 **전혀 없는** 기존 형태의 화면 목업
  마크다운을 준비한다.
- **Run**: 변경 전후로 같은 입력을 렌더해 결과를 비교한다. (변경 전 결과는
  현재 코드로 미리 만들어 보관한다.)
- **Expected**: 결과가 **동일**하다. 빈 사이드바나 빈 마커 자리가 생기지 않는다.
- **Pass criterion**: 두 렌더 결과의 본문이 일치한다.

### T9. 그림 없는 기획서는 경고로 드러난다

- **Setup**: 그림(화면 목업·다이어그램)이 하나도 없는 글만 있는 마크다운을
  준비한다.
- **Run**: 기획서를 만든다.
- **Expected**: 품질 검사 경고에 **그림이 없다**는 항목이 나온다. 그래도
  기획서 파일은 정상적으로 만들어진다 (막지 않는다).
- **Pass criterion**: 경고 출력에 해당 항목이 존재하고, 종료 코드는 0이며,
  결과 HTML 파일이 생성된다.

### T10. 그림이 있으면 그 경고는 뜨지 않는다 (거짓 경고 방지)

- **Setup**: 다이어그램이 하나 있는 마크다운을 준비한다.
- **Run**: 기획서를 만든다.
- **Expected**: 그림 없음 경고가 **뜨지 않는다**.
- **Pass criterion**: 경고 출력에 해당 항목이 없다.

### T11. 계획 작성 지침이 양식 재료를 요구한다

- **Setup**: 계획 작성 지침 문서를 대상으로 한다.
- **Run**: 지침에 양식 재료(큰 그림 + 번호별 상세) 요구와 **빠졌을 때 경고하고
  진행**한다는 규칙이 명시돼 있는지 확인한다.
- **Expected**: 두 규칙이 모두 문서에 존재한다. "재료 없으면 중단"이라는 문구는
  없어야 한다 (막지 않기로 한 결정).
- **Pass criterion**: 요구 규칙과 경고-진행 규칙이 확인되고, 중단 규칙은 없다.

### T12. 기존 deck 계약이 그대로 통과한다 (회귀)

- **Setup**: 없음.
- **Run**: 기존 deck 문서 테스트와 정적 다이어그램 테스트를 그대로 실행한다.
- **Expected**: 전부 통과. 기존 테스트 파일은 수정되지 않았다.
- **Pass criterion**: 두 테스트 스크립트가 exit 0.

### T13. 아카이브된 기획서를 다시 만들어도 지금과 같이 열린다

- **Setup**: 아카이브된 계획 폴더 하나(예: 최근 것)를 고른다.
- **Run**: 그 폴더로 기획서를 다시 만든다.
- **Expected**: 정상적으로 만들어지고, 새 양식 때문에 깨지거나 빈 사이드바가
  끼어들지 않는다.
- **Pass criterion**: 생성이 exit 0 이고, 결과에 빈 상세 사이드바가 없다.

### T19. 검증 메시지 표가 그림 아래에 나온다

- **Setup**: 화면 목업에 검증 규칙 2건을 쓴다. 한 건은 여러 번호에 걸치게 한다
  (예: 이메일 형식 오류 — 입력칸 ①과 제출 버튼 Ⓐ 양쪽).
- **Run**: 기획서를 만든다.
- **Expected**: 그림 아래에 표가 나오고, 머리글은 체크 시점 / 조건 / 메시지 /
  노출 유형이며, 여러 번호에 걸친 규칙이 한 행에 그 번호들을 함께 표시한다.
- **Pass criterion**: 표가 렌더되고 규칙 수만큼 행이 있으며, 여러 번호 표기가 보인다.

### T20. 컴포넌트 상태 변형이 그림 아래 띠로 나온다

- **Setup**: 같은 번호의 컴포넌트에 상태 2개(기본 / Invalid)를 쓴다.
- **Run**: 기획서를 만든다.
- **Expected**: 그림 아래에 상태 띠가 나오고, 각 상태에 이름과 번호가 붙는다.
- **Pass criterion**: 상태 칸이 쓴 개수만큼 렌더된다.

### T21. 번호별 상세가 파이프라인 단계와 이어진다

- **Setup**: 번호별 상세에 파이프라인 단계 이름을 단다 (기능 2개 + 액션 1개).
- **Run**: 기획서를 만든다.
- **Expected**: 각 항목 제목 옆에 단계 이름 태그가 붙는다.
- **Pass criterion**: 단계 태그가 3개 렌더되고 단계 이름이 그대로 나온다.

### T22. 마커를 안 쓰면 자동으로 번호가 붙는다 (기본 동작)

- **Setup**: 컴포넌트에 번호를 **하나도 쓰지 않은** 화면 목업을 만든다. 캡션
  (헤더)과 입력칸 2개, 버튼 2개를 넣는다.
- **Run**: 기획서를 만든다.
- **Expected**: 입력칸은 1·2, 버튼은 A·B를 자동으로 받는다. **캡션은 번호를 받지
  않는다** (받으면 실제 항목의 번호가 밀린다). 짝 검사가 오탐 경고를 내지 않는다.
- **Pass criterion**: 마커가 정확히 4개이고 숫자·문자 계열이 각각 맞으며,
  "그림에 없는 번호" 경고가 뜨지 않는다.

### T23. 자동 번호를 끌 수 있다

- **Setup**: T22 문서에 자동 번호 끄기를 지정한다.
- **Run**: 기획서를 만든다.
- **Expected**: 마커가 하나도 붙지 않는다. 검증 표 등 나머지는 그대로 나온다.
- **Pass criterion**: 마커 0개, 검증 표는 존재.

### T24. 스크롤 영역은 하나뿐이다 (이중 스크롤 금지)

- **Setup**: 기획서 하나를 만든다.
- **Run**: 결과 문서의 스크롤 설정을 확인한다.
- **Expected**: 문서 껍데기 안쪽 한 곳만 스크롤한다. 그 뒤의 바깥 문서는
  스크롤하지 않는다(스크롤바가 하나만 보인다). 인쇄할 때는 이 제약이 풀려
  내용이 잘리지 않는다.
- **Pass criterion**: 바깥 문서 스크롤 차단과 스크롤 체이닝 차단이 확인되고,
  안쪽 스크롤 영역은 그대로이며, 인쇄 규칙에 되돌림이 들어 있다.

### T25. BE 최상단에 "어느 화면이 부르는가"가 나온다

- **Setup**: BE 화면설계서에 호출 화면 1건을 쓴다 (화면 이름·코드·요소·시점).
- **Run**: 기획서를 만든다.
- **Expected**: 표가 **그림보다 위에** 나온다. 백엔드 독자의 첫 질문이 "누가 나를
  부르나"이기 때문이다.
- **Pass criterion**: 표의 내용이 모두 렌더되고, 위치가 그림보다 앞선다.

### T26. 큰 그림을 여러 장(구성 + 순서) 그릴 수 있다

- **Setup**: 큰 그림을 2장 쓴다 — 구성도 하나, 순서도 하나. 각 장에 이름을 단다.
- **Run**: 기획서를 만든다.
- **Expected**: 두 장이 모두 렌더되고 각 장에 이름표가 붙는다.
- **Pass criterion**: 다이어그램 2개, 이름표 존재, 순서도 문법이 그대로 실린다.

### T27. 상태 띠를 테이블 스키마로 쓸 수 있다

- **Setup**: 상태 띠 제목을 "데이터 모양 (테이블 스키마)"로 바꾸고, 표의 컬럼과
  비고를 담은 카드를 1장 쓴다.
- **Run**: 기획서를 만든다.
- **Expected**: 바꾼 제목이 나오고 FE 기본 제목("컴포넌트 상태")은 나오지 않는다.
- **Pass criterion**: 제목이 교체되고 컬럼 내용이 렌더된다.

### T28. 실패·응답 표를 직접 정한 컬럼으로 쓸 수 있다

- **Setup**: 검증표를 컬럼 직접 지정 형태로 쓴다 (번호 / 조건 / 응답 / 본문·메시지
  / 기록·데이터 영향), 규칙 2건.
- **Run**: 기획서를 만든다.
- **Expected**: 바꾼 제목과 컬럼으로 표가 나오고 규칙이 2행이다.
- **Pass criterion**: 제목·컬럼이 그대로이고, 해당 표의 행이 정확히 2개다
  (같은 표 부품을 쓰는 호출 화면 표와 섞어 세지 않는다).

### T29. 순서도 글자가 배경에 묻히지 않는다 (대비)

- **Setup**: 없음 — 렌더러의 색 규칙을 대상으로 한다.
- **Run**: 순서도 요소별 색 규칙이 있는지 확인한다.
- **Expected**: 메시지 글자, else 분기 라벨, 참여자 상자에 각각 규칙이 있다.
- **Pass criterion**: 세 규칙이 모두 존재한다.

## Pass criteria

- 위 블록 exit 0.
- T8(하위 호환)과 T12(기존 계약)가 통과 — 기존 기획서가 달라지지 않았다.
- T4(지어내지 않음)가 통과 — 결정적 변환 원칙이 지켜졌다.
- FE 예시(T1–T6)와 BE 예시(T7)를 **실제로 열어 눈으로 확인** — 그림이 먼저
  보이고 설명이 번호로 그림에 매달려 있다.
