## 1. 문제

- 상황: 프로젝트에서 같은 작업이 되풀이될 때마다 모델이 처음부터 길을 정해 토큰을 쓴다. 스킬로 만들어도 모델이 그 글을 읽는 순간 똑같이 든다(2026-11-24 대화).
- 기대: 정해진 흐름은 작은 sh(톱니)가 돌고, 모델은 판단이 필요한 단계의 글과 앞 단계 결과만 읽는다. 그 단위들은 호스트 스킬 폴더가 아니라 프로젝트 scv 안에 있다.
- 실제: SCV 에 그런 단위를 두고 이어 돌리는 장치가 없다. 가장 비슷한 routine 은 할 일과 지킬 선만 적고 길은 모델이 매번 정한다(core/protocols/routine.md).
- 재현 조건: 같은 종류의 작업을 두 번 시키면, 두 번 모두 모델이 단계를 새로 정하고 중간 과정을 모두 읽는다.

## 6. 해결과 검증

- 해결책과 고른 이유: 톱니(아주 작은 sh — scv/gears/teeth 한 곳, 설명 · 예시는 톱니 사전)와 기어(스킬 — GEAR.md 맨 위 flow 줄로 톱니를 잇고, 글은 판단 단계 @ 만)를 두고, 실행기가 톱니는 직접 돌리고 @ 에서만 그 기어의 글과 앞 결과를 넘긴다. 처음에는 합성을 따로 둔 순서 파일에 적었는데, 실제로 돌린 것을 본 사용자가 'sh 는 순수함수처럼 아주 작게, 스킬에서 합성함수처럼 드러내 쓰기'를 요구해 다시 짰다. 밖으로 나가는 톱니는 선택 창의 '실행' 답을 훅이 적은 뒤에만 돈다 — 모델이 묻지 않고 넘어가지 못하게.
- 고치기 전후 값: 전: 같은 작업을 시킬 때마다 모델이 단계를 새로 정하고 중간 과정을 모두 읽는다. 후(릴리스 노트 예시, 이 저장소의 실제 커밋): 톱니 셋이 돈 뒤 모델이 읽은 것은 기어의 글 6줄과 앞 단계 결과 12줄, 돌려준 것은 요약 4줄 — 톱니 본문 · 톱니 사전 · 중간 결과는 읽지 않았다. 시험 25개 통과(맥 bash 5 · 맥 bash 3.2 + UTF-8 · 리눅스), 명령 22 → 23. 따로 한 검토가 찾은 결함 10건 가운데 9건을 고쳤다 — 가장 무거운 것은 밖으로 나가는 톱니가 확인 없이 도는 길 넷(이름이 겹친 기어 폴더 · 사전의 중복 항목 · 거절을 실행으로 읽는 답 · 잘못 적힌 표시)이었고, 모두 시험 T19 ~ T21 로 고정했다. 남긴 1건: 예시의 끝 줄바꿈은 견주지 않는다(문서에 적음).
- 부작용과 회귀 시험: 부작용: 톱니의 설명을 sh 안이 아니라 톱니 사전에 둔다(코드 주석 금지 규칙 때문) — 본문과 사전이 어긋날 수 있어 검사가 양쪽을 맞춰 본다. 검사는 순수 톱니를 실제로 돌린다. 선택 도구가 없는 호스트에서는 밖으로 나가는 톱니를 돌릴 수 없다. 순수 톱니에는 파일을 바꾸거나 다른 코드를 돌리는 명령을 둘 수 없다 — 낱말 무늬로 잡으므로 전부 잡지는 못한다. 회귀 시험: core/tests/test-gear-run.sh T1 ~ T25, 명령 개수 시험 넷.

## 7. 배운 것

- 다음에 같은 문제를 만나면 진단하는 법: 기어가 기대와 다르게 돌면 gear.sh check 부터 — 사전과 파일, 흐름, 예시를 한 번에 본다. 톱니 하나는 gear.sh run <톱니> 로 따로 돌려 본다. 확인 답이 안 먹으면 질문 글 끝에 확인 표(표:단계)가 그대로 들어갔는지, 답이 정확히 "실행"인지, 실행 상태 폴더(scv/journal/.gear-run)를 훅과 같은 자리로 보고 있는지 본다.
- 다른 곳에도 쓸 수 있는 것: 글 표기를 실행하지 않고 푸는 함수(scv_gear_lit_decode), 사전의 예시를 실제로 돌려 맞춰 보는 검사, '멈추고 표를 주고 이어 가는' 실행 방식은 다른 단계형 명령에도 쓸 수 있다. 사용자의 선택 답을 훅이 적고 스크립트가 그 기록을 요구하는 방식은 다른 위험한 동작의 확인에도 쓸 수 있다. 배운 것: "아니면 그냥 돌린다"로 짠 판정은 잘못 적힌 값에서 열린다 — 아는 값일 때만 돌리게 짠다. 내 시험이 다 통과해도 다른 눈의 검토 한 번이 확인 없이 도는 길 넷을 찾았다.
