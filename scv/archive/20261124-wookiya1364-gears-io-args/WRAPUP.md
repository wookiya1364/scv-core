# 마무리 보고 — 기어의 입력 · 출력을 종류 이름 + 예시로 보이고, 이름 붙은 인자로 같은 기어를 다르게 쓰기 + 글 대신 그림으로 보여 주기

<!-- 계획을 세울 때 아는 만큼(적어도 1번) 채우고, 일이 끝난 뒤 모든 칸을 채운다.
     고장을 고치는 계획이 아니면 2 ~ 5번은 묶음마다 "해당 없음 — 이유" 한 줄로 건너뛴다.
     1 · 6 · 7번은 모든 계획이 채운다. 빈 칸이 있으면 보관되지 않는다. -->

## 1. 문제

- 상황: 기어 파일 맨 위에는 흐름 · 하는 일 · 낱말만 있어, 합성 순서는 보이지만 그 기어가 무엇을 받아 무엇을 돌려주는지는 파일에도 목록에도 없다. 넣을 수 있는 입력은 표준 입력 하나뿐이다(2026-11-24 대화, 0.100.0).
- 기대: 기어 파일과 목록에서 값의 종류 이름과 실제 입력 예 → 출력 예가 보이고, 같은 기어를 값만 바꿔(예: 12개 → 30개) 다시 쓸 수 있다.
- 실제: 기어의 입력 · 출력은 색인 파일에만 계산돼 있다(예시 기어는 `none → notes`). 개수 같은 조절 값이 톱니 안에 박혀 있어(예시 톱니는 12개 고정) 값을 바꾸려면 톱니를 새로 써야 한다(2026-11-24 확인: 목록 출력 · 색인 파일 · 톱니 파일).
- 재현 조건: 0.100.0 에서 기어 목록을 내면 기어 줄에 이름 · 하는 일 · 흐름만 나온다. 실행 명령에 `count=30` 같은 낱말을 붙이면 아무 말 없이 무시되고 톱니는 12개 그대로 돈다(2026-11-24 시험용 프로젝트에서 확인).
- (둘째 부분) 상황: 순서 · 갈래 · 전후 비교를 글로만 설명하면 읽는 데 오래 걸린다. 같은 계획 요약을 흐름도와 차트로 보여 주자 사용자가 "글보다 훨씬 빨리 이해된다"고 했다(2026-11-24 대화).
- (둘째 부분) 기대: 흐름 · 구조 · 수치 비교를 설명할 때는 그림이 먼저 나오고, 그림 도구가 없는 곳에서는 화살표 한 줄과 표로 나온다. 짧은 답은 글 그대로다.
- (둘째 부분) 실제: SCV 의 글쓰기 규칙에 그림에 대한 말이 없다(2026-11-24 확인: 글쓰기 규칙 문서에서 그림 · 차트 낱말 0건). 모델이 그림을 쓰는지는 그때그때 다르다.
- (둘째 부분) 재현 조건: 흐름이나 전후 비교를 묻는 요청을 하면, 사용자가 그림을 따로 청하지 않는 한 글과 표만 나온다.

## 2. 관찰

해당 없음 — 고장을 고치는 계획이 아니라 있는 기능을 넓히는 일이다

## 3. 가설

해당 없음 — 원인을 찾는 일이 아니라 가설을 세우지 않았다

## 4. 실험

해당 없음 — 원인 실험이 없다. 검증은 6번에 적는다

## 5. 원인

해당 없음 — 고장이 아니라 원인이 없다

## 6. 해결과 검증

- 해결책과 고른 이유: 기어 글 맨 위에 값의 종류 이름(in · out)과 실제 예시(예)를 함께 적게 하고, 인자를 사전의 기본값 → 기어 글 → 실행 때 준 값 순으로 정하게 했다. 종류 이름만 적으면 "항상 이 값이 나온다"로 읽힌다는 사용자 지적 때문에 예시를 따로 뒀고, 조절 값이 톱니 안에 박혀 있으면 값만 다른 요청마다 톱니를 새로 써야 해서 인자를 넣었다. (둘째 부분) 글쓰기 규칙 10조와 매 턴 글의 한 구절, 직전 답의 그림 판정과 다음 턴 알림 한 줄 — 규칙만 적으면 긴 세션에서 흐려진 적이 있어 알림을 붙였고, 틀린 알림의 값이 작도록 규약은 다시 싣지 않게 했다.
- 고치기 전후 값: 모르는 인자를 준 실행은 말없이 무시(12개 그대로) → 종료 코드 2 와 쓸 수 있는 이름. 기어 목록 줄은 이름 · 하는 일 · 흐름 → 값 · 인자 추가. 같은 기어에 count 를 주지 않으면 4줄, count=2 면 2줄(시험용 프로젝트 실제 실행). 기어 시험 25개 → 43개, 그림 규칙 시험 0 → 9개. 실행 10번 2.22초 → 2.92초, 검사 5번 2.46초 → 3.41초(인자 없는 프로젝트, 같은 기계 · 바쁜 상태). 그림 알림: 실제 세션 기록 808턴에서 11번(맞음 8 · 틀림 3 — 판정은 Claude).
- 부작용과 회귀 시험: 실행 한 번이 약 1.3배 느려졌다(인자가 없으면 인자 계산을 건너뛰게 한 뒤의 값 — 그 전에는 기어 시험 전체가 29초 → 101초였고 건너뛰게 한 뒤 73초). 만든 사전은 인자가 있는 줄에 여덟째 칸이 생긴다. 턴 끝 훅을 고쳐서 "턴 끝 훅이 커밋된 것과 같은가"를 보는 시험 하나가 커밋 전에는 걸린다(커밋된 상태로 도는 리눅스에서는 통과). 관련 시험 19개를 맥 · 맥 옛 셸 · 리눅스에서 돌렸다 — 맥 18개 통과(위의 1개 제외), 옛 셸 52줄 통과, 리눅스 19개 통과.

## 7. 배운 것

- 다음에 같은 문제를 만나면 진단하는 법: 기어가 무엇을 받고 내는지 모르겠으면 목록의 값 · 인자 칸과 기어 글의 예 줄을 먼저 본다. 인자가 안 먹으면 종료 코드 2 의 오류 글에 쓸 수 있는 이름이 나온다. 시험이 갑자기 느려지면 실행 한 번을 고치기 전 코드와 같은 프로젝트에서 10번씩 재어 견준다(이번에 그렇게 찾았다).
- 다른 곳에도 쓸 수 있는 것: 맥의 sed 는 한 줄짜리 입력에 N 을 쓰면 아무것도 내지 않는다 — 줄 잇기는 셸의 글 바꾸기로 한다. 끝에 줄바꿈이 없는 파일을 read 로 읽으면 마지막 줄을 놓친다. 선택 창은 바로 앞에 쓴 글을 가리고 원격에서는 터미널 탭을 못 본다 — 판단에 필요한 숫자는 질문 글 안에 넣고 결과는 대화와 파일로 보낸다. 알림을 더할 때는 실제 기록으로 뜨는 횟수와 틀린 횟수를 먼저 재서 보여 주고 켠다.
