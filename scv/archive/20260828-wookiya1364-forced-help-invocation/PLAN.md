# 일반 대화에서 scv:help 를 실제로 강제한다 — 표시줄 + 점층 강화 되돌림

## Summary

일반 대화 턴에서 help 액션이 **실제로 호출될 때까지** 응답 종료를 되돌려 세운다.
지금은 매 턴 "help 로 라우팅하라"는 글만 주입되고 호스트가 그것을 강제할 수단이
없어, 모델이 대부분 흘린다. 되돌림 회차마다 지시 강도를 올리고, 화면에는 강제
상태와 이번 턴의 되돌림 횟수를 한 줄로 띄워 "되는지 안 되는지 구분이 안 간다"는
문제를 함께 없앤다.

## Goals / Non-Goals

- **Goals**
  - 일반 대화 턴에서 help 액션 호출을 **기계적으로** 강제한다 (안내가 아니라 되돌림).
  - 되돌림 회차가 커질수록 사유 문구의 강도를 올린다 — 같은 문구를 반복해 같은
    실패를 반복하지 않는다.
  - 강제 동작 여부와 이번 턴의 되돌림 횟수를 사용자가 **화면에서 바로 구분**한다.
  - 호출 여부 판정에 **위조 불가능한 근거**만 쓴다 — 호스트가 직접 찍은 영수증.
  - 강제를 별도 스위치로 분리해, 되돌림만 끄고 안내는 남기는 중간 단계를 만든다.
  - 호스트 상한에 걸려 끝내 실패한 턴을 팀 기록에 한 줄 남긴다.

- **Non-Goals**
  - help 프로토콜 본문 변경 — 라우팅과 강제만 다루고 Mode 판정은 기존 문법에 맡긴다.
  - 다른 SCV 액션(promote/work/…)의 호출 강제 — 이번 범위는 help 하나다.
  - 호스트의 연속 차단 상한을 우리가 조절하는 것 — 환경변수를 읽지도 쓰지도 않는다.
  - 래퍼별 훅 등록 방식 변경 — 필요한 세 이벤트는 이미 등록돼 있다.
  - 하위 작업자(서브에이전트) 턴 강제 — 이미 지시를 받고 도는 중이라 대상이 아니다.
  - 영수증 저장소의 형식·수명·권한 정책 변경 — 읽는 소비자만 하나 늘린다.

## Approach Overview

호스트를 직접 조사해 확인한 사실이 설계의 출발점이다.

1. 사용자 프롬프트 훅은 프롬프트를 **바꿔치기할 수 없다**. 컨텍스트에 글을 덧붙이는
   경로 하나만 있다. 그래서 "부탁"이 상한이었다.
2. 스킬 호출을 강제하는 장치는 호스트에 **없다**.
3. 그러나 응답 종료 훅은 **차단 결정과 사유**로 모델을 되돌려 세울 수 있다.
4. 호스트에는 연속 차단 상한이 있고 **기본값은 8**이다. 넘기면 호스트가 경고와 함께
   턴을 스스로 끝낸다 — 우리가 상한을 두지 않아도 세션이 갇히지 않는다.
5. 스킬 호출 직전 훅에서 **영수증**이 이미 발행되고 있다. 호스트가 보고한 액션 id 를
   그대로 적는 기록이라 모델이 위조할 수 없다 — 가드가 이 성질에 기대고 있고,
   호출 여부 판정도 같은 성질에 기대면 된다.

따라서 세 훅이 각각 한 가지를 맡는다. 새 표시 장치는 만들지 않는다.

- **사용자 프롬프트 훅** — 표시줄과 명령형 안내를 내보내고, 이번 턴의 시작 시점을
  영수증 줄 수로 찍어 둔다. 되돌림 횟수도 여기서 0으로 되돌린다. 전체 상태 점검은
  넣지 않는다: 강제가 붙으면 help 가 어차피 돌고, 같은 점검을 한 턴에 두 번 하게
  된다.
- **스킬 호출 직전 훅** — 변경 없음. 이미 help 호출 시 영수증을 발행한다.
- **응답 종료 훅** — 턴 시작 이후 영수증에 help 가 찍혔는지 본다. 찍혔으면 통과.
  없으면 차단 결정을 내고 되돌림 횟수를 1 올린다. 자체 상한은 두지 않는다. 사유
  문구는 회차의 함수다.

판정 자체는 순수하다. 파일과 표준입출력을 만지는 부분은 파이프라인의 양 끝에만 둔다.

## 순수함수 · 파이프라인 (Pure functions & pipeline)

```
flow(
  readTurnFacts,     // 훅 페이로드 + 저장소 → TurnFacts
  classifyTurn,      // TurnFacts → TurnKind
  decideStop,        // (TurnKind, attempts) → Decision
  renderReason,      // (Decision, attempts) → 사유 문구
  emitDecision,      // 사유 문구 → 표준출력 + 횟수 증가
)
```

| # | 단계 | 받는 값 → 돌려주는 값 | 순수/부수효과 |
|---|---|---|---|
| 1 | `readTurnFacts` | 훅 페이로드(JSON) + 설정 + 영수증/턴 상태 → `TurnFacts`(스위치·세션·턴시작표시·영수증줄·이벤트이름) | 부수효과 (입구) |
| 2 | `classifyTurn` | `TurnFacts` → `TurnKind`(`off` / `no-scv` / `subagent` / `unmarked` / `satisfied` / `pending`) | 순수 |
| 3 | `decideStop` | (`TurnKind`, 되돌림 횟수) → `Decision`(`pass` / `block`) | 순수 |
| 4 | `renderReason` | (`Decision`, 되돌림 횟수) → 사유 문구 (회차별 강도) | 순수 |
| 5 | `emitDecision` | 사유 문구 → 표준출력 JSON + 횟수 증가 + 실패 시 기록 한 줄 | 부수효과 (출구) |

사용자 프롬프트 훅도 같은 모양을 쓴다.

```
flow(
  readSettings,      // 설정 파일 → Switches
  markTurnStart,     // (세션, 영수증) → TurnMark
  renderBanner,      // (Switches, TurnMark) → 표시줄 한 줄
  renderDirective,   // Switches → 명령형 안내 블록
  emitLines,         // 두 텍스트 → 표준출력
)
```

- 부수효과 위치: `readTurnFacts` / `readSettings` (읽기), `markTurnStart`,
  `emitDecision`, `emitLines` (쓰기). 가운데 판정·문구 생성 단계는 파일도 시각도
  난수도 만지지 않는다 — 그래서 페이로드와 횟수만 주면 그대로 시험할 수 있다.
- 재사용: 설정 읽기는 기존 설정 라이브러리를 그대로 쓴다. 영수증 경로 계산은 가드가
  이미 하고 있으므로 그 계산을 공용 라이브러리로 뽑아 **가드와 종료 훅이 같은 한
  곳을 쓴다** — 두 벌로 두면 경로 규칙이 조용히 갈라진다.

## Guardrails

- **세션을 막지 않는다.** 잘못된 JSON, 읽기 도구 없음, 저장소 접근 불가, 턴 시작
  표시 없음 — 전부 통과시킨다. 기존 두 훅의 NON-BLOCKING 보장이 이번에도 상한이다.
  이 기능은 편의이지 안전장치가 아니다.
- **턴 시작 표시가 없으면 되돌리지 않는다.** 장치가 고장 났을 때 매 턴 되돌리면
  대화 자체가 못 쓰게 된다. 고장은 열림 쪽으로 넘어간다.
- **영수증 저장소를 우리가 쓰지 않는다.** 발행은 가드만 한다. 종료 훅은 읽기만
  한다. 위조 불가라는 성질은 "모델이 못 쓰는 기록"이라는 데서 나오므로, 소비자가
  쓰기 시작하면 그 성질이 사라진다.
- **호스트 상한을 건드리지 않는다.** 연속 차단 상한 환경변수를 읽지도 쓰지도 않는다.
  마지막 안전망은 호스트 몫으로 남긴다.
- **하위 작업자 턴은 가로채지 않는다.** 종료 이벤트가 하위 작업자의 것이면 즉시
  통과한다.
- **다른 SCV 액션이 도는 턴은 가로채지 않는다.** 이미 액션 프로토콜이 실린 턴을
  끊으면 진행 중인 작업이 깨진다 — 기존 계약 그대로다.
- **호스트 중립.** 핵심부 스크립트는 호스트 이름을 적지 않는다. 이벤트 이름과 결정
  형식은 기존 가드 훅이 이미 쓰는 방식(래퍼가 모드를 주입하고 템플릿은 계약된 모양만
  출력)을 따른다.
- **whitespace 계약**: 파일 끝 빈 줄 금지, 줄 끝 공백 금지.

## 성공지표 (Metrics)

| 지표 | 지금 (baseline) | 목표 (target) | 어떻게 재나 |
|---|---|---|---|
| 일반 대화 턴에서 help 가 실제로 호출된 비율 | 측정된 값 없음. 사용자 체감으로 "안 뜰 때가 더 많다" | 100% — 되돌림이 보장한다 | 팀 기록의 강제 실패 줄 수 ÷ 강제 대상 턴 수 |
| 호출까지 걸린 되돌림 회차 | 해당 없음 (되돌림 자체가 없었음) | 평균 2회 이하 | 종료 훅이 올리는 횟수, 실패 기록에 함께 남는다 |
| 호스트 상한에 걸려 끝내 실패한 턴 | 해당 없음 | 0에 수렴 | 팀 기록의 실패 줄 개수 |
| 턴당 추가되는 컨텍스트 | 라우팅 안내 약 8줄 | 표시줄 1줄 + 안내 약 8줄 (전체 상태 점검 6KB 주입 대비 매우 작게 유지) | 프롬프트 훅 출력 바이트 수 |
| 사용자가 동작 여부를 화면에서 구분 가능한가 | 불가 — 첫 문제 제기의 원인 | 매 턴 가능 | 표시줄 유무 |

실패 회차가 계속 높게 나오면 그것이 사유 문구를 손볼 근거다 — 그래서 실패를 기록에
남긴다.

## 예외처리 (Edge cases)

- **턴 시작 표시가 없다** (프롬프트 훅이 안 돌았거나 못 썼다) → 되돌리지 않는다.
  고장은 열림 쪽으로 넘어간다.
- **영수증 저장소를 읽을 수 없다** → 되돌리지 않는다. 판정 근거가 없는데 막으면
  대화 자체가 못 쓰게 된다.
- **지난 턴의 help 영수증이 남아 있다** → 통과 근거가 되지 않는다. 턴 시작 표시
  이후의 줄만 본다.
- **하위 작업자 턴** → 가로채지 않는다. 이미 지시를 받고 도는 중이다.
- **이미 다른 SCV 액션이 도는 턴** → 가로채지 않는다. 영수증에 다른 액션 id 가
  찍혀 있는 것으로 판별한다.
- **help 가 호출됐지만 오류로 끝났다** → 통과시킨다. 부르면 통과가 이번 계약이고,
  오류 자체는 help 가 보고한다.
- **호스트가 상한에서 턴을 끊었다** → 그대로 넘어간다. 다음 턴 시작에 실패 한 줄을
  남기는 것으로 끝낸다.
- **두 스위치가 서로 다른 상태다** (라우팅 켬 + 강제 끔) → 안내는 나오고 되돌림만
  없다. 두 스위치는 독립이다.
- **읽기 도구(JSON 파서)가 기계에 없다** → 기존 훅과 같이 조용히 통과한다.

## Exit criteria

- TESTS.md 시나리오가 모두 통과한다.
- 기존 `test-journal.sh`, `test-always-on.sh`, `test-guard.sh`,
  `test-guard-consistency.sh`, `test-settings.sh` 가 계속 통과한다.
- 강제 스위치가 켜진 상태에서 help 를 부르지 않은 턴은 **한 번도 그냥 끝나지
  않는다** — 되돌림 결정이 반드시 나온다.
- 같은 턴의 1회차와 3회차 사유 문구가 서로 다르다.
- 화면 표시줄만 보고 강제가 켜져 있는지, 이번 턴에 몇 번 되돌렸는지 알 수 있다.
- 스위치를 끄면 이 기능이 존재하지 않는 것처럼 동작한다 — 표시줄도 되돌림도 없다.
- 호스트 상한에 걸려 실패한 턴이 팀 기록에 한 줄 남는다.
- 템플릿 지문이 갱신돼 있다.

## Suggested path

1. 영수증 경로 계산을 공용 라이브러리로 뽑고, 가드가 그것을 쓰도록 바꾼다
   (동작 불변 — 기존 가드 테스트가 그대로 통과해야 한다).
2. 새 스위치를 설정 등록부와 예시 파일에 올린다 (기존 스위치와 같은 판정 규칙).
3. 사용자 프롬프트 훅에 표시줄·명령형 안내·턴 시작 표시·횟수 초기화를 넣는다.
4. 응답 종료 훅에 판정·회차별 사유·차단 결정·횟수 증가·실패 기록을 넣는다.
5. 새 테스트를 쓰고, 기존 테스트가 모두 초록인지 확인한다.
6. 템플릿 지문을 다시 계산한다.
7. CHANGELOG 를 갱신한다.

## Risks / Open Questions

- **되돌림이 잦으면 대화가 느려진다.** 회차별 강도 상승으로 대개 1~2회에 끝나는 것을
  전제한다. 실패 기록이 쌓이면 문구를 손볼 근거로 쓴다.
- **턴 경계 판정.** 영수증은 세션 단위 누적 기록이라 "이번 턴"은 줄 수 차이로만
  구분된다. 프롬프트 훅이 돌지 않은 경로(예: 호스트가 프롬프트 이벤트를 보내지 않는
  실행 형태)에서는 턴 시작 표시가 없고, 그때는 규칙대로 통과한다.
- **호스트 상한 기본값 의존.** 기본 8은 현재 호스트의 값이다. 값이 바뀌어도 우리
  동작은 그대로이고, 바뀌는 것은 "몇 번째에 호스트가 끊는가"뿐이다. 우리 테스트는
  그 숫자에 기대지 않는다.
- **강제가 켜진 채 help 가 실패하는 경우.** help 자체가 오류로 끝나도 영수증은
  찍히므로 통과한다 — 의도된 동작이다(부르면 통과). 오류 자체는 help 가 보고한다.
