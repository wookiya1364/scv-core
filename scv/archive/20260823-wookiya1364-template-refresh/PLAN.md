# 템플릿 갱신을 내용으로 판단한다

## Summary

SCV 버전을 올렸는데 프로젝트의 템플릿 문서가 그대로 남는 일이 잦다. 원인은 하나다.

**자동 갱신이 번호로만 판단한다.** 프로젝트에 찍힌 템플릿 번호가 배포본 번호보다
낮을 때만 실제로 갱신한다. 릴리스에서 템플릿 파일은 바뀌었는데 템플릿 번호를 안
올리면, 두 번호가 같아서 **아무 일도 일어나지 않는다.**

판단 기준을 번호에서 **내용**으로 바꾼다. 번호를 올리는 걸 잊어도 잡힌다.

그리고 그보다 큰 문제를 같이 고친다 — **갱신이 안 되는 것보다 조용히 안 되는 게
문제다.** 지금도 부분 실패를 말하기는 하는데 표준오류로만 나가서 눈에 안 띈다.

## Goals / Non-Goals

**Goals**

1. 자동 갱신 판단을 템플릿 **내용 지문**으로 바꾼다. 번호 누락으로 건너뛰는 일을 없앤다.
2. 업데이트 명령이 끝난 뒤 갱신이 **바로** 일어나게 한다 (지금은 다음 명령까지 기다림).
3. 갱신이 부분적이거나 아예 못 돌았으면 **반드시 눈에 띄게** 알린다.
4. 판단 로직을 순수함수 하나로 모은다 — 지금은 조건이 여러 줄에 흩어져 있다.

**Non-Goals**

- **편집 중인 파일을 덮어쓰지 않는다.** 지금의 거절 동작을 그대로 둔다. 이건 안전장치다.
- **되돌림 방지를 없애지 않는다.** 배포본이 더 오래됐으면 갱신하지 않는다. 없애면
  두 대의 기계가 서로의 템플릿을 무한히 뒤집는다.
- **번호 통일은 이번에 하지 않는다.** 템플릿 번호를 SCV 번호로 바꾸면 숫자가
  내려가서 지금 비교기가 "오래됨"으로 읽는다. 지문이 자리잡은 뒤에 따로 한다.

## 지금 무슨 일이 벌어지나

자동 갱신은 모든 SCV 명령에서 돈다. 순서는 이렇다.

1. 프로젝트 인덱스에서 찍힌 템플릿 번호를 읽는다.
2. 배포본의 템플릿 번호와 **같으면 그대로 끝낸다.**  ← 여기가 문제
3. 배포본이 더 오래됐으면 끝낸다 (되돌림 방지 — 정당하다).
4. 아니면 동기화를 돌리고, 전부 성공했을 때만 스탬프를 올린다.

2번 때문에, 템플릿 파일이 바뀌어도 번호가 그대로면 영원히 갱신되지 않는다.

## 설계

### 지문

빌드할 때 템플릿 트리 전체의 지문을 하나 만든다. 파일별 해시는 **이미 계산하고
있다** — 그 결과를 경로 순으로 정렬해 한 번 더 해싱하면 끝이다. 새로 만들 게 거의 없다.

지문은 배포본에 번호와 나란히 실린다. JSON 파싱 없이 한 줄로 읽을 수 있게 둔다.

프로젝트 인덱스에는 **마지막으로 맞춘 지문**을 찍는다. 지금 번호를 찍는 자리 옆이다.

### 판단 — 순수함수 하나

```
scv_template_decide <stamped_digest> <payload_digest> <stamped_ver> <payload_ver>
  -> refresh | refresh:version | refresh:unstamped | skip:same | skip:backward
```

규칙은 **세 줄**이다.

- **배포본 번호가 프로젝트보다 오래되면 → 갱신하지 않는다.** (되돌림 방지 유지)
- **지문이 다르면 갱신한다.** 번호가 같아도 갱신한다.   ← 이번 수정의 본체
- **번호가 다르면 갱신한다.** 지문이 같아도 갱신한다.   ← 예전 동작 그대로

**지문은 번호를 대체하지 않고 더한다.** 처음 구현은 지문만 보게 만들었고, 그러자
번호 스탬프만 낡고 내용은 같은 프로젝트가 영영 안 고쳐졌다 — 그 번호를 읽는 다른
코드들이 계속 틀린 값을 본다. 기존 테스트가 이걸 잡았다.

지문 스탬프가 아직 없는 프로젝트(기존 전부)는 "다름" 으로 본다 — 한 번 갱신하고
찍는다. 그 뒤로는 정상 경로다. 되돌림 방지는 이 경우에도 그대로 적용된다.

**지문 없음과 인덱스 손상을 반드시 구분한다.** 지금 코드는 스탬프를 못 읽으면
"손상됐다" 고 보고 멈춘다. 기존 프로젝트는 번호 스탬프는 있고 지문 스탬프만
없는 것이 **정상 상태**다. 이걸 손상으로 읽으면 갱신이 영원히 안 돈다.

- 번호 스탬프 있음 + 지문 스탬프 없음 → **정상. 갱신하고 찍는다**
- 번호 스탬프 없음 → 손상. 지금처럼 안내만 한다
- 템플릿 2.0 이전 → 지금처럼 안내만 한다 (대화형 이전이 필요하다)

이 함수는 파일도 시각도 만지지 않는다. 문자열 넷을 받아 문자열 하나를 낸다.
그래서 조합 18가지를 전수로 검사할 수 있다.

### 업데이트 직후 갱신 — **하지 않기로 했다**

처음에는 업데이트가 끝나면 갱신을 한 번 돌리려 했다. **불가능하고, 억지로 하면
지금보다 나빠진다.**

`core/protocols/update.md` 5항이 이미 이걸 금지하고 있고 이유가 맞다. 플러그인
payload 는 버전별로 캐시되므로, 업데이트 명령이 도는 시점의 세션은 **아직 옛
payload 를 들고 있다.** 거기서 갱신을 부르면 옛 템플릿을 깔아놓고 성공했다고
보고한다 — 조용한 실패보다 나쁘다.

실제 교체는 마켓플레이스 갱신과 재적용으로 일어나는데, 호스트가 슬래시 명령끼리
호출을 허용하지 않으므로 그 사이에 끼어들 자리가 없다. 우회로도 없다.

**대신 다음 명령에서 반드시 닫히게 하고(1단계), 못 닫혔으면 눈에 띄게 말한다
(아래).** 원래 혼선은 "다음 명령을 써도 갱신이 안 되는 것" 이었고 그건 해결됐다.
남은 "업데이트와 갱신 사이에 명령 하나가 낀다" 는 훨씬 작은 문제다.

### 조용한 실패 없애기

지금 부분 실패 보고는 표준오류로만 나간다. 세 가지를 바꾼다.

1. 갱신이 부분적이면 **무엇이 왜 남았는지** 목록으로 보인다 (지금도 하지만 묻힌다).
2. 아예 못 돌았으면 **그 이유를 이름으로** 말한다 — 꺼짐 / 링크 / 구버전 / 스탬프 없음 /
   배포본이 더 오래됨. 지금은 일부만 말한다.
3. 상태 명령이 **현재 어긋남 여부**를 한 줄로 보여준다. 사용자가 언제든 확인할 수 있다.

## 단계

### 1단계 — 지문 산출과 판단 (완료)

- 빌드에서 템플릿 지문을 만들어 배포본에 싣는다.
- 순수 판단 함수를 신설한다.
- 자동 갱신이 그 함수를 쓰게 바꾼다.
- 동기화와 최초 설치가 지문을 찍게 한다.

**완료 판정**: 번호가 같고 템플릿 내용이 다르면 갱신이 돈다. 배포본이 더 오래되면
안 돈다. 기존 테스트 전부 통과. — **충족.** run-dry 972 PASS/0 FAIL(기준선과
동일), test-autosync 통과, 실제 시나리오 확인.

### 2단계 — 업데이트 직후 갱신 (**취소**)

위 "업데이트 직후 갱신" 참조. 호스트 구조상 만들 수 없고, 만들면 옛 템플릿을
깔고 성공을 보고한다.

### 3단계 — 보고 경로 (완료)

- 조용하던 경로 셋을 없앤다: 자동 갱신 꺼둠 / 배포본 파일 누락 / 번호가 빈 값.
- 상태 명령에 어긋남 절을 넣는다 — **어긋났을 때만** 나온다.

**완료 판정**: 안 되는 경우들이 서로 구분되는 문구를 낸다. 멀쩡한 프로젝트는
한 줄도 늘지 않는다. — **충족.**

## 위험과 대응

| 위험 | 대응 |
|---|---|
| **지문이 기계마다 다르게 나온다** | 경로 순 정렬 + 내용만 해싱. 시각·권한·소유자 제외. 테스트로 두 번 계산해 비교 |
| **매 명령마다 지문 계산이 느리다** | 배포본 지문은 빌드 때 미리 계산해 파일로 싣는다. 실행 중엔 문자열 비교 한 번 |
| **되돌림 방지가 깨진다** | 번호 비교를 판단 함수 안에 그대로 남긴다. 전수 검사로 고정 |
| **업데이트 직후 갱신이 편집 중 파일을 건드린다** | 동기화의 거절 동작을 그대로 탄다. 새 경로가 아니다 |
| **래퍼 두 곳이 어긋난다** | 2단계를 래퍼 반영까지 포함해 하나로 본다 |

## 미결 사항

- **래퍼 두 곳 반영.** core 를 벤더링해야 실제 사용자에게 간다.
- **변경 이력.** 이 저장소는 릴리스 커밋에서 쓰는 방식이라 미뤘다.
- **번호 통일.** 템플릿 번호를 SCV 번호로 바꾸면 숫자가 내려가 지금 비교기가
  "오래됨" 으로 읽는다. 지문이 자리잡았으므로 이제 안전하게 할 수 있다 — 별건이다.

## 다음 작업과의 연결

판단 함수가 이 저장소의 **순수함수 두 번째 사례**가 된다. 첫 사례인 설정 조회와
같은 모양이다 — 순수부는 문자열만 다루고, 파일은 바깥 한 줄이 맡는다.

이게 끝나면 설정 이사를 한다. 설정 이사는 템플릿 파일을 바꾸는 작업이라,
**이 작업이 먼저 끝나야 사용자에게 실제로 전달된다.**
