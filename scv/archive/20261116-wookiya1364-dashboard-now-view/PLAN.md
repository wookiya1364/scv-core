# 대시보드 — 지금 하는 일이 늘 보이게 (지금 하는 일 · 뒤에서 도는 일 · 최근 끝난 일)

## Summary

오래 걸리는 일이 뒤에서 도는 동안 대화에는 아무것도 나오지 않고, 대시보드는 "사용자 차례"라고 표시한다. 그래서 사용자는
일이 멈췄는지 도는지 알 수 없어 "지금 뭐 하고 있어?"를 거듭 묻는다(2026-11-16, 두 세션에서 같은 날 일어남).
대시보드에 세 가지가 늘 보이게 한다: **지금 하는 일**(무엇을, 언제부터), **뒤에서 도는 일**(일마다 이름 · 걸린 시간 ·
마지막 진행 줄 · 막대), **최근 끝난 일**(시각과 한 줄 결과). 그리고 도는 일이 있는 동안에는 "사용자 차례"로 바뀌지 않게 한다.

확인한 사실(2026-11-16, 대시보드 코드를 읽음):

- 대시보드는 "뒤에서 도는 일이 있다"를 표시 하나로만 기억하고, **새 턴이 시작될 때마다 그 표시를 지운다**(`hooks/register.tsx` 의
  턴 시작 처리). 뒤의 일이 끝나서 턴이 다시 시작됐다고 가정하기 때문이다. 사용자가 중간에 말을 걸어도 턴이 시작되므로,
  질문 하나에 표시가 지워지고 그 답이 끝나면 "사용자 차례 — 대화창에서 이어서 하라고 말해 주세요"가 된다.
- 표시가 맞게 남아 있을 때도 화면에는 "배경 작업을 기다리는 중 — 끝나면 스스로 이어집니다" 한 줄뿐이다 — 무엇이 얼마나 됐는지 없다.
- 뒤에서 도는 일로 세는 것은 셋뿐이다: 뒤로 보낸 명령, 지켜보기, 스스로 맞춘 깨우기(`hooks/model.ts` 의 `isBackgroundStart`).
  터미널 탭에서 시작한 명령은 세지 않는다.
- 대시보드의 할 일 목록은 `TodoWrite` · `TaskCreate` · `TaskUpdate` 에서만 채워진다(`applyTaskEvent`). 데스크톱 앱이 쓰는
  할 일 목록 도구(`mcp__ccd_turn__update_plan`)는 읽지 않아, 앱에서는 "지금 하는 일"로 쓸 재료가 비어 있다.
- 대시보드는 도구의 결과 글을 받는다(`const ran = await next(e)` 뒤에서 시험 결과를 읽는 코드가 이미 있다). 뒤로 보낸 명령의
  결과 글에는 그 일의 이름표와 출력 파일 위치가 적혀 있다.
- 대시보드는 3초마다 스스로 다시 그리고(`REFRESH_MS`), 파일 읽기와 프로그램 실행 기능을 이미 쓴다.

사용자 결정(2026-11-16, 선택 창): 이 방식으로 계획한다. 보태신 말: "지금 하는 작업이 뭔지 그냥 보였으면 좋겠다. 따로 띄운
터미널 화면처럼 '지금 하는 일'과 시각, '도는 프로세스 수', '최근 끝난 일'이 계속 보이면 안심이 된다. 터미널을 항상 띄우라는
뜻이 아니라, 무슨 작업을 하느라 시간이 걸리는지, 무슨 작업이 되고 있는지를 보고 싶다."

## Goals / Non-Goals

- **Goals**
  - **지금 하는 일**이 늘 보인다 — 한 줄(쉬운 말)과 시작 시각. 턴이 도는 중이든, 뒤의 일을 기다리는 중이든.
  - **뒤에서 도는 일**이 일마다 한 줄로 보인다 — 이름, 걸린 시간, 마지막 진행 줄, 진행 줄에 "10 / 64" · "[4/7]" 꼴이 있으면 막대.
  - **최근 끝난 일**이 시각과 함께 최근 5개까지 보인다 — 실패는 실패라고 적힌다.
  - 뒤에서 도는 일이 하나라도 있으면, 사용자가 중간에 말을 걸어도 "사용자 차례"로 바뀌지 않는다. 목록에서 빠지는 것은 그 일이 끝났을 때뿐이다.
  - 데스크톱 앱의 할 일 목록(`mcp__ccd_turn__update_plan`)이 대시보드의 할 일 목록과 "지금 하는 일"에 실린다.
  - 다른 기기에서 보는 화면(거울 세션)에도 같은 세 가지가 보인다.
- **Non-Goals**
  - 터미널 탭을 자동으로 띄우기 — 사용자가 바란 것은 대시보드에서 보이는 것이다.
  - 명령의 출력 전체 보여 주기 — 마지막 진행 줄 하나만.
  - 휴대폰 알림 더하기 · 바꾸기.
  - 코어의 훅이나 규약 고치기 — 대시보드가 받는 일(도구 호출 · 턴 시작 · 끝)만으로 한다.
  - 코덱스.
  - 앱 자체의 할 일 목록 화면 바꾸기.
  - 릴리스 — 구현 뒤 사용자가 시킬 때 따로 한다.

## Approach Overview

뒤에서 도는 일을 "있다 / 없다" 표시 하나가 아니라 **일의 목록**으로 기억한다. 일 하나는 이름 · 시작 시각 · 출력 파일 위치 ·
마지막 진행 줄 · 상태(도는 중 / 끝 / 실패)를 가진다.

- 시작: 뒤로 보낸 명령 · 지켜보기 · 터미널 탭 명령의 도구 호출이 끝난 뒤, 그 결과 글에서 이름표와 출력 파일 위치를 읽어 목록에 넣는다.
  이름은 명령에 붙인 설명 글을 쓴다(없으면 명령의 앞부분).
- 진행: 3초마다 도는 일의 출력 파일 끝부분을 읽어 마지막 줄을 싣는다. 줄은 한 줄 · 120자로 자른다.
- 끝: 그 일이 끝났다는 알림(끝 알림 글, 멈춤 도구 호출)이 오면 상태를 끝 · 실패로 바꾸고 "최근 끝난 일"로 옮긴다.
- 턴 시작은 더는 목록을 지우지 않는다. "누구 차례인가"는 목록에 도는 일이 남아 있는지로 정한다.
- "지금 하는 일" 한 줄은 재료를 차례로 본다: 할 일 목록의 하는 중인 항목 → 계획의 하는 중인 단계 → 지금 도는 도구의 설명 →
  (턴이 끝났고 도는 일이 있으면) "뒤에서 도는 일을 기다리는 중" → 기본 글.
- 화면: 지금의 "다음 할 일" 줄 위에 세 묶음을 그린다. 도는 일이 없고 끝난 일도 없으면 "지금 하는 일" 한 줄만 보인다.

확인하지 못한 것이 둘 있어, 구현 첫 단계에서 확인한다(결과: 둘 다 앱의 기능 설명서에서 답을 찾았다 — 파일은 프로젝트 밖도 4MB 까지
읽을 수 있고, 끝 알림은 "뒤 작업 알림" 출처가 붙어 온다. 실제 앱에서 해 본 것은 아니다):

1. 대시보드가 프로젝트 폴더 밖에 있는 출력 파일을 읽을 수 있는가 — 안 되면 프로그램 실행으로 끝 몇 줄만 읽는다.
2. 일이 끝났다는 알림이 대시보드에 어떤 일로 닿는가(턴 시작의 글인가, 받은 글인가) — 닿지 않으면 출력 파일이 한동안
   바뀌지 않는 것을 "끝난 듯"(회색)으로 보이고, 다음 턴의 도구 호출에서 확정한다.

## 순수함수 · 파이프라인 (Pure functions & pipeline)

```
// 일이 생기고 끝나는 길
flow(
  jobStartOf,      // (도구 이름, 입력, 결과 글, 시각) → 일의 시작 | 없음
  jobEndOf,        // (도구 이름, 입력) 또는 (받은 글) → 일의 끝 | 없음
  applyJobEvent,   // (일 목록, 시작 | 진행 | 끝) → 일 목록
  applyDone,       // (끝난 일 목록, 끝난 일 한 줄) → 끝난 일 목록(최근 것만)
)

// 3초마다 도는 길
flow(
  readJobTails,    // 도는 일들 → 일마다 출력의 끝부분        (부수효과: 파일 읽기)
  progressOf,      // 출력의 끝부분 → 마지막 진행 줄 · 한 것 / 전체
  applyJobEvent,   // (일 목록, 진행) → 일 목록
)

// 그리는 길
flow(
  applyTaskEvent,  // (할 일 목록, 도구 이름, 입력) → 할 일 목록 (앱의 할 일 도구도 읽음)
  nowLine,         // (할 일 목록, 계획 단계, 지금 도구, 일 목록, 턴 상태) → 지금 하는 일 한 줄 · 시작 시각
  turnStateOf,     // (턴 상태, 멈춤, 보조 작업 수, 도는 일 수, 깨우기 표시) → 일하는 중 | 뒤의 일 기다림 | 사용자 차례
  nowBlock,        // (지금 하는 일, 일 목록, 끝난 일 목록, 지금 시각) → 화면에 그릴 줄들
)
```

| # | 단계 | 하는 일 | 받는 값 → 돌려주는 값 | 순수/부수효과 |
|---|---|---|---|---|
| 1 | `jobStartOf` | 도구 호출이 뒤에 일을 남겼는지 보고 그 일의 이름 · 출력 위치를 뽑음 | (도구, 입력, 결과 글, 시각) → 일의 시작 또는 없음 | 순수 |
| 2 | `jobEndOf` | 끝 알림 글이나 멈춤 호출에서 어느 일이 어떻게 끝났는지 뽑음 | (도구, 입력) 또는 (받은 글) → 일의 끝 또는 없음 | 순수 |
| 3 | `applyJobEvent` | 일 목록에 시작 · 진행 · 끝을 반영함 | (일 목록, 사건) → 일 목록 | 순수 |
| 4 | `applyDone` | 끝난 일 한 줄을 더하고 최근 것만 남김 | (끝난 일 목록, 한 줄) → 끝난 일 목록 | 순수 |
| 5 | `readJobTails` | 도는 일마다 출력 파일의 끝부분을 읽음 | 도는 일들 → 일마다 끝부분 글 | 부수효과 (입구) |
| 6 | `progressOf` | 끝부분에서 마지막 진행 줄과 "한 것 / 전체"를 뽑고 줄을 자름 | 끝부분 글 → 진행 줄 · 한 것 · 전체 | 순수 |
| 7 | `applyTaskEvent` | (기존) 할 일 도구 호출을 할 일 목록에 반영 — 앱의 할 일 도구를 더함 | (할 일 목록, 도구, 입력) → 할 일 목록 | 순수 |
| 8 | `nowLine` | 재료를 차례로 보고 "지금 하는 일" 한 줄과 시작 시각을 정함 | (할 일 목록, 계획 단계, 지금 도구, 일 목록, 턴 상태) → 한 줄 · 시각 | 순수 |
| 9 | `turnStateOf` | (기존) 누구 차례인지 정함 — 도는 일 수를 받도록 바꿈 | (턴 상태, 멈춤, 보조 작업 수, 도는 일 수, 깨우기 표시) → 상태 | 순수 |
| 10 | `nowBlock` | 세 묶음을 화면 줄로 만듦(걸린 시간 · 막대 · 시각) | (지금 하는 일, 일 목록, 끝난 일 목록, 지금 시각) → 줄들 | 순수 |

- 부수효과 위치: 5(파일 읽기)뿐이고, 나머지 부수효과(상태 저장 · 화면 그리기 · 거울 세션 보내기)는 지금처럼 `register.tsx` 의 처리기에 있다.
  순수 단계는 모두 `hooks/model.ts` 에 둔다.
- 구현하며 달라진 것: 5번은 `readJobTails`(부수효과)와 `tailOf`(순수, 끝부분 자르기)로 나뉘었다. 끝난 일의 한 줄을 만드는 `doneLine`,
  끝이 가리키는 일을 찾는 `findJob`, 할 일 목록에서 새로 끝난 항목을 뽑는 `newlyDone` 을 보탰다(모두 순수).
  끝 알림은 두 곳에서 받는다 — 쉬는 세션을 깨운 알림은 턴 시작의 글에서, 도는 턴 안으로 들어온 알림은 프롬프트 제출에서.
- 재사용: `applyTaskEvent` · `turnStateOf` · `describeTool`(명령의 설명 글 뽑기) · `formatDuration`(걸린 시간) · `shorten`(줄 자르기) ·
  3초 갱신 · 거울 세션 보내기. 일 목록의 "보조 작업"(하위 에이전트) 줄은 지금 있는 `agentLines` 를 그대로 쓴다.

### 합성 설계 체크리스트 (Composition checklist)

| # | 물음 | 답 | 근거 |
|---|---|---|---|
| 1 | 각 단계가 요소 단위 단항 순수 함수인가 | 1 ~ 4 · 6 ~ 10 이 순수 | `hooks/model.ts` 의 `jobStartOf`(1124) · `jobEndOf`(1154) · `applyJobEvent`(1185) · `applyDone`(1219) · `progressOf`(1226) · `applyTaskEvent`(540) · `nowLine`(1244) · `turnStateOf`(289) · `nowBlock`(1274) — 모두 값만 받고 값만 돌려줌. 시험 T14 가 같은 입력에 같은 출력을 봄 |
| 2 | 단계의 입출력이 밝혀져 있고 입력은 필요한 것만 받는가 | 예 | `progressOf` 는 출력 전체가 아니라 `tailOf` 가 자른 끝 4천 자만 받고, `nowLine` 은 계획 전체가 아니라 하는 중인 단계의 번호 · 이름만 받음 |
| 5 | 큰 데이터나 조기 종료가 있으면 필요한 만큼만 읽는가 | 끝부분만 읽음 | `hooks/register.tsx` 의 `readJobTails`(410): 출력 파일이 바뀌었을 때만 읽고, 256KB 까지는 통째로 읽어 끝을 자르며 그보다 크면 끝 4천 자만 읽음 — 시험 T12 가 큰 파일을 통째로 읽지 않는 것과 바뀌지 않은 파일을 다시 읽지 않는 것을 봄 |
| 6 | 입력을 변이하지 않고 새 값을 만드는가 | 예 | `applyJobEvent` · `applyDone` 은 목록을 새로 만들어 돌려줌 — 시험 T14 가 넘긴 목록이 호출 뒤에도 그대로인 것을 봄 |
| 7 | 부수효과가 파이프라인 양 끝에만 있는가 | 예 | 파일 읽기는 `readJobTails` 한 곳, 상태 저장은 `endJob`(394)과 도구 호출 · 턴 시작 처리기의 끝, 그리기는 `nowCard`(960) — 순수 단계는 모두 `model.ts` 에 있음 |
| 8 | 실패할 수 있는 단계를 일반 합성에 그대로 섞지 않았는가 | 예 | 파일 정보를 못 얻으면 그 일을 건너뛰고, 읽은 글이 비면 `progressOf` 가 빈 줄을 돌려줘 진행을 반영하지 않음 — 일 줄은 이름과 걸린 시간만으로 그려짐(시험 T3 의 둘째 줄) |

## Guardrails

- 순수 단계는 `hooks/model.ts` 에, 부수효과는 `hooks/register.tsx` 에만 둔다(지금 구조).
- 대시보드가 읽는 파일은 그 일의 출력 파일뿐이다. 다른 파일을 찾아다니지 않는다.
- 진행 줄은 한 줄 · 120자로 자르고 제어 문자를 지운다. 거울 세션으로 보내는 것도 그 잘린 줄뿐이다 — 출력 전체를 보내지 않는다.
- 도는 일은 여덟 개까지만 기억한다(넘으면 가장 오래 끝난 것부터 버리고, 도는 일은 버리지 않는다).
- 3초 갱신 한 번이 느려지지 않게, 일마다 출력의 끝부분만 읽는다.
- 일이 끝났는지 모를 때 "끝났다"고 그리지 않는다 — 모르면 "끝난 듯"으로 구별해 그린다.
- 뒤에서 도는 일이 없을 때의 "사용자 차례" 동작과 빨강 멈춤은 건드리지 않는다.
- 공개 저장소에 들어가는 글 · 시험 자료에 다른 프로젝트의 이름이나 내용을 적지 않는다.

## Exit criteria

- TESTS.md 의 시나리오가 모두 통과한다.
- 뒤의 일이 도는 중에 사용자가 말을 걸어도 "사용자 차례"가 나오지 않는 것을 시험으로 재현하고(고치기 전 실패) 고친 뒤 통과를 봤다.
- 실제 세션에서 뒤로 보낸 명령 하나를 돌리며 대시보드 화면을 사용자에게 그대로 보였고, 사용자가 "이대로 계속"을 골랐다.
- 확인하지 못한 두 가지(프로젝트 밖 파일 읽기, 끝 알림이 닿는 길)를 실제로 해 본 결과가 마무리 보고에 적혀 있다.
- 기존 대시보드 시험 129개가 그대로 통과한다.

## Suggested path

1. 확인 못 한 두 가지를 실제로 해 본다 — 프로젝트 밖 출력 파일 읽기, 끝 알림이 닿는 길
2. 재현 시험을 먼저 쓰고 실패를 본다 — 뒤의 일이 도는 중에 사용자가 말을 걸면 "사용자 차례"가 나오는 것
3. 일 목록을 만든다 — `jobStartOf`, `jobEndOf`, `applyJobEvent`, `applyDone`

9. 대시보드 시험 전부를 돌린다 — 밀어 올리기 전 확인

## Risks / Open Questions

- **프로젝트 밖 파일 읽기가 막혀 있을 수 있다**: 출력 파일은 임시 폴더에 있다. 1단계에서 해 보고, 막히면 프로그램 실행으로 끝 몇 줄만 읽는다.
  그것도 안 되면 진행 줄 없이 이름 · 걸린 시간만 보이고, 그 한계를 사용자에게 말한다.
- **끝 알림을 못 받을 수 있다**: 그러면 일이 끝났는데 "도는 중"으로 남는다. 출력 파일이 한동안 바뀌지 않으면 "끝난 듯"으로 그리고,
  다음 턴이 시작되면서 온 글에서 확정한다. 1단계 결과에 따라 시험 T2 의 "끝을 아는 길"을 한 줄로 고정한다.
- **터미널 탭의 일은 끝을 알기 어렵다**: 시작은 도구 호출로 알지만 끝은 대시보드에 오지 않을 수 있다. 탭을 멈추는 호출과
  탭을 읽은 결과에서 끝을 알고, 그 밖에는 "터미널 탭에서 도는 중(끝은 탭에서 확인)"으로 그린다.
- **진행 줄에 비밀 값이 섞일 수 있다**: 명령의 출력 마지막 줄을 그대로 보이기 때문이다. 한 줄 · 120자로 자르고, 거울 세션에도 그 줄만 보낸다.
  더 가려야 하는지는 실제 화면을 보인 뒤 사용자가 정한다.
- **"지금 하는 일"의 재료가 없을 때**: 할 일 목록도 계획 단계도 없이 생각만 하는 동안에는 기본 글("결과를 읽거나 다음을 정하는 중")이 나온다.
  이 글로 충분한지는 실제 화면에서 본다.
- **앱의 할 일 도구의 입력 꼴이 바뀔 수 있다**: 꼴을 못 읽으면 할 일 목록을 건드리지 않는다(지금 값 유지).
