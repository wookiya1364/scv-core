# 대시보드 — 함께 하는 단계는 모두 진행 중으로 (여러 단계 동시 진행 표시)

## Summary

한 작업 세션이 계획의 여러 단계를 동시에 하면서 단계 보고 도구로 둘째 단계의 시작을 알리자, 대시보드가
"진행은 지금 단계(4번)에만 보낼 수 있습니다"라고 거절했다(2026-11-16, 다른 프로젝트의 세션 기록에서 확인). 그 세션은
한 단계만 진행 중으로 알리고, 나머지는 메모 글에만 "함께 진행"이라고 적었다. 화면에는 한 단계만 진행 중으로 보였다.
시작했다고 알린 단계는 어느 자리에 있든, 몇 개든 모두 진행 중으로 받고 그리게 고친다.

확인한 사실(2026-11-16, 코드):

- 단계 알림 검사 `checkSignal` 은 시작 · 막힘을 '끝나지 않은 첫 단계'에만 받는다(`hooks/model.ts`).
- 단계 상태 계산 `deriveStages` 는 그 첫 단계만 진행 중 · 막힘으로 만들고, 뒤 단계는 무엇이 적혀 있든 대기로 만든다.
- 맨 위 한 줄(`headline`)과 '지금 여기' 표시는 진행 중인 첫 단계 하나만 가리킨다.
- 작업을 어느 단계 몫으로 적을지는 값 하나(`workingOn`)가 기억한다 — 마지막에 시작한 단계가 끝나면, 아직 하는 중인 다른 단계가 있어도 비게 된다.
- 세는 줄(`countStages`)과 단계 그림은 단계마다 따로라서 여러 진행 중을 이미 그릴 수 있다.

사용자 결정(2026-11-16, 선택 창): "이대로 계획 쓰고 고치기" — 알린 단계는 어디든 모두 진행 중, 릴리스는 실제 화면 결과를 본 뒤 따로 묻는다.

## Goals / Non-Goals

- **Goals**
  - 끝나지 않은 단계면 어느 자리든 시작 · 막힘 알림을 받는다.
  - 시작했다고 알린 단계는 모두 진행 중으로 보인다 — 세는 줄, 단계 줄, 맨 위 한 줄이 같은 수를 말한다.
  - 한 단계가 끝나도, 아직 하는 중인 다른 단계에 작업이 계속 적힌다.
  - 알림의 답이 지금 진행 중인 단계 번호를 모두 말한다 — 번호를 잘못 보낸 것을 보낸 쪽이 바로 안다.
- **Non-Goals**
  - SCV 코어의 규약 글 고치기 — 세션은 스스로 여러 단계를 알리려 했다. 막은 것은 대시보드다.
  - 계획 문서의 `parallel_groups` 를 읽어 함께 할 수 있는 단계만 받기 — 알린 그대로 받는다.
  - 보조 일꾼(서브에이전트)의 작업을 그 일꾼이 맡은 단계 몫으로 나눠 적기 — 어느 일꾼이 어느 단계인지 대시보드는 모른다.
  - 남은 시간 추정을 병렬에 맞게 고치기.
  - 릴리스 — 결과를 보여 준 뒤 사용자에게 묻는다.
  - 코덱스.

## Approach Overview

알림으로 온 단계에는 '알린 단계'라는 표를 붙인다(`mergeMarks`). 계획 문서의 진행 줄("N단계 시작")로 온 표시도 같은 표를 받는다 —
단계 보고 도구가 없는 곳에서도 같게 보이게. 상태 계산은 지금 규칙(끝나지 않은 첫 단계만)에 한 줄을 더한다: 알린 단계는 자리에
상관없이 그 알림대로 진행 중 · 막힘이다. 손으로 남은 표시는 표가 없으니 지금처럼 대기다.
진행 중 · 막힘이라고 알린 단계가 하나라도 있는 동안에는, 아무 표시가 없는 첫 단계를 진행 중으로 짐작하지 않는다 — 알린 것이 있으면
알린 것만 믿는다. 알린 진행이 없을 때(차례로 하는 보통의 경우)는 지금처럼 끝나지 않은 첫 단계가 진행 중이다.

검사는 자리를 보지 않는다 — 끝나지 않은 단계면 받는다. 이미 끝난 단계는 거절한다. 답에는 지금 진행 중인 단계 번호를 붙인다.
맨 위 한 줄은 진행 중 · 막힘 · 사용자 차례인 단계 번호를 모두 말한다(이어진 번호 셋 이상은 `7~13` 처럼 줄인다).
작업을 적을 단계는 값 하나 대신 '시작한 단계 목록'으로 기억하고, 가장 늦게 시작해 아직 끝나지 않은 단계에 적는다.

## 순수함수 · 파이프라인 (Pure functions & pipeline)

```
// 단계 알림이 올 때
flow(
  readSignals,       // (없음) → 계획들 · 지금까지의 알림            (부수효과: 저장소 읽기)
  checkSignal,       // (알림, 계획들, 알림들) → 받을지 · 거절 이유
  applySignal,       // (알림들, 알림, 지금) → 새 알림들
  nextStarted,       // (시작한 단계 목록, 알림) → 새 목록
  signalAnswer,      // (알림, 단계 상태들) → 답 글 (진행 중인 번호 포함)
  writeSignals,      // 새 알림들 · 새 목록 → (없음)                 (부수효과: 저장 · 답 돌려주기)
)

// 그릴 때
flow(
  mergeMarks,        // (계획, 알림들) → 알린 단계에 표가 붙은 계획
  deriveStages,      // 계획 → 단계 상태들
  activeSteps,       // 단계 상태들 → 진행 중 · 막힘 · 사용자 차례인 단계 번호 묶음
  headline,          // (단계 상태들, 막힘들, 남은 시간) → 맨 위 한 줄
  drawStages,        // 단계 상태들 → 단계 줄과 '지금 여기' 표시      (부수효과: 그리기)
)
```

| # | 단계 | 하는 일 | 받는 값 → 돌려주는 값 | 순수/부수효과 |
|---|---|---|---|---|
| 1 | `readSignals` | (기존) 계획들과 지금까지의 알림을 읽음 | (없음) → 계획들 · 알림들 | 부수효과 (입구) |
| 2 | `checkSignal` | 알림을 받을지 정함 — 자리는 보지 않고, 이미 끝난 단계만 거절 | (알림, 계획들, 알림들) → 받음 · 거절 이유 | 순수 |
| 3 | `applySignal` | (기존) 같은 단계의 앞 알림을 새 알림으로 바꿈 | (알림들, 알림, 지금) → 알림들 | 순수 |
| 4 | `nextStarted` | 시작한 단계 목록을 고침 — 시작이면 넣고, 끝 · 막힘이면 뺌 | (목록, 알림) → 목록 | 순수 |
| 5 | `signalAnswer` | 알림의 답 글을 만듦 — 진행 수와 지금 진행 중인 번호 | (알림, 단계 상태들) → 글 | 순수 |
| 6 | `writeSignals` | (기존) 알림과 목록을 저장하고 답을 돌려줌 | 알림들 · 목록 → (없음) | 부수효과 (출구) |
| 7 | `mergeMarks` | 계획의 표시와 알림을 합침 — 알린 단계에 '알린 단계' 표를 붙임 | (계획, 알림들) → 계획 | 순수 |
| 8 | `deriveStages` | 단계 상태를 정함 — 알린 단계는 어디든 그 알림대로, 알린 진행이 없으면 첫 단계 규칙 | 계획 → 단계 상태들 | 순수 |
| 9 | `activeSteps` | 진행 중 · 막힘 · 사용자 차례인 단계 번호를 상태별로 묶음 | 단계 상태들 → 번호 묶음 | 순수 |
| 10 | `headline` | 맨 위 한 줄을 만듦 — 묶음의 번호를 모두 말함 | (단계 상태들, 막힘들, 남은 시간) → 글 | 순수 |
| 11 | `drawStages` | 단계 줄을 그림 — 진행 중인 단계마다 '지금 여기' | 단계 상태들 → 화면 조각 | 부수효과 (출구) |

- 부수효과 위치: 1(읽기), 6 · 11(저장 · 그리기) — 양 끝. 2~5 · 7~10 은 `hooks/model.ts` 에 둔다.
- 재사용: `applySignal`, `countStages`, `applyBlocks`, `applyTurn`, `stepDurationsFromSignals` 는 그대로 쓴다.

## Guardrails

- 한 단계씩 차례로 하는 계획의 화면은 글자까지 지금과 같다(기존 시험이 기대값을 바꾸지 않고 통과).
- 손으로 남은 표시가 뒤 단계에 있을 때의 동작(대기)은 건드리지 않는다.
- 알림의 저장 모양(`StepSignal`)은 바꾸지 않는다 — 앞 버전이 저장한 알림을 그대로 읽는다. 거울이 보내는 상태의 모양도 그대로다.
- 순수 단계는 `hooks/model.ts`, 부수효과는 `hooks/register.tsx`.
- 다른 프로젝트의 이름 · 내용은 이 계획과 코드 · 시험 · 릴리스 글에 적지 않는다.

## Exit criteria

- TESTS.md 의 시나리오가 모두 통과한다.
- 두 단계를 차례로 시작이라고 알리면 둘 다 받아들여지고, 화면에 둘 다 진행 중 · 세는 줄 '진행 2'인 것을 시험으로 봤다(고치기 전에는 실패).
- 기존 대시보드 시험이 통과한다 — "진행은 지금 단계에만"을 보던 기대값은 새 동작으로 바꾸고 그 시험 이름을 마무리 보고에 적는다.
- 실제로 그린 화면 글을 사용자에게 보였다.

## Suggested path

1. 시험을 먼저 쓰고 실패를 본다 — 두 단계 동시 진행 · 하나가 끝나도 남는 진행 · 끝난 단계 거절
2. 알림 검사를 풀고 답 글에 진행 중인 번호를 붙인다 — `checkSignal`, `signalAnswer`, `readSignals`, `writeSignals`
3. 알린 단계를 어디든 진행 중으로 계산한다 — `mergeMarks`, `deriveStages`
4. 맨 위 한 줄과 '지금 여기'가 진행 중인 단계를 모두 말하게 한다 — `activeSteps`, `headline`, `drawStages`
5. 작업을 적을 단계를 목록으로 기억한다 — `nextStarted`
6. 대시보드 시험 전부와 타입 검사를 돌린다 — 밀어 올리기 전 확인
7. 실제로 그린 화면 글을 사용자에게 보인다 — 두 단계가 함께 진행 중인 화면을 그려 그 글을 그대로 보여 줌

## Risks / Open Questions

- **번호를 잘못 보내면 그 단계가 진행 중으로 보인다**: 앞에는 자리 검사가 이것을 막았다. 답 글이 지금 진행 중인 번호를 모두 말하니 보낸 쪽이 바로 알고 고칠 수 있다(그 단계를 끝이나 막힘으로 다시 알리는 것 말고 '취소'는 없다 — 필요해지면 새 계획).
- **시작만 알리고 끝을 알리지 않은 단계는 계속 진행 중으로 남는다**: 앞에는 첫 단계만 진행 중일 수 있어 이런 흔적이 가려졌다. 알린 그대로 보이는 것이 맞다고 보고 둔다.
- **보조 일꾼의 작업은 가장 늦게 시작한 단계에 적힌다**: 일꾼마다 맡은 단계를 대시보드는 모른다.
- **남은 시간 추정은 단계를 차례로 한다고 보고 센다**: 함께 하는 단계가 많으면 실제보다 길게 나온다.
