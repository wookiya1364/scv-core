## 1. 문제

- 상황: Claude 앱의 SCV 창(대시보드 모드 0.2.30)과 SCV 본체 0.101.0 을 쓰는 프로젝트. 창에는 기어와 묻기 방식이 없고, 다른 프로젝트의 실제 세션에서는 선택 창 없이 글로 물으며 턴이 끝났다.
- 기대: 창에서 컨텍스트 · 사용량 · 묻기 방식 · 기어 · 단계가 항상 보이고, 눌러서 묻기 방식을 바꾸고 기어를 쓸 수 있다. 고를 것은 항상 선택 창으로 나온다. 값이 필요한 기어는 값을 안내받는다.
- 실제: 컨텍스트 · 사용량은 진행 중인 계획이 있을 때만 나온다. 기어 · 묻기 방식은 창에 없다(모드 코드에 언급 0건). 실제 세션에서 끝 답이 있는 134턴 중 12턴이 글로 물으며 끝나 사용자가 채팅으로 답했다. 기어 규약에 값을 물으라는 내용이 없다.
- 재현 조건: 진행 중인 계획이 없는 프로젝트에서 SCV 창을 연다 → 컨텍스트 · 사용량이 없다. 앱의 마무리 요약 도구에 질문과 버튼을 넣고 턴을 끝낸다 → 선택 창은 뜨지 않고 다음 턴에 알림만 실린다.

## 2. 관찰

- 관찰한 사실과 측정값: 실제 세션 한 개(137턴 중 끝 답이 있는 134턴, 본체 0.97.0 ~ 0.101.0): 선택 창을 쓴 턴 21. 끝 답을 판정 함수에 넣으면 12턴이 글로 물음(첫 조사는 끝 세 줄만 봐서 9턴으로 셌다). 요약 도구 호출 121번 중 34번(33턴)에 질문이 실렸고, 글로 물은 12턴 중 10턴이 그 안에 있다. 종료 훅에 걸린 시간: 이 세션 가운데값 4.4초, 그 프로젝트는 최근 25~35초.
- 정상일 때와 차이: 같은 세션의 21턴은 선택 창으로 물었다. 0.82 까지는 글로 물으며 끝나면 종료 훅이 턴을 막아 선택 창을 다시 부르게 했다.

## 3. 가설

- H1: 판정 함수가 이 꼴들을 못 알아본다 — 틀림(12턴 모두 알아봄).
- H2: 알아보지만 막지 않는다 — 0.83.0 부터 턴 끝 검사가 기본으로 알림만 남긴다.
- H3: 모델이 결정을 선택 도구가 아니라 앱의 마무리 요약 도구에 넣는다 — 호스트 규칙(요약 상자에 질문과 버튼)과 SCV 규칙(선택 창)이 갈린다.
- H2: 알아보지만 막지 않는다 — 0.83.0 부터 턴 끝 검사가 기본으로 알림만 남긴다.
- H3: 앱의 마무리 요약 도구에 질문을 두라는 호스트 규칙과 SCV 규칙이 갈려, 요약 도구 뒤 끝 글에서 묻게 된다 — 추정(4턴에서 본 꼴).

## 4. 실험

- 방법과 같게 둔 것: (1) 끝 답 134개를 판정 함수와 종료 훅에 그대로 넣었다. (2) 턴 끝에서 잡는 코드를 만들어 같은 134개를 다시 넣었다. (3) 요약 도구 호출 121번의 입력을 고친 가드에 넣었다. 세 번 모두 같은 세션 기록, 같은 호스트 프로필(선택 도구 있음), 다른 검사는 끔.
- 결과와 가설별 판정: H1 틀림 — 12/12 를 알아봄, 맺음말 5개는 0. H2 맞음 — 턴 끝에서 잡게 고치니 막힘 12 · 잘못 막힘 0. 다만 그 방식은 답 글 뒤 종료 훅(4~35초)과 모델 한 번을 더 기다려야 선택 창이 떠서 쓰지 않기로 했다. H3 맞음 — 요약 도구 호출 121번 중 질문이 실린 34번이 거절, 87번은 통과, 글로 물은 12턴 중 10턴이 여기서 잡힘.

## 5. 원인

- 직접 원인과 일어난 길: 모델이 결정을 마무리 요약 도구의 질문 칸에 넣음 → 선택 창이 뜨지 않음 → (10턴은 끝 글에서도 물음) 종료 훅이 알아보지만 알림만 남김 → 사용자가 채팅으로 답함.
- 근본 원인: 앱이 모델에게 요약 상자에 질문과 버튼을 두라고 하고, SCV 의 매 턴 안내("요약 상자는 요약만")는 말로만 있어 지켜지지 않았다. 지키게 하는 장치가 턴 끝에만 있었고 그것도 0.83.0 부터 알림뿐이었다. 창 쪽은 기어 · 묻기 방식이 대시보드보다 뒤에 나와 아직 반영되지 않았다.

## 6. 해결과 검증

- 해결책과 고른 이유: 가드에 규칙 S 를 넣어, 래퍼가 알려 준 요약 도구에 질문이 실리면 그 호출을 거절하고 선택 도구부터 부르게 했다. 끝 글이 나오기 전의 자리라 선택 창이 늦게 뜨지 않고 답이 두 번 보이지도 않는다(턴 끝에서 잡는 방식은 만들었다가 사용자 판단으로 걷어 냄). 창은 컨텍스트 · 사용 한도 · 묻기 방식 · 기어 · 단계를 위에 두고 나머지를 접었다. 기어는 gear.sh ask 와 규약으로 값을 선택 창에서 안내한다.
- 고치기 전후 값: 요약 도구에 질문이 실린 호출 34번: 전에는 모두 통과 → 지금은 모두 거절(질문 없는 87번은 그대로 통과). 계획이 없을 때 창의 컨텍스트 · 사용 한도: 안 나옴 → 나옴. 창의 기어 · 묻기 방식: 없음 → 있음. 매 턴 안내 줄: 389B → 396B(한도 400B). 모드 시험: 162 → 176.
- 부작용과 회귀 시험: 선택 창이 지금보다 자주 뜬다(실제 세션 기준 134턴 중 33턴 꼴 — 사용자가 숫자를 보고 고름). 규칙 S 는 래퍼가 값을 넘겨야 돌므로 래퍼 릴리스 전에는 변화가 없다. 회귀: test-choice-block(9) · test-choice-questions · test-help-first · test-guard · test-gear-run(T52~T54) · test-instruction-diet · 모드 시험 176개가 맥 기본 셸(bash 3.2)에서 통과. 리눅스 · 전체 시험 · 앱에서의 실제 모습은 아직 확인하지 않았다.

## 7. 배운 것

- 다음에 같은 문제를 만나면 진단하는 법: "선택 창이 안 떴다"는 말을 들으면 세션 기록에서 턴마다 (가) 선택 도구 호출, (나) 요약 도구 입력의 질문 칸, (다) 끝 답을 판정 함수에 넣은 값을 함께 본다. 끝 답만 보면 요약 상자에만 실린 질문(이번에 23턴)을 놓친다. 끝 세 줄만 훑는 빠른 조사는 3턴을 놓쳤으니 판정 함수로 센다.
- 다른 곳에도 쓸 수 있는 것: 어긋남을 고치게 하려면 답이 다 나온 뒤(턴 끝)보다 그 어긋남을 만드는 도구 호출 앞에서 잡는 편이 낫다 — 기다림도 되풀이도 없다. 고친 검사는 실제 세션의 입력을 그대로 다시 넣어 숫자로 확인한다.
