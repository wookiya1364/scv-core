# 마무리 보고 — 단계 보고가 턴 끝 검사에 안 잡히던 것 · 재는 검사가 옆 파일에 기대는 함수를 빼던 것

## 1. 문제

- 상황: 대시보드가 켜진 세션에서 구현 중인 계획의 파일을 바꾼 턴이, 단계 보고 도구를 실제로 불렀는데도 "단계를 알려라"로 계속 막혔다. 재는 검사는 고친 함수 가운데 하나를 "답이 달라 뺌"으로 내고 견주지 않았다
- 기대: 단계 보고 도구를 부른 턴은 막히지 않는다. 답이 같은 함수는 앞뒤 시간이 견줘진다
- 실제: 단계 보고 도구가 "기록함"이라고 답했는데도 턴 끝 검사가 두 번 막고 나서야(막은 횟수 한도) 지나갔다. 재는 검사는 겹침 검사 함수를 두 번 다 "답이 달라 뺌"으로 냈다 — 전체 코드로 견주면 답은 같았다(2,228바이트 둘 다)
- 재현 조건: 대시보드를 켠 앱 세션에서 구현 중인 계획의 파일을 바꾸고 단계 보고 도구를 부른 뒤 턴을 끝낸다. 재는 검사는 옆 파일의 함수에 기대는 함수가 든 파일을 고친 뒤 견주기 명령을 돌린다

## 2. 관찰

- 관찰한 사실과 측정값: 단계 보고 도구를 16번 넘게 부른 세션의 턴 폴더에 표시 파일이 한 번도 생기지 않았다. 도구 앞 훅에 그 호출 모양의 입력을 직접 넣으면 표시 2줄이 남고 판정은 통과였다. 셸 명령 → 단계 보고 도구 2번 → 셸 명령 순서에서 정산 흔적의 시각은 뒤 셸 명령이 시작한 시각이었고(10초 사이에 훅이 돈 흔적 없음), 가운데를 앱의 다른 도구로 바꾸면 그 흔적이 뒤 셸 명령보다 4초 앞섰다. 재는 검사는 그 커밋에서 잴 파일 하나만 꺼낸다(두 곳)
- 정상일 때와 차이: 훅이 도는 도구는 부른 순간에 턴 폴더에 흔적이 남는다. 단계 보고 도구만 흔적이 없다. 재는 검사는 옆 파일에 기대지 않는 함수는 정상으로 견준다(같은 실행에서 통과 2)

## 3. 가설

- H1: 도구 앞 훅이나 턴 끝 검사의 판정에 버그가 있다
- H2: 훅은 멀쩡하고, 그 도구의 호출에는 훅이 닿지 않는다 — 대시보드의 도구는 앱의 모드가 직접 처리한다
- H3: 도구 이름이 호스트 프로필에 적힌 것과 다르다
- H4: 재는 검사가 앞 코드를 꺼낼 때 옆 파일을 빠뜨린다

## 4. 실험

- 방법과 같게 둔 것: (가) 임시 프로젝트에서 설치된 훅에 그 도구 호출의 입력을 직접 넣었다. (나) 실제 세션에서 가운데 도구만 바꿔 정산 흔적의 시각을 견줬다 — 앞뒤 셸 명령과 만든 파일은 같게 두었다. (다) 대화 기록에서 실제 호출의 도구 이름을 읽었다. (라) 재는 검사와 같은 입력으로 함수를 앞 코드 전체 · 뒤 코드 전체에서 불러 답을 견줬다
- 결과와 가설별 판정: H1 틀림 — (가)에서 표시 2줄 · 통과. H2 맞음 — (나)에서 단계 보고 도구는 흔적 없음, 앱의 다른 도구는 흔적 있음. 다만 훅이 아예 안 도는지, 다른 폴더 정보로 돌아 일찍 끝나는지는 가리지 못했다. H3 틀림 — (다)에서 이름이 같았다. H4 맞음 — (라)에서 답이 같았고, 꺼내는 코드가 파일 하나만 꺼낸다

## 5. 원인

- 직접 원인과 일어난 길: 턴 끝 검사는 도구 앞 훅이 턴 폴더에 남기는 표시만 센다. 대시보드의 단계 보고 도구는 앱의 모드가 받아 처리해서 그 훅이 닿지 않으므로 표시가 0 이고, 검사는 부르지 않은 턴과 가리지 못해 막는다. 재는 검사는 앞 코드의 파일이 옆 파일을 불러오지 못해 기대는 함수가 없는 채로 돌고, 다른 답이 나와 견주지 않는다
- 근본 원인: 턴 끝 검사가 "도구를 불렀다"는 사실을 호스트가 훅을 돌려 줄 때만 알 수 있게 짜여 있었다 — 호스트가 직접 처리하는 도구에는 훅이 돌지 않을 수 있다는 것을 확인하지 않았고, 단계 보고 검사의 시험은 훅이 남기는 표시를 손수 만들어 넣어서 이 틈을 볼 수 없었다. 재는 검사는 "잴 함수가 있는 파일"만 필요하다고 보고, 그 파일이 다른 파일을 불러온다는 것을 빠뜨렸다 — 처음 넣을 때의 시험이 한 파일 안의 함수만 썼다

## 6. 해결과 검증

- 해결책과 고른 이유: (1) 턴 끝 검사가 막을 참일 때만(보고가 필요하고 표시가 0) 대화 기록의 끝 8 ~ 9MB 에서 "이번 턴이 시작된 뒤 어시스턴트가 그 도구를 부른 줄"을 세어 표시 대신 쓴다. 턴 시작 시각은 턴 번호 파일이 만들어진 시각으로 본다 — 처음에는 턴을 시작할 때 시각을 따로 적었는데, PR 의 맥 검사에서 턴 시작의 사진 한도(0.3초)가 333ms 로 넘어서 시작 길에 더한 프로그램 호출을 없앴다. 훅이 도는지에 기대지 않고 코어만 고치면 되어서 골랐다(사용자 선택 — 대시보드가 표시를 남기는 길 · 막지 않는 길은 버림). (2) 재는 검사는 잴 파일이 있는 폴더의 파일들을 그 커밋에서 함께 꺼낸다(사용자 선택 — 코어 전체 꺼내기는 버림). 길이 달라진 곳: 계획은 앞 코드를 꺼내는 두 곳을 다 고친다고 했지만, 달라진 함수를 고르는 곳은 본문 글만 견줘서 옆 파일이 필요 없었다 — 견주는 곳 하나만 고쳤다. 폴더는 하위 폴더 없이 그 폴더의 파일만 꺼낸다(저장소 맨 위의 파일을 재도 저장소 전체를 풀지 않게)
- 고치기 전후 값: 표시 없이 이번 턴의 호출이 대화 기록에 있는 턴의 판정 block → pass(이 세션의 실제 호출 줄로 확인). 이 세션의 실제 대화 기록에서 이번 턴의 호출 3번을 3으로 셌다(도구 이름이 든 줄 56개 가운데). 30MB 대화 기록에서 턴 끝 검사 시간: 보고가 필요 없는 턴 275 → 274ms, 막을 참인 턴 306 → 400ms(통째로 훑으면 +348ms, tail 로 자르면 +600 ~ 700ms 였다). 재는 검사: 옆 파일에 기대는 함수 "답이 달라 뺌" 1 → 0, 이 저장소의 겹침 검사 함수는 0.93.0 과 견줘 통과(45.1 → 44.3ms, 0.98배). 폴더째 꺼내는 데 0.08초
- 부작용과 회귀 시험: 턴 끝 검사 시험에 T43 ~ T52(10줄), 재는 검사 시험에 S15b 6줄을 더했고 bash 3.2 · 5 에서 실패 0. 고치기 전에 T43 · T47 · T50 과 S15b 3줄이 실패하는 것을 봤다. 전체 시험 한 번(115개): 통과 114 · 실패 1 — 실패한 것은 "끝 훅에 커밋 안 된 변경이 있으면 실패"하는 시험이고 커밋한 뒤 통과한다. 순수 검사 · 함수 사전 검사(C 설정 포함) · 호스트 이름 검사 · 훅 일관성 검사 통과, 틀 요약값 다시 만듦. 재는 검사(계획 끝): 새 함수 2 · 한도 넘음 0. 남은 것: 대화 기록의 줄 모양은 호스트 판마다 다를 수 있다 — 달라지면 0 으로 세어 지금처럼 두 번 막고 지나간다. 한 턴이 대화 기록을 8MB 넘게 쓰고 호출이 그보다 앞에만 있으면 놓친다. 다른 폴더의 파일에 기대는 함수는 여전히 "답이 달라 뺌"이 될 수 있다(코어에는 지금 없다). 실제 앱 세션에서 막히지 않는 것은 릴리스 뒤 다시 연 세션에서만 볼 수 있다

## 7. 배운 것

- 다음에 같은 문제를 만나면 진단하는 법: "불렀는데 검사가 모른다" 싶으면 판정과 관찰을 따로 본다. 먼저 훅에 그 호출 모양의 입력을 직접 넣어 판정이 멀쩡한지 본다(이번에 1분). 그다음 실제 세션에서 훅이 도구마다 남기는 흔적의 시각을 본다 — 셸 명령 → 그 도구 → 셸 명령 순서로 돌리고 정산 파일의 고친 시각이 가운데 도구의 시각인지 뒤 셸 명령의 시각인지 견주면, 그 도구에 훅이 닿는지 갈린다. 대조로 같은 순서에 다른 도구를 넣는다
- 다른 곳에도 쓸 수 있는 것: 호스트가 해 주는 일(훅 돌리기)에만 기대는 검사는 호스트가 그 일을 건너뛰는 순간 조용히 틀린다 — 호스트와 무관한 근거(대화 기록)를 둘째 근거로 둔다. 큰 파일의 끝만 읽을 때 맥에서는 tail -c 가 가장 느리고(0.58초) dd 로 건너뛰는 것이 빠르다(0.16초). 대화형 셸의 grep 은 다른 프로그램일 수 있어서 시간은 스크립트 안에서 재야 한다(처음에 21ms 로 잘못 쟀다). 사전의 예 하나를 25번 되풀이해 재는 도구는 그 함수가 기대는 것까지 함께 꺼내야 답이 같다
