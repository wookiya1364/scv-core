## 1. 문제

- 상황: SCV 창의 단계 흐름은 멈춘 그림이라 일하는 중인지 내 차례인지가 한눈에 들어오지 않는다. 요구 확인과 결과 확인은 대화창에서만 답한다. 하던 일 중에 다른 일이 오면 하던 일을 멈추는 길밖에 없어, 한 폴더에 여러 일의 변경이 섞였다(다른 프로젝트의 세션을 조사한 값: 계획 기록 없이 코드를 고친 끼어듦 82번 중 32번이 하던 계획의 파일을 건드림 — 2026-11-27)
- 기대: 창이 움직임으로 상태를 알리고, 내 차례가 맨 위의 카드로 떠 단추 한 번으로 답하고, 두 일을 갈라 동시에 하고 합칠 때 결과가 달라진 것을 잡는다
- 실제: 대시보드 코드에 움직임이 하나도 없고, 창에서 질문에 답하는 길이 없고, SCV 본체에는 멈추고 돌아오기만 있다(2026-11-27 코드에서 확인)
- 재현 조건: 계획을 진행하며 SCV 창을 본다 — 단계 그림이 멈춰 있다. Claude 가 질문을 열면 창에는 '답을 기다리는 중'만 뜬다. 진행 중인 계획이 있을 때 목표가 다른 일을 시키면 하던 계획이 보류된다

## 6. 해결과 검증

- 해결책과 고른 이유: (1) 움직임은 CSS 로 그리고, 움직일 것이 있는 그림만 움직이는 틀에 그린다 — 1단계의 실제 창 시험에서 SMIL 로 위치를 옮기는 빛은 가는 길이 그려지지 않았고 CSS 는 그려졌다. 스위치를 끄면 전의 그림 함수를 그대로 쓴다. (2) 내 차례 카드는 질문 도구 호출을 가로챈 쪽이 엔진의 선택 창과 창의 답 가운데 먼저 온 것을 돌려준다 — 2단계의 실제 앱 시험에서 창 쪽이 먼저 답하자 질문 도구가 그 답을 받았고 선택 창은 0.08초 뒤 끊겼다. 대화창의 선택 창은 그대로 둔다. (3) 두 일은 지금 상태를 임시 색인으로 사진 찍어 따로 만든 폴더(git worktree)로 보내고, 합칠 때는 객체만으로 합침을 계산해 커밋 없이 작업 파일에 옮긴다 — 원래 폴더의 커밋하지 않은 작업 · 색인 · 가지를 건드리지 않으려는 것이다. 확인 결과는 가를 때 적어 두고 합친 뒤 다시 돌려 값 줄끼리 비교한다
- 고치기 전후 값: 대시보드 시험 294개 → 319개(실패 0, 지난 294개는 기대값을 고치지 않음) · 타입 오류 10개 → 10개 · 창을 그리는 시간은 움직임을 켠 쪽이 끈 쪽의 1.00 ~ 1.25배(한도 1.5배, 예: 3.51 ms 대 3.52 ms) · 가장 긴 단계 그림 650자(한도 131,072자) · Claude 가 읽는 안내 글 +672바이트(계획이 진행 중일 때만). 본체의 계획 시험 11줄 → 18줄(실패 0, 새 bash 와 맥 기본 bash 3.2) · 함수 사전 467개 → 473개(예시 전부 맞음). 실제로 돌린 예: 가르기 → 뒤에서 도는 에이전트가 따로 만든 폴더에서 이음 → 합치기에서 '보스 10 → 5'를 잡고 다시 하기 단계를 더함
- 견본대로 다시 고침(2026-11-28, 18 ~ 20단계): 실제 창을 본 사용자가 두 일 화면이 승낙한 견본과 다르다고 했다 — 같은 내용을 회색 글 줄로만 그렸고 시험은 글만 봤다. 견본의 원본을 읽어 요소를 하나씩 맞췄다: 맨 위 '지금 · 돌아갈 곳' 칸과 색 이름표, 갈라짐 · 합침 옆의 작은 그림, 두 칸의 색 이름표 · 색 점 · 색 상태 글, 합친 뒤의 묶음(함께 한 일 · 합침 · 다시 하기). 함께 실제 창에서 찾은 것 셋을 고쳤다(보내기 단추 하나 · 막힌 작업 칸의 겹침 없앰 · 카드로 답한 것을 SCV 의 선택 답 훅에 알림). 대시보드 시험 294 + 28개, 본체 계획 시험 18줄(더한 단계의 번호 확인 포함)
- 선과 꼭짓점 높이(2026-11-28, 22단계): 보낸 비교 그림을 본 사용자가 3단계와 4단계 사이의 선이 끊겼고 꼭짓점이 제목보다 아래에 있다고 했다. 까닭은 둘 — 선이 단계 그림 안에만 있어 그림 밖(두 칸 · 합친 기록 옆, 꼭짓점 위쪽)에는 선이 없었고, 꼭짓점이 그림의 14픽셀 높이에 있는데 제목 줄의 가운데는 10픽셀이었다. 고침: 움직이는 그림에 위에서 내려오는 선 조각을 더하고, 그림 아래와 묶음 옆에는 남는 높이만큼 늘어나는 선(색을 칠한 가는 상자)을 두고, 제목 위에 4픽셀(반 줄의 0.4)을 둔다. 값: 꼭짓점과 제목 줄 가운데의 차이 4.0 → 0.0픽셀, 묶음 줄의 높이 180 = 그 옆 선의 높이 180(앱의 그리는 규칙대로 그린 미리 보기의 측정). 대시보드 시험 322 → 326개(실패 0, 지난 294개는 그대로). 실제 창에서는 아직 보지 못했다
- 이름표 낱말(2026-11-28, 23단계): 두 칸의 이름표가 일하는 자리를 풀어 쓴 말이라 이름으로는 어색하다고 사용자가 알려 '분기' · '원본'으로 바꿨다(사용자가 낸 말, 다른 후보와 나란히 그린 그림을 보고 고름). 옛 낱말 둘은 프로젝트의 낱말 사전에 올렸다. 고친 시험은 옛 낱말을 쓰는 코드 사본에서 실패하고(lanes T28) 새 코드에서 통과한다. 본체가 찍는 글과 지난 문서 · 견본 그림은 그대로다
- 두 칸의 단계 누르기(2026-11-28, 24단계): 실제 창을 본 사용자가 두 칸 안의 단계를 눌러도 자세한 칸이 나오지 않는다고 했다 — 그 줄이 누를 수 없는 글이었다. 이름을 단추로 바꾸고, 초점을 '이 계획의 단계 · 상대 일의 단계' 둘로 나눠 자세한 칸이 초점의 계획으로 값을 구하게 했다. 같은 때 실제 창 사진에서 두 칸이 카드 너비를 채우지 않는 것을 찾아 고쳤다(선 옆의 줄에 넣으면서 내용만큼만 넓어졌다). 대시보드 시험 326 → 328개(실패 0, 지난 294개는 그대로). 실제 창에서는 다음 다시 읽기 뒤에 본다
- 실제 창 확인(2026-11-28 09:00 ~ 09:37, 21단계): 다시 읽기를 두 번 하며 실제 창을 찍어 견본과 나란히 놓았다 — 선이 가른 단계에서 다음 단계까지 이어지고, 꼭짓점이 제목 줄 높이이고, 이름표가 '분기' · '원본'이고, 두 칸의 단계를 누르면 자세한 칸이 뜬다. 사용자가 직접 눌러 본 뒤 "마음에 든다"고 답했다. 그 뒤의 손질 둘(두 줄로 넘어간 이름 옆의 색 점을 첫 줄로 · 끈 화면의 제목 자리를 예전 그대로)은 다음 다시 읽기 뒤에 보인다. 대시보드 시험 328개(실패 0, 지난 294개는 그대로)
- 계획 끝의 속도 검사(2026-11-28, 25단계): 새 판을 내기 전에 돌린 견줌 검사에서 합침을 적는 함수(`scv_plan_mark_join`)가 입력 4배에 시간 9.0배로 한도(8배)를 넘었다(다시 측정해도 7.5 ~ 8.7배). 까닭은 둘 — 계획 글을 다시 쓰는 함수 다섯이 줄마다 `out="$out…"` 꼴로 글 전체를 다시 펼쳐 붙였고(52,000자 · 4,000줄의 글에서 507 ms, 덧붙이기는 43 ms), 끝의 줄바꿈 하나를 떼는 방식이 줄바꿈으로 끝나지 않는 글을 처음까지 훑었다(같은 글에서 385 ms, 마지막 글자만 보면 3 ms). 줄은 덧붙이기(`+=`)로 붙이고 끝 줄바꿈은 마지막 글자만 보고 떼게 바꿨다 → 9.0배 → 2.5배(한 번 102 ms → 65 ms). 결과는 같다: 사전의 예시(473개 함수) 전부 맞음, 본체의 계획 연결 시험이 두 셸(새 bash · 맥 기본 3.2)에서 통과, 고치기 전 코드와 견준 함수 14개 가운데 한도 넘음 0개 · 답이 달라진 것 0개(고친 옛 함수 8개는 0.63 ~ 0.93배로 빨라짐)
- 부작용과 회귀 시험: 본체 전체 시험 130개 중 129개 통과 — 실패 1개는 시간 측정 시험으로, 컴퓨터 부하가 99일 때 2,184 ms(한도 2,000 ms)였고 혼자 다시 돌리면 930 ms 로 통과한다(고치기 전 코드는 851 ~ 916 ms). 부하가 있을 때 고치기 전 코드와 번갈아 돌린 값은 887 ~ 1,966 ms(고치기 전) · 1,999 ~ 2,049 ms(고친 뒤)로 흩어져 차이를 가릴 수 없어서 CPU 시간으로 다시 비교했다: 함수 파일을 한 번 읽기 12.1 → 12.4 ms, 계획 명령을 한 번 시작하기 30.3 → 31.2 ms — 그 시험의 17번 호출에 더한 몫은 약 4 ms 다. 가르기 · 합치기만 쓰는 파일은 그 갈래에서만 읽게 줄였다(시작 31.6 → 31.2 ms). 16단계에서 다시 돌린 값은 부하 30에서 1,992 ms 로 통과했다. 한 번에 실패 0 으로 끝난 전체 실행은 없다(다른 프로젝트의 작업이 CPU 를 쓰고 있었다). 회귀 시험: 모드 시험의 motion T4 ~ T10 · card T11 ~ T19 · lanes T28 ~ T30 · order T31, 본체 test-plan-link 의 T20 ~ T25b. 실제 창 확인(2026-11-28 00:08 ~ 00:16, 고친 파일 넷을 설치된 0.7.1 에 얹음): 번지는 점 · 한 번 내려가는 빛 · 두 일이 나란히 → 합친 뒤가 찍혔고, 질문 셋이 모두 카드의 단추로 답해졌고, 질문이 열려 있는 동안 계획 칸을 바꾸거나 크게 보기를 눌러도 질문이 닫히지 않았다(시험 틀에서 닫히던 것은 시험 틀만의 일이다). 실제 창에서 새로 본 것 셋: 보내기 단추가 둘로 보인다(입력 칸이 스스로 그리는 단추와 따로 둔 단추), 질문이 열려 있는 동안 빨간 막힌 작업 칸에도 같은 질문이 허락 기다림으로 겹쳐 보인다, 카드로 답한 것은 SCV 의 선택 기록(계획 이력의 선택 줄)에 남지 않고 답 뒤의 등록 유지가 거절된다 — 모드가 답한 질문에는 도구 뒤 훅이 돌지 않는다. 확인하지 못한 것: 빈 글 보내기를 눌렀을 때, 직접 쓴 글로 답하기(실제 창), 원격 화면, codex

## 7. 배운 것

- 다음에 같은 문제를 만나면 진단하는 법: 시험 틀에서 질문이 열려 있는 동안의 창을 볼 때는 '띄운 창'의 찾기 · 누르기를 쓰지 않는다(그 호출이 끝나기를 기다려 멈춘다) — 엔진의 그리기 결과를 읽고 엔진에 직접 누르기 · 입력을 시킨다. 시험의 '선택 창 흉내'는 끊김 신호를 받으면 끝나야 한다. 시간 측정 시험이 실패하면 코드를 의심하기 전에 컴퓨터 부하와 다른 프로젝트의 프로세스를 먼저 보고, 고치기 전 코드와 번갈아 돌려 비교한다. 부하가 있는 컴퓨터에서 두 코드의 속도를 비교할 때는 벽시계가 아니라 CPU 시간을 쓴다(벽시계 값은 같은 코드에서도 887 ~ 1,966 ms 로 흩어졌다). 질문에 답이 어디서 왔는지는 대화 기록 줄로 가린다 — 사람이 선택 창에서 답한 줄에는 수락 표시가 있고, 모드(창의 단추)가 답한 줄에는 없다. 보고에서 되돌리는 명령을 실행 단추가 붙는 칸으로 적지 않는다 — 다음 행동 옆에 그 칸만 있으면 그것이 눌린다(실제로 한 번 되돌려졌다)
- 승낙받은 견본이 있으면 그것이 명세다: 만들기 전에 견본의 원본을 읽어 요소를 하나씩 목록으로 만들고, 보여 주기 전에 견본과 결과를 한 그림에 나란히 놓아 본다. 글만 보는 시험은 모습이 달라도 통과한다
- 다른 곳에도 쓸 수 있는 것: 시험 틀이 그린 나무(JSON)를 페이지로 옮겨 사진으로 찍는 방법 — 실제 창을 찍을 수 없을 때 증거 그림을 만든다. 임시 색인으로 작업 폴더의 사진을 찍는 방법 — 작업 파일과 색인을 건드리지 않고 지금 상태를 커밋 객체로 남긴다. 도구 호출을 가로채 '먼저 온 답'을 돌려주는 방법 — 엔진의 선택 창을 없애지 않고 답하는 길을 하나 더한다
- 실제 창을 찍을 수 없을 때(화면 잠김 · 사용자가 원격): 앱 묶음에 든 그리는 코드를 읽으면 상자 · 글 · 그림이 화면 단위로 바뀌는 규칙을 알 수 있다(너비는 글자 칸, 높이는 줄, 세로 간격은 반 줄, 그림은 픽셀). 그 규칙 그대로 그린 미리 보기는 고치기 전의 어긋남을 실제 창의 지난 사진과 같은 값으로 내놓았다 — 흉내 낸 배치보다 믿을 수 있다. 그래도 실제 창 확인을 대신하지는 않는다
- 고치기 전에 계획의 지킬 것을 다시 읽는다: 처음 고친 것은 멈춘 그림의 점선까지 바꿔 '끈 그림은 예전과 글자까지 같다'는 약속과 '지난 시험의 기대값을 고치지 않는다'는 끝 기준에 걸렸다. 문서를 고치다가 알아차려 되돌렸다 — 코드를 쓰기 전에 읽었어야 했다
- 미리 보기는 내용이 짧을 때와 길 때를 둘 다 그린다: 두 칸이 너비를 채우지 않는 것은 내용이 짧은 실제 예시에서만 보였고(미리 보기의 긴 글은 저절로 너비를 채웠다), 한쪽 칸이 다른 칸을 밀어내는 것은 이름이 아주 긴 경우에만 보였다
- 데스크톱 앱은 맞춤을 정하지 않은 가로 상자 바로 아래의 글 · 단추 · 그림을 세로 가운데에 둔다(앱 묶음의 화면 규칙에서 확인). 미리 보기 도구가 이 규칙을 빠뜨려 색 점의 자리가 실제 창과 달랐다 — 실제 창 사진을 확대해 찾았고, 규칙을 도구에 더했다. 미리 보기는 실제 창 사진과 한 번은 맞대 봐야 한다
- 셸에서 글을 줄마다 다시 지을 때: `out="$out"…"$line"` 은 붙일 때마다 글 전체를 다시 펼쳐 줄 수의 제곱으로 느려진다(맥 기본 bash 3.2 에서는 같은 글에 2,425 ms) — `out+=` 로 붙인다. 끝의 줄바꿈을 `${text%줄바꿈}` 으로 떼면 줄바꿈으로 끝나지 않는 글은 처음까지 훑는다 — 마지막 글자만 본다. 사전의 예시에는 줄바꿈 없이 끝나는 글이 많아, 예시를 100번 되풀이하는 속도 검사에서만 드러났다. 그 검사는 계획의 끝이 아니라 함수를 쓴 단계에서 한 번 돌린다
