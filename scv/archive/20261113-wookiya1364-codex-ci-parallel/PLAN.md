# 코덱스 래퍼의 CI 시간 줄이기 — 시험을 여러 러너에 나눠 함께 돌린다

## Summary

코덱스 래퍼는 PR 검사 한 번에 12 ~ 15분, 코어가 릴리스된 뒤 래퍼가 릴리스될 때까지 71 ~ 74분이 걸린다. 클로드 코드 래퍼는 3 ~ 5분 · 26 ~ 28분이다. 시간의 대부분은 러너 하나에서 차례로 도는 두 덩어리(코어 시험 전부 11.6분 · 어댑터 시험 파일 하나 맥 6.6분)이고, 같은 덩어리가 릴리스 한 번에 다섯 번 돈다. 시험을 여러 러너에 나눠 함께 돌리고, 동기화 봇의 겹치는 한 번을 없앤다.

## Goals / Non-Goals

- **Goals**
  - 코덱스 PR 검사에서 코어 시험 전부를 여덟 조각으로 나눠 여덟 러너에서 함께 돌린다
  - 가장 오래 걸리는 어댑터 시험 파일(원자성 시험)을 세 부분으로 나눠 맥 · 리눅스 각각 세 러너에서 함께 돌린다
  - 동기화 봇은 PR 을 열기 전에 가벼운 검증(체크섬 · 목록 · 문법)만 한다 — 시험 전부는 PR 검사가 한 번만 돌린다
  - 조각 수와 부분의 구성이 설정 안에서 어긋나지 않게 시험 하나가 지킨다
  - 목표 값: PR 검사 5분 안 · 릴리스 흐름 12분 안 · 코어 → 코덱스 릴리스 30분 안 (사용자 승인 2026-11-13)
- **Non-Goals**
  - 시험의 내용 · 시간 한도를 바꾸는 일
  - 클로드 코드 래퍼와 코어의 CI
  - 릴리스 흐름(develop → stage → main)의 PR 을 하나로 줄이는 일
  - 버전만 바꾼 PR 에서 무거운 시험을 건너뛰게 하는 일 — 목표에 못 미치면 다음 계획에서 정한다
  - 코덱스 래퍼의 새 버전 내기 — 설정만 main 까지 반영한다

## Approach Overview

1. **코어 시험** — 코어가 자기 CI 에서 쓰는 조각 실행기(`run-focused.sh --shard i/N`)가 복사본 안에 이미 있다. 시간표(`core/tests/timings.tsv`)로 조각의 무게를 맞추고, 조각 안에서는 시험이 하나씩 돈다. PR 검사의 "코어 시험" 작업을 조각 여덟 개의 묶음으로 바꾼다. 시간표의 core/tests 102줄 합이 1,167초라 여덟 조각이면 조각마다 145초쯤이고, 가장 긴 시험 하나가 127초다. 흐름 시험(run-dry)과 복사본 검증은 첫 조각에서만 돈다.
2. **어댑터 시험** — 원자성 시험 파일은 서로 독립인 경우 28개가 다섯 묶음으로 나뉘어 있다. 묶음을 골라 도는 길(부분 번호)을 파일에 더하고, 묶음별 실제 시간을 재서 세 부분의 무게를 맞춘다. 번호를 주지 않으면 지금처럼 전부 돈다. PR 검사에 "원자성 시험" 작업을 운영체제 둘 × 부분 셋으로 더하고, 지금의 어댑터 작업에서는 그 파일을 뺀다(나머지 셋은 합쳐 1분 안이라 그대로 둔다).
3. **동기화 봇** — PR 을 열기 전의 검증 단계에서 시험 실행(어댑터 시험 · 흐름 시험 · 코어 시험 전부)을 빼고 파일 검증만 남긴다. 봇이 여는 PR 은 PR 검사를 전부 거친다.
4. **지키는 시험** — 조각 수가 이름 · 목록 · 명령 세 곳에서 같은지, 원자성 시험의 부분들이 묶음 전부를 한 번씩만 덮는지, 봇이 시험 전부를 돌리지 않는지를 보는 시험 하나를 더하고 PR 검사의 첫 작업에서 돌린다.

## 순수함수 · 파이프라인 (Pure functions & pipeline)

```
PR 검사:   flow( 검증, [코어 조각 1..8 | 어댑터 맥 · 리눅스 | 원자성 부분 1..3 × 맥 · 리눅스] )
조각 하나: flow( 시험 목록 읽기, 조각 고르기, 차례로 돌리기, 결과 줄 내기 )
원자성:    flow( 부분 번호 읽기, 묶음 고르기, 고른 묶음 돌리기, 결과 줄 내기 )
```

| # | 단계 | 하는 일 | 받는 값 → 돌려주는 값 | 순수/부수효과 |
|---|---|---|---|---|
| 1 | 검증 | 체크섬 · 목록 · 문법과 조각 설정을 지키는 시험을 돌린다 | 저장소 → 통과 / 실패 | 부수효과 (입구) |
| 2 | 조각 고르기 | 시간표로 무게를 맞춰 이 조각이 돌 시험을 고른다 (코어의 실행기 그대로) | 시험 목록 · 시간표 · 조각 번호 → 시험 목록 | 순수 |
| 3 | 차례로 돌리기 | 고른 시험을 하나씩 돌린다 (코어의 실행기 그대로) | 시험 목록 → 결과 줄 | 부수효과 (실행) |
| 4 | 묶음 고르기 | 부분 번호로 원자성 시험의 묶음을 고른다 | 부분 번호 → 묶음 번호들 | 순수 |
| 5 | 고른 묶음 돌리기 | 고른 묶음의 경우만 돌린다 | 묶음 번호들 → 검사 줄 · 결과 줄 | 부수효과 (실행) |
| 6 | 봇의 가벼운 검증 | 체크섬 · 목록 · 문법 · 복사본 검증만 한다 | 새 코어 복사본 → 통과 / 실패 | 부수효과 (입구) |

- 부수효과 위치: 시험 실행(3 · 5)과 검증(1 · 6). 무엇을 돌릴지 고르는 것(2 · 4)은 글만 받아 글만 낸다
- 재사용: 조각 고르기와 돌리기는 복사본 안의 코어 실행기를 그대로 쓴다. 새로 짓는 것은 원자성 시험의 묶음 고르기뿐이다

## Guardrails

- 시험 파일의 검사 내용과 시간 한도는 건드리지 않는다. 원자성 시험은 묶음을 고르는 길만 더한다 — 번호 없이 돌리면 지금과 같은 67줄이 나온다
- 조각 수는 한 곳에서 바꾸면 시험이 나머지 자리의 어긋남을 잡게 한다(이름 · 목록 · 명령)
- 맥 작업은 한 번에 다섯 개를 넘기지 않는다 — 계정이 맥 작업을 다섯 개까지만 함께 돌린다(코어 CI 의 기록)
- 봇의 워크플로는 main 에서 돈다 — 설정이 main 에 닿아야 다음 코어 릴리스부터 적용된다
- 코덱스 저장소의 PR 제목에는 계획이 코어에 있다는 것을 밝힌다(출처 검사)
- 목표에 못 미치면 멈추고 실제 값을 알린다 — 한도를 느슨하게 하거나 시험을 빼서 맞추지 않는다

## Exit criteria

- All TESTS.md scenarios pass
- 설정을 고친 PR 의 실행에서: 가장 긴 작업이 300초 안, 코어 조각의 시험 수 합이 고치기 전과 같고, 원자성 부분의 검사 줄 합이 67
- 코덱스 저장소의 develop → stage → main 까지 설정이 반영된다(새 버전 없음)
- 릴리스 흐름과 코어 → 코덱스 전체 시간은 반영하는 실행과 다음 코어 릴리스에서 재서 마무리 보고에 적는다 — 이번에 잴 수 없는 값은 못 쟀다고 적는다

## Suggested path

1. 원자성 시험의 묶음별 시간을 재고, 조각 설정을 지키는 시험을 먼저 쓴다 — 고치기 전에 실패하는 것을 눈으로 본다
2. 원자성 시험에 묶음을 골라 도는 길을 더한다 — `묶음 고르기`, `고른 묶음 돌리기`
3. PR 검사의 코어 시험을 여덟 조각으로 나눈다 — `조각 고르기`, `차례로 돌리기`
4. PR 검사에 원자성 시험 작업(운영체제 둘 × 부분 셋)을 더하고 어댑터 작업에서 그 파일을 뺀다 — `고른 묶음 돌리기`
5. 동기화 봇의 검증에서 시험 실행을 뺀다 — `봇의 가벼운 검증`
6. 코덱스 저장소에 PR 을 올려 새 조각으로 돈 실제 시간을 읽고 사용자에게 보인다 — 목표 값과 견준다
7. 병합하고 develop → stage → main 까지 반영한 뒤 그 실행의 시간을 잰다 — 릴리스 흐름의 값을 얻는다
8. 마무리 보고를 채우고 보관한다 — 다음 코어 릴리스 때 잴 값을 남은 것으로 적는다

## Risks / Open Questions

- 조각으로 나누면 러너마다 준비(체크아웃 · 복사)가 따로 든다 — 조각이 너무 많으면 준비 시간이 이득을 먹는다. 여덟에서 시작해 실제 값으로 본다
- 러너 속도가 작업마다 −27% ~ +24% 다르다(코어의 기록) — 가장 긴 조각이 300초에 닿을 수 있다. 닿으면 조각 수를 다시 본다
- 맥 러너가 붐비면 맥 작업이 줄을 서서 전체가 길어진다 — 맥 작업은 넷(어댑터 1 · 원자성 3)으로 다섯 안에 둔다
- 봇이 시험을 돌리지 않으므로 고장 난 코어가 오면 PR 이 빨간불로 열린다 — 병합은 막히지만 PR 은 생긴다
- 릴리스 흐름은 PR 둘이 차례로 검사를 기다린다 — PR 검사가 5분이어도 12분 안에 들어오는지는 재 봐야 안다
