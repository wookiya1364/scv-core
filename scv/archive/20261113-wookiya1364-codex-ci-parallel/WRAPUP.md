# 마무리 보고 — 코덱스 래퍼의 CI 시간 줄이기 — 시험을 여러 러너에 나눠 함께 돌린다

## 1. 문제

- 상황: 코덱스 래퍼의 PR 검사가 한 번에 12 ~ 15분, 코어가 릴리스된 뒤 코덱스 래퍼가 릴리스될 때까지 71 ~ 74분 걸린다. 사용자가 "터무니없이 많은 시간"이라고 했다(2026-11-13)
- 기대: 클로드 코드 래퍼만큼 — PR 검사 5분 안 · 릴리스 흐름 12분 안 · 코어 → 코덱스 릴리스 30분 안
- 실제: PR 검사 741 ~ 923초 · 릴리스 흐름 1,541 ~ 1,593초 · 코어 → 코덱스 71 · 74분. 클로드 코드 래퍼는 192 ~ 328초 · 592 ~ 646초 · 26 · 28분
- 재현 조건: 코덱스 저장소에 아무 PR 이나 올리거나 코어를 릴리스한 뒤, GitHub 실행 기록에서 워크플로와 작업의 걸린 시간을 읽는다

## 2. 관찰

- 관찰한 사실과 측정값: 릴리스 PR 한 번의 검사에서 오래 걸린 단계는 셋이다 — 코어 시험 전부 695초(러너 하나, 4개씩 겹쳐) · 어댑터 시험 맥 441초 · 리눅스 262초. 어댑터 시험 넷 가운데 원자성 시험 파일 하나가 맥 395초 · 리눅스 240초이고 나머지 셋은 합쳐 1분 안이다. 동기화 봇은 PR 을 열기 전에 같은 시험 전부를 한 번 더 돈다(768 ~ 1,068초). 코어 시험 시간표의 core/tests 102줄 합은 1,167초다
- 정상일 때와 차이: 코어 자신은 같은 시험을 조각으로 나눠 돈다(릴리스 검증 여덟 조각, 조각마다 125 ~ 227초). 클로드 코드 래퍼는 가장 긴 단계가 맥 247초다. 코덱스만 러너 하나에서 차례로 돈다

## 3. 가설

- H1: 시간의 대부분은 러너 하나에서 차례로 도는 두 덩어리(코어 시험 전부 · 원자성 시험)다 — 러너에 나누면 가장 긴 조각의 시간으로 준다
- H2: 같은 덩어리가 릴리스 한 번에 여러 번 돌아서 전체가 길다 — 봇의 한 번을 없애면 그만큼 준다
- H3: 여덟 조각 · 세 부분이면 PR 검사가 5분 안에 든다

## 4. 실험

- 방법과 같게 둔 것: 시험의 내용과 한도는 그대로 두고 어디서 도는지만 바꿨다. 설정을 고친 PR(코덱스 504)이 새 조각으로 스스로 돌았고, 그 실행 기록에서 작업별 시간 · 조각의 통과 수 · 부분의 검사 줄 수를 읽어 고치기 전 실행(코덱스 501)과 견줬다. 원자성 시험은 로컬 맥에서 묶음별 시간을 먼저 쟀다(4 · 59 · 104 · 60 · 72초)
- 결과와 가설별 판정: H1 맞음 — PR 검사 전체 741 ~ 923초 → 227초, 가장 긴 작업 695초 → 205초. H2 는 이번에 잴 수 없다 — 봇의 실행은 다음 코어 릴리스 때 돈다. H3 맞음 — 여덟 조각(123 ~ 205초) · 세 부분(맥 142 ~ 170초 · 리눅스 58 ~ 102초)으로 5분 안에 들었다. 릴리스 흐름(새 버전 없이 main 까지)은 1,541 ~ 1,593초 → 673초

## 5. 원인

- 직접 원인과 일어난 길: 코덱스의 PR 검사는 코어 시험 전부를 러너 하나에서(4개씩 겹쳐) 돌렸고, 어댑터 작업은 5분짜리 원자성 시험 파일을 통째로 차례로 돌렸다. 러너 하나의 시간이 곧 검사의 시간이었고, 그 검사가 동기화 봇 · 동기화 PR · 릴리스 PR · 릴리스 흐름의 PR 둘에서 되풀이됐다
- 근본 원인: 코어는 자기 CI 를 조각으로 나눴지만(2026-11 초) 그 방식을 래퍼로 옮기지 않았다 — 코덱스의 설정은 "한 러너에서 겹쳐 돌리기"에 머물렀다. 봇의 검증은 PR 검사가 생기기 전의 안전장치가 그대로 남아 같은 시험을 두 번 돌렸다

## 6. 해결과 검증

- 해결책과 고른 이유: PR 검사의 코어 시험을 여덟 조각으로(복사본 안의 코어 실행기를 그대로 씀), 원자성 시험을 운영체제 둘 × 세 부분으로 나눠 함께 돌리고, 동기화 봇은 파일 검증만 한다(사용자 선택). 원자성 시험은 다섯 묶음을 함수로 감싸 부분 번호로 고르게 했다 — 본문은 건드리지 않았고 번호 없이 돌리면 전부 돈다. 조각 수 · 부분 구성 · 봇의 검증이 어긋나면 잡는 시험 하나를 더했다. 여덟은 시간표의 합(1,167초)을 조각마다 145초쯤으로 나눈 값이다
- 고치기 전후 값: PR 검사 전체 741 ~ 923초 → 227초. 가장 긴 작업 695초 → 205초. 원자성 시험 맥 395초 → 가장 긴 부분 170초, 리눅스 240초 → 102초. 릴리스 흐름 1,541 ~ 1,593초 → 673초(새 버전 없는 반영 실행). 코어 시험의 통과 수 101 → 13 + 14 + 12 + 14 + 9 + 12 + 13 + 14 = 101. 원자성 검사 줄 67 → 17 + 29 + 21 = 67(맥 · 리눅스 둘 다). 코어 → 코덱스 릴리스 전체(71 ~ 74분)는 이번에 못 쟀다
- 부작용과 회귀 시험: 지키는 시험(test-ci-shards.sh) 7줄 — 고친 설정은 통과, 고치기 전 설정은 종료 코드 1(여섯 군데를 댐), 한 곳만 바꾼 다섯 가지를 잡고, 잘못된 부분 번호 다섯은 종료 코드 2 로 아무것도 돌지 않는다. 코덱스 PR 504 의 검사 18개 성공, 반영 흐름의 PR 둘도 성공. 남은 것: 봇이 시험을 돌리지 않으므로 고장 난 코어가 오면 PR 이 빨간불로 열린다(병합은 막힌다). 러너 수가 늘어 작업이 3개에서 17개가 됐다 — 맥 작업은 넷으로 계정 한도(다섯) 안이다. 봇의 실제 시간과 코어 → 코덱스 전체 시간은 다음 코어 릴리스에서 잰다

## 7. 배운 것

- 다음에 같은 문제를 만나면 진단하는 법: "CI 가 길다"면 실행 기록에서 작업 → 단계 → 시험 순으로 시간을 읽어 덩어리를 찾는다(이번에 단계 둘이 전체의 대부분이었다). 그 덩어리가 릴리스 한 번에 몇 번 도는지도 센다 — 한 번의 길이와 되풀이 횟수는 따로 줄인다
- 다른 곳에도 쓸 수 있는 것: 설정을 고친 PR 은 새 설정으로 스스로 도니, 올리기만 하면 실제 값이 나온다 — 미리 어림하지 않아도 된다. 긴 시험 파일을 나눌 때 본문을 고치지 않고 묶음을 함수로 감싸 번호로 고르게 하면 합이 그대로인지를 줄 수로 바로 견줄 수 있다. 나눈 수는 이름 · 목록 · 명령 세 곳에 적히므로 시험 하나가 셋을 맞대게 한다. 아직 부분 번호를 모르는 시험을 번호를 줘서 부르면 전부를 돈다 — 지키는 시험을 먼저 쓸 때 그 호출이 10분을 썼다
