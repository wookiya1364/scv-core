# 재지 못한 함수만 다시 재기

## Summary

재는 명령 시험의 S13 이 맥 러너에서 "재지 못함 1"로 실패했다(코어 PR 527 의 맥 조각 7번, 두 번 연속). 재 보니 원인은 "너무 짧음"이 아니라 "벽시계가 CPU 보다 훨씬 큼"이었다: 맥 러너가 잠깐 바쁠 때 프로그램을 띄우는 함수는 벽시계만 늘고 CPU 는 그대로다.
그 순간은 짧다. 재는 명령이 "재지 못함"이 나온 함수만 최대 두 번 더 잰다. 규칙과 한도는 바꾸지 않는다.

## Goals / Non-Goals

- **Goals**
  - 함수 하나를 잰 결과가 "재지 못함"이면 같은 되풀이 수로 최대 두 번 더 잰다. 잰 값이 나오면 그 값을 쓴다
  - 다시 잰 것을 숨기지 않는다 — 표 아래에 "다시 잰 함수" 한 줄, 살펴보기용 기록 파일
  - 가짜 시간 도구로 "한 번 못 재고 다시 재서 잼" · "계속 못 잼"을 시험으로 지킨다
  - 고친 뒤 시험 뒤의 맥 러너 3대에서 다시 재서 "재지 못함" 줄 수를 전(0 · 2 · 11)과 견준다
- **Non-Goals**
  - "재지 못함"의 규칙 · 한도 바꾸기 (사용자 선택 2026-11-12)
  - 붐빔 재기에 프로그램 띄우기를 포함하기 (판정이 바뀐다 — 따로 재 봐야 한다)
  - 왜 일곱 조각의 7번 조각에서 났는지 가르기 (추정만 있다)

## Approach Overview

사용자가 2026-11-12 선택 창에서 정한 것: 고칠 길 "재지 못한 함수만 다시 잼".

잰 것 (2026-11-12, 코어 저장소의 측정 실행 43221464415 — 맥 러너 여섯 대, 러너마다 임시 함수 셋 × 두 배 × 여덟 번 = 48줄):

| 러너 상태 | 벽시계 ÷ CPU | 벽시계 0.5초 이상 | 그중 비율 1.5 이상 | 재지 못함 |
|---|---|---|---|---|
| 갓 띄움 1 · 2 · 3 | 1.00 ~ 1.62 | 0 · 3 · 6줄 | 0 · 0 · 0줄 | 0 · 0 · 0줄 |
| 7번 조각의 시험 뒤 1 · 2 · 3 | 1.01 ~ 2.18 | 0 · 7 · 18줄 | 0 · 3 · 16줄 | 0 · 2 · 11줄 |

- 시험 뒤의 러너 3번에서는 실제 시험도 S13 에서 실패했다(재현). 재지 못한 것은 `t_rev`(프로그램 하나를 띄우는 함수)였다.
- 그 순간 맥의 시스템 프로그램이 CPU 를 35 ~ 49%씩 쓰고 있었다(`iconservicesagent` · `secinitd` · `mds_stores` · `mdworker_shared`).
- 붐빔 재기(`pb_load_now`)는 CPU 만 쓰는 반복이라 프로그램 띄우기의 기다림을 잡지 못한다 — 비율 1.5 이상 19줄 가운데 6줄만 붐빔 보정으로 건졌다.
- 일시적이다: 가장 나쁜 러너에서 라운드별 재지 못함은 3 · 0 · 1 · 1 · 3 · 1 · 2 · 0 이었다. 한 줄이 재지 못할 가능성은 11/48(23%), 세 번 모두 못 잴 가능성은 약 1.2%다.
- 이 맥에서는 벽시계 ÷ CPU 가 1.03 ~ 1.12 로 한 번도 재지 못하지 않았다.

하는 일:

1. **다시 잴지 정하기** — 순수 함수가 "지금 잣대 · 다시 잰 횟수 · 한도"로 한 번 더 잴지 가린다.
2. **다시 재기** — 함수 하나를 재는 곳(`pb_measure_fn`)이 "재지 못함"이면 같은 되풀이 수로 다시 잰다. 한도는 2번(`SCV_PB_REMEASURE`, 0 이면 끔).
3. **남기기** — 다시 잰 함수와 횟수를 표 아래 한 줄로 보이고, 기록 파일(`SCV_PB_REMEASURE_LOG`)을 주면 줄마다 적는다.
4. **시험** — 시간 재는 도구를 바꿔 끼울 수 있게 하고(`SCV_PB_TIME_TOOL`), 가짜 도구로 두 장면을 지킨다.

## 순수함수 · 파이프라인 (Pure functions & pipeline)

함수 하나를 재는 줄에 "다시 잴지 정하기" 한 단계가 끼어든다. 재는 일(프로그램을 돌리고 시계를 읽음)은 지금처럼 부수효과이고, 정하는 일만 순수다.

```
flow(
  run_measured,      // 함수 · 되풀이 수 → 벽시계 · CPU · 메모리               (부수효과: 실행 · 시계)
  pb_pick_measure,   // 벽시계 · CPU · GPU 값 · 붐빔 → cpu | wall-gpu | unmeasured  (순수, 그대로)
  pb_remeasure,      // 잣대 · 다시 잰 횟수 · 한도 → 1(한 번 더) | 0            (순수, 새로)
  run_measured,      // (1 일 때만) 같은 되풀이 수로 다시                        (부수효과)
  pb_row,            // 잰 줄 둘 → 표의 한 줄                                    (순수, 그대로)
)
```

| # | 단계 | 하는 일 | 받는 값 → 돌려주는 값 | 순수/부수효과 |
|---|---|---|---|---|
| 1 | run_measured | 함수를 정한 횟수만큼 돌려 시간과 메모리를 잰다 | 함수 · 되풀이 수 → 잰 값 | 부수효과 (실행 · 시계) |
| 2 | pb_pick_measure | 잰 값으로 판정 잣대를 고른다 | 벽시계 · CPU · GPU 값 · 붐빔 → 잣대 | 순수 |
| 3 | pb_remeasure | 재지 못했고 한도가 남았으면 한 번 더 재라고 한다 | 잣대 · 다시 잰 횟수 · 한도 → 1 \| 0 | 순수 |
| 4 | pb_row | 잰 줄을 표의 한 줄로 만든다 | 잰 줄 둘 → 표 줄 | 순수 |

- 부수효과 위치: 재기(1)와 다시 잰 것을 기록 파일에 적는 일. 둘 다 `pb_measure_fn` 안이다.
- 재사용: 재기 · 잣대 고르기 · 표 만들기는 그대로 쓴다. 되풀이 수는 처음 맞춘 값을 그대로 쓴다.

### 합성 설계 체크리스트 (Composition checklist)

| # | 물음 | 답 | 근거 |
|---|---|---|---|
| 1 | 각 단계가 요소 단위 단항 순수 함수인가 | 새 순수 함수 둘은 받은 글자만 보고 돌려준다(다시 잴지 · 표 아래 한 줄). 파일도 시계도 읽지 않는다. 재는 검사에서 둘 다 한도 안이다 | `core/scripts/lib/pure-bench.sh` 282줄(`pb_remeasure`) · 294줄(`pb_remeasure_line`) |
| 7 | 부수효과가 파이프라인 양 끝에만 있는가 | 재기는 이 줄의 일 자체다. 정하는 단계는 재기 사이에서 값만 본다. 다시 잰 것을 파일에 적는 일은 재기 뒤 한 곳이다 | `core/scripts/pure-bench.sh` 274줄(다시 잴지 묻는 반복) · 285줄(기록) · 120줄(시간 도구 고르기) |
| 그 밖 | 2 · 3 · 4 · 5 · 6 · 8 · 9 · 10 | 해당 없음 | 순회하는 자료가 없다 — 함수 하나에 최대 두 번 더 잰다 |

## Guardrails

- `pb_pick_measure` 의 규칙과 수(50ms · 20ms · 500ms · 1.5배)를 고치지 않는다.
- 다시 재기는 "재지 못함"일 때만 한다. 처음에 잰 함수는 더 재지 않는다.
- 다시 잰 뒤에도 재지 못하면 "재지 못함"으로 적는다.
- 잰 줄의 칸 수와 표의 끝 줄을 바꾸지 않는다 — 읽는 쪽(견주기 · 표 만들기 · 시험)이 그대로 돈다.
- 측정용 브랜치는 합치지 않고 지운다.
- 맥과 리눅스, 옛 셸과 새 셸에서 모두 돈다.

## Exit criteria

- TESTS.md 의 T1 ~ T5 가 통과한다
- 시험 뒤의 맥 러너에서 다시 잰 "재지 못함" 줄 수가 이 계획에 적혀 있다
- 측정용 브랜치가 지워져 있다

## Suggested path

1. 다시 잴지 정하는 순수 함수와 예를 쓰고 함수 사전을 다시 만든다 — `pb_remeasure`
2. 함수 하나를 재는 곳이 재지 못하면 같은 되풀이 수로 다시 재게 하고, 다시 잰 것을 표 아래와 기록 파일에 남긴다 — `run_measured`, `pb_pick_measure`, `pb_remeasure`
3. 시간 재는 도구를 바꿔 끼울 수 있게 하고, 가짜 도구로 두 장면을 시험에 더한다 — `pb_remeasure`
4. 두 셸에서 재는 명령 시험 넷과 함수 사전 검사를 돌린다 — 통과를 확인하는 일
5. 시험 뒤의 맥 러너 3대에서 다시 재서 전과 견주고, 측정용 브랜치를 지운다 — 고친 것이 실제 환경에서 듣는지 확인하는 일
6. PR 을 develop 에 올리고 검사 결과를 읽는다 — 다른 운영체제에서의 통과를 확인하는 일

## 결과 (2026-11-12)

고친 재는 명령을 측정용 브랜치에 실어, 7번 조각의 시험을 먼저 돌린 맥 러너에서 다시 쟀다(실행 43224317080 · 43225519680, 러너마다 48줄).

| 실행 | 러너 | 벽시계 0.5초 이상 | 그중 비율 1.5 이상 | 처음에 재지 못함 → 다시 잼 | 끝에 남은 재지 못함 |
|---|---|---|---|---|---|
| 고치기 전 | 3대 | 0 · 7 · 18줄 | 0 · 3 · 16줄 | (다시 재지 않음) | 0 · 2 · 11줄 |
| 고친 뒤 첫째 | 3대 | 0 · 4 · 6줄 | 0 · 1 · 1줄 | 0 · 0 · 0번 | 0 · 0 · 0줄 |
| 고친 뒤 둘째 | 6대 | 4 · 10 · 5 · 12 · 9 · 0줄 | 0 · 2 · 1 · 0 · 0 · 0줄 | 1 · 1 · 1 · 0 · 0 · 0번 | 모두 0줄 |

- 고친 뒤 아홉 대 432줄 가운데 처음에 재지 못한 측정은 3번이었고, 셋 모두 한 번 다시 재서 값이 나왔다(`cpu`). 끝에 남은 "재지 못함"은 0줄이다. 그 아홉 대에서 실제 시험의 S13 도 모두 통과했다.
- 한계: 고친 뒤의 러너들은 고치기 전의 가장 나쁜 러너(48줄 가운데 11줄)만큼 바쁘지 않았다. 그만큼 바쁜 상태에서의 값은 재지 못했다 — 그때의 통과 가능성 약 93%는 고치기 전 값으로 한 셈이다.
- 측정용 브랜치는 지웠다.

## Risks / Open Questions

- 계속 바쁜 컴퓨터에서는 다시 재도 재지 못한다 — 시험이 그때도 실패할 수 있다(가장 나쁜 러너의 값으로 셈하면 약 7%).
- 왜 일곱 조각의 7번 조각에서 두 번 연속 났는지는 가르지 못했다. 시험이 시작되는 때가 맥의 시스템 프로그램이 바쁜 때와 겹쳤다는 추정뿐이다.
- 다시 재면 그 함수에만 한 번에 0.3 ~ 0.8초가 더 든다.
