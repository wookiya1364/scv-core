# 1부

## 1부 질문 1 — 

**rebase와 merge 선택 기준**

혼자 쓰는 브랜치를 정리할 때는 rebase, 여럿이 같이 쓰는 브랜치에 합칠 때는 merge가 기본임. 이미 남과 공유한 기록은 rebase로 고치지 않는 것이 가장 중요한 원칙임.

- **차이**: merge는 두 갈래를 그대로 두고 "합쳤다"는 기록(머지 커밋)을 하나 더 남기는 방식이고, rebase는 내 작업을 최신 기준 위에 다시 쌓아 한 줄로 만드는 방식임. 그래서 merge는 기록이 사실대로 남지만 복잡해지고, rebase는 깔끔하지만 기존 커밋이 새 커밋으로 바뀜.
- **rebase가 맞는 경우**: 아직 올리지 않았거나 나만 쓰는 작업 브랜치에 main의 최신 내용을 반영할 때, 그리고 리뷰 요청 전에 자잘한 커밋을 정리할 때임. 기록이 한 줄이 되어 읽기 쉽고 문제 커밋을 찾기도 쉬워짐.
- **merge가 맞는 경우**: 작업 브랜치를 main 같은 공용 브랜치에 합칠 때, 그리고 여러 사람이 같이 쓰는 브랜치에 최신 내용을 가져올 때임. 기존 커밋을 건드리지 않아 안전하고, 언제 무엇을 합쳤는지도 남음.
- **공유한 브랜치를 rebase하면 안 되는 이유**: rebase는 커밋을 새로 만들기 때문에 다른 사람이 받아 간 기록과 내 기록이 서로 달라짐. 그러면 강제로 덮어써서 올려야 하고, 그 과정에서 동료의 작업이 꼬이거나 사라질 수 있음.
- **충돌 처리**: merge는 충돌을 한 번에 몰아서 해결하고, rebase는 커밋마다 하나씩 해결함. 오래 떨어져 있던 브랜치라면 rebase 쪽이 같은 충돌을 여러 번 만날 수 있어 더 번거로움.
- **흔한 조합**: 작업 중에는 내 브랜치를 rebase로 최신 상태로 맞추고, 끝나면 main에 merge로 합치는 방식임. 다만 팀 규칙이 정해져 있으면 그것이 우선임.


## 1부 질문 2 — git rebase 와 merge 는 언제 어느 쪽을 써야 해? 이유도 설명해 줘.

**`set -e`가 오류를 놓치는 이유**

`set -e`는 "명령이 실패하면 무조건 멈춤"이 아니라, "실패 여부를 아무도 확인하지 않는 명령이 실패했을 때만 멈춤"이라서 예외 자리가 많음.

- **조건 검사 자리에 있는 명령**: `if`, `while`, `until`의 조건, `!`로 뒤집은 명령, `&&`·`||`로 이어진 줄의 마지막을 뺀 나머지는 실패해도 멈추지 않음. 셸이 "실패를 이미 누군가 확인하고 있다"고 보기 때문임.
- **함수 안까지 번지는 예외 (가장 자주 당하는 함정)**: 함수를 `if myfunc; then`이나 `myfunc || echo 실패`처럼 부르면, 그 함수 안의 모든 명령에서 `set -e`가 꺼짐. 그래서 함수 중간에서 명령이 실패해도 끝까지 실행되고, 함수 안에서 `set -e`를 다시 써도 소용없음.
- **파이프 중간의 실패**: `a | b`는 마지막 명령 `b`의 결과만 봄. `a`가 실패해도 `b`가 성공하면 통과하므로, `set -o pipefail`을 함께 켜야 잡힘.
- **변수 선언과 함께 쓴 명령 치환**: `local x=$(실패하는명령)`이나 `export x=$(...)`는 `local`·`export` 자체가 성공해서 실패가 가려짐. 선언과 대입을 두 줄로 나누면(`local x` 다음 줄에 `x=$(...)`) 잡힘.
- **명령 치환 안쪽**: `echo "$(실패하는명령)"`처럼 다른 명령의 인자로 쓰이면 바깥 `echo`가 성공하므로 지나감. bash에서는 `$(...)` 안쪽 셸이 `set -e`를 물려받지 않는 경우도 있어서 `shopt -s inherit_errexit`(bash 4.4 이상)가 필요함.
- **백그라운드 실행과 프로세스 치환**: `명령 &`나 `<(명령)`의 실패는 `wait`로 직접 결과를 받아 확인하지 않으면 드러나지 않음.
- **산술 표현의 반대 방향 함정**: `((count++))`는 결과값이 0이면 "실패"로 취급되어, 오류가 아닌데도 스크립트가 멈춤.

**권장하는 대응**

- 스크립트 첫머리에 `set -euo pipefail`을 쓰고, bash 4.4 이상이면 `shopt -s inherit_errexit`도 추가함.
- 중요한 명령은 `set -e`에 기대지 말고 `명령 || { echo "실패" >&2; exit 1; }`처럼 직접 확인함.
- 함수의 성공 여부를 `if`로 검사해야 한다면, 함수 안의 각 단계에 `|| return 1`을 붙여 둠.
- `shellcheck`(셸 스크립트 문법 검사 도구)을 돌리면 `local x=$(...)` 같은 패턴을 자동으로 짚어줌.


## 1부 질문 3 — bash 스크립트에서 set -e 를 써도 오류가 그냥 지나가는 경우가 왜 생겨?

**캐시를 넣으면 버그가 늘어나는 이유**

같은 정보가 원본과 복사본 두 군데에 생기고, 둘이 어긋나는 순간이 반드시 생기기 때문임. 캐시(자주 쓰는 결과를 미리 저장해 두고 재사용하는 것)는 속도를 얻는 대신 "이 복사본이 아직 맞는가"라는 새 문제를 떠안는 구조임.

- **낡은 값 문제**: 원본이 바뀌었는데 캐시는 옛 값을 계속 돌려줌. 그래서 언제 캐시를 버릴지 정해야 하는데, 원본을 바꾸는 경로가 여러 개라 하나만 빠뜨려도 틀린 값이 나감.
- **재현이 어려움**: 캐시가 차 있을 때와 비어 있을 때 동작이 달라짐. 그래서 "내 쪽에서는 잘 되는데" 같은 상황이 생기고, 다시 시도하면 사라져서 원인 찾기가 오래 걸림.
- **동시 접근 문제**: 여러 요청이 동시에 읽고 쓰면 순서가 꼬여, 옛 값이 새 값을 덮어쓰는 일이 생김.
- **구분 기준 실수**: 무엇을 기준으로 저장할지 잘못 정하면 다른 사람의 결과가 나감. 예를 들어 사용자 구분을 빼먹으면 A의 정보가 B에게 보이는 사고가 됨.
- **만료 순간의 몰림**: 캐시가 한꺼번에 비워지면 모든 요청이 원본으로 몰려 서버가 느려지거나 죽음.
- **문제를 가림**: 원본이 느리거나 고장 나도 캐시 덕에 멀쩡해 보이다가, 캐시가 비는 순간 한꺼번에 드러남.
- **테스트할 경우의 수 증가**: 캐시 있음·없음·낡음·만료 직전을 각각 확인해야 해서 빠지는 경우가 생김.

그래서 보통은 실제로 느린 곳을 측정으로 확인한 뒤에만 넣고, 넣을 때는 "언제 버릴지"를 먼저 정하는 것이 권장됨.

# 2부

## 2부 질문 1 — 

**rebase와 merge 선택 기준**

아직 나 혼자만 쓰는 브랜치를 정리할 때는 rebase, 여럿이 함께 쓰는 브랜치에 작업을 합칠 때는 merge가 기본임.

- **차이의 핵심**: merge는 두 갈래의 기록을 그대로 두고 "여기서 합쳤다"는 기록을 하나 더 남기는 방식이고, rebase는 내 작업을 최신 기준 위에 다시 쌓아 기록을 새로 쓰는 방식임. 그래서 merge는 다른 사람과 공유해도 안전하지만 기록이 복잡해지고, rebase는 기록이 한 줄로 깔끔해지지만 이미 공유한 브랜치에 쓰면 다른 사람의 기록과 어긋남.
- **rebase가 맞는 경우**: 내 작업 브랜치에 메인 브랜치의 최신 내용을 반영할 때와 합치기 전에 자잘한 커밋을 정리할 때임.
- **merge가 맞는 경우**: 완성된 작업을 메인 브랜치에 합칠 때와 여러 사람이 같이 쓰는 브랜치를 다룰 때임.
- **꼭 지킬 규칙**: 이미 올려서 다른 사람이 받아 간 브랜치는 rebase하지 않음. 기록이 새로 쓰여 강제로 덮어써야 하고, 그 과정에서 동료의 작업이 꼬이거나 사라질 수 있기 때문임.
- **충돌 처리의 차이**: merge는 충돌을 한 번에 몰아서 해결하고, rebase는 커밋마다 하나씩 해결해야 함. 오래 묵은 브랜치라면 merge 쪽이 덜 번거로움.
- **흔한 조합**: 작업 중에는 rebase로 내 브랜치를 최신 상태로 맞추고, 끝나면 merge로 메인에 합치는 방식임. 팀에 정해진 규칙이 있으면 그 규칙이 우선임.


## 2부 질문 2 — git rebase 와 merge 는 언제 어느 쪽을 써야 해? 이유도 설명해 줘.

**`set -e`가 오류를 놓치는 이유**

`set -e`는 "실패하면 무조건 멈춤"이 아니라, 실패 여부를 검사 중인 자리나 결과가 다른 명령에 가려지는 자리에서는 멈추지 않도록 설계된 규칙임. 그래서 아래 경우에는 오류가 나도 스크립트가 그대로 진행함.

- **파이프 중간의 실패**: `a | b`에서는 마지막 명령 `b`의 결과만 보므로 `a`가 실패해도 통과함. `set -o pipefail`을 함께 켜면 잡힘.
- **조건 검사 자리의 명령**: `if`, `while`의 조건이나 `&&`, `||`로 이어진 명령(맨 마지막 제외), `!`를 붙인 명령은 실패해도 멈추지 않음.
- **조건 자리에서 부른 함수 (가장 흔한 함정)**: `if my_func; then`이나 `my_func || true`처럼 부르면 함수 안 전체에서 `set -e`가 꺼지므로, 함수 중간 명령이 실패해도 끝까지 실행됨.
- **`local`·`export`와 함께 쓴 대입**: `local x=$(cmd)`는 `cmd`가 실패해도 `local` 자체가 성공해서 통과함. `local x` 다음 줄에 `x=$(cmd)`로 나누면 잡힘.
- **다른 명령의 인자로 들어간 `$(...)`**: `echo "$(cmd)"`는 `cmd`가 실패해도 `echo`가 성공하므로 통과함.
- **`$(...)` 안쪽의 실패**: 괄호 안에서는 `set -e`가 기본으로 꺼져서, 중간 명령이 실패해도 마지막 명령만 성공하면 통과함. bash 4.4 이상은 `shopt -s inherit_errexit`로 막을 수 있지만, 맥 기본 bash(3.2)에는 이 옵션이 없음.
- **백그라운드 실행과 `<(...)`**: `cmd &`나 `<(cmd)` 안의 실패는 본 스크립트에 전달되지 않음. 백그라운드는 `wait`로 결과를 직접 확인해야 함.

**줄이는 방법**

- 스크립트 첫머리에 `set -euo pipefail` 사용.
- `local` 선언과 대입을 두 줄로 분리.
- 중요한 명령은 `cmd || exit 1`처럼 직접 검사하고, `set -e`는 보조 안전망으로만 생각함.
- shellcheck(셸 스크립트 검사 도구)를 돌리면 위 함정 중 일부(`local` 대입 등)를 미리 알려줌.


## 2부 질문 3 — bash 스크립트에서 set -e 를 써도 오류가 그냥 지나가는 경우가 왜 생겨?

**캐시를 넣으면 버그가 늘어나는 이유**

캐시는 같은 정보를 두 군데에 두는 일이라, 원본과 복사본이 서로 달라지는 순간이 생기기 때문임. 그 어긋남이 드물게, 특정 타이밍에만 나타나서 찾기도 어려움.

- **핵심 흐름**: 캐시는 원본을 매번 읽는 대신 복사본을 따로 보관해 두는 것임. 원본이 바뀌면 복사본도 바꾸거나 버려야 하는데, 원본을 바꾸는 길이 여러 개라 그중 하나만 빠뜨려도 옛날 값이 계속 보이게 됨.
- **언제 버릴지 정하기 어려움**: 너무 빨리 버리면 캐시를 넣은 효과가 없고, 너무 늦게 버리면 틀린 값을 보여줌.
- **동시에 일어나는 일**: 한쪽이 원본을 고치는 사이 다른 쪽이 옛날 값을 다시 캐시에 넣으면, 틀린 값이 오래 남음.
- **구분 기준 실수**: 사용자나 권한, 언어별로 달라야 할 결과를 같은 이름으로 저장하면, 남의 정보가 보이는 사고로 이어짐.
- **재현이 어려움**: 캐시가 비어 있을 때는 정상이고 차 있을 때만 틀려서, 개발 환경에서는 안 보이고 실제 서비스에서만 터지는 경우가 많음.
- **확인할 상태가 늘어남**: 캐시가 있을 때, 없을 때, 오래됐을 때, 가득 찼을 때를 모두 따져야 해서 테스트할 경우가 몇 배로 늘어남.
- **원인이 가려짐**: 느린 원인을 고치지 않고 캐시로 덮으면, 캐시가 비는 순간 요청이 한꺼번에 원본으로 몰려 장애가 남.

그래서 보통은 느린 곳을 실제로 확인한 뒤에, 값이 조금 오래돼도 괜찮은 곳부터 넣는 것이 안전함.
