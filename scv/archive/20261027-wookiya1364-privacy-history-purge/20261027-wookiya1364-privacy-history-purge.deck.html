# 공개 저장소 개인정보 정리 — 과거 기록까지 지우고, 다시 쌓이지 않게, SCV 기록은 비공개 저장소로

## Summary

네 공개 저장소(코어 · claude 래퍼 · codex 래퍼 · 모드)의 지금 파일과 git 과거 기록에서 개인정보를 모두 지운다.
대상은 주제와 상관없는 개인 대화, 회사 팀 이름, 내 컴퓨터 경로, 세션 id다(실명 · 개인 메일은 사용자 결정으로 남긴다). 앞으로 커밋할 때 다시
쌓이지 않게 CI 검사를 건다. SCV 기록(일지 · 대화 · 드림 · 자료)은 공개 저장소에서 빼고, 새 비공개 저장소
`scv-records` 로 옮긴다. 계획의 근거로 쓰던 대화도 거기서 같은 경로로 찾는다.

사용자 요청(대화 Turn 70~71): "찾은 것 위험도 낮음~높음 모두 과거기록까지 제거 · 앞으로 쌓이지 않도록 · 열린 PR 도
깨지지 않도록 · 철저히 계획". 선택 창 답: 범위는 모드까지 네 저장소, 열린 PR 은 먼저 병합한 뒤 다시 쓴다, 세션 링크
줄은 과거에서 지우고 앞으로 안 붙인다, 비공개 저장소 이름은 scv-records.

- 코어 릴리스 payload 는 `core/` · `tools/` · 루트 문서만 담고 `scv/` 기록은 담지 않는다(`tools/export-core.sh`). 기록을 지워도 payload 와 그 해시는 그대로다(확인).
- 기록 밖(계획 · 결정 · 코드)에는 개인정보가 없다(확인). 모드만 보관 계획 하나에 세션 id 가 예시로 들어 있다.
- `git filter-repo` 가 설치돼 있지 않다(확인).
- GitHub 은 병합된 PR 의 옛 커밋(`refs/pull/*`)과 화면 캐시를 따로 보관하고, 포크에는 옛 기록이 그대로 남는다. 이 둘은 강제 덮어쓰기로 지워지지 않는다. GitHub 지원 요청이 필요하다(GitHub 공식 안내 "Removing sensitive data from a repository").

## Goals / Non-Goals

- **Goals**
  - 네 저장소의 모든 브랜치 · 태그의 파일과 커밋 메시지 · 작성자 정보에서 개인정보를 0건으로 만든다.
  - (바뀜, 2026-10-27 사용자 결정) 실명 · 개인 메일은 공개 GitHub 계정의 정체성이라 그대로 둔다 — 작성자 정보와 플러그인 설명 파일의 메일은 바꾸지 않는다.
  - SCV 기록을 비공개 `scv-records` 로 옮기고, 이 컴퓨터의 SCV 가 앞으로도 그쪽에 기록하게 한다.
  - 다시 쌓이지 않게 막는다: 커밋 작성자 설정, 네 저장소 CI 의 개인정보 검사, 세션 링크 줄 안 붙이기.
  - 릴리스 · 코어 고정 · 채널이 다시 쓴 뒤에도 그대로 동작한다.
  - GitHub 에 남는 옛 사본(PR ref · 캐시 · 포크)을 지우는 지원 요청 문안을 준비한다.
- **Non-Goals**
  - 커밋 작성자 이름 · 메일과 플러그인 설명 파일 메일 바꾸기(사용자 결정: 계정에서 빠지면 안 됨).
  - SCV 제품의 기본값("기록은 커밋") 바꾸기 — 다른 사용자 프로젝트의 동작은 그대로다. 이 저장소들만 비공개로 옮긴다.
  - 기능 변경.
  - 포크 주인의 사본을 지우는 일(우리 권한 밖). 요청만 한다.

## Approach Overview

1. **멈추고 백업한다.** 문서 PR 네 개를 먼저 병합한다. 그 뒤 네 저장소의 자동 작업(동기화 · 채널 · 릴리스)을 잠시 끈다. 각 저장소를 통째로(`--mirror`) 이 컴퓨터에 백업한다. 백업은 되돌리기용이며 어디에도 올리지 않는다.
2. **기록을 먼저 옮긴다.** 비공개 `scv-records` 를 만든다. 코어 · 모드의 지금 SCV 기록(커밋 안 된 것 포함)을 저장소별 폴더에 그대로 복사해 올린다.
3. **규칙을 만든다(순수).** 작성자 바꾸기 표, 글자 바꾸기 표(메일 · 경로 · 세션 id), 지울 경로(SCV 기록 폴더), 메시지에서 지울 줄(Claude-Session · 세션 링크)을 정한다. 실명 · 회사 팀 이름처럼 공개 코드에 적으면 안 되는 말은 이 컴퓨터의 비공개 파일에만 둔다.
4. **다시 쓴다.** 백업에서 만든 작업 사본에 `git filter-repo` 를 돌린다. 순서는 코어가 먼저다 — 코어의 옛 → 새 커밋 번호 표를 얻어, 래퍼의 `core.lock.json` · 변경 기록 속 코어 커밋 번호를 그 표로 바꾼다. 그다음 래퍼 둘, 마지막이 모드다.
5. **올리기 전에 검증한다.** 다시 쓴 사본 전체(모든 ref)를 훑어 개인정보 0건을 확인한다. 코어 태그의 payload 해시가 릴리스 자산과 같은지, 래퍼의 코어 고정이 새 코어 커밋을 가리키는지, 브랜치 · 태그 수가 같은지, 테스트가 통과하는지 확인한다.
6. **실행 직전 확인 → 올린다.** 사용자 확인 뒤 영구 브랜치 규칙을 잠시 끄고 브랜치 · 태그를 강제로 덮어쓴다. 규칙은 원래대로 되돌린다. 릴리스는 태그 이름에 붙어 있어 그대로 남는다.
7. **뒤처리.** 자동 작업을 다시 켜고, 채널 브랜치를 다시 만들고, CI 를 돌린다. 옛 설치본에서 플러그인 업데이트가 되는지 임시 설정으로 확인한다. 이 컴퓨터의 클론 · 워크트리 · 마켓 사본을 새 기록에 맞춘다. GitHub 지원 요청 문안을 사용자에게 건넨다.
8. **다시 쌓이지 않게.** 네 저장소에 작성자 noreply 설정을 하고, 코어에 개인정보 검사(`core/scripts/check-privacy.sh`)를 넣어 네 저장소 CI 에서 돌린다. 공개 저장소에서는 SCV 기록 폴더를 무시한다. 이 컴퓨터에서는 그 폴더가 `scv-records` 작업 사본을 가리키게 한다. 세션 링크 줄은 더 붙이지 않는다.

## 순수함수 · 파이프라인 (Pure functions & pipeline)

```
flow(
  snapshotRepos,     // 저장소 목록 → 백업 · 작업 사본 경로, 브랜치 · 태그 · 해시 목록 (입구)
  buildRules,        // 개인정보 목록 + 저장소 → 작성자 표 · 글자 바꾸기 표 · 지울 경로 · 지울 메시지 줄
  planRewrite,       // 규칙 + 저장소 → filter-repo 인자
  mapCoreShas,       // 코어 옛→새 커밋 표 → 래퍼용 글자 바꾸기 줄 (40자 · 7자)
  scanForLeaks,      // 다시 쓴 사본의 파일 · 메시지 · 작성자 → 남은 개인정보 목록
  compareInvariants, // 전 · 후 목록 → 어긋난 것 (payload 해시 · 브랜치 · 태그 · 고정)
  pushRewrite,       // 검증 통과 사본 + 사용자 확인 → 원격 덮어쓰기 (출구)
)
```

| # | 단계 | 하는 일 | 받는 값 → 돌려주는 값 | 순수/부수효과 |
|---|---|---|---|---|
| 1 | `snapshotRepos` | 네 저장소를 통째로 백업하고 작업 사본과 전(前) 목록을 만든다 | 저장소 목록 → 경로 · 목록 | 부수효과 (입구) |
| 2 | `buildRules` | 무엇을 무엇으로 바꾸고 무엇을 지울지 표로 만든다 | 개인정보 목록 → 규칙 표 | 순수 |
| 3 | `planRewrite` | 규칙을 저장소별 다시 쓰기 명령 인자로 바꾼다 | 규칙 + 저장소 → 인자 | 순수 |
| 4 | `mapCoreShas` | 코어 커밋 번호가 바뀐 대로 래퍼 속 번호를 바꿀 줄을 만든다 | 옛→새 표 → 바꾸기 줄 | 순수 |
| 5 | `scanForLeaks` | 다시 쓴 사본에 개인정보가 남았는지 찾는다 | 사본 내용 → 남은 목록 | 순수 |
| 6 | `compareInvariants` | 바뀌면 안 되는 것이 그대로인지 전 · 후를 맞춘다 | 전 · 후 목록 → 어긋남 | 순수 |
| 7 | `pushRewrite` | 확인받은 사본으로 원격을 덮어쓴다 | 사본 + 확인 → 원격 | 부수효과 (출구) |

- 부수효과 위치: `snapshotRepos`(클론 · 파일 읽기)와 `pushRewrite`(원격 덮어쓰기)만. 다시 쓰기 실행(filter-repo)은 작업 사본 안에서만 일어나고, 원격은 7단계 전까지 그대로다.
- 재사용: 코어의 `journal-append.sh --redact-only` 가린 규칙(비밀값 패턴)을 `scanForLeaks` 패턴의 출발점으로 쓴다. 코어 `tools/export-core.sh` 로 태그별 payload 해시를 다시 만든다. 개인정보 검사는 기존 출처 게이트(`check-provenance.sh`)와 같은 모양으로 branch-flow 에서 돈다.

## Guardrails

- 원격을 바꾸는 단계(규칙 끄기 · 강제 덮어쓰기 · 비공개 저장소 만들기 · 자동 작업 끄기)는 실행 직전에 사용자 확인을 받는다. 계획 승인만으로 하지 않는다.
- 덮어쓰기 전에 네 저장소의 `--mirror` 백업이 있고, 백업에서 다시 올리는 길(되돌리기)을 미리 시험해 둔다.
- 실명 · 회사 팀 이름 · 개인 메일 같은 개인 값은 공개 저장소의 코드 · 테스트 · 문서 · 계획에 적지 않는다. 이 컴퓨터의 비공개 파일과 GitHub 비밀값(Actions secret)에만 둔다. 이 계획서도 그 값을 적지 않는다.
- 영구 브랜치 규칙은 덮어쓰기 동안만 끄고, 끝나면 같은 설정으로 되돌린다(전 · 후 설정 JSON 비교).
- 모드 저장소의 다른 세션 작업 중 파일은 건드리지 않는다. 모드는 그 세션이 커밋하거나 정리한 뒤에 다시 쓴다.
- 코어 payload 는 바이트 그대로다. 바뀌면 멈춘다.
- 다시 쓰기 중에는 새 커밋 · PR 을 만들지 않는다. 자동 작업도 꺼 둔다.
- 맥 + 리눅스, bash 3.2 에서 개인정보 검사가 똑같이 돈다.

## Exit criteria

- TESTS.md 의 모든 시나리오가 통과한다.
- 네 저장소를 새로 클론해 모든 브랜치 · 태그를 훑으면 개인정보 0건이다(작성자 · 메시지 · 파일).
- 릴리스 · 코어 고정 · 채널 · CI 가 다시 쓴 뒤에도 그대로 동작한다.
- 이 컴퓨터의 SCV 가 기록을 `scv-records` 에 남기고, 공개 저장소의 작업 트리는 기록 때문에 더러워지지 않는다.
- 개인정보가 든 커밋은 네 저장소 CI 에서 막힌다.
- GitHub 지원 요청 문안이 사용자에게 전달되었다(보내는 것은 사용자 몫).

## Suggested path

1. `git filter-repo` 를 설치하고, 문서 PR 넷을 병합하고, 모드의 다른 세션 작업이 정리되었는지 확인한다 — 다시 쓰기 전 준비
2. 네 저장소를 백업하고 전 목록(브랜치 · 태그 · 태그별 payload 해시 · 규칙 설정)을 만든다 — `snapshotRepos`
3. 비공개 `scv-records` 를 만들고(확인 후) 코어 · 모드 기록을 옮긴다 — 기록을 비공개 저장소로 옮긴다
4. 규칙 표와 저장소별 인자를 만들고, 개인 값은 비공개 파일에 둔다 — `buildRules`, `planRewrite`
5. 코어를 작업 사본에서 다시 쓰고 커밋 번호 표를 얻는다 — `planRewrite`, `mapCoreShas`
6. 래퍼 둘 · 모드를 다시 쓴다(코어 번호 표 적용) — `planRewrite`
7. 남은 개인정보를 찾고 바뀌면 안 되는 것을 맞춘다. 테스트도 돌린다 — `scanForLeaks`, `compareInvariants`
8. 백업에서 되돌리는 길을 시험한다(dry-run) — 되돌리기 준비를 확인한다
9. 사용자 확인 뒤 규칙을 끄고 덮어쓰고 규칙을 되돌린다 — `pushRewrite`
10. 자동 작업을 켜고 채널을 다시 만들고 CI · 플러그인 업데이트 · 로컬 사본을 확인한다 — 다시 쓴 뒤 뒤처리
11. 개인정보 검사 · 작성자 설정 · 기록 폴더 연결 · 세션 줄 중단을 넣는다 — 다시 쌓이지 않게 막는다
12. GitHub 지원 요청 문안(PR ref · 캐시 · 포크)을 만들어 건넨다 — 남은 옛 사본 정리를 요청한다

## Risks / Open Questions

- **GitHub 의 옛 사본.** 병합된 PR 의 옛 커밋 · 화면 캐시 · claude 래퍼의 포크 1개에는 덮어쓴 뒤에도 옛 기록이 남는다. 지원 요청으로 PR ref 와 캐시는 지울 수 있다. 포크는 주인에게 부탁할 수밖에 없다. 그 전까지는 "완전 삭제"가 아니다.
- **설치된 플러그인 업데이트.** 사용자들의 마켓 사본(claude · codex)은 옛 기록을 갖고 있다. 강제 덮어쓰기 뒤 업데이트가 실패할 수 있다(미확인). 임시 설정에서 옛 설치 → 덮어쓰기 → 업데이트 순서로 확인하고, 실패하면 마켓을 지웠다 다시 넣는 안내를 릴리스 노트에 싣는다.
- **커밋 번호에 기대는 것들.** 래퍼 고정(`source_commit`), 채널 버전(`-dev.<commit>`), 변경 기록 · 릴리스 노트 속 번호, 다른 저장소의 PR 본문 링크가 바뀐다. 고정과 문서 속 번호는 번호 표로 바꾼다. GitHub PR 본문 · 댓글 속 옛 번호는 git 밖이라 바뀌지 않는다(링크만 깨짐).
- **PR 본문 · 댓글 · 릴리스 본문.** git 기록이 아니므로 다시 쓰기로 지워지지 않는다. 그 안의 개인정보(경로 · 세션 id)를 따로 훑어 API 로 고친다(범위에 넣음, TESTS T12).
- **이 컴퓨터의 다른 사본.** 형제 저장소 클론, 스크래치 클론, 워크트리, `~/.claude/plugins` 마켓 사본이 옛 기록을 갖고 있다. 다시 클론하거나 맞춘다. `~/.claude/plugins` 는 손으로 고치지 않고 마켓 업데이트 · 다시 넣기로만 맞춘다.
- **filter-repo 의 7자 번호 바꾸기.** 짧은 번호는 우연히 다른 글자와 겹칠 수 있다. 번호 표의 7자 줄은 저장소 안에서 유일한 것만 쓰고, 바꾼 줄 수를 세어 확인한다.
- **SCV 기록 폴더 연결 방식.** 공개 저장소에서 무시하는 기록 폴더가 비공개 작업 사본을 가리킬 때, SCV 스크립트(기록 쓰기 · pr-helper 의 기록 커밋)가 그대로 동작하는지 미확인이다. 실제로 돌려 확인한다(T8).

# Test Plan — 공개 저장소 개인정보 정리 — 과거 기록까지 지우고, 다시 쌓이지 않게, SCV 기록은 비공개 저장소로

## Overview

사용자가 요구한 것은 세 가지다. 첫째, 감사에서 찾은 개인정보(실명 · 개인 메일 · 주제 밖 개인 대화 · 회사 팀 이름 · 내
컴퓨터 경로 · 세션 id)를 네 공개 저장소의 과거 기록까지 모두 지운다. 둘째, 앞으로 커밋할 때 다시 쌓이지 않게 막는다.
셋째, SCV 기록은 비공개 저장소로 옮긴다. 이와 함께 열린 PR · 릴리스 · 코어 고정 · 채널이 깨지지 않아야 한다. 아래
시나리오는 이것들을 하나씩 확인한다. 개인 값(실명 · 회사 팀 이름 · 개인 메일)은 이 문서에 적지 않는다. 검사는 이
컴퓨터의 비공개 목록 파일(`~/.config/scv/privacy-terms`, 권한 600 — 저장소 밖)과 GitHub 비밀값에서 읽는다.

## Test scenarios

### T1. 새 클론의 모든 ref 에 개인정보가 없다

- **Setup**: 덮어쓴 뒤, 네 저장소를 새로 `--mirror` 클론한다.
- **Run**: 모든 브랜치 · 태그의 파일 내용 · 커밋 메시지 · 작성자 · 커미터를 비공개 목록 + 공통 패턴(개인 메일, `/Users/<이름>/`, `/private/tmp/claude-<숫자>`, `session_01…`, `Claude-Session:`)으로 훑는다.
- **Expected**: 맞는 곳 0건.
- **Pass criterion**: 네 저장소 모두 0건. 검사 스크립트 종료 코드 0.

### T2. 작성자 정보는 그대로다 (사용자 결정, 2026-10-27)

- **Run**: 다시 쓰기 전 · 후 네 저장소의 작성자 · 커미터 이름 · 메일 목록을 비교한다.
- **Expected**: 같다 — 실명 · 개인 메일은 공개 계정의 정체성이라 남긴다.
- **Pass criterion**: 목록 차이 0.

### T3. SCV 기록이 공개 저장소에서 사라졌다

- **Run**: 코어 · 모드의 모든 ref 에서 `scv/journal/`, `scv/conversations/`, `scv/dreams/`, `scv/raw/` 경로가 있었던 커밋을 찾는다.
- **Expected**: 0건. 계획 보관(`scv/archive/`) · 결정 기록은 남아 있다.
- **Pass criterion**: 기록 경로 0건, 보관 계획 수는 전과 같다.

### T4. 비공개 scv-records 에 기록이 모두 있다

- **Setup**: `scv-records`(비공개)를 클론한다.
- **Run**: 저장소별 폴더(core · mods)의 파일 수와 내용 해시를 옮기기 전 목록과 맞춘다. 보관 계획 하나를 골라 그 `raw_sources` 대화 경로가 `scv-records/<저장소>/` 아래에 있는지 본다.
- **Expected**: 파일 수 · 해시가 같고, 근거 대화를 찾을 수 있다. 저장소가 비공개다(`gh api … .private == true`).
- **Pass criterion**: 차이 0, 비공개 확인.

### T5. 코어 payload 가 바이트 그대로다

- **Run**: 다시 쓴 코어의 최근 태그 다섯 개 이상(마지막 릴리스 포함)에서 `tools/export-core.sh` 로 payload 를 만들어 해시를 낸다. 같은 태그의 GitHub 릴리스 자산 SHA-256 과 래퍼 `core.lock.json` 의 payload 해시와 맞춘다.
- **Expected**: 모두 같다.
- **Pass criterion**: 어긋남 0.

- **Expected**: 모두 있음 · 같음, 옛 번호 0건.
- **Pass criterion**: 래퍼 검증 스크립트(`tools/verify-core.sh` · `scripts/verify-core.sh`) 통과, 옛 번호 0건.

- **Run**: 전 · 후 목록을 비교한다 — 브랜치 이름 · 수, 태그 이름 · 수, 릴리스 이름 · 자산 · 최신 표시.

- **Expected**: CI 통과. 채널 브랜치가 새 코어 커밋으로 다시 만들어진다. 업데이트가 되거나, 안 되면 마켓을 지웠다 다시 넣는 안내대로 하면 된다(그 안내가 릴리스 노트에 실린다).
- **Pass criterion**: CI · 채널 통과, 업데이트 결과와 대처가 확인됨.

### T14. 되돌리는 길이 있다

- **Run**: 덮어쓰기 전에, 백업 미러로 다시 올리는 명령을 `--dry-run` 으로 돌려 본다. 덮어쓴 뒤에도 백업이 남아 있는지 확인한다.
- **Expected**: dry-run 이 ref 목록을 정확히 내놓는다. 백업이 남아 있다(공개된 곳에 올리지 않음).
- **Pass criterion**: 둘 다 참.

### T15. 열린 PR 이 깨지지 않았다

- **Run**: 덮어쓰기 직전과 직후 네 저장소의 열린 PR 목록을 본다.
- **Expected**: 직전에 열린 PR 이 0개다(문서 PR 넷은 먼저 병합). 직후에도 깨진 PR 이 없다.
- **Pass criterion**: 열린 PR 0, 또는 열린 PR 마다 diff 가 덮어쓰기 전과 같다.

### T16. GitHub 지원 요청 문안

- **Run**: 저장소별 PR 번호 범위와 옛 커밋 목록(백업에서)을 담은 지원 요청 문안을 만든다. 포크 주인에게 보낼 짧은 부탁 문안도 만든다.
- **Expected**: 사용자가 그대로 보낼 수 있는 문안 두 개.
- **Pass criterion**: 사용자에게 전달됨.

# 공개 저장소 개인정보 정리 — 과거 기록까지 지우고, 다시 쌓이지 않게, SCV 기록은 비공개 저장소로

## Summary

네 공개 저장소(코어 · claude 래퍼 · codex 래퍼 · 모드)의 지금 파일과 git 과거 기록에서 개인정보를 모두 지운다.
대상은 주제와 상관없는 개인 대화, 회사 팀 이름, 내 컴퓨터 경로, 세션 id다(실명 · 개인 메일은 사용자 결정으로 남긴다). 앞으로 커밋할 때 다시
쌓이지 않게 CI 검사를 건다. SCV 기록(일지 · 대화 · 드림 · 자료)은 공개 저장소에서 빼고, 새 비공개 저장소
`scv-records` 로 옮긴다. 계획의 근거로 쓰던 대화도 거기서 같은 경로로 찾는다.

사용자 요청(대화 Turn 70~71): "찾은 것 위험도 낮음~높음 모두 과거기록까지 제거 · 앞으로 쌓이지 않도록 · 열린 PR 도
깨지지 않도록 · 철저히 계획". 선택 창 답: 범위는 모드까지 네 저장소, 열린 PR 은 먼저 병합한 뒤 다시 쓴다, 세션 링크
줄은 과거에서 지우고 앞으로 안 붙인다, 비공개 저장소 이름은 scv-records.

### 조사로 확인한 사실 (2026-10-27)

| 항목 | 코어 | claude | codex | 모드 |
|---|---|---|---|---|
| 공개 여부 | 공개 | 공개 | 공개 | 공개 |
| 커밋 작성자 실명 · 개인 메일 | 484 | 413 | 279 | 59 |
| 커밋 메시지의 세션 id(Claude-Session 줄 등) | 172 | 76 | 57 | 39 |
| 파일 속 개인 메일 | 0 (일지 속 남의 메일 1) | 플러그인 설명 2 | 플러그인 설명 1 | 0 |
| SCV 기록 공개(일지 · 대화 · 드림 · 자료) | 있음 — 경로 · 세션 id · 개인 대화 · 회사 팀 이름 | 없음 | 없음 | 있음 — 대화 · 드림, 보관 계획에 세션 id |
| 브랜치 / 태그 | 4 / 82 | 10 / 90 | 8 / 70 | 3 / 14 |
| 포크 | 0 | **1** | 0 | 0 |
| 영구 브랜치 규칙(강제 덮어쓰기 금지, 우회자 없음) | 있음 | 있음 | 있음 | 없음 |
| 코어 커밋 번호를 고정한 곳 | — | `vendor/scv-core/core.lock.json` 의 `source_commit` | 같음 | — |

- 코어 릴리스 payload 는 `core/` · `tools/` · 루트 문서만 담고 `scv/` 기록은 담지 않는다(`tools/export-core.sh`). 기록을 지워도 payload 와 그 해시는 그대로다(확인).
- 기록 밖(계획 · 결정 · 코드)에는 개인정보가 없다(확인). 모드만 보관 계획 하나에 세션 id 가 예시로 들어 있다.
- `git filter-repo` 가 설치돼 있지 않다(확인).
- GitHub 은 병합된 PR 의 옛 커밋(`refs/pull/*`)과 화면 캐시를 따로 보관하고, 포크에는 옛 기록이 그대로 남는다. 이 둘은 강제 덮어쓰기로 지워지지 않는다. GitHub 지원 요청이 필요하다(GitHub 공식 안내 "Removing sensitive data from a repository").

## Goals / Non-Goals

- **Goals**
  - 네 저장소의 모든 브랜치 · 태그의 파일과 커밋 메시지 · 작성자 정보에서 개인정보를 0건으로 만든다.
  - (바뀜, 2026-10-27 사용자 결정) 실명 · 개인 메일은 공개 GitHub 계정의 정체성이라 그대로 둔다 — 작성자 정보와 플러그인 설명 파일의 메일은 바꾸지 않는다.
  - SCV 기록을 비공개 `scv-records` 로 옮기고, 이 컴퓨터의 SCV 가 앞으로도 그쪽에 기록하게 한다.
  - 다시 쌓이지 않게 막는다: 커밋 작성자 설정, 네 저장소 CI 의 개인정보 검사, 세션 링크 줄 안 붙이기.
  - 릴리스 · 코어 고정 · 채널이 다시 쓴 뒤에도 그대로 동작한다.
  - GitHub 에 남는 옛 사본(PR ref · 캐시 · 포크)을 지우는 지원 요청 문안을 준비한다.
- **Non-Goals**
  - 커밋 작성자 이름 · 메일과 플러그인 설명 파일 메일 바꾸기(사용자 결정: 계정에서 빠지면 안 됨).
  - SCV 제품의 기본값("기록은 커밋") 바꾸기 — 다른 사용자 프로젝트의 동작은 그대로다. 이 저장소들만 비공개로 옮긴다.
  - 기능 변경.
  - 포크 주인의 사본을 지우는 일(우리 권한 밖). 요청만 한다.

## Approach Overview

1. **멈추고 백업한다.** 문서 PR 네 개를 먼저 병합한다. 그 뒤 네 저장소의 자동 작업(동기화 · 채널 · 릴리스)을 잠시 끈다. 각 저장소를 통째로(`--mirror`) 이 컴퓨터에 백업한다. 백업은 되돌리기용이며 어디에도 올리지 않는다.
2. **기록을 먼저 옮긴다.** 비공개 `scv-records` 를 만든다. 코어 · 모드의 지금 SCV 기록(커밋 안 된 것 포함)을 저장소별 폴더에 그대로 복사해 올린다.
3. **규칙을 만든다(순수).** 작성자 바꾸기 표, 글자 바꾸기 표(메일 · 경로 · 세션 id), 지울 경로(SCV 기록 폴더), 메시지에서 지울 줄(Claude-Session · 세션 링크)을 정한다. 실명 · 회사 팀 이름처럼 공개 코드에 적으면 안 되는 말은 이 컴퓨터의 비공개 파일에만 둔다.
4. **다시 쓴다.** 백업에서 만든 작업 사본에 `git filter-repo` 를 돌린다. 순서는 코어가 먼저다 — 코어의 옛 → 새 커밋 번호 표를 얻어, 래퍼의 `core.lock.json` · 변경 기록 속 코어 커밋 번호를 그 표로 바꾼다. 그다음 래퍼 둘, 마지막이 모드다.
5. **올리기 전에 검증한다.** 다시 쓴 사본 전체(모든 ref)를 훑어 개인정보 0건을 확인한다. 코어 태그의 payload 해시가 릴리스 자산과 같은지, 래퍼의 코어 고정이 새 코어 커밋을 가리키는지, 브랜치 · 태그 수가 같은지, 테스트가 통과하는지 확인한다.
6. **실행 직전 확인 → 올린다.** 사용자 확인 뒤 영구 브랜치 규칙을 잠시 끄고 브랜치 · 태그를 강제로 덮어쓴다. 규칙은 원래대로 되돌린다. 릴리스는 태그 이름에 붙어 있어 그대로 남는다.
7. **뒤처리.** 자동 작업을 다시 켜고, 채널 브랜치를 다시 만들고, CI 를 돌린다. 옛 설치본에서 플러그인 업데이트가 되는지 임시 설정으로 확인한다. 이 컴퓨터의 클론 · 워크트리 · 마켓 사본을 새 기록에 맞춘다. GitHub 지원 요청 문안을 사용자에게 건넨다.
8. **다시 쌓이지 않게.** 네 저장소에 작성자 noreply 설정을 하고, 코어에 개인정보 검사(`core/scripts/check-privacy.sh`)를 넣어 네 저장소 CI 에서 돌린다. 공개 저장소에서는 SCV 기록 폴더를 무시한다. 이 컴퓨터에서는 그 폴더가 `scv-records` 작업 사본을 가리키게 한다. 세션 링크 줄은 더 붙이지 않는다.

## 순수함수 · 파이프라인 (Pure functions & pipeline)

```
flow(
  snapshotRepos,     // 저장소 목록 → 백업 · 작업 사본 경로, 브랜치 · 태그 · 해시 목록 (입구)
  buildRules,        // 개인정보 목록 + 저장소 → 작성자 표 · 글자 바꾸기 표 · 지울 경로 · 지울 메시지 줄
  planRewrite,       // 규칙 + 저장소 → filter-repo 인자
  mapCoreShas,       // 코어 옛→새 커밋 표 → 래퍼용 글자 바꾸기 줄 (40자 · 7자)
  scanForLeaks,      // 다시 쓴 사본의 파일 · 메시지 · 작성자 → 남은 개인정보 목록
  compareInvariants, // 전 · 후 목록 → 어긋난 것 (payload 해시 · 브랜치 · 태그 · 고정)
  pushRewrite,       // 검증 통과 사본 + 사용자 확인 → 원격 덮어쓰기 (출구)
)
```

| # | 단계 | 하는 일 | 받는 값 → 돌려주는 값 | 순수/부수효과 |
|---|---|---|---|---|
| 1 | `snapshotRepos` | 네 저장소를 통째로 백업하고 작업 사본과 전(前) 목록을 만든다 | 저장소 목록 → 경로 · 목록 | 부수효과 (입구) |
| 2 | `buildRules` | 무엇을 무엇으로 바꾸고 무엇을 지울지 표로 만든다 | 개인정보 목록 → 규칙 표 | 순수 |
| 3 | `planRewrite` | 규칙을 저장소별 다시 쓰기 명령 인자로 바꾼다 | 규칙 + 저장소 → 인자 | 순수 |
| 4 | `mapCoreShas` | 코어 커밋 번호가 바뀐 대로 래퍼 속 번호를 바꿀 줄을 만든다 | 옛→새 표 → 바꾸기 줄 | 순수 |
| 5 | `scanForLeaks` | 다시 쓴 사본에 개인정보가 남았는지 찾는다 | 사본 내용 → 남은 목록 | 순수 |
| 6 | `compareInvariants` | 바뀌면 안 되는 것이 그대로인지 전 · 후를 맞춘다 | 전 · 후 목록 → 어긋남 | 순수 |
| 7 | `pushRewrite` | 확인받은 사본으로 원격을 덮어쓴다 | 사본 + 확인 → 원격 | 부수효과 (출구) |

- 부수효과 위치: `snapshotRepos`(클론 · 파일 읽기)와 `pushRewrite`(원격 덮어쓰기)만. 다시 쓰기 실행(filter-repo)은 작업 사본 안에서만 일어나고, 원격은 7단계 전까지 그대로다.
- 재사용: 코어의 `journal-append.sh --redact-only` 가린 규칙(비밀값 패턴)을 `scanForLeaks` 패턴의 출발점으로 쓴다. 코어 `tools/export-core.sh` 로 태그별 payload 해시를 다시 만든다. 개인정보 검사는 기존 출처 게이트(`check-provenance.sh`)와 같은 모양으로 branch-flow 에서 돈다.

## Guardrails

- 원격을 바꾸는 단계(규칙 끄기 · 강제 덮어쓰기 · 비공개 저장소 만들기 · 자동 작업 끄기)는 실행 직전에 사용자 확인을 받는다. 계획 승인만으로 하지 않는다.
- 덮어쓰기 전에 네 저장소의 `--mirror` 백업이 있고, 백업에서 다시 올리는 길(되돌리기)을 미리 시험해 둔다.
- 실명 · 회사 팀 이름 · 개인 메일 같은 개인 값은 공개 저장소의 코드 · 테스트 · 문서 · 계획에 적지 않는다. 이 컴퓨터의 비공개 파일과 GitHub 비밀값(Actions secret)에만 둔다. 이 계획서도 그 값을 적지 않는다.
- 영구 브랜치 규칙은 덮어쓰기 동안만 끄고, 끝나면 같은 설정으로 되돌린다(전 · 후 설정 JSON 비교).
- 모드 저장소의 다른 세션 작업 중 파일은 건드리지 않는다. 모드는 그 세션이 커밋하거나 정리한 뒤에 다시 쓴다.
- 코어 payload 는 바이트 그대로다. 바뀌면 멈춘다.
- 다시 쓰기 중에는 새 커밋 · PR 을 만들지 않는다. 자동 작업도 꺼 둔다.
- 맥 + 리눅스, bash 3.2 에서 개인정보 검사가 똑같이 돈다.

## Exit criteria

- TESTS.md 의 모든 시나리오가 통과한다.
- 네 저장소를 새로 클론해 모든 브랜치 · 태그를 훑으면 개인정보 0건이다(작성자 · 메시지 · 파일).
- 릴리스 · 코어 고정 · 채널 · CI 가 다시 쓴 뒤에도 그대로 동작한다.
- 이 컴퓨터의 SCV 가 기록을 `scv-records` 에 남기고, 공개 저장소의 작업 트리는 기록 때문에 더러워지지 않는다.
- 개인정보가 든 커밋은 네 저장소 CI 에서 막힌다.
- GitHub 지원 요청 문안이 사용자에게 전달되었다(보내는 것은 사용자 몫).

## Suggested path

1. `git filter-repo` 를 설치하고, 문서 PR 넷을 병합하고, 모드의 다른 세션 작업이 정리되었는지 확인한다 — 다시 쓰기 전 준비
2. 네 저장소를 백업하고 전 목록(브랜치 · 태그 · 태그별 payload 해시 · 규칙 설정)을 만든다 — `snapshotRepos`
3. 비공개 `scv-records` 를 만들고(확인 후) 코어 · 모드 기록을 옮긴다 — 기록을 비공개 저장소로 옮긴다
4. 규칙 표와 저장소별 인자를 만들고, 개인 값은 비공개 파일에 둔다 — `buildRules`, `planRewrite`
5. 코어를 작업 사본에서 다시 쓰고 커밋 번호 표를 얻는다 — `planRewrite`, `mapCoreShas`
6. 래퍼 둘 · 모드를 다시 쓴다(코어 번호 표 적용) — `planRewrite`
7. 남은 개인정보를 찾고 바뀌면 안 되는 것을 맞춘다. 테스트도 돌린다 — `scanForLeaks`, `compareInvariants`
8. 백업에서 되돌리는 길을 시험한다(dry-run) — 되돌리기 준비를 확인한다
9. 사용자 확인 뒤 규칙을 끄고 덮어쓰고 규칙을 되돌린다 — `pushRewrite`
10. 자동 작업을 켜고 채널을 다시 만들고 CI · 플러그인 업데이트 · 로컬 사본을 확인한다 — 다시 쓴 뒤 뒤처리
11. 개인정보 검사 · 작성자 설정 · 기록 폴더 연결 · 세션 줄 중단을 넣는다 — 다시 쌓이지 않게 막는다
12. GitHub 지원 요청 문안(PR ref · 캐시 · 포크)을 만들어 건넨다 — 남은 옛 사본 정리를 요청한다

## Risks / Open Questions

- **GitHub 의 옛 사본.** 병합된 PR 의 옛 커밋 · 화면 캐시 · claude 래퍼의 포크 1개에는 덮어쓴 뒤에도 옛 기록이 남는다. 지원 요청으로 PR ref 와 캐시는 지울 수 있다. 포크는 주인에게 부탁할 수밖에 없다. 그 전까지는 "완전 삭제"가 아니다.
- **설치된 플러그인 업데이트.** 사용자들의 마켓 사본(claude · codex)은 옛 기록을 갖고 있다. 강제 덮어쓰기 뒤 업데이트가 실패할 수 있다(미확인). 임시 설정에서 옛 설치 → 덮어쓰기 → 업데이트 순서로 확인하고, 실패하면 마켓을 지웠다 다시 넣는 안내를 릴리스 노트에 싣는다.
- **커밋 번호에 기대는 것들.** 래퍼 고정(`source_commit`), 채널 버전(`-dev.<commit>`), 변경 기록 · 릴리스 노트 속 번호, 다른 저장소의 PR 본문 링크가 바뀐다. 고정과 문서 속 번호는 번호 표로 바꾼다. GitHub PR 본문 · 댓글 속 옛 번호는 git 밖이라 바뀌지 않는다(링크만 깨짐).
- **PR 본문 · 댓글 · 릴리스 본문.** git 기록이 아니므로 다시 쓰기로 지워지지 않는다. 그 안의 개인정보(경로 · 세션 id)를 따로 훑어 API 로 고친다(범위에 넣음, TESTS T12).
- **이 컴퓨터의 다른 사본.** 형제 저장소 클론, 스크래치 클론, 워크트리, `~/.claude/plugins` 마켓 사본이 옛 기록을 갖고 있다. 다시 클론하거나 맞춘다. `~/.claude/plugins` 는 손으로 고치지 않고 마켓 업데이트 · 다시 넣기로만 맞춘다.
- **filter-repo 의 7자 번호 바꾸기.** 짧은 번호는 우연히 다른 글자와 겹칠 수 있다. 번호 표의 7자 줄은 저장소 안에서 유일한 것만 쓰고, 바꾼 줄 수를 세어 확인한다.
- **SCV 기록 폴더 연결 방식.** 공개 저장소에서 무시하는 기록 폴더가 비공개 작업 사본을 가리킬 때, SCV 스크립트(기록 쓰기 · pr-helper 의 기록 커밋)가 그대로 동작하는지 미확인이다. 실제로 돌려 확인한다(T8).

# Test Plan — 공개 저장소 개인정보 정리 — 과거 기록까지 지우고, 다시 쌓이지 않게, SCV 기록은 비공개 저장소로

## Overview

사용자가 요구한 것은 세 가지다. 첫째, 감사에서 찾은 개인정보(실명 · 개인 메일 · 주제 밖 개인 대화 · 회사 팀 이름 · 내
컴퓨터 경로 · 세션 id)를 네 공개 저장소의 과거 기록까지 모두 지운다. 둘째, 앞으로 커밋할 때 다시 쌓이지 않게 막는다.
셋째, SCV 기록은 비공개 저장소로 옮긴다. 이와 함께 열린 PR · 릴리스 · 코어 고정 · 채널이 깨지지 않아야 한다. 아래
시나리오는 이것들을 하나씩 확인한다. 개인 값(실명 · 회사 팀 이름 · 개인 메일)은 이 문서에 적지 않는다. 검사는 이
컴퓨터의 비공개 목록 파일(`~/.config/scv/privacy-terms`, 권한 600 — 저장소 밖)과 GitHub 비밀값에서 읽는다.

## Test scenarios

### T1. 새 클론의 모든 ref 에 개인정보가 없다

- **Setup**: 덮어쓴 뒤, 네 저장소를 새로 `--mirror` 클론한다.
- **Run**: 모든 브랜치 · 태그의 파일 내용 · 커밋 메시지 · 작성자 · 커미터를 비공개 목록 + 공통 패턴(개인 메일, `/Users/<이름>/`, `/private/tmp/claude-<숫자>`, `session_01…`, `Claude-Session:`)으로 훑는다.
- **Expected**: 맞는 곳 0건.
- **Pass criterion**: 네 저장소 모두 0건. 검사 스크립트 종료 코드 0.

### T2. 작성자 정보는 그대로다 (사용자 결정, 2026-10-27)

- **Run**: 다시 쓰기 전 · 후 네 저장소의 작성자 · 커미터 이름 · 메일 목록을 비교한다.
- **Expected**: 같다 — 실명 · 개인 메일은 공개 계정의 정체성이라 남긴다.
- **Pass criterion**: 목록 차이 0.

### T3. SCV 기록이 공개 저장소에서 사라졌다

- **Run**: 코어 · 모드의 모든 ref 에서 `scv/journal/`, `scv/conversations/`, `scv/dreams/`, `scv/raw/` 경로가 있었던 커밋을 찾는다.
- **Expected**: 0건. 계획 보관(`scv/archive/`) · 결정 기록은 남아 있다.
- **Pass criterion**: 기록 경로 0건, 보관 계획 수는 전과 같다.

### T4. 비공개 scv-records 에 기록이 모두 있다

- **Setup**: `scv-records`(비공개)를 클론한다.
- **Run**: 저장소별 폴더(core · mods)의 파일 수와 내용 해시를 옮기기 전 목록과 맞춘다. 보관 계획 하나를 골라 그 `raw_sources` 대화 경로가 `scv-records/<저장소>/` 아래에 있는지 본다.
- **Expected**: 파일 수 · 해시가 같고, 근거 대화를 찾을 수 있다. 저장소가 비공개다(`gh api … .private == true`).
- **Pass criterion**: 차이 0, 비공개 확인.

### T5. 코어 payload 가 바이트 그대로다

- **Run**: 다시 쓴 코어의 최근 태그 다섯 개 이상(마지막 릴리스 포함)에서 `tools/export-core.sh` 로 payload 를 만들어 해시를 낸다. 같은 태그의 GitHub 릴리스 자산 SHA-256 과 래퍼 `core.lock.json` 의 payload 해시와 맞춘다.
- **Expected**: 모두 같다.
- **Pass criterion**: 어긋남 0.

### T6. 래퍼의 코어 고정이 새 코어 커밋을 가리킨다

- **Run**: 두 래퍼의 모든 브랜치 끝에서 `vendor/scv-core/core.lock.json`(codex 는 `plugins/scv/vendor/…`)의 `source_commit` 을 읽어, 다시 쓴 코어에 그 커밋이 있는지와 그 커밋의 payload 해시가 lock 과 같은지 본다. 래퍼 기록 전체에서 옛 코어 번호(번호 표의 왼쪽)를 찾는다.
- **Expected**: 모두 있음 · 같음, 옛 번호 0건.
- **Pass criterion**: 래퍼 검증 스크립트(`tools/verify-core.sh` · `scripts/verify-core.sh`) 통과, 옛 번호 0건.

### T7. 브랜치 · 태그 · 릴리스가 그대로다

- **Run**: 전 · 후 목록을 비교한다 — 브랜치 이름 · 수, 태그 이름 · 수, 릴리스 이름 · 자산 · 최신 표시.
- **Expected**: 같다(가리키는 커밋 번호만 바뀜).
- **Pass criterion**: 이름 · 수 · 자산 차이 0.

### T8. 이 컴퓨터의 SCV 가 기록을 비공개 저장소에 남긴다

- **Setup**: 기록 폴더 연결을 마친 코어 작업 사본.
- **Run**: SCV 대화 한 턴을 기록하고(`journal-append.sh`), `pr-helper` 의 기록 커밋 단계를 dry-run 으로 돌린다.
- **Expected**: 새 기록이 `scv-records` 작업 사본에 생긴다. 공개 저장소의 `git status` 에는 기록 파일이 나오지 않는다. pr-helper 가 실패하지 않는다.
- **Pass criterion**: 세 조건 모두 참.

### T9. 다시 쌓이지 않게 — 개인정보 검사가 막는다

- **Setup**: 코어의 `core/scripts/check-privacy.sh` 와 네 저장소 branch-flow 연결.
- **Run**: 임시 브랜치(또는 같은 입력의 로컬 실행)로 다섯 경우를 넣는다 — (a) 개인 메일 작성자(기본은 허용, `SCV_PRIVACY_EMAILS=on` 일 때만 막음), (b) 추가 줄에 `/Users/<이름>/` 경로, (c) 커밋 메시지에 `Claude-Session:` 줄, (d) 비밀 목록의 낱말(실명 · 팀 이름) 하나, (e) 깨끗한 커밋.
- **Expected**: (a)는 기본에서 통과하고 켰을 때 실패한다. (b)~(d)는 실패하고 무엇이 걸렸는지 말한다(개인 값 자체는 출력에서 가린다). (e)는 통과한다.
- **Pass criterion**: 다섯 경우 모두 기대대로. 맥 · 리눅스 결과 같음.

### T10. 작성자 설정과 세션 줄 중단

- **Run**: 이 세션이 이후 만드는 커밋 · PR 본문에 세션 링크 줄이 없는지 확인한다. (작성자 이름 · 메일은 사용자 결정으로 그대로 — T2.)
- **Expected**: 세션 줄이 없다.
- **Pass criterion**: 모두 참.

### T11. 영구 브랜치 규칙이 원래대로다

- **Run**: 덮어쓰기 전 · 후 ruleset JSON(규칙 종류 · 대상 · 우회자 · 시행 상태)을 비교한다.
- **Expected**: 같다(`enforcement: active`).
- **Pass criterion**: 차이 0.

### T12. PR · 릴리스 본문의 개인정보도 정리되었다

- **Run**: 네 저장소의 PR 본문 · 댓글 · 릴리스 본문을 API 로 훑는다(T1 과 같은 패턴).
- **Expected**: 맞는 곳을 고쳐 0건. 고칠 수 없는 것(남의 댓글 등)은 목록으로 보고.
- **Pass criterion**: 고칠 수 있는 것 0건, 나머지는 목록.

### T13. 덮어쓴 뒤 CI · 채널 · 플러그인 업데이트

- **Run**: 네 저장소 develop · stage · main CI 를 다시 돌린다. 채널 동기화로 `channel/dev` · `channel/stage` 를 다시 만든다. 덮어쓰기 전에 임시 설정 폴더에 옛 기록으로 설치해 둔 claude · codex 플러그인을 업데이트한다.
- **Expected**: CI 통과. 채널 브랜치가 새 코어 커밋으로 다시 만들어진다. 업데이트가 되거나, 안 되면 마켓을 지웠다 다시 넣는 안내대로 하면 된다(그 안내가 릴리스 노트에 실린다).
- **Pass criterion**: CI · 채널 통과, 업데이트 결과와 대처가 확인됨.

### T14. 되돌리는 길이 있다

- **Run**: 덮어쓰기 전에, 백업 미러로 다시 올리는 명령을 `--dry-run` 으로 돌려 본다. 덮어쓴 뒤에도 백업이 남아 있는지 확인한다.
- **Expected**: dry-run 이 ref 목록을 정확히 내놓는다. 백업이 남아 있다(공개된 곳에 올리지 않음).
- **Pass criterion**: 둘 다 참.

### T15. 열린 PR 이 깨지지 않았다

- **Run**: 덮어쓰기 직전과 직후 네 저장소의 열린 PR 목록을 본다.
- **Expected**: 직전에 열린 PR 이 0개다(문서 PR 넷은 먼저 병합). 직후에도 깨진 PR 이 없다.
- **Pass criterion**: 열린 PR 0, 또는 열린 PR 마다 diff 가 덮어쓰기 전과 같다.

### T16. GitHub 지원 요청 문안

- **Run**: 저장소별 PR 번호 범위와 옛 커밋 목록(백업에서)을 담은 지원 요청 문안을 만든다. 포크 주인에게 보낼 짧은 부탁 문안도 만든다.
- **Expected**: 사용자가 그대로 보낼 수 있는 문안 두 개.
- **Pass criterion**: 사용자에게 전달됨.
