# 지난 작업 찾기가 제목이 아니라 본문까지 훑는다

## Summary

"예전에 이거 어떻게 했더라" 라고 물으면, 지금은 계획서 제목만 훑어 고른 뒤 고른 것을 통째로
읽는다. 제목에 안 적힌 말은 못 찾고, 읽는 양은 계획 하나당 평균 143줄이다. 본문까지 훑어
맞는 대목만 출처와 함께 돌려주면, 못 찾던 것을 찾고 읽는 양도 준다.

## Goals / Non-Goals

- **Goals**
  - 기록이 실제로 쌓이는 곳을 한 번의 실행으로 훑는다 — 보관된 계획서와 그 검사·구조·보관 기록,
    결정 기록, 대화 기록(보관된 것 포함), 소비된 원자료.
  - 맞는 대목만 출처(어느 계획의 어느 줄)와 함께 돌려준다.
  - 한 낱말이 아니라 여러 낱말로 물어도 답한다.
  - 찾은 것이 없으면 없다고 말한다.

- **Non-Goals**
  - 의미 검색을 하지 않는다. 낱말이 그대로 있어야 찾는다.
  - 낱말 하나만 주고 정확한 답을 기대하지 않는다. 여러 낱말을 같이 줄수록 좋아지는 방식이다.
  - 색인 파일을 새로 만들어 두지 않는다. 훑는 데 37밀리초면 충분하다.
  - 지금 진행 중인 계획은 찾지 않는다. 지난 것을 찾는 기능이다.
  - 코드는 훑지 않는다. 그건 다른 도구가 한다.

## Approach Overview

한 번 부르면 결과가 나오는 도우미 하나를 더한다. 낱말들을 받아 기록이 쌓이는 곳을 훑고, 맞은
자리마다 출처 한 줄과 그 대목 몇 줄을 낸다.

**어디를 훑는가** — 계획서만으로는 모자란다. 세어 보니 계획서 밖에 더 많은 기록이 있다.

| 곳 | 줄 수 | 왜 훑는가 |
|---|---|---|
| 보관된 계획서 | 8,180 | 무엇을 하려 했는가 |
| 보관된 검사 | 5,744 | 무엇을 지키기로 했는가 — "회귀" 로 물으면 계획 29건보다 많은 40건이 여기 있다 |
| 보관된 구조 그림 | 2,990 | 어디에 앉는가 |
| 보관 기록 | 790 | 왜 끝났다고 봤는가 |
| 소비된 원자료 | 1,908 | 처음에 왜 하려 했는가 |
| 대화 기록 | 1,753 | 어떤 대안을 버렸는가 |
| 결정 기록 | 1,145 | 무엇을 정했고 왜인가 |

생성물은 훑지 않는다. 기획서 HTML 42개가 5.5MB 인데 전부 위 문서에서 만들어진 것이라
같은 내용을 두 번 세게 될 뿐이다.

**대화 기록은 두 곳에 있다.** 활성 폴더에 2개, 보관 하위 폴더에 16개다. 하위 폴더를 빠뜨리면
대화에서는 거의 아무것도 못 찾는다.

고르는 일은 그대로 사람이 읽고 판단할 몫으로 둔다. 도우미는 후보와 근거를 모아줄 뿐이고,
통째로 읽는 것은 정말 필요할 때만 한다.

**점수는 파일이 아니라 줄로 센다.** 시제품으로 둘을 비교해 봤다. 파일 단위로 "이 낱말이
어딘가 있나" 를 세면 한 계획이 계획서·검사·구조·보관 기록 네 곳에서 따로 올라와 상위 8칸 중
3칸을 혼자 차지했고, 보여주는 대목도 첫 낱말이 처음 나온 줄일 뿐이라 쓸모가 없었다.

줄 단위로 "이 줄에 물어본 낱말이 몇 개나 같이 나오나" 를 세자 달라졌다. "회귀 느림 관문" 으로
물었을 때 1·2위가 정확히 답이었다 — 회귀 관문을 기억해 두는 계획의 보관 기록과 그 결정
기록이고, 둘 다 실제 수치("관문 3개 1회 + 22회 재사용")를 담은 줄을 보여줬다.

**세 가지를 지킨다.**

1. 훑을 때 **아무 낱말이라도** 걸리면 후보로 본다. 첫 낱말로만 훑으면 순서만 바꿔도 결과가
   달라진다 — 시제품에서 "회귀 느림 관문" 은 63곳, "관문 회귀" 는 4곳이 나왔다. 같은 물음이다.
2. **출처는 계획 폴더 하나로 묶는다.** 한 계획의 네 문서가 각각 한 칸을 먹으면 안 된다.
   묶음 안에서 가장 잘 맞은 줄 하나를 대표로 보이고, 어느 종류의 문서인지 함께 적는다.
3. **여러 낱말이 맞은 것이 있으면 하나만 맞은 것은 뒤로 민다.** 시제품에서 상위 5개 중 3개가
   낱말 하나만 맞은 잡음이었다.

기존 제목 목록은 그대로 둔다. 새 도우미가 아무것도 못 찾았을 때 돌아갈 자리가 필요하다.

## 순수함수 · 파이프라인 (Pure functions & pipeline)

```
flow(
  parseTerms,       // 물음 한 줄 → 낱말 목록
  scoreLines,       // 훑은 줄들 + 낱말 목록 → 줄마다 함께 맞은 낱말 수
  dropWeak,         // 점수 매긴 줄들 → 잡음을 뒤로 민 줄들
  groupBySource,    // 줄들 → 계획 폴더별 묶음 (대표 줄 하나)
  renderHits,       // 묶음 → 사람이 읽는 줄들
)
```

| # | 단계 | 받는 값 → 돌려주는 값 | 순수/부수효과 | 상태 |
|---|---|---|---|---|
| 1 | `parseTerms` | 물음 한 줄 → 낱말 목록 | 순수 | 추가 |
| 2 | `sweepCorpus` | 낱말 목록 → 훑은 줄들 (출처·줄번호·내용) | 부수효과 (입구, 파일 읽기) | 추가 |
| 3 | `scoreLines` | 훑은 줄들 + 낱말 목록 → 줄마다 함께 맞은 낱말 수 | 순수 | 추가 |
| 3b | `dropWeak` | 점수 매긴 줄들 → 잡음을 버린 줄들 | 순수 | 추가 |
| 4 | `groupBySource` | 줄들 → 계획 폴더별 묶음 (대표 줄 하나) | 순수 | 추가 |
| 5 | `renderHits` | 출처별 묶음 → 사람이 읽는 줄들 | 순수 | 추가 |
| 6 | `printResult` | 읽는 줄들 → 표준 출력 | 부수효과 (출구) | 추가 |

- 부수효과 위치: 2번(파일 훑기)과 6번(출력)뿐이다. 3·3b·4·5 는 문자열만 받아 문자열만 낸다.
- 재사용: 훑기는 이미 쓰는 검색 도구를 그대로 쓴다. 출력 모양은 결정 기록을 이름으로 꺼내는
  기존 도우미의 모양을 따른다.

## 예외처리 (Edge cases)

| 상황 | 어떻게 되는가 |
|---|---|
| 찾은 것이 없다 | 없다고 말한다. 비슷한 것을 대신 내놓지 않는다. |
| 보관된 계획이 하나도 없다 | 아직 없다고 말하고, 계획 세우기를 권한다. |
| 낱말을 안 줬다 | 쓰는 법을 한 줄 보여주고 끝낸다. |
| 맞은 자리가 아주 많다 | 상위 몇 건만 보이고, 전체가 몇 건인지 함께 적는다. |
| 한 계획 안에서 여러 번 맞았다 | 그 계획을 한 묶음으로 보이고, 대목은 몇 개만 추린다. |
| 결정 기록이나 대화 기록이 없다 | 있는 곳만 훑는다. 없다고 멈추지 않는다. |
| 대화가 보관 하위 폴더에 있다 | 하위 폴더까지 훑는다. 지금 18개 중 16개가 거기 있다. |
| 생성물(기획서 HTML)이 섞여 있다 | 훑지 않는다. 같은 내용을 두 번 세게 될 뿐이다. |
| 한 낱말이 여러 종류의 기록에서 맞았다 | 종류를 구분해 보인다. 검사에서 맞은 것과 계획에서 맞은 것은 뜻이 다르다. |
| 낱말에 검색 기호가 섞여 있다 | 글자 그대로 찾는다. 기호로 해석하지 않는다. |
| 아주 긴 줄에서 맞았다 | 맞은 자리 앞뒤만 잘라 보인다. |

## Guardrails

- 읽기만 한다. 어떤 파일도 만들거나 고치지 않는다.
- 설치할 것을 늘리지 않는다. bash 와 이미 쓰는 도구만 쓴다.
- 없는 것을 지어내지 않는다. 못 찾으면 못 찾았다고 한다.
- 기존 제목 목록 기능을 없애지 않는다. 새 도우미가 빈손일 때 돌아갈 자리다.
- 진행 중인 계획은 건드리지 않는다.
- 출력은 한눈에 읽히는 분량으로 끊는다. 통째로 쏟아내면 지금 문제를 그대로 옮긴 것이다.
- 생성물은 훑지 않는다. 기획서 HTML 은 위 문서들로 만들어진 것이라 같은 내용이 두 번 잡힌다.

## Exit criteria

- TESTS.md 의 모든 항목이 통과한다.
- 제목에 없고 본문에만 있는 낱말("회귀", "훅", "설정")로 물었을 때 실제로 찾는다.
- 전체 계약 검사가 통과한다.
- 훑는 데 걸리는 시간이 사람이 기다린다고 느낄 정도가 아니다. 파일 244개 22,510줄을 한 번의
  훑기로 보면 26밀리초다(실측). 줄마다 셸에서 다시 비교하면 3.7초가 되므로, 훑기는 한 번에
  끝내고 그 뒤를 순수한 계산으로 처리한다.

## Suggested path

1. 낱말 쪼개기와 점수 매기기를 쓴다. 문자열만 받아 문자열만 내는 부분이다.
2. 훑기를 붙인다. 세 곳을 대상으로 하고, 없는 곳은 건너뛴다.
3. 출처별로 묶고 사람이 읽는 모양으로 낸다.
4. 지난 작업 찾기 절차가 이 도우미를 먼저 부르도록 바꾼다. 빈손이면 제목 목록으로 돌아간다.
5. 검사를 채운다.

## 구현에서 드러난 것 (실측)

- **한 번의 계산 규칙은 훑기 뒤에도 적용된다.** 줄마다 셸에서 다시 비교하자 327줄에 11초가
  걸렸다. 한 번의 awk 로 바꾸니 같은 일이 10밀리초였다.
- **큰 문자열에 셸 치환을 돌리지 말 것.** 74킬로바이트에 공백 제거를 돌리는 줄 하나가
  1.5초를 먹었다. 비었는지는 길이로만 본다.
- **검색 도구는 파일이 하나뿐이면 파일 이름을 생략한다.** 이름 표시를 강제하지 않으면
  기록 파일이 하나인 프로젝트에서 한 건도 못 읽는다.
- **이 시스템의 문자 처리 도구는 한글을 바이트로 센다.** 자르기는 보여줄 몇 줄에만,
  글자를 아는 셸에서 한다.
- **외부 명령을 쓰는 함수는 순수가 아니라 결정적으로 표시한다.** awk 프로그램 글은 함수 밖
  상수로 둔다 — 검사기가 프로그램 안의 부등호를 파일 리다이렉션으로 오해한다.
- 최종 속도: 244파일 22,510줄에 0.2초.

## Risks / Open Questions

- 낱말이 그대로 있어야 찾는다. 다른 말로 적힌 같은 개념은 못 찾는다. 이건 의도한 한계이고,
  의미 검색은 설치할 것을 늘리므로 넣지 않는다.
- 흔한 낱말로 물으면 너무 많이 맞을 수 있다. 상위 몇 건으로 끊고 전체 수를 함께 보여
  사람이 다시 좁히게 한다.
- 아카이브가 지금의 몇 배로 자라면 훑는 시간이 늘어난다. 지금은 26밀리초라 여유가 크다.
- 낱말 하나로만 물으면 줄 단위 점수가 변별력을 잃는다. 그때는 맞은 수가 많다는 것만 알려주고
  다시 좁히도록 안내한다.
