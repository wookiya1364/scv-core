# 마무리 보고 — 비우기로 줄인다 — 대화가 길어지면 요약 대신 비우고, 기록의 끝부분으로 새로 시작한다

## 1. 문제

- 상황: 대시보드는 턴이 끝났을 때 컨텍스트가 기준(50%)을 넘으면 요약 명령을 써서 대화를 SCV 기록으로 바꿔 끼웠다. 요약이 느리고 좋지 않다는 의견이 있었다. 공식 문서는 여러 컨텍스트에 걸친 긴 일에 "상태를 파일에 두고 새 컨텍스트로 시작"을 권한다. 사용자는 비우기(clear)로 바꾸기로 골랐다(2026-11-25 15:53).
- 기대: 턴 끝에 기준을 넘으면 창이 비운다. 새 대화는 기록의 끝부분(12,000자)과 뒤에서 도는 일 목록으로 시작한다. 비우기가 거절되면 전의 길(기록으로 바꿔 끼우기)로 넘어간다. 비운 직후 사용자는 대화창에서 마지막 대화를 읽을 수 있다(9단계에서 더한 기대).
- 실제: 1 ~ 4단계를 설치본에 얹고 실제 앱에서 비우자, 새 대화에 기록이 실리지 않았다. 뒤에서 도는 일 목록에는 아침에 끝난 일 넷이 실리고, 그때 돌고 있던 하위 작업은 빠졌다. 비운 뒤 대화창에는 아무것도 보이지 않아, 사용자가 "어디까지 했어?"라고 물어야 했다.
- 재현 조건: 색인이 282줄인 이 프로젝트에서, 일하던 대화 기록이 계획으로 넘어간(promoted) 표시만 있을 때, 기준을 넘긴 턴 끝에 창이 자동으로 비운다.

## 2. 관찰

- 관찰한 사실과 측정값: 비운 뒤 도는 세션 시작 훅의 제한은 30초다. 그 훅의 요약 단계에 있는 색인 거르기(`record_index_filter`)는 색인 40줄에서 1.45초, 80줄에서 11.26초, 160줄에서 45초를 넘었다. 실제 색인 282줄에서는 274초가 지나도 끝나지 않았다. 코어 훅은 '진행 중' 표시의 기록만 실었다 — 앞 대화의 기록(29턴)은 promoted 라 빠졌다. 뒤에서 도는 일 목록은 명령 · 감시 · 터미널 탭만 담았고, 끝난 일을 빼지 않았다. 비운 뒤의 글은 모두 Claude 에게만 가고, 대화창에는 아무것도 넣지 않았다(코드 확인).
- 정상일 때와 차이: 정상이면 훅이 30초 안에 끝나 새 대화의 첫 글에 기록 끝부분이 실린다. 시험 프로젝트(30,100자 기록)에서는 훅이 기록 11,545자를 실었다(evidence/step-1-hook-chars.svg). 실제 앱의 이 프로젝트에서는 실린 기록이 0자였다(evidence/step-7-clear-hook.svg).

## 3. 가설

- H1: 훅이 제한 30초 안에 끝나지 못해 글을 싣지 못했다 — 색인 거르기가 줄마다 색인 전체를 글자 무늬로 다시 훑어, 줄이 늘면 걸린 시간이 훨씬 빨리 는다.
- H2: 훅이 빨리 끝나도, 실을 기록을 고르지 못한다 — 고르기가 '진행 중' 표시만 보고 promoted 기록을 뺀다.
- H3: 목록이 실제와 다른 것은 목록을 만드는 쪽이 하위 작업을 담지 않고, 끝난 일을 가려낼 정보를 쓰지 않기 때문이다.

## 4. 실험

- 방법과 같게 둔 것: 같은 색인 거르기 함수를 색인 40 · 80 · 160 · 282줄로 돌려 걸린 초를 측정했다. 고친 함수와 옛 함수에 같은 입력 31가지를 넣어 결과를 견줬다. 설치된 훅을 이 프로젝트에서 비우기 입력으로 돌려 걸린 초와 실린 글자 수를 측정했다. 대시보드 쪽은 2026-11-25 실제 세션에서 본 모습(끝난 탭 명령 · 끝난 명령 · 돌고 있는 하위 작업)을 모드 시험으로 옮겼다.
- 결과와 가설별 판정: H1 맞음 — 한 번 훑는 방식으로 바꾸자 282줄에서 0.04초였고(두 셸), 옛 함수와 31가지 입력에서 결과가 같았다. H2 맞음 — 고를 대화가 없을 때 3일 안에 손댄 가장 최근 기록을 싣게 하자, 설치된 훅이 0.44초 만에 22 ~ 29턴의 끝부분(11,441자)을 실었다. H3 맞음 — 하위 작업을 싣고 끝을 아는 일만 빼게 하자, 모드 시험에서 목록이 돌고 있는 일과 같아졌다(247 통과).

## 5. 원인

- 직접 원인과 일어난 길: 창이 비운다 → 세션 시작 훅이 돈다 → 요약 단계의 색인 거르기가 줄마다 색인 전체를 다시 훑는다 → 282줄에서 274초를 넘긴다 → 훅이 제한 30초 안에 끝나지 않아 기록 끝부분도 실리지 않는다. 또 고를 기록이 '진행 중' 표시뿐이라 promoted 기록이 빠졌다. 목록은 끝난 일을 빼지 않고 하위 작업을 담지 않았다.
- 근본 원인: 1 ~ 4단계의 시험은 작은 임시 프로젝트에서 '진행 중' 기록 하나로 돌았다(TESTS T4). 큰 색인 · promoted 기록 · 끝난 일이 섞인 목록은 실제 앱에서 처음 만났다. 색인 거르기의 걸린 시간을 줄 수마다 보는 시험은 6단계(T11) 전에는 없었다.

## 6. 해결과 검증

- 해결책과 고른 이유: 1단계 — 비운 뒤에는 기록 끝부분 12,000자(턴 머리에서 시작)와 전체 기록의 자리 한 줄만 싣는다(`scv_resume_tail`, 코어 커밋 69936b1). 2 ~ 4단계 — 턴 끝에 비우고, 비워지지 않으면 전의 길로 넘어가고, 첫 글에 뒤에서 도는 일을 싣고, 창 글자를 "비우기"로 바꿨다(대시보드 커밋 2d976e1). 6 · 7단계 — 색인 거르기를 한 번 훑기로 바꾸고, 비운 뒤에는 요약 묶음 대신 부를 명령 한 줄만 남기고, 고를 기록이 없으면 3일 안의 가장 최근 기록을 싣는다(`scv_resume_pick_recent`, 16ce645). 8단계 — 목록에 하위 작업을 싣고, 턴 끝에 탭 목록을 한 번 읽어 끝을 아는 일만 뺀다(b0ba069). 9단계 — 창이 비운 직후 마지막 대화 셋(사용자 글 + Claude 의 마지막 답 전부)을 대화창에 보인다. 처음에는 알림 글로 넣었으나(8d20ae2) 실제 앱에서 그 줄이 기록에만 저장되고 화면에는 그려지지 않았다. 그래서 대시보드가 자기 명령을 돌리고 그 출력 줄에 직전 대화를 그리며, 저장되는 줄은 표시용 한 줄로 바꾼다(853d0c4). 방법은 세션만의 시험 모드로 실제 앱에서 가렸다 — 알림 줄은 안 보임, 기록 줄은 흐린 한 줄, 명령의 출력 줄은 여러 줄 그대로 보임. 고른 것은 모두 사용자 선택이다: 느린 함수 고치기 + 비운 뒤 요약 건너뛰기, 목록 함께 고치기, 탭 목록을 읽게 하고 얹기, 최근 기록 규칙 그대로 두기, 대화창에 알림 글 · 답도 전부 그대로, 알림 글이 안 보인 뒤에는 '대화창 방법 더 찾기', 대시보드도 실제 확인 없이 함께 릴리스.
- 고치기 전후 값: 시험 기록 30,100자에서 비운 뒤 훅 출력은 30,810 → 12,426자, 그 가운데 기록은 30,099 → 11,545자다(두 셸 같은 값). 색인 거르기는 282줄에서 274초를 넘겨 멈춤 → 0.04초. 이 프로젝트에서 비운 뒤 실린 기록은 0 → 11,441자(22 ~ 29턴, 훅 0.44초). 설치본의 임시 프로젝트(기록 27,662자)에서 비운 뒤 훅은 12,825자, 요약 뒤 훅은 28,361자 그대로였다. 실제 앱에서는 2026-11-25 21:41 KST 에 창이 자동으로 비우기를 한 번 돌렸고, 새 대화의 첫 글에 대화 기록 1 ~ 5턴이 실렸다(사용자가 자동이었다고 확인).
- 부작용과 회귀 시험: 본체 시험 test-resume-tail 43 · test-record-index 48 · test-session-resume 43 이 맥 기본 셸(3.2)과 새 셸(5.3)에서 통과했다. 순수성 · 순수 함수 사전 · 틀 지문도 통과했다. 모드 시험은 239 → 247 → 251 → 253 통과 · 0 실패다. 부작용: 줄이 통째로 같은 레코드 둘은 이제 하나가 남는다(옛 함수는 둘 다 버렸다). 턴 끝마다 터미널 탭 목록을 허락을 묻지 않고 한 번 읽는다 — 사용자가 골랐다. 비우면 기록에 적히기 전의 말은 잃는다. 못 본 것: 9단계의 직전 대화가 대시보드 자체의 자동 비우기에서 실제로 보이는지(시험 모드로 같은 방법은 봤고, 모드 시험 253 통과, 대시보드 커밋 853d0c4) · 수천 자짜리 답이 그 줄에 다 그려지는지 · 휴대폰 등 다른 화면, 턴 끝 탭 목록 읽기가 화면에 보이는지와 걸리는 시간, 비운 뒤 PR 감시 · 이어진 세션이 남는지. 21:41 의 비우기에서는 뒤에서 도는 일 목록이 실리지 않았다 — 그때 도는 일이 없었고, 그래서 빠진 것인지는 가리지 못했다. 리눅스에서는 돌리지 않았다. 대시보드의 타입 검사는 도구가 없어 돌리지 않았다. 사용자가 실제 앱 확인을 PR 뒤로 미루기로 골랐고, 대시보드를 실제 확인 없이 함께 릴리스하기로 골랐다(2026-11-25).

## 7. 배운 것

- 다음에 같은 문제를 만나면 진단하는 법: 비운 뒤 첫 글에 기록이 없으면, 설치된 세션 시작 훅을 `{"source":"clear"}` 입력으로 직접 돌려 걸린 초와 출력 글자 수를 측정한다. 30초를 넘으면 훅 안의 단계를 하나씩, 입력 줄 수를 바꿔 가며 측정한다. 빨리 끝나는데 기록이 없으면 기록 고르기(표시 · 손댄 시각)를 본다. 목록이 실제와 다르면 실제 세션에서 본 모습을 그대로 모드 시험의 입력으로 옮긴다.
- 다른 곳에도 쓸 수 있는 것: 훅처럼 제한 시간이 있는 곳은 실제 프로젝트 크기의 입력(색인 수백 줄 · 기록 수만 자)으로 걸린 시간을 측정하는 시험을 둔다 — 작은 임시 프로젝트의 시험은 이 결함을 잡지 못했다. 줄마다 전체를 다시 훑는 함수는 한 번 훑기로 바꾸고, 옛 함수와 같은 입력으로 결과를 견준다. 모델에게만 가는 글과 사용자 눈에 보이는 글은 따로 따져야 한다 — 비운 뒤의 글이 Claude 에게만 가서 사용자는 아무것도 못 봤다.
