# 검토 시점에 실제 결과 보여 주기 — 실체 보여 주기 다시 재기

## Summary

설치본 0.66.0 긴 과제 확인(T9)에서 실체 보여 주기 안내는 6과제 모두 쓰이지 않았다(0/6). 기록을 읽어 보니 과제 지시가
"구현 한 덩어리마다 커밋하고 검토 요청"으로 검토 시점을 정해 두었고, 모델은 매 턴 세 줄 안내보다 사람의 그 명시적 지시를 따랐다 —
SCV 규칙(사용자 지시에 양보)으로도 맞는 동작이다. 판정기는 뜻이 맞는 질문 하나("나머지도 … 갈까요?")를 놓쳤다.
그래서 사용자가 검토 시점을 정해 둔 일에서는 **그 시점에 요약 대신 실제로 돌린 결과를 보이고 묻게** 안내를 고치고, **검토 시점 줄을
뺀 과제로 켬 · 끔을 다시 재서** 안내만의 효과를 본다. 판정기 개선(순서 판정)도 시도했으나 정답 표본에서 기준에 못 미쳐 이 계획에서
뺐다 — 측정은 판정자(새 Claude)가 질문마다 판정한다(사용자 결정, 2026-10-10).

## Goals / Non-Goals

- **Goals**
  1. **안내 문구**: 사용자가 검토 시점을 정해 둔 일(예: "구현 한 덩어리마다 커밋하고 검토 요청", "끝나면 보고")에서는 그 시점을 지키되,
     그때 요약 대신 실제로 돌린 결과(명령 출력 · 함수 호출 결과)를 그대로 보이고 묻는다. 검토 시점이 없는 일은 지금처럼 처음 돌아가는
     순간에. 매 턴 안내는 세 줄 그대로 문구만 바꾸고, 규칙 본문은 실체 보여 주기 계약 한 곳(사용자 결정, 2026-10-09).
  2. **판정기 — 이 계획에서 뺌**(사용자 결정, 2026-10-10 — 아래 시도는 기록으로 남긴다). 시도한 정의: 실사용 보고의 '실제 결과를 보여 준 턴'을 질문 낱말 단서('계속' + '고칠') 대신, 바뀐 턴 안의 순서 — 첫 편집 → 실행 →
     그 실행 결과를 보인 뒤의 질문(확인 창 또는 턴을 끝내는 글 질문) — 로 센다. '결과를 보였다'는 실행 결과의 한 줄 이상이 그 뒤 모델의
     글 · 질문에 그대로 나오거나, 결과 끝 요약 줄의 숫자가 결과 낱말(통과 · 실패 · passed · 오류 등)과 함께 나오는 것(사용자 결정).
     실행은 명령 입력이 있는 도구 호출 중 살펴보기 · 버전 관리 명령(cat · grep · git …)만으로 된 것을 뺀 것.
     (구현 전 바로잡음, 2026-10-10: 초안은 '한 줄 이상이 그대로'만 두었으나 T9 mobly 사례는 '9 passed in 0.96s'를 '9개 모두 통과'로
     바꿔 말해 그 정의로는 잡히지 않는다 — 판정기를 돌리기 전에 사용자가 숫자 인용을 더하기로 정했다.)
  3. **판정기 오차 — 시도 결과**: 돌리기 전에 실제 기록 40턴(T9 17 + 사용자 세션 23)의 정답을 가린 판정으로 고정하고 쟀다. 옛 판정기는
     잡음 0 · 놓침 15, 순서 판정은 잡음 14 · **잘못 잡음 7**(기준 2 이하) · 놓침 1 · mobly 잡음 → 미달. 코어 판정기는 그대로 두고 개선은
     따로 계획한다(사용자 결정, 2026-10-10).
  4. **효과 측정**: 같은 6과제에서 '커밋 뒤 검토 요청' 줄만 뺀 지시로 켬 · 끔 × 1번(12번). 판정자(새 Claude)가 질문마다 판정한 '실제 결과를
     먼저 보여 준 과제'가 켬 4/6 이상이고 끔보다 3과제 이상 많으면 통과(사용자 결정 — 판정 방법은 2026-10-10 판정자로).
  5. **문구 측정**: 검토 시점 줄을 그대로 둔 원래 6과제 × 켬 1번 — 검토 창 앞에 실제 실행 결과가 있는 과제 4/6 이상, 첫 검토 창은 과제
     지시의 시점(커밋 뒤)에서 앞당겨지지 않음. 비교는 T9(0.66.0) 기록(사용자 결정).
  6. **멈춤 문턱**: 켬이 끔보다 숨은 테스트를 2과제 이상 덜 통과하거나, 실행당 선택 창 수 · 실행 시간 중앙값이 1.5배 이상이면 멈추고
     결과를 보이며 다시 정한다(사용자 결정).
  7. **두 래퍼**: 규칙은 코어 한 곳. 코어 릴리스 뒤 두 래퍼 동기화 · 릴리스(클로드는 선택 창 문구, 코덱스는 글 질문 문구).
- **Non-Goals**
  - 긴 작업 중간에 안내를 다시 싣기(도구 사용 뒤 훅) — 이번엔 뺀다. 문구 · 판정기 결과를 본 뒤 정한다(사용자 결정).
  - 실체 보여 주기를 사용자 지시보다 앞세우기 — SCV 규칙 7조(사용자 지시에 양보)와 부딪쳐 고르지 않았다.
  - 판정기 바꾸기(순서 판정 · 단서 낱말 넓히기) — 순서 판정이 정답 표본에서 잘못 잡음 7/25 로 기준(2 이하)에 못 미쳐 뺐다. 코어 판정기는
    그대로, 개선은 따로 계획(사용자 결정, 2026-10-10).
  - 막는 검사 더하기 · 해로운 변경 먼저 묻기 등 다른 SCV 규칙 바꾸기 · 모델 · 생각 깊이 바꾸기.
  - 실사용 보고(T10)의 기간 · 기준 정하기 — 따로 정한다.

## Approach Overview

규칙 본문은 실체 보여 주기 계약(`core/contracts/show-real.md`)에 더한다 — 같은 요구는 한 곳에만. 모델이 실제로 읽는 것은 매 턴
세 줄이므로, 그 세 줄의 문구에 '검토 시점을 정해 두었으면 그 시점에 실제 결과'를 넣는다. 줄 수는 그대로 두고, 매 턴 크기 여유
(클로드 래퍼 기준 지금 11,336바이트, 상한 12,000바이트) 안에서만 늘린다.
판정기(실사용 보고)는 바꾸지 않는다 — 순서 판정을 만들어 정답 표본으로 쟀으나 기준에 못 미쳐 되돌렸다(사용자 결정, 2026-10-10).
측정은 판정자(새 Claude)가 첫 편집 뒤의 질문마다 그 질문과 앞 기록을 잘리지 않게 읽고 판정한다 — 절차는 결과를 열기 전에 고정.
측정은 저장소 밖 장치(`~/scv-experiments/longbench`)로 한다. 과제 지시에서 검토 시점 줄만 뺀 판을 장치에 더하고, 브랜치 플러그인
사본을 측정 세션에만 싣는다(사용자 설치본은 건드리지 않음). 판정 기준 · 정답 표본 · 멈춤 문턱은 돌리기 전에 장치 기준 문서에 고정한다.

## 순수함수 · 파이프라인 (Pure functions & pipeline)

매 턴 안내 — 이미 있는 흐름, 마지막 단계의 문구만 바뀐다:

```
flow(
  scv_show_real_switch,    // (설정 값 원문)                        → on | off
  scv_show_real_channel,   // (선택 창 이름, 사람 없는 실행, 입력 종류) → choice | text | none
  scv_show_real_rule,      // (on|off, 통로)                         → 매 턴 세 줄(검토 시점 문구 포함, off 면 빈 값)
)
```

실사용 보고 판정은 이 계획에서 바꾸지 않는다(판정기 개선을 뺐다). 측정 판정 — 저장소 밖 장치(`judge_runs.py`):

```
flow(
  readRun,          // (실행 폴더)                 → 세 단계 대화 기록 · 결과             — 부수효과(입구)
  extractQuestions, // (대화 기록)                 → 첫 편집 뒤 질문마다 앞 기록 20개 + 질문
  judgeQuestion,    // (질문 묶음)                 → yes | no                             — 외부 판정자 호출
  tally,            // (판정 · 결과)               → T8 · T9 · T10 숫자
)
```

| # | 단계 | 받는 값 → 돌려주는 값 | 순수/부수효과 |
|---|---|---|---|
| 1 | 설정 · 호스트 설정 · 훅 입력 읽기 | 프로젝트 → 설정 원문 · 선택 창 이름 · 사람 없는 실행 여부 | 부수효과 (입구) |
| 2 | scv_show_real_rule | on/off · 통로 → 세 줄(검토 시점 문구 포함) | 순수 |
| 3 | 출력 | 세 줄 → 매 턴 블록 | 부수효과 (출구) |
| 4 | extractQuestions(측정) | 대화 기록 → 질문 묶음 | 순수 |
| 5 | judgeQuestion(측정) | 질문 묶음 → yes/no | 외부 호출 |

- 부수효과 위치: 설정 · 호스트 설정 · 훅 입력 · 세션 기록 읽기(입구)와 표준 출력(출구). 측정은 실행 준비 · 세션 · 숨은 테스트가 부수효과.
- 재사용: 실체 보여 주기의 두 흐름(`lib/show-real.sh`), 확인 통로 판단(`choice-gate.sh tool` · `unattended`), 측정 장치(`drive_lb.py` ·
  `lb.py` · 실사용 보고로 판정하던 T9 방식).

## Guardrails

- frontmatter `invariants:` 셋을 지킨다 — 끄면 바이트 단위로 같음, 사용자 검토 시점은 그대로, 결과물 변화 없는 일은 묻지 않음.
- 규칙 본문은 계약 한 곳. 매 턴 블록은 세 줄 그대로, 크기 상한 12,000바이트 안.
- 막는 검사를 더하지 않는다 — 실체 보여 주기는 안내다(종료 훅 · 쓰기 검사 그대로).
- 판정기(실사용 보고)는 바꾸지 않는다 — 이 계획에서 뺐다(사용자 결정, 2026-10-10).
- 판정 기준 · 판정자 절차 · 멈춤 문턱은 결과를 열기 전에 고정하고, 결과를 본 뒤 바꾸지 않는다.
- 측정은 브랜치 사본을 측정 세션에만 싣는다 — 사용자 설치본은 건드리지 않는다. 측정은 CI 에 넣지 않는다.
- 공개 저장소 — 표본 · 보고서에 대화 내용 · 경로 · 메일 주소를 넣지 않는다(숫자 · 날짜 · 과제 이름만). 정답 표본 원본은 저장소 밖에.
- 맥(bash 3.2 · BSD 도구)과 리눅스(GNU) 모두에서 같은 결과. 순수 함수는 순수성 검사기를 통과한다.
- 측정 실행끼리 서로의 프로세스를 죽이지 않게 — 같은 과제 실행은 하나씩.

## 예외처리 (Edge cases)

- **검토 시점이 있지만 결과물이 안 바뀌는 일**: '결과물 변화 없음' 그대로 — 보여 주지도 묻지도 않는다.
- **사람이 없는 실행 · 자동 알림 턴**: 지금처럼 묻지 않고 실제 결과를 보고에 남긴다.
- **검토 시점에 돌려 볼 수 없음**(실행 환경 없음 등): 돌려 보지 못한 이유를 한 줄로 밝히고 지금처럼 묻는다 — 실제 결과로 꾸미지 않는다.
- **판정자가 답하지 못함**: 두 번 다시 묻고, 그래도 실패면 그 질문은 판정 불가로 따로 센다(측정 절차).
- **측정 장치 고장**(세션 시작 실패 · 대화 기록 없음 · 관리자 실패): 그 실행만 다시(기존 규칙).

## Exit criteria

- All TESTS.md scenarios pass (자동 검사는 맥 · 리눅스 CI, 측정은 이 맥에서).
- 두 측정(검토 시점 뺀 과제의 효과 · 원래 과제의 문구)이 목표에 닿는다 — 못 미치면 **여기서 멈추고** 결과를 보이며 다음 수단
  (예: 긴 작업 중 다시 싣기)을 사용자와 다시 정한다.
- 멈춤 문턱에 걸리지 않는다.
- 코어 릴리스 뒤 두 래퍼 설치본에서 새 문구가 확인된다 — 릴리스 · 래퍼 반영은 단계마다 사용자 확인.
- **사용자 결정(2026-10-10)**: 원래 과제 측정(T9)이 앞당김 1건으로 기준(0)에 못 미쳤다 — 커밋 전 설계 질문 하나에 돌려 본 결과를
  곁들인 것을, 미리 정한 규칙대로 앞당김으로 셌다. 멈춤 규칙대로 멈춰 보고했고, 사용자가 기준을 고치지 않고 '미달 1건'으로 적은 채
  마무리하기로 정했다(근거: 커밋 뒤 검토에서 실제 결과 6/6, 효과 측정 켬 6/6 · 끔 3/6, 멈춤 문턱 안). 실사용에서 검토를 일찍 청하는
  일이 보이면 그때 다시 본다.

## Suggested path

1. 구현 전 고정: 두 측정 · 멈춤 문턱의 판정 기준을 장치 기준 문서에 적는다.

3. 매 턴 세 줄과 계약에 검토 시점 문구를 더하고 단위 검사(끄면 같음 · 크기 · 통로 셋 · 규칙 한 곳)를 돌린다.
4. 장치에 '검토 시점 줄 뺀' 지시 판을 더하고, 브랜치 사본으로 18번 잰다(뺀 과제 켬 · 끔 12 + 원래 과제 켬 6).
5. 고정한 기준으로 판정 → 못 미치거나 멈춤 문턱이면 멈추고 사용자와 다시 정한다. 닿으면 코어 릴리스 → 두 래퍼 동기화 · 릴리스 →
   설치본 확인.

## Risks / Open Questions

- 모델이 '사용자가 검토 시점을 정해 둠'을 알아보는지는 문구에 달렸다 — 원래 과제 측정(목표 5)이 그것을 본다.
  → 측정(2026-10-10): 원래 과제 6/6 이 커밋 뒤 검토에서 실제 결과를 보였다.
- 원래 과제의 '앞당김' 규칙은 검토 요청과 설계 질문을 가르지 않는다 — 커밋 전 설계 질문에 결과를 곁들인 1건이 미달로 남았다.
  실사용에서 검토를 일찍 청하는 일이 보이면 다시 본다(사용자 결정, 2026-10-10).
- '결과를 보였다'를 기록 모양만으로 가르기는 어려웠다(순서 판정 잘못 잡음 7/25) — 실사용 보고(T10)의 숫자도 같은 한계(옛 판정기는 놓침이
  많다)를 안고 읽어야 하고, 판정기 개선은 정답을 자르지 않은 표본으로 따로 계획한다.
- 측정은 과제마다 1번 — 우연과 가르기 어렵다(지난 실측과 같은 한계). 4/6 · 끔보다 3 이상 문턱이 그 한계를 줄인다.
- 매 턴 크기 여유가 약 660바이트뿐이다 — 문구가 길어지면 다른 블록과 부딪칠 수 있다.
- 실사용(T10)은 이 계획 밖이다.
