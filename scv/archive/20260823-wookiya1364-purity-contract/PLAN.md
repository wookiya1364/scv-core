# 순수부와 효과부 — 원칙을 규칙으로

## Summary

지난 두 작업(템플릿 갱신, 설정 이사)에서 순수함수 + 전수 검사 + 정적 검사를
실제로 썼고 효과가 있었다. 그런데 그것은 **그 두 작업에서 내가 그렇게 한 것**일
뿐, 저장소의 규칙이 아니었다. 다음 작업에서 지켜진다는 보장이 없다.

원칙을 문서에만 쓰면 두 달 뒤에 원래대로 돌아간다. 지켜지는지 기계가 봐야 한다.

## Goals / Non-Goals

**Goals**

1. 경계를 계약으로 적는다 — 순수 / 결정적 변환 / 효과 세 층.
2. 선언을 코드 옆에 둔다 — 함수 위 표식.
3. 검사기를 만든다. 두 곳에 복사해 둔 임시 검사를 하나로 모은다.
4. 저장소 관문으로 CI 에서 돈다.
5. 계획 작성 규칙에 넣어 **다음 작업부터 자동 적용**되게 한다.

**Non-Goals**

- 기존 스크립트 전부를 순수함수로 옮기지 않는다. 표식이 붙은 것만 검사한다.
- 증명하지 않는다. 흔한 실수를 막는 그물이지 울타리가 아니다.

## 설계

### 함수

| 이름 | 층 | 입출력 |
|---|---|---|
| `purity_violations` | @pure (검사기 안) | 층 + 함수본문 → 위반 줄 |
| `_purity_strip_benign` | 효과 없음 (필터) | 코드 → 오탐 원인이 지워진 코드 |
| `_purity_scan_file` | 효과 | 파일 → 표식 목록 |

**검사기의 판정부 자체가 순수함수다** — 코드 텍스트를 받아 위반 목록을 낸다.

### 세 층

- **순수** (`# @pure`) — 외부 명령조차 부르지 않는다.
- **결정적 변환** (`# @deterministic`) — `jq`·`sha256sum` 은 허용. 디스크·시각·
  무작위·네트워크는 금지.
- **효과** (표식 없음) — 파일·명령·시각. 얇아야 하고 판단이 없어야 한다.

### 오탐을 먼저 지운다

이게 없으면 규칙이 무력화된다. 사람들이 무시하기 시작하기 때문이다.

- `(( ))` 산술 비교의 부등호는 리다이렉션이 아니다
- `<<<` 히어스트링은 파일 읽기가 아니다
- `>/dev/null` 은 파일 쓰기가 아니다
- `command -v` 는 도구가 있는지 볼 뿐 실행하지 않는다

## 이번에 드러난 것

**검사기가 스스로 구멍을 드러냈다.** 처음 구현은 결정적 층에서 파일 읽기를
놓쳤다 — `cat` 이 엄격 층에만 있었기 때문이다. 자체 확인이 그것을 잡았다.
`cat`·`find`·`ls`·`stat`·`readlink` 를 어느 층에서든 금지로 옮겼다.

자체 확인이 없었다면 통과만 하고 아무것도 안 보는 검사기가 됐을 것이다.

## 한계 (문서에 명시)

- `sed`/`awk`/`grep`/`jq` 에 **파일 이름을 인자로** 주면 잡지 못한다.
- 함수가 부르는 **다른 함수**의 순수성은 따라 들어가지 않는다.

잡히지 않는다고 허용된 것은 아니다. 계약이 검사보다 우선한다.

## 다음 작업과의 연결

저널 색인이 이 규칙의 **첫 적용 사례**가 된다. 규칙을 먼저 세우고 색인이 그것을
통과하는지 보는 순서다 — 반대로 하면 규칙을 결과에 맞추게 되어 검증이 안 된다.
