# /scv:update — gh 없이 최신 버전 확인, 앱 · 터미널 어디서든 직접 올리기

## Summary

`/scv:update` 는 지금 두 군데에서 막힌다. 최신 버전 확인은 `gh` 도구가 있어야만 되고(없으면 "확인 불가"만 나온다),
올리는 일은 슬래시 명령 두 줄을 안내만 하는데 그 명령은 클로드 앱에 입력하면 플러그인 화면만 뜨고 올라가지 않는다.
최신 버전은 `git` 으로 읽고, 올리는 일은 Claude Code 명령줄(`claude plugin …`)로 직접 해서, 터미널이든 앱이든
`/scv:update` 한 번으로 끝나게 한다.

확인한 사실(2026-11-16):

- `git ls-remote --tags` 로 `gh` 와 같은 값(0.94.0)을 1초에 읽었다. `git` 은 SCV 의 필수 도구다.
- `claude plugin marketplace update <마켓>` · `claude plugin update <플러그인> -s <범위>` 가 명령줄에 있다(2.1.322 도움말).
  앱 세션의 셸에서도 `claude` 가 보이고, 2026-11-15 릴리스 때 앱 세션에서 이 두 명령으로 설치본을 올렸다.
- `/scv:mods` 는 이미 같은 방식(`scripts/mods.sh` — 순수 계획 함수 + 가짜 `claude` 시험)으로 모드를 올린다.
- 지금 설명서(`skills/update/SKILL.md`)는 "자동 실행 금지 — 안내만"이라고 적는다(0.11.2 때 정한 것).
  코어 규약(`core/protocols/update.md`)은 "호스트가 지원하는 방법만 쓴다"라고만 적어, 명령줄로 올리는 것과 어긋나지 않는다.

사용자 결정(2026-11-16, 선택 창): 새 버전이 있으면 **묻지 않고 바로 올린다**. 그림 문서는 만들지 않는다.

같은 날 보탠 요구: 업데이트를 두 번 하기 번거로우니 `/scv:update` 한 번에 **설치된 모드까지 함께** 올린다(앱 · 터미널 둘 다).
확인한 사실: 모드 엔진(`scripts/mods.sh update`)은 이미 명령줄 방식이라 이어서 부르기만 하면 된다. 다만 그 엔진은 올릴 때
설치 범위를 지정하지 않아(명령줄 기본값 "자동 고르기"), 같은 모드가 두 범위(계정 전체 · 이 프로젝트)에 깔려 있으면 한쪽만 오른다.
사용자 결정(선택 창): 이 틈도 **같이 고친다** — 모드도 깔린 범위마다 올린다.

## Goals / Non-Goals

- **Goals**
  - 최신 버전을 `gh` 없이 읽는다 — `gh` 가 없는 컴퓨터에서도 "확인 불가"가 아니라 버전이 나온다.
  - `/scv:update` 가 새 버전을 직접 올린다 — 클로드 앱 세션과 터미널 세션 둘 다에서.
  - 설치 범위(user · project)가 여럿이면 범위마다 올리고, 범위마다 앞뒤 버전을 보고한다.
  - 실패는 실패라고 말한다 — 어느 단계가 왜 실패했는지와 다음 행동 한 줄.
  - "최신인지만 알려 줘"처럼 확인만 요청받으면 올리지 않고 버전만 보고한다(설명서에 적는다).
  - `/scv:update` 한 번에 설치된 모드까지 함께 올린다 — 본체가 이미 최신이어도 모드는 올린다.
  - 모드도 깔린 범위마다 올린다 — `/scv:update` 로 부르든 `/scv:mods` 로 부르든 같다.
- **Non-Goals**
  - 코덱스 래퍼 — 이 명령이 없다.
  - 모드 설치 · 삭제 · 목록 — `/scv:mods-install` · `/scv:mods-remove` · `/scv:mods` 가 그대로 맡는다.
  - Claude Code 설정 폴더를 옮긴 뒤 생기는 마켓 경로 문제를 찾아 주거나 고치기 — 사용자가 고르지 않았다(실패 보고만 한다).
  - 개발 · 스테이징 채널 바꾸기 — `/scv:channel` 이 맡는다.
  - 올린 것을 세션을 새로 열지 않고 적용하기 — Claude Code 가 정한 일이라 바꿀 수 없다.
  - 릴리스 — 구현이 끝난 뒤 사용자가 시킬 때 따로 한다.

## Approach Overview

엔진은 지금의 `scripts/update.sh` 하나다. 인자가 없으면 지금처럼 진단 다섯 줄만 내고(읽기만),
`apply` 를 받으면 올린다. 흐름은 `/scv:mods` 의 엔진과 같은 꼴이다: 양 끝에서 읽고(태그 목록, 설치 목록),
가운데 순수 함수가 "최신 버전"과 "실행할 명령 줄"을 정하고, 끝에서 명령을 실행한 뒤 다시 읽어 앞뒤를 견준다.

- 최신 버전: 플러그인 저장소의 태그 목록에서 `v<숫자>.<숫자>.<숫자>` 꼴만 골라 숫자로 견줘 가장 큰 것.
  접미사가 붙은 태그와 채널 가지는 세지 않는다. `gh` 는 더 쓰지 않는다 — 길이 하나라 컴퓨터마다 결과가 같다.
- 올릴지: 설치 버전이 최신과 같으면 아무 명령도 실행하지 않는다. 다르거나 최신을 못 읽었으면 실행한다
  (못 읽은 경우에도 올리기는 명령줄이 스스로 판단하고, 결과는 앞뒤 버전으로 보고한다).
- 실행: 마켓 새로 받기 한 번 → 설치 범위마다 플러그인 올리기. 앞 단계가 실패하면 뒤 단계를 실행하지 않는다.
- 설명서: 슬래시 명령 안내와 "자동 실행 금지"를 걷어 내고 엔진 호출로 바꾼다. 올린 뒤에는
  "새 세션을 열면 적용된다"를 말한다(무언가 바뀌었을 때만).
- README 세 언어판의 업데이트 안내도 같은 말로 맞춘다(주 안내는 `/scv:update`, 슬래시 명령은 터미널용 참고 한 줄).
- 모드: `apply` 는 본체 단계가 끝난 뒤(이미 최신이어도) 모드 엔진의 올리기를 이어서 부르고 그 출력을 그대로 잇는다.
  본체 결과와 모드 결과는 따로 보고한다 — 한쪽이 실패해도 다른 쪽의 결과를 가리지 않는다. 모드 마켓이나 설치된 모드가 없으면
  모드 쪽은 아무 명령도 실행하지 않는다.
- 모드 범위: 모드 엔진이 설치 목록에서 범위까지 읽고, 올리기 명령을 범위마다 낸다. 범위가 하나면 지금과 같은 명령 · 같은 출력이다.

## 순수함수 · 파이프라인 (Pure functions & pipeline)

```
flow(
  read_latest_tags,       // 저장소 주소 → 태그 줄들            (부수효과: 네트워크)
  update_latest_version,  // 태그 줄들 → 최신 버전 | 빈 값
  read_installed,         // (없음) → "범위 버전" 줄들           (부수효과: claude plugin list)
  update_plan,            // (op, 설치 줄들, 최신, 플러그인, 마켓) → 실행할 명령 줄들
  update_run_steps,       // 명령 줄들 → "STEP … ok|fail" 줄들   (부수효과: claude plugin …)
  update_summary,         // (앞 설치 줄들, 뒤 설치 줄들, STEP 줄들) → RESULT · NEXT 줄
  run_mods_update,        // (없음) → 모드 엔진의 출력 줄들        (부수효과: 모드 엔진 실행)
)

// 모드 엔진 안 (기존 흐름에 범위만 보탬)
flow(
  read_state,    // (없음) → "모드 범위 버전" 줄들              (부수효과)
  mods_plan,     // (op, 모드, 마켓, 설치 줄들) → 범위가 붙은 명령 줄들
  run_steps,     // 명령 줄들 → STEP 줄들                       (부수효과)
  mods_summary,  // (앞 줄들, 뒤 줄들) → 범위별 RESULT 줄
)
```

| # | 단계 | 하는 일 | 받는 값 → 돌려주는 값 | 순수/부수효과 |
|---|---|---|---|---|
| 1 | `read_latest_tags` | 플러그인 저장소의 태그 목록을 받아 옴 | 저장소 주소 → 태그 줄들(실패하면 빈 값과 이유) | 부수효과 (입구) |
| 2 | `update_latest_version` | 태그 가운데 가장 높은 정식 버전을 고름 | 태그 줄들 → `x.y.z` 또는 빈 값 | 순수 |
| 3 | `read_installed` | 설치된 SCV 의 범위와 버전을 읽음 | (없음) → "범위 버전" 줄들 | 부수효과 (입구) |
| 4 | `update_plan` | 실행할 명령을 순서대로 정함 | (op, 설치 줄들, 최신, 플러그인, 마켓) → 명령 줄들(없으면 0줄) | 순수 |
| 5 | `update_run_steps` | 정한 명령을 차례로 실행하고 실패에서 멈춤 | 명령 줄들 → STEP 줄들 | 부수효과 (출구) |
| 6 | `update_summary` | 앞뒤 버전을 견줘 결과와 다음 행동을 정함 | (앞 줄들, 뒤 줄들, STEP 줄들) → RESULT · NEXT 줄 | 순수 |
| 7 | `run_mods_update` | 모드 엔진의 올리기를 이어서 부름 | (없음) → 모드 엔진의 출력 줄들과 종료 코드 | 부수효과 (출구) |
| 8 | `read_state` | (모드 엔진) 설치된 모드의 범위와 버전을 읽음 | (없음) → "모드 범위 버전" 줄들 | 부수효과 (입구) |
| 9 | `mods_plan` | (모드 엔진) 올릴 명령을 범위마다 정함 | (op, 모드, 마켓, 설치 줄들) → 범위가 붙은 명령 줄들 | 순수 |
| 10 | `mods_summary` | (모드 엔진) 범위별 앞뒤 버전으로 결과를 정함 | (앞 줄들, 뒤 줄들) → RESULT 줄들 | 순수 |

- 부수효과 위치: 1(네트워크), 3 · 8(설치 목록 읽기), 5 · 7(명령 실행) — 모두 양 끝. 2 · 4 · 6 · 9 · 10 은 인자만 보고 값만 돌려준다.
- 8 · 9 · 10 은 지금 있는 함수다 — 받는 줄과 내는 줄에 범위 한 칸이 늘 뿐, 새 단계를 만들지 않는다.
- 구현하며 보탠 것: 설치 목록 읽기 `plugin_lines`(모드 엔진에 두고 두 엔진이 함께 씀 — 다른 프로젝트의 설치본을 빼는 규칙이 한 곳에만 있게),
  채널 읽기 `read_channel`(부수효과, 입구), 범위별 올리기 줄 `mods_update_lines`(순수). 5번의 이름은 모드 엔진의 것과 겹치지 않게 `update_run_steps` 로 했다.
- 재사용: `scripts/mods.sh` 의 명령 실행 · 상태 읽기 꼴과 `tests/test-mods.sh` 의 가짜 `claude` 틀.
  함수 이름은 구현 때 기존 것과 겹치면 기존 것을 쓴다.

### 합성 설계 체크리스트 (Composition checklist)

| # | 물음 | 답 | 근거 |
|---|---|---|---|
| 1 | 각 단계가 요소 단위 단항 순수 함수인가 | 2 · 4 · 6 · 9 · 10 이 순수 | `scripts/update.sh` 의 `update_latest_version` · `update_plan` · `update_summary`(셋 다 `@deterministic` 선언, 순수성 검사 통과), `scripts/mods.sh` 의 `mods_update_lines` · `mods_plan` · `mods_summary` — 인자만 받고 줄만 돌려줌. 시험 T2 가 같은 입력에 같은 출력 · 바깥 호출 0번을 봄 |
| 2 | 단계의 입출력이 밝혀져 있고 입력은 필요한 것만 받는가 | 예 | 함수마다 머리 주석에 받는 값 → 돌려주는 값을 적음. `read_installed` 가 설치 목록 전체에서 SCV 의 "범위 버전" 줄만 골라 `update_plan` 에 넘김 |
| 7 | 부수효과가 파이프라인 양 끝에만 있는가 | 예 | `update_main` 안의 순서: `read_latest_tags` · `read_channel` · `read_installed`(읽기) → `update_plan` → `update_run_steps`(실행) → `read_installed` → `update_summary` → `run_mods_update`(실행). 읽고 실행하는 함수는 모두 `@effect` 로 선언 |
| 8 | 실패할 수 있는 단계를 일반 합성에 그대로 섞지 않았는가 | 예 | 태그 읽기 실패는 빈 최신 값으로 `update_plan` 에 넘어가 "그래도 실행"이 되고, 명령 실패는 `update_run_steps` 가 마지막 줄 `FAILED <단계>` 로 내어 `update_summary` 가 실패 결과로 바꿈 — 시험 T6 · T8 통과 |
| 10 | 자주 도는 곳은 측정한 뒤에 고쳤는가 | 재서 적음 | 사람이 부를 때만 도는 명령. 실제 진단 한 번: 고치기 전(`gh`) 0.61초, 고친 뒤(`git`) 0.59초. 실제 올리기 한 번: 11.6초(명령줄 호출 4번) |
| 그 밖 | 3 · 4 · 5 · 6 · 9 | 해당 없음 | 태그 수백 줄을 한 번 훑는 것이 전부 — 큰 모음 · 조기 종료 · 구조 공유가 걸릴 자리가 없음 |

## Guardrails

- 인자 없는 진단은 읽기만 한다. 출력 다섯 줄의 이름과 순서를 바꾸지 않는다(`tests/test-mods.sh` 가 본다).
- 플러그인을 바꾸는 길은 `claude plugin …` 명령줄 하나뿐이다. Claude Code 의 플러그인 폴더 · 목록 파일을 직접 읽어 고치지 않는다.
- 실패한 단계를 "했다"고 보고하지 않는다. 앞 단계가 실패하면 뒤 단계를 실행하지 않는다.
- 본체 결과와 모드 결과를 섞지 않는다. 모드가 실패해도 본체가 오른 사실은 그대로 보고하고, 종료 코드는 실패로 낸다.
- 확인만 하는 진단(인자 없음)은 모드도 건드리지 않는다.
- 모드가 한 범위에만 깔린 경우 모드 엔진이 부르는 명령과 내는 줄을 바꾸지 않는다(`tests/test-mods.sh` 가 그대로 통과).
- 설치된 채널(개발 · 스테이징 · 운영)을 바꾸지 않는다.
- 프로젝트 파일을 건드리지 않는다. 템플릿 맞추기(sync)를 이 명령 안에서 부르지 않는다(코어 규약 5번).
- 맥 기본 셸(bash 3.2)과 새 셸(bash 5), 맥과 리눅스에서 같은 결과를 낸다 — 버전 정렬에 GNU 전용 옵션을 쓰지 않는다.
- 공개 저장소에 들어가는 글에 개인 경로 · 세션 이름 · 다른 사용자의 사정을 적지 않는다.

## Exit criteria

- TESTS.md 의 시나리오가 모두 통과한다(두 셸).
- `gh` 를 뺀 실제 환경에서 진단을 한 번 돌려 최신 버전이 읽히는 출력을 사용자에게 그대로 보였다.
- 설명서에 "슬래시 명령 두 줄을 직접 치라"는 업데이트 안내가 0곳이다. README 세 언어판은 주 안내가 `/scv:update` 이고,
  슬래시 명령 두 줄은 "터미널 세션에서는 이것으로도 된다"는 참고 한 줄로만 남는다 — 코어의 README 검사가 그 두 문구를 요구해서다
  (사용자 결정 2026-11-16: 코어 검사를 고치지 않고 한 줄로 남김).
- 기존 `tests/test-mods.sh` · `tests/test-channel-engine.sh` · `tests/test-core-contract.sh` 가 그대로 통과한다.
- 실제로 올라가는 것은 다음 릴리스 때 앱 세션에서 `/scv:update` 로 확인한다 — 이 계획이 끝난 시점에는 "확인 못 한 것"으로 적는다.

## Suggested path

1. 새 시험 파일을 먼저 쓰고 실패를 본다 — 가짜 `claude` · 가짜 `git` 으로 TESTS 의 T1~T9 를 옮김
2. 최신 버전 읽기를 `git` 으로 바꾼다 — `read_latest_tags`, `update_latest_version`
3. 올리기를 넣는다 — `read_installed`, `update_plan`, `update_run_steps`, `update_summary`
4. 모드 엔진이 범위마다 올리게 한다 — `read_state`, `mods_plan`, `mods_summary`
5. 본체 뒤에 모드 올리기를 잇는다 — `run_mods_update`
6. 설명서를 고친다 — 안내 대신 엔진 호출, 확인만 요청이면 올리지 않음, 모드도 함께 오름, 새 세션 안내
7. README 세 언어판의 업데이트 안내를 맞춘다 — 옛 안내 0곳으로
8. 두 셸에서 관련 시험을 돌리고, `gh` 를 뺀 실제 진단 출력을 사용자에게 보인다 — 실제 결과 보여 주기
9. 전체 시험을 한 번 돌린다 — 밀어 올리기 전 확인

## Risks / Open Questions

- **개발 · 스테이징 채널 설치본**: 그 설치본에서 "최신"은 정식 태그가 아니다. 구현 때 채널 읽기(`scripts/lib/channel.sh`)를 보고,
  운영 채널이 아니면 올리지 않고 `/scv:channel` 을 안내하는 쪽을 기본으로 한다 — 시험에 한 줄로 고정한다.
- **태그는 있는데 릴리스가 덜 끝난 몇 분**: 태그가 먼저 생기고 릴리스 파일이 약 5분 뒤에 붙는다. 그 사이에는
  "새 버전 있음"이라 올리기를 실행해도 버전이 안 바뀔 수 있다 → 앞뒤 버전이 같으면 "이미 최신"으로 보고하므로 거짓 성공은 없다.
- **project 범위**: 명령줄의 project 범위는 지금 폴더의 프로젝트에만 닿는다. 다른 프로젝트의 설치본은 그 프로젝트에서 부를 때 오른다.
- **`/reload-plugins` 가 앱에서 되는지**: 확인하지 못했다. 그래서 적용 안내는 어디서나 되는 "새 세션을 연다"로 적는다.
  `/scv:mods` · `/scv:channel` 의 같은 안내는 이 계획에서 건드리지 않는다.
- **릴리스 방식**: 래퍼만 바뀌는 변경이다. 버전 번호와 릴리스 절차는 구현 뒤 사용자가 시킬 때 정한다.
- **모드 두 범위의 근거가 한 건**: 한쪽만 오르는 것은 다른 사용자의 화면 한 장과 코드 읽기(범위를 넘기지 않음, 명령줄 기본값 "자동 고르기")로 봤고,
  이 컴퓨터에서 다시 일으켜 보지는 않았다. 구현 때 가짜 `claude` 로 먼저 실패를 본다(T18).
- **project 범위의 모드**: 본체와 같다 — 지금 폴더의 프로젝트에만 닿는다.
- **`claude` 가 셸에 없는 환경**: 올리지 못한다고 말하고 터미널에서 칠 명령을 안내한다(T7).
