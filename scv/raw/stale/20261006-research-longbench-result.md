# 긴 공개 과제 실측 결과 — 글로 된 견본은 낮았고, '실체를 일찍 보여 주기'는 지금 SCV 와 가르지 못했다 (2026-10-06 ~ 07)

## 한 줄 결론

남이 만든 긴 과제 6개 × 3번에서, 글로 된 견본 확인(plan)은 지금 SCV(on)보다 낮았고(7/18 · 12/18, p = 0.25),
실제로 돌아가는 것을 일찍 보여 주기(real)는 지금 SCV 보다 조금 높았다(12/18 · 10/18, p = 0.63) — 둘 다 돌리기 전에 고정한 판정으로는
**가르지 못함**이다. 같은 지금 SCV 를 두 번 돌려도 12/18 → 10/18 로 흔들려서, 6과제로는 이 크기의 차이를 가를 수 없다.

### 첫 실측 — 글로 된 견본 확인

남이 만든 긴 과제 6개 × 3번에서 지금 SCV(on)는 18번 중 12번, 견본 확인 지시를 더한 SCV(plan)는 7번 숨은 테스트를 통과했다.
돌리기 전에 고정한 판정(과제 단위 부호 뒤집기 검정)으로는 **가르지 못함**(양측 p = 0.25)이고, 방향은 견본 확인 쪽이 낮다
(6과제 중 4과제에서 낮음, 1과제에서 높음, 1과제 같음). 작은 과제 실측(12/18 → 18/18)과 반대 방향이다.

## 무엇을 쟀나

- 과제: SWE-Interact(scaleapi, Apache-2.0)의 DeepSWE 과제 중 이 맥에서 검증된 6개 — awilix · ofetch(TS), sqlite-utils · mobly · cattrs · tomlkit(Py).
  숨은 의도가 형식 · 취향이 아니라 기능 명세이고, 관리자(사용자 역할)가 구현을 검토하며 요구를 하나씩 드러낸다.
- 방식: on = 지금 SCV(설치본 0.65.0). plan = on + 계획 verify-by-sample 목표 1~4의 지시 한 단락(세션 지시로 넣음, 종료 훅 검사는 없음).
- 진행: 과제마다 계획 → 구현 → 테스트 세 단계, 단계마다 새 Claude Code 세션(Opus 5.5, 기본 생각 깊이). 관리자는 Opus 가 과제의 persona 로 맡음.
- 채점: 과제의 숨은 테스트(원래 tests/test.sh 0~4단계) — base · new 모두 통과면 1.
- 규모: 6과제 × 2방식 × 3번 = 36번, 동시 8개, 13:16 ~ 16:03.

## 돌리기 전에 고정한 판정

비교 단위는 과제(같은 과제의 반복은 독립이 아니다). 과제별 통과율 차이 d = plan − on 6개에 대한 정확한 부호 뒤집기 검정(64가지, 양측).
p < 0.05 일 때만 낫다 · 못하다로 판정한다. 6개로는 모든 과제가 같은 쪽이어야 p < 0.05 가 가능하고(최소 p ≈ 0.031),
d = 0 인 과제가 하나라도 있으면 최소 p ≈ 0.063 이다 — 이 실측은 아주 크고 고른 차이만 가를 수 있다.

## 계획 verify-by-sample 에 대한 시사점 (제안 — 계획은 바꾸지 않았다)

1. 긴 기능 명세 과제에서는 견본 확인의 이득이 보이지 않았고 점추정은 손해다. '건너뛰면 막는 검사'로 강제하기 전에 근거를 다시 세워야 한다.
2. 보기 하나짜리 확인 창 지시는 그대로 구현하면 매번 거절된다 — 구현한다면 문구부터 고친다.
3. 늘어난 상호작용이 대부분 추천 보기 클릭이었다 — 견본을 보여 줄 때 '이대로 좋음'을 기본으로 두는 방식이 바쁜 사용자에게서 정보를 끌어내지 못할 수 있다.

### 두 실측을 합친 결론

- 글로 된 견본(첫 실측 7/18)보다 실체를 일찍 보여 주는 쪽(두 번째 12/18)이 나았다 — 같은 시간에 잰 비교는 아니라 서술로만 쓴다.

- 실체 보여 주기는 해를 보이지 않았다(시간 비슷하거나 짧음, 거절 0). 대신 사용자 클릭이 33% 늘었고, 글로 드러난 요구 수는 늘지 않았다.
- 관리자 역할은 AI 라서, 사람이 실체를 볼 때 요구를 더 빨리 말하는지(사용자 원칙의 핵심)는 이 실측이 직접 재지 못한다 — 실사용 기록으로 확인할 몫이다.
