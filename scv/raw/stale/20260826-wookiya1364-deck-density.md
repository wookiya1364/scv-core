# deck 밀도 — "big pictures, few words"가 없다

2026-08-26. eli5 스킬(claude-plugins-community)과 비교하다가 대표님이 결론:
"현재의 scv:deck이 기획서로 역할할 가치가 있는지 생각해보면 아닌 것 같다.
수정이 필요한 시점이다." eli5에서 가져올 것은 단 하나 — **그림은 크게, 글은
적게**라는 밀도 감각. 실측으로 현재 상태를 확인했다.

## 실측 1 — 그림이 사라진 지 오래다

archive 전체 21개 deck의 다이어그램 개수(mermaid/svg):

- **17/21개가 다이어그램 0개.**
- **최근 8개는 연속 0개** (20260821-run-dry-layout-guard 이후 전부).
- 마지막으로 다이어그램이 있던 deck: 20260818 (env-example-autorefresh,
  regression-runner-env-leak — 각 2개).
- 표(table)조차 최근 4개(0825 계열)는 전부 0개.

즉 "그림이 작다/안 보인다"(20260813 deck-redesign)를 고치고 나니,
이제는 **그림이 아예 없다**. 렌더러 품질 문제가 아니라 **공급 문제**다.

## 실측 2 — 화면을 열어 보면 (20260825-pr-evidence-notify, 1440×900)

- **슬라이드 1 (Why)**: 검은 화면에 문장 2개. 화면의 ~85%가 빈 공간.
  그림·구조·강조 아무것도 없다. 그리고 그 두 문장이
  "CI 는 실패만 증적(정책), pr-helper 는 PR 본문에만 첨부 — Slack 에 성공
  slug 증적을 올리는 주체가 없었다" — 내부자 약어 그대로다.
- **슬라이드 2 (What)**: 불릿 텍스트 벽. 특히
  `어댑터 로드 → notifier_validate_env → notifier_resolve_channel →
  notifier_post_message → notifier_upload_file` 같은 **파이프라인이 산문
  화살표로** 적혀 있다. 이건 문장이 아니라 그림 한 장이어야 할 내용이다.
- **원문 패널이 기본 열림**: 화면 오른쪽 ~30%를 raw 마크다운이 차지.
  첫인상이 "기획서"가 아니라 "마크다운 재출력기".

## 원인 정리 — 변환기는 밀도를 만들 수 없다

- deck의 결정적 변환은 **충실도**(원본=렌더링)는 보장하지만, 소스 md가
  글 위주면 출력도 글 위주다. 정확히 설계대로 동작한 결과가 이 화면이다.
- deck.md Step 0.5(기획자 구조 합성)는 **섹션 순서**(배경→As-Is→To-Be→변경점)
  를 잡아줄 뿐, "이 문장은 그림이 되어야 한다"는 **밀도 판단이 없다**.
- lint도 섹션 **유무**만 본다 (비목표/성공지표/인수기준…). 다이어그램 0개,
  슬라이드당 어절 수 같은 **밀도 지표가 없다**.
- 실무 흐름상 promote가 만드는 PLAN.md가 deck의 주 입력인데, PLAN.md 작성
  지침에 다이어그램 의무가 사실상 없다시피 하니 위 "공급 문제"로 이어진다.

## 방향 후보 (promote에서 결정할 것 — 여기선 기록만)

1. **밀도 패스(소스 단계)**: 빌드 전에 소스 md를 훑어 "그림이 될 수 있는
   문장"(화살표 나열, 상태 전이, 목록형 구조)을 mermaid로 승격 제안 —
   충실도 원칙 유지: 내용 창작이 아니라 **표현 형식 전환**, 사용자 승인 후
   소스에 반영.
2. **밀도 lint**: 다이어그램 0개 경고, 슬라이드/섹션당 어절 수 상한 경고,
   "화살표 산문" 감지.
3. **첫 화면 규칙**: 표지/Why에 요약 그림 1장(전체 구조 속 위치) 강제 —
   eli5의 "첫 화면에서 그림 한 장으로 때린다".
4. **원문 패널 기본 닫힘**: 원문은 동봉하되 첫인상은 기획서가 차지.
5. (상류) promote의 PLAN.md 템플릿에 다이어그램 최소 요건 — deck만 고치면
   공급 문제가 남는다.

## 미확인 / 열린 질문

- 문서 모드(기본)와 슬라이드 모드 중 어디를 먼저 고칠지 — 이번 실측은
  슬라이드 모드 화면. 문서 모드의 밀도는 별도 확인 필요.
- 밀도 패스를 결정적 변환 안에 둘지(코드), 호스트 에이전트 지시문에 둘지
  (프로토콜) — 20260813 재설계의 교훈: **팔레트를 지시문에 박았다가 코드를
  고쳐도 안 바뀌는 사고**가 있었다. 같은 실수를 피할 위치 선정이 핵심.
- 어절 수 상한의 적정값 — 실측 기준 슬라이드 2는 명백히 초과, 슬라이드 1은
  반대로 과소(빈 화면). "적은 글"과 "빈 화면"은 다르다.
