# 릴리스 기계장치 두 곳 — 측정 기록과 결정

2026-08-14. 0.26.0 배송을 마치고 남은 두 항목을 처리한다. 둘 다 "초록인데 망가져
있던" 것이고, 둘 다 사람이 손으로 때워서 넘어갔던 것이다.

## 확인 1 — `promote.yml` 이 3초 만에 포기한 진짜 이유

0.26.0 승격에서 `scv-claude-code` 의 promote 워크플로가 두 번 조기 종료했고 두 번 다
손으로 머지했다. #115 의 rollup 을 그대로 떠 보면 원인이 드러난다.

```
Contract (${{ matrix.os }})   status=COMPLETED  conclusion=SKIPPED
Contract (ubuntu-latest)      status=COMPLETED  conclusion=SUCCESS
check-branch-flow             status=COMPLETED  conclusion=SUCCESS
Contract (macos-latest)       status=COMPLETED  conclusion=SUCCESS
```

첫 줄이 범인이다. 경로 필터로 건너뛴 매트릭스 잡은 **확장되지 않은 이름 그대로**
목록에 오르고, 진짜 잡들보다 **먼저** 온다. 당시 대기 조건은 "체크가 몇 개
존재하는가" 였다.

```
count=1  →  대기 탈출
gh pr checks --watch  →  "완료된 항목 하나" →  즉시 성공 반환
gh pr merge           →  필수 체크가 아직 없어서 거부
```

이 블록이 틀린 건 두 번째다. 그전 버전은 "체크가 통과했는가" 를 물었는데
`gh pr checks` 는 하나라도 대기 중이면 0이 아닌 값으로 끝나므로 대기 내내 "아직"
으로 읽혔다. 두 번의 오답이 서로 반대 방향이라는 게 핵심이다 — 세 번째 자작 판정을
또 만들 게 아니라, 머지를 결정하는 주체에게 물어야 한다.

### 결정 — `mergeStateStatus` 를 본다, 단 조건은 셋

`CLEAN` 하나만 요구하면 반대쪽 함정에 빠진다. 그 건너뛴 자리표시자가 rollup 을 계속
`UNSTABLE` 로 붙잡아 아무것도 머지되지 않는다. 세 가지가 동시에 성립해야 한다.

| 확인 | 왜 |
|---|---|
| 실패한 체크가 없다 | 900초 기다릴 이유가 없다. 즉시 중단 |
| 도는 체크가 없다 | check run 과 commit status 두 모양을 다 읽어야 한다 |
| GitHub 이 `BLOCKED` 이라 하지 않는다 | 필수 체크 집합이 뭔지는 GitHub 만 안다 |

`DIRTY`/`DRAFT` 는 즉시 중단, `BEHIND` 는 `update-branch` 후 계속, `UNKNOWN` 은
판정이 아니라 "아직 계산 안 됨" 이므로 대기.

### 검증 방식 — 문자열 검사로는 못 잡는다

이 블록은 두 번 다 **그럴듯하게 읽혔다**. "체크가 통과할 때까지 기다린다" 도,
"체크가 생길 때까지 기다린다" 도 문장으로는 맞다. 틀린 건 특정 입력에서의 **동작**
이다. 그러므로 동작을 검사한다.

워크플로에 마커를 넣고, 테스트가 그 블록을 **잘라내 그대로 실행**한다. `gh` 와
`sleep` 만 대역을 세우고, 픽스처는 호출마다 다음 상태로 넘어간다 — 변하지 않는
픽스처는 "제대로 기다렸다" 와 "포기했다" 를 구분하지 못한다.

회귀 케이스는 **부정형**으로 쓴다. "결국 머지된다" 는 픽스처는 옛 코드도 새 코드도
MERGE 로 끝나 판별력이 없다. 자리표시자만 있는 상태 다음에 **빨간 체크**를 놓으면,
일찍 머지하는 코드는 그걸 못 보고 MERGE, 제대로 기다리는 코드는 STOP 이다.

> 이 수정은 **다음** 릴리스부터 듣는다. `workflow_dispatch` 는 기본 브랜치의 워크플로
> 파일을 실행한다.

## 확인 2 — Core 를 손으로 심어서 봇과 경합한 것

0.25.0 과 0.26.0 에서 같은 일이 반복됐다. 릴리스 브랜치에서 버전 올리는 김에 벤더
트리도 같이 복사했고, 봇 PR 은 도착하자마자 "이미 반영됨" 이 되어 닫혔다.

```
060d3bd chore: release 0.26.0 — Core 0.26.0, deck redesign
        ← 브랜치 chore/release-0.26.0 (봇 브랜치가 아니다)
```

문제는 중복이 아니다. **두 경로가 같은 일을 하지 않는다.** 봇은 게시된 릴리스
아티팩트를 해석해 canonical 과 materialized 해시를 둘 다 기록한다. 손으로 복사하면
그 시점 작업 트리에 있던 것이 기록된다. 작업 트리가 깨끗했을 때만 같은 결과이고,
나중에 둘을 구분할 방법이 없다.

### 결정 — 금지가 아니라 선언

Core 계약이 바뀌면 봇이 못 따라오는 경우가 실제로 있다. 그러므로 막되 빠져나갈 길을
둔다. 기존 `[no-plan: <이유>]` 와 **같은 모양**으로 `[manual-vendor: <이유>]` — 배울
관례를 둘로 늘리지 않는다.

면제: 봇 브랜치 · 릴리스 체인(stage/main) · 이유가 있는 선언. 빈 표지는 거부한다.
이유가 표지의 전부이기 때문이다.

경로는 `*/vendor/scv-core/` 모양으로 맞춘다. 래퍼마다 벤더 트리 깊이가 다르고, 여기에
경로를 박으면 이 파일이 호스트 종속이 된다.

## 확인 3 — `check-provenance.sh` 에 테스트가 하나도 없었다

머지를 막는 게이트인데 검증이 없다. 실패 방향이 양쪽 다 조용하다.

- 안 막게 된 게이트 = "아무도 위반하지 않는 저장소" 와 구별되지 않는다
- 다 막게 된 게이트 = 처음 막힌 사람이 발견한다

픽스처는 **실제 git 저장소**로 만든다. 검증 대상에 diff 를 읽는 방식(merge-base
해석, 경로 모양)이 포함되므로, 스텁은 git 의 동작이 아니라 내가 이해한 git 을
검증하게 된다.

마지막 케이스로 두 게이트가 무언가를 **실제로 거부하는지** 확인한다. 첫 줄에서 0으로
끝나는 스크립트는 통과 케이스를 전부 통과시키고, 그러면 스위트는 아무것도 판정하지
않는 게이트를 건강하다고 보고한다.

## 예상 함정

- 새 스크립트는 벤더링된 뒤에야 래퍼 워크플로가 찾을 수 있다. 래퍼에 스텝을 지금 같이
  넣으면 CI 가 "파일 없음" 으로 빨개진다. Core 를 먼저 내고, 봇 동기화가 들어간 뒤에
  래퍼를 낸다.
- `core/` 안의 파일은 호스트 토큰(`Claude`, `Codex` 등)을 담을 수 없다. 새 스크립트와
  테스트 모두 래퍼 저장소 이름을 쓰면 안 된다.
- 워크플로 `run:` 블록 안에서는 `${{ … }}` 가 치환된다. 주석에 매트릭스 표기를 그대로
  쓰면 안 된다.
