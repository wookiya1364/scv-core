2026-08-26. 대표님이 실무에서 많이 쓰는 기획서(화면설계서/스토리보드) 양식을
샘플 이미지로 제공: `scv/raw/20260826-wookiya1364-deck-format-sample.png`
(회원가입 페이지, PAGE CODE FO-SU-02-01 예시).

전제: 같은 날의 진단(`20260826-wookiya1364-deck-density.md`)과 한 몸이다 —
**eli5식 "큰 그림, 적은 글" 감각은 유지**하면서, 기획서 양식은 아래 골자를
따른다.

## 샘플 이미지의 구조 (충실 전사)

- **상단 헤더 바**: `PATH`(페이지 이름, 예: 회원가입 페이지) + `PAGE CODE`
  (예: FO-SU-02-01). 페이지마다 고유 코드가 있고, 버튼 설명에서 이동 대상을
  이 코드로 지칭한다 (예: "회원가입 완료 시 FO-SU-02-02 로 이동").
- **중앙: 와이어프레임 목업** — 실제 화면 구조. 컴포넌트마다 **번호 마커**
  (①②③…)가 붙는다. 버튼 같은 액션 요소는 **문자 마커**(ⒶⒷ…)로 구분.
- **우측 사이드바 1 — Function Description**: 번호별로 해당 컴포넌트의
  역할·제약을 상세 기술. 예: ① 이메일 인풋 박스 — 텍스트 입력 제한, 320자
  초과 입력 막음, 주소 앞자리 64자+@+도메인 255자 제한, 허용 기호, 포커스
  아웃 시 이메일 중복 여부 및 형식 유효성 체크.
- **우측 사이드바 2 — Button Description**: 문자 마커별로 **액션 상세** —
  클릭 시 어떤 검증이 돌고, 성공/실패 각각 어떤 메시지·이동이 일어나는지,
  이동 대상 PAGE CODE까지 명시.
- **좌측 보조 열**: 컴포넌트의 **상태 변형** — 기본/포커스/입력 중/가림/
  Valid/Invalid 상태를 축소 목업으로 나열.
- **하단 중앙: 검증 메시지 표** — 체크 시점 / 조건 / 메시지 / 노출 유형.

핵심 원리: **그림(와이어프레임)이 주인공이고, 글은 번호로 그림에 매달린다.**
글이 그림 밖 사이드바로 빠지므로 화면 자체는 깨끗하게 유지된다 — eli5의
"big pictures, few words"와 정확히 같은 방향.

## 대표님 요구 — 영역별 변형 (기본 골자는 동일)

- **FE**: 우측 사이드바에 해당 번호 컴포넌트의 **역할**을 기술하고, 버튼 등
  **액션이 존재하면 액션에 대해서도 상세 기술**해야 한다 (위 Function /
  Button Description 이원 구조).
- **BE**: 기존 골자는 FE와 같다. 다만 **화면이 존재하지 않으므로**, 목업
  자리에 해당하는 큰 그림(구성도/흐름도)에 번호를 붙이고, **API와 함수의
  역할을 자세하게 설명**한다.
- **나머지 영역**(인프라, 데이터, 운영 등)도 영역이 달라지더라도 **기본
  골자는 같아야 한다**: 큰 그림 하나 + 번호 마커 + 우측 번호별 상세 +
  액션(있다면) 상세.

## 기존 deck 자산과의 연결점 (참고)

- deck에는 이미 `screen` 펜스(JSON 와이어프레임 렌더)가 있다 — 번호 마커와
  우측 사이드바 연동이 없을 뿐, 목업 그리기 자체는 있다.
- FEATURE_ARCHITECTURE.md의 mermaid 다이어그램이 BE의 "큰 그림" 후보다 —
  노드에 번호를 달고 사이드바에서 번호별 API/함수 설명을 하는 형태로 확장
  가능.
- 미확인: 현재 `screen` 스키마에 마커/주석(annotation) 개념이 있는지 —
  promote 계획 수립 시 스키마 확인 필요.
